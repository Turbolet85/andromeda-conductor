## Design Philosophy

- **Determinism under a seed** — the timeline engine runs on a `current_thread` tokio runtime with zero work-stealing, so the same scenario + seed always produces the same emission stream shape; reproducibility is a property the architecture enforces in the runtime flavor, not a convention bolted on later.
- **Headless-drivable core, thin shells** — all engine logic lives in runtime-agnostic library crates that both `scripts/agent-run.sh` (the source of truth) and the optional Tauri 2 GUI call identically; the CLI/headless path is the release gate and the GUI is convenience only.
- **Compiler-enforced module seams** — the modular monolith is realized as a crate-per-seam Cargo workspace where `Cargo.toml` dependency edges *are* the architecture and a forbidden cross-seam dependency simply will not compile.
- **Outcomes are values, errors are harness faults** — verification verdicts (`Pass`/`Fail`/`CalibrationRegion`) and report states (`Pass`/`Fail`/`ManualCheck`/`KnownResidual`/`Blocked`) are typed return values; `Result::Err` is reserved strictly for Conductor's own failures (config parse, transport down, MCP unreachable), so the report can correctly classify a model-backed SUT's behavior by matching on types rather than catching exceptions.
- **Journal-relative ground truth** — every SLO is measured as `read_back_observed_at − journal_emitted_at` against an on-disk JSONL emission journal, never wall-clock-from-test-start; file artifacts are the agent-parseable ground truth and the embedded SQLite index is a thin convenience layer over them.

## Established Decisions

- **[Language / Runtime] Rust 2024 + tokio 1.48.x:** Pinned by brief for Pulse-consistency; tonic/prost require a tokio reactor and the deterministic phase scheduler maps cleanly to `tokio::time` for exact gap/silence/ramp timing.
- **[Async Runtime Flavor] tokio `current_thread`, core-owned:** Zero work-stealing makes emission ordering a deterministic function of the seed; throughput headroom is irrelevant because load-testing is an explicit non-goal (Pulse prior art saturated ~10k spans/s). `#[tokio::main(flavor = "current_thread")]` on the CLI path; hand-built `Builder::new_current_thread()` owned by the core under Tauri so Tauri's own multi_thread runtime stays the GUI shell's concern.
- **[Determinism RNG] rand_chacha `ChaCha8Rng` seeded via `seed_from_u64`:** The timeline scheduler's sole source of non-determinism is a seedable `ChaCha8Rng` (rand_chacha 0.9 + rand_core 0.9), seeded `seed_from_u64(scenario.seed)`; ChaCha8's algorithm is stable across platforms and crate versions, so the same seed reproduces the same emission-stream shape on any host — `StdRng` (no cross-version stability guarantee) was rejected for exactly this reason. The seed materially shapes timing (bounded per-gap jitter), and a transition's `elapsed_ms` is a deterministic cumulative sum of effective gaps, never a clock read.
- **[OTLP Emission Strategy] opentelemetry-proto 0.32.0 raw types over the SDK exporter:** The `opentelemetry-otlp` exporter is a near-deal-breaker — it offers no control over fingerprint identity, severity boundaries, or root-vs-child error placement and spawns its own batch tasks on the runtime. Raw message structs give byte-level control, which fault injection requires; this is the single most consequential fork in the build.
- **[Backend Framework] None (no web framework):** Conductor is a gRPC client + MCP client + Tauri IPC host, not a server; it exposes no HTTP/network surface of its own, so Axum/Actix and REST/GraphQL/tRPC are all out of scope.
- **[Database] rusqlite 0.38.0 with `bundled` SQLite, synchronous:** Quiz I pinned file artifacts + a thin SQLite index; rusqlite keeps the storage seam synchronous (no async-runtime entanglement) and `bundled` yields a self-contained cross-platform build with JSON1 for indexing fingerprint arrays. The brief's stale `rusqlite 0.31 / SQLite ≥3.38` pin is ratified to 0.38.0 (a free maintenance/correctness win). sqlx (async-first) and SeaORM (ORM over-scope) were rejected.
- **[ORM] None — raw SQL:** `runs.db` is a small fixed set of hand-written tables of run metadata (`runs`, the scenario-grained run index; `run_envelope`, the run-level envelope standing; `run_check`, the per-check index keyed `(run_id, scenario, check_index)`), each added additively under `CREATE TABLE IF NOT EXISTS`; an ORM's entity/migration machinery is weight with no payoff for hand-written append + a handful of cross-run SELECTs + one run-scoped teardown. That teardown is `RunsDb::delete_run` (2026-09-06) — three LITERAL `DELETE … WHERE run_id = ?1` statements over `runs` / `run_check` / `run_envelope` in one transaction, rusqlite bound parameters, idempotent, and never `format!`-assembled even over a hard-coded table list (security-plan §Security Anti-Patterns → Input). The seam is its sole implementation: the `conductor cleanup <run_id>` verb is the only caller and the harness shells issue no SQL of their own.
- **[MCP Read-Back Client] hand-rolled line-delimited JSON-RPC (rmcp removed 2026-06-27):** The read-back client (`conductor-verify/src/jsonrpc.rs` + `client.rs`) speaks JSON-RPC directly over the sidecar's stdio — `initialize` (capturing the server's `protocolVersion` for negotiation) + `tools/list` + `tools/call` — returning the **raw `serde_json::Value` result**. rmcp 1.7.0 was the original choice (typed SDK + version negotiation) but was **removed** when proven against the live sidecar: Pulse's MCP *server* is itself hand-rolled JSON-RPC (`crates/mcp-server/src/jsonrpc.rs`) and **non-MCP-compliant for `tools/call`** — it returns the raw tool payload as the JSON-RPC `result` (no `{content:[…]}` envelope), which rmcp's typed `call_tool` deserializes into `ServerResult` and rejects as `UnexpectedResponse` on *every* live call (rmcp exposes no raw-result escape). A hand-rolled client is therefore the faithful match to Pulse's actual wire format; version negotiation reduces to reading the `initialize` result's `protocolVersion`, the contract manifest still pins `2024-11-05`, and the preflight gate still guards a strict-newer mismatch. The hardened spawn (fixed program path + `.env(...)` data-dir + injection-reject) is unchanged. (The original rmcp-selection rationale → `architecture-amendments.md`.)
- **[Validation Library] serde 1.0.x + garde 0.22.1:** garde (the modern rewrite of `validator`) expresses scenario bounds declaratively next to the serde structs — `range` rules for simple bounds (a bounded error fraction, shipped as `EmissionShape::Error { error_percent: u32 }` ∈ 0..=100 — an integer percent, not an f64, so `PhaseSpec`/`Scenario` keep `Eq`; non-negative durations, sane ramp factors) and `#[garde(custom)]` field validators for the rest; cross-field invariants spanning distinct fields (p50≤p95≤p99 ordering, severity-mix sums, the fault ⇒ `occurrences = 0` silence rule `fault_phases_are_silent`) use garde's `Context` pattern or a field-level `custom` one altitude up (the fault rule sits on `Scenario::phases`, like `no_duplicate_pids` on `p_ids`), since garde 0.22.1's `custom` is field-level only (no container-level custom) — with no async or web-framework coupling. **A THIRD route exists, and its boundary is structural:** the one-altitude-up `custom` covers only an invariant CONTAINED WITHIN the lifted field (`fault_phases_are_silent` needs `phases` alone), because a field-level `custom` receives `(&field, &())` and can see no SIBLING field. An invariant spanning a field and its sibling therefore cannot be a garde validator at all under 0.22.1 — it ships as a plain load-path method invoked from `Scenario::from_toml_str`, the shape `Scenario::check_capabilities` already uses, `Scenario::check_budgets` (`budget_ms` ≤ its scenario's own `slo_tier` deadline) joined, and `Scenario::check_checklist` (a declared `[[checklist]]` may not sit beside a non-empty `expected` — the checklist renders only on the operator-checklist path a checks-bearing scenario never takes) now joins. **A nested spec field must `dive`, never `skip`** — a `skip`ped nested struct deserializes unvalidated because garde never descends into it. **Pinned 0.22.1**, not the originally-chosen 0.23.0: its `garde_derive 0.23.0` proved absent from the registry, so 0.23.0 + the `derive` feature is unbuildable. validator (predecessor) and serde_valid (JSON-Schema niche) were rejected.
- **[Scenario Config Format] TOML on disk via the `toml` crate (0.9):** scenario config files under `scenarios/` are declarative TOML, serde-deserialized and bounds-checked with garde at load. The load-error mapping is **three-way**: `Scenario::from_toml_str` → `CoreError::Config` on a parse failure OR on a non-garde load-path check failure (`check_budgets`, `check_capabilities`, `check_checklist`), and `CoreError::Validation` only on a garde failure — because `Validation` is pinned `#[from] garde::Report` and structurally cannot carry a hand-written message. All three are harness faults on the `Result::Err` side of the verdict/error wall. TOML was chosen over JSON (the only other candidate; serde_json was already present) for hand-author ergonomics + inline comments across the per-P-ID scenario files — a P4 user decision. The `toml` crate is audit/deny-clean; serde_json remains the run-report-envelope / JSONL-journal serializer.
- **[Accepted Capability Set] a versioned SUT capability manifest, not a compile-time constant:** which Pulse P-IDs a scenario may name is **data** — `contracts/pulse-capabilities.toml`, read and bounds-checked at load (same `toml` + serde stack, no new dependency). Validation is two-layered: garde's `pid_format` asserts the `P-NNN` **shape** only, and `Scenario::check_capabilities` asserts **membership** against the manifest, applied by `Scenario::from_toml_str_with(&str, &CapabilityManifest)` at the three binary-edge load sites (`conductor-cli::paths`, `conductor-tauri::commands`, `list_scenarios(dir, &manifest)`). A malformed / absent / unparseable manifest is a **harness fault** (`CoreError`, `Result::Err`) carrying a named reason — never `Blocked` (a blocked row needs `run_id`/`seed`/`scenario`/`p_ids`/`slo_tier`, none of which exist at manifest-load time) and never a silent widening. This supersedes the original compile-time `001..=060` bound in `pid_format`, which the SUT outgrew. The **accepted set** is data; the **coverage classification** stays code-native (`coverage_matrix()` in `conductor-core`, a no-runtime-IO `static`), and `check_sut_drift` asserts set-equality between the two — deliberately a two-source comparison, which sourcing the classification from the manifest would collapse into a self-check. So re-aiming at a newer Pulse release is a manifest edit **plus** a matching classification row: an accepted id with no row (or a classified id the manifest no longer accepts) is a `CoreError::SutDrift`, never a silent gap. The `KNOWN_UNCLASSIFIED` residual ledger that briefly bridged the two is retired to `[]`. **A second integrity gate sits beside it on a different axis:** `check_sut_drift` asks whether every accepted capability is *classified*, while `check_scenario_backing` asks whether every capability classified `Auto` — the mode that claims Conductor both drives the stimulus and asserts the reaction — actually has a scenario naming it. A capability can pass the first and fail the second, because classification is a statement of intent and a scenario is what makes it true. The `UNBACKED_AUTO` pin records the `Auto` claims no scenario yet backs, held to exact-set equality against the committed catalog (a new unbacked claim, a pin a scenario now covers, or a pin that lost its `Auto` classification are each a `CoreError::UnbackedCoverage`), so the ledger can only shrink under compulsion. Only `Auto` participates — `DriveObserve` is operator-confirmed by definition, and `StaticOnly` / `NotConductors` are deliberately not Conductor's to drive. `Scenario::from_toml_str(&str)` and `PId`'s shape are unchanged — garde's `dive` propagates `Context`, so threading the accepted set through garde would have forced a context onto `PId`/`PhaseSpec`/`EmissionSpec`/`ExpectedCheck` and changed `PId`'s public API.
- **[Error Handling] thiserror 2.0.18 in seam crates + anyhow 1.0.104 at edges, plus a type-level verdict/error wall:** The report's states require *matching on error variants* — "MCP tool absent" → `Blocked`, "transport refused" → harness error, "wrong incident" → `Fail` — so verification outcomes are VALUES (`Verdict`/`ReportState`), never Rust errors; `Result::Err` is reserved for harness failures only. `tonic::Status` codes and MCP error responses are first-class verification inputs. anyhow lives only in `conductor-cli` / `#[tauri::command]` edges.
- **[Module Boundaries] Crate-per-seam Cargo workspace:** In Rust, crates are compiler-enforced visibility boundaries; one workspace with a runtime-agnostic `conductor-core` plus the seam crates `conductor-timeline`/`conductor-emit`/`conductor-faults`/`conductor-verify`/`conductor-report` (+ `conductor-cli` bin and the `conductor-tauri` bin) makes a forbidden cross-seam dependency fail to compile, gives per-seam `cargo test -p` (and, with the qualifier below, `cargo build -p`), ships a single deployable, and mirrors Pulse's `crates/…` layout. The compiler enforces; cargo-modules/cargo-rail only audit. **The forbidden-edge property is compiler-enforced and unqualified; the standalone per-seam BUILD is neither gate-verified nor currently true of every member.** Workspace feature unification can mask a feature a crate uses but declares only in `[dev-dependencies]`, so the crate compiles in the workspace and in `cargo test -p` while failing alone — as measured at HEAD 2026-09-04: `cargo check -p conductor-verify --lib` is red on `tokio::time::sleep` (`preflight.rs:336`) because tokio's `time` feature sits in that crate's `[dev-dependencies]` (`Cargo.toml:31`) and not its `[dependencies]` (`:10`), while `cargo test -p conductor-verify` passes precisely because the dev-dep supplies it. No CI job builds a member standalone, so nothing catches this; repairing the manifest is route-owned (*Dependency polish*), and until it lands, read "independent per-seam build" as an intent, not a guarantee.
- **[Workspace / Core Structure] Runtime-agnostic core library + CLI bin + Tauri bin:** This is the structural decision that makes "headless-drivable" real — engine logic lives in a core usable outside Tauri, and both `agent-run` and Tauri commands call it, enforcing the headless/CLI/GUI split at compile time.
- **[Real-time Strategy] Tauri 2 IPC `Channel` for in-app live updates only:** Streams live counters / target status backend→frontend without per-message JSON overhead; FCM/APNs/web-push are irrelevant on a local tool, and Conductor must NOT emit native OS toasts because those are Pulse behavior it observes via the operator checklist.
- **[Message Broker] N/A:** Single-process modular monolith; inter-module flow is in-process Rust calls / `tokio::sync::mpsc` channels at most — no Kafka/NATS/Redis. The only queue-like surface is the OTLP gRPC stream to Pulse, which is the SUT, not Conductor's infrastructure.
- **[Deployment] Local `cargo build --release` + `scripts/agent-run.sh`:** Headless is the source of truth, co-located with Pulse (which binds loopback `:4317` only, ruling out remote/containerized execution); the Tauri 2 bundler (v2.10.x) produces the GUI artifact as convenience, not a release gate. No cloud / container / serverless.
- **[CI/CD] GitHub Actions, build + test only:** `cargo build` / nextest / clippy on the dev OS target verify the harness compiles and unit/golden tests pass; end-to-end dynamic scenario proof requires a live Pulse (`mcp-server` feature + `ANDROMEDA_PULSE_MCP_ENABLED`) and is an operator/local gate, not a CI gate, because CI has no Pulse instance.
- **[Timing-Tolerance Model] Hybrid journal-relative deadline + tier-scaled bounded slack:** Latency is always `read_back_observed_at − journal_emitted_at` (never wall-clock-from-test-start); deterministic/hard SLOs get a tolerance band scaled to hardware-profile-aware tiers (<5s / <20s / <90s), while sample-count floors (50-sample latency / 10-span error-rate) and model-interpretive timings route to the calibration-region bucket instead of hard-failing. **The tier deadline is a CEILING, not necessarily the deadline itself:** an `[[expected]]` check may declare its own sub-tier `budget_ms` and is then graded against a per-check EFFECTIVE deadline (`ExpectedCheck::effective_deadline_ms(tier)` — the budget when declared, else the tier's), so `evaluate_slo` takes an effective `deadline_ms` and `SloOutcome` carries it. Every expected check persists its own `latency_ms`/`deadline_ms`/`verdict` rather than only the run's shared whole-loop value — and because the corpus is observed ONCE per scenario, the per-check latencies are equal by construction and the DEADLINE is what separates two checks' timing verdicts. `slo_tier` keeps its closed three-value set and the latency formula is unchanged. This reconciles determinism-under-seed with the reality that Pulse runs in real time as a black box.
- **[Read-Back Dependency Posture] Version-pinned MCP contract + preflight gate (protocol `2024-11-05` · tool presence · data-dir canary) + per-scenario explicit degrade:** At suite start, MCP `initialize` asserts the negotiated protocol version — **pinned at `2024-11-05`, Pulse's actual hand-rolled server version, read from the `initialize` result (no client-library default to drift from)** — plus presence of each required tool (`query_incident_list` · `retrieve_report` with `degraded_mode` · `retrieve_telemetry_slice` · `mark_incident_resolved`) against a pinned manifest; the gate then attempts a **canary round-trip** — Conductor emits a unique fingerprint-storm and asserts Pulse opened an incident **AFTER the storm's emission instant** — to prove the data-dir/workspace wiring before any scenario trusts read-back, and to attribute the incident to THIS run rather than to corpus residue. **The gate reached `ready:true` for the first time on 2026-08-16** (`canary_round_trip: "ok"`, `blocked_precondition: null`, exit 0). Evidence: `conductor-0.2.0/chunks/2026-08-16-canary-fingerprint-derivation-aligned/evidence/leg-verdict.md`.

**Freshness is the carrier because NO read-back field varies with the emitted payload** (measured 2026-08-16). Titles are scrubbed; and `retrieve_telemetry_slice.fingerprint_refs` — the former carrier — is populated from the **L4 model's `evidence_refs`** (`andromeda-pulse pulse-app/src/inference_runtime.rs:684-701`), which the deterministic-L4 fixture now POPULATES with a constant `det-*` triple (`det-span-…` / `det-template-0007` / `det-fingerprint-…` — measured live 2026-08-18 at SUT HEAD `efabe8e`): non-empty but payload-INVARIANT, so freshness stays the carrier because the values never vary with what Conductor emitted, not because the field is empty; the chain is `deterministic_inference.rs → interpretation/markdown.rs → mcp-server/tools.rs:436`. Pulse's own computed fingerprint lands in the `span_events.fingerprint` column, and **no MCP tool reads `span_events`** — so it reaches no read-back surface at any width, and the old assertion could never have passed however the derivations were aligned. Conductor stamps the emission instant from `std::time` and compares against `opened_at_unix_nano`, which Pulse sources from the corpus row's own `created_unix_nano` (`mcp-server/tools.rs:412`, surfaced at `:348-354`). **Honest limit:** freshness proves causation-in-time, not PAYLOAD identity, because every L4-authored field (`title` / `severity` / `fingerprint` / `evidence_refs`) is a fixture constant. **A SECOND axis was measured 2026-09-01 (Pulse HEAD `83d4060`) and closes the same way:** `incident_events` — the corpus table persisting created/resolved lifecycle events, and the one table whose content is NOT L4-authored — is written by `crates/triage/src/incident/persistence.rs::save_incident_event` and read only corpus-side (`crates/corpus/src/disposition.rs` + a `contract.rs` test helper), with ZERO references in `crates/mcp-server`; it reaches no MCP tool at any width. Reaching it is a **Pulse 0.4.0 residual candidate**, not Conductor's to build.

**But "no stronger claim exists" is RETIRED — a stronger one does, on a different axis.** Payload fidelity is unattainable; **runtime-STATE fidelity is not**, and is live-proven: Conductor writes through `mark_incident_resolved` and observes the consequence through `query_incident_list`. It survives deterministic L4 precisely because it depends on no L4-authored field — it varies with what Conductor DID, not with what it EMITTED. Measured 2026-09-01: incident 6 resolved and gone from the active set with `idle_seconds_at_resolve = 0.0`, against Pulse's 120s auto-resolve idle threshold (its corpus records the incident active 16:42:38→16:43:23, a 45s life), so the resolver is excluded by construction and Conductor's write is the only remaining cause — `conductor-run/tests/lifecycle_harvest.rs`.

**Two mechanisms measured the same day bound how that attribution can be built.** (1) **At most ONE incident is active per DEDUPE TUPLE:** Pulse's producer dedupes a new incident against an OPEN incident carrying the same `(kind, scope, scope_id)` tuple — the workspace scopes the CANDIDATE SET, the tuple is the key, **as measured at `andromeda-pulse pulse-app/src/inference_runtime.rs:811`** (`.find(|inc| inc.kind == kind && inc.scope == scope && inc.scope_id == scope_id)` over `registry.list_active(&digest.workspace)`, HEAD `83d4060`). The originating leg's storms all shared one tuple, which is why it observed the effect at workspace grain (`created=false deduped=true` observed while one was open; every `created=true` occurred with the active set empty; a new incident formed the same second the prior was resolved) — **the leg evidence stands; only the generalisation was unlicensed.** So a spared-control design is unattainable WITHIN a tuple, and the freshness caveat "a concurrent unrelated incident inside the poll window would satisfy it" cannot arise within one — attribution rides LIVENESS instead (an incident refreshed seconds ago cannot be the idle-resolver's). Across DIFFERENT scopes both remain possible: a cross-scope two-incident control is a weighable route option, untested, **not** a retirement. (2) **The DECLINED write arm is unreachable through MCP:** Pulse guards on `UPDATE … WHERE id = ?5 AND updated_unix_nano <= ?2` returning `DeclinedStale` on zero rows (`crates/corpus/src/contract.rs:652-659`), and its dispatch stamps `now` fresh per call, so the predicate fails only against a future-stamped row. That arm is stub-proven and permanently so.

**Conductor's fingerprint now IS Pulse's derivation**, recomputed over the same preimage the wire carries: blake3 over `exception_type` + `\0` + `normalize_stacktrace(render_stacktrace(spec))`, truncated to `FINGERPRINT_BYTES = 16` and rendered as **32 lowercase hex chars** (`conductor-emit/src/exception.rs`), transcribed from `andromeda-pulse crates/buffer/src/fingerprint.rs` (`compute_exception_fingerprint`) at HEAD `efabe8e`. - **[Probabilistic-Assertion Policy] Two-state split (hard-fail / calibration-region):** Deterministic claims (hard signals, baseline math, suppression/bypass logic, lifecycle timing) are hard pass/fail; model-interpretive claims (severity choice, hypothesis quality, P-008 root-vs-deep weighting) are calibration-region + report-for-human and never hard-failed on exact values — because exact-match assertions cannot fairly judge a model-backed detector. ## Conventions

**Interface surfaces (three pinned, no network API of Conductor's own):**
- **Outbound emission:** OTLP over gRPC to `127.0.0.1:4317` via tonic 0.14.6 / tonic-prost 0.14.6; OTLP wire format built from opentelemetry-proto raw types. OpenTelemetry Semantic Conventions are the shared vocabulary (`service.name`, span `Status.Code=ERROR`, exception span events with `exception.type`/`message`/`stacktrace`, log `SeverityNumber` at boundaries); W3C Trace Context propagates across emulated service edges.
- **Inbound verification:** MCP read-back via a hand-rolled line-delimited JSON-RPC client over the sidecar's stdio (rmcp removed — Pulse's `tools/call` is non-MCP-compliant); a version-pinned contract manifest + `initialize` preflight gate, with the **blocked** report state on mismatch.
- **Internal core↔UI:** Tauri 2 `#[tauri::command]` request/response for start/stop/picker actions; `Channel` for streaming live counters. REST / GraphQL / tRPC are N/A.

**Error handling:** Typed `thiserror` enums per seam crate (e.g. `EmitError`, `VerifyError`, `ContractMismatch`, `ConfigError`); `anyhow` only at `conductor-cli` / `#[tauri::command]` edges. A type-level verdict/error wall separates verification outcomes from harness failures: `enum Verdict { Pass, Fail, CalibrationRegion }` and `enum ReportState { Pass, Fail, ManualCheck, KnownResidual, Blocked }` are returned as `Ok(...)`; `Result::Err` means a harness fault (config parse, transport down, MCP unreachable). Read-back transport/decode/JSON-RPC errors fan out into `VerifyError` variants (`Transport`/`Protocol`/`Decode`/`JsonRpc` — blocked/fail/harness-error); garde's validation `Report` becomes a `ConfigError` harness-failure class via `#[from]`. `tonic::Status` codes and MCP error responses are first-class verification inputs, not panics.

**Naming patterns:** snake_case Rust source files and identifiers (per Rust convention); crates named `conductor-<seam>` (kebab-case crate names, snake_case module paths); scenarios keyed by Pulse capability P-ID, drawn from the SUT capability manifest's accepted set — "no scenario without a P-ID". On-disk artifacts use kebab-case Markdown filenames (e.g. `coverage-matrix.md`, run report) and per-run JSONL journals.

**Config conventions:** Declarative scenario config (no scenario DSL) deserialized with serde and bounds-checked with garde at load; validation co-located with the serde structs in their owning seam crates, diving into nested spec structs rather than skipping them. Durations are non-negative; an error fraction is bounded (shipped as an integer `error_percent` ∈ 0..=100); ramp factors validated sane; latency targets enforce p50≤p95≤p99 ordering and severity-mix sums. A phase's emission shape is declared data — `EmissionSpec { signal, occurrences, shape }`, where `occurrences: 0` is a deliberate silence window and the shape selects its emit-primitive family. A phase may also declare a FAULT for its window — the optional `[phases.fault]` table (`PhaseSpec.fault: Option<FaultSpec>`, serde default absent, garde `dive`) carrying the closed `FaultKindSpec::PortOccupier` kind (an unknown kind is a parse error, never an inferred default), under the scenario-level invariant that a fault-declaring phase is a silence window (`fault_phases_are_silent`: fault ⇒ `occurrences = 0` — during a port-occupier hold nothing real listens on the egress target). An `[[expected]]` check may additionally declare `budget_ms` — optional integer milliseconds (`#[serde(default)]`, garde `range(min = 1, max = MAX_BUDGET_MS)`, the ceiling DERIVED from `SloTier::Tier90s.deadline_ms()` rather than re-pinned as a literal) — the sub-tier deadline that check is graded against; absent means it inherits its scenario's tier. Because the rule spans `expected` and its sibling `slo_tier`, it is checked at load by `Scenario::check_budgets()` rather than by garde (§Established Decisions [Validation Library]). No committed scenario TOML declares one. A scenario may additionally declare `[[checklist]]` — an array-of-tables of `ChecklistItem { induced, observation }` (`#[serde(default)]`, garde `dive`, both halves `length(min = 1, max = MAX_CHECKLIST_TEXT)` with `MAX_CHECKLIST_TEXT = 200`, a dialog row's display bound) carrying the operator-checklist rows a hold renders; `HoldPoint` carries the same vector so the hold projects them to its shell. Because that rule spans `checklist` and its sibling `expected`, it too is checked at load — by `Scenario::check_checklist()`, which rejects a `[[checklist]]` declared beside a non-empty `expected` (the checklist renders only on the operator-checklist path, which a checks-bearing scenario never takes). Exactly two committed scenarios declare it: `halo-hue-encoding` and `halo-breathing-encoding`.

**Data model conventions (SQLite / `runs.db`):** Raw SQL, no migration framework; primary index keyed by `run_id` (with `seed`/`scenario`) per the Run-History decision — no synthetic UUID/serial PK is introduced. Timestamps are stored as journal-relative values whose source of truth is the JSONL journal; wall-clock stamps for the journal come from `std::time::SystemTime`/`Instant` (never tokio's virtual clock, which would break journal-relative SLO math). Column types are fixed on first write (no migration framework to coerce later): on `runs`, `latency_ms` is INTEGER milliseconds (NULL for blocked rows); `journal_emitted_at`/`read_back_observed_at` are stored as TEXT RFC-3339 (the JSONL envelope's wire form), while the integer-millisecond value the SLO math consumes is the separate `latency_ms` INTEGER column; `slo_tier` is a closed TEXT enum over exactly `<5s`/`<20s`/`<90s`. Nullability is qualified PER TABLE: on `run_check` both `latency_ms` and `deadline_ms` are INTEGER **NOT NULL** — a blocked or declare-only check emits no row at all rather than a NULL one — and `budget_ms` is INTEGER NULL when the check inherits its scenario's tier. Fingerprint arrays are stored as a JSON1 TEXT array of fingerprint strings and indexed via SQLite JSON1.

## Standard Contracts

Conductor exposes no HTTP service, so it has no `/health` or `/ready` HTTP endpoints. The equivalent contracts every scenario/module must follow are the **MCP preflight readiness gate** and the **run report artifact envelope** — these are the shared shapes scopes depend on.

The probe's REPORTING is name-only (a finding names handles, never values — the redaction property holds), and its CHECK is graded PER HANDLE by kind: this flag and `ANDROMEDA_PULSE_L4_DETERMINISTIC` keep the truthy `"true"`/`"1"` gate (`conductor_core::flag_declared`), while the PATH-valued `ANDROMEDA_PULSE_DATA_DIR` is met by presence-after-trim (`conductor_core::handle_declared`), so all three subjects are meetable (§Standard Contracts — Liveness equivalent). An absent declaration of THIS handle is named upstream as an unmet contract term AND distinguished at the probe: `ANDROMEDA_PULSE_MCP_ENABLED=false` leaves `handles-declared` naming that handle alone (measured 2026-09-04, `preconditions-probe-reads-path-handles-by-presence`).
- `ANDROMEDA_PULSE_L4_DETERMINISTIC` — Pulse-side flag that swaps a canned `L4Output` for the Llama-3.2-3B inference, which is what makes a live leg reproducible. Asserted **not** set by Conductor itself; Conductor READS it in its own environment as ONE OF TWO `shell-declaration` proxies the run contract observes (with `ANDROMEDA_PULSE_MCP_ENABLED`) — the shell that launches Conductor is the one that launches `pulse-app` — and an absent declaration surfaces as an unmet contract term naming both candidate causes, never as a claimed measurement of `pulse-app`.
- `ANDROMEDA_PULSE_DATA_DIR` — the live Pulse-under-test's data directory. **Conductor MUST propagate it to the spawned `andromeda-pulse-mcp` sidecar** so the sidecar reads the SAME `{data_dir}/corpus/corpus.db` the live Pulse writes; the read-back tools filter incidents by the `workspace` column, whose value is the key `pulse-app` PUBLISHES at `{data_dir}/run/workspace-key` (its detected root) and only FALLS BACK to `data_dir` when that file is absent or invalid (`crates/mcp-server/src/bin/andromeda-pulse-mcp.rs:74` + `tools.rs:336`; measured 2026-09-01, HEAD `83d4060`) — so the `= data_dir` equality no longer holds unconditionally, while the propagation obligation stands unchanged: a mismatch makes every `query_incident_list` come back empty (false pass-as-empty / perpetual blocked). If the live Pulse leaves it unset, Conductor resolves and passes the identical platform default (`%APPDATA%\andromeda-pulse` on Windows · `$XDG_CONFIG_HOME`/`~/.andromeda-pulse` on Linux). The preflight canary verifies the wiring.
- Pulse-side `mcp-server` cargo feature must be built — a precondition Conductor asserts and reports as the `blocked` precondition string.
- No `DATABASE_URL` (SQLite path is a local file), no secrets/cloud env vars (local-only tool).

## Infrastructure Patterns

**Build system:** Cargo (cargo 1.85, Rust 2024 edition, MSRV 1.94.1). Lint with `cargo clippy`; test with `cargo nextest` — the pinned runner, driven through a zero-retry `ci` profile in `.config/nextest.toml` (no retries mask flakes — the determinism invariant) plus `cargo test --doc` for the doctests nextest skips — over the dev-test stack rstest/proptest/insta/assert_cmd/assert_fs/predicates; line coverage via `cargo-llvm-cov` (requires the `llvm-tools-preview` toolchain component). Exact tool/dep versions live in test-plan §4. `bundled` SQLite compiles SQLite C from source (longer cold builds, fully self-contained). tonic 0.14 moved prost codegen to `tonic-prost-build` — build scripts use that crate (budget a small adjustment when mining Pulse's prior-art injectors that predate the split). Optional `cargo-modules` / `cargo-rail` audit the dependency graph. The `conductor-tauri` GUI bin uses `tauri-build` (build-dep): its `tauri::generate_context!` resolves `build.frontendDist` (`ui/dist`) at COMPILE time, so the webview bundle MUST be built (`npm run build`) before any workspace `cargo build`/`nextest`/`clippy` that compiles `conductor-tauri` — wired as an `ensure_frontend` step into `scripts/agent-run.{sh,ps1}` (the `run` verb) and the CI Rust job (a bare `cargo build` does NOT run `beforeBuildCommand` — only the Tauri CLI does). **`npm run build` is necessary but NOT sufficient, and the PROFILE does not decide it:** whether the binary loads the embedded bundle or `devUrl` turns on the **`custom-protocol` feature** — `tauri` 2.11.3's `build.rs` computes `let dev = !custom_protocol` and emits `cargo:dev`, which `tauri-build` 2.6.0 reads back through `DEP_TAURI_DEV` (`is_dev()`), **as measured 2026-09-01** (a bare `cargo build --release -p conductor-tauri` emitted `cargo:rustc-cfg=dev` and opened on `http://localhost:5173`; the same build with `--features tauri/custom-protocol` opened on `http://tauri.localhost/`). A binary that must serve the bundle is therefore built `cargo build --release -p conductor-tauri --features tauri/custom-protocol`, which is what both harness shells do for `--e2e`. The Tauri tree adds many `unmaintained`-but-non-vulnerable transitive advisories (gtk-rs Linux-webview path · `unic-*` via `urlpattern` · `proc-macro-error`) + the `MPL-2.0` / `Apache-2.0 WITH LLVM-exception` licenses — all justified in `deny.toml`. Each entry names its crate and dependency path inline; BOTH supply-chain runners are green over the un-drifted lock — `cargo deny check advisories bans licenses sources` exit 0 and `cargo audit` exit 0 (1239 advisories loaded, 564 packages scanned, 18 allowed warnings: 17 `unmaintained` + 1 `unsound`, every one `deny.toml`-adjudicated), as measured 2026-09-05 against advisory-db HEAD `5a0ebedf` with `git status --porcelain` empty. ## Cross-cutting Patterns

- **Config management:** Local files + environment variables only — declarative scenario config files (serde + garde, no DSL), a pinned MCP contract manifest file, and the Pulse-side `ANDROMEDA_PULSE_MCP_ENABLED` + `ANDROMEDA_PULSE_DATA_DIR` env flags (the latter propagated to the spawned sidecar so it reads the live Pulse's corpus). Conductor's own configuration handles live under the reserved `CONDUCTOR_*` env namespace (`CONDUCTOR_RUNS_DIR`, `CONDUCTOR_SCENARIOS_DIR`, `CONDUCTOR_CONTRACT_MANIFEST`, `CONDUCTOR_SEED`); precedence is files over env defaults, and CLI flags over env. No secrets manager and no cloud config (local-only tool, no credentials).
- **Development Style:** **agent-driven** — the headless `scripts/agent-run.sh` path is the source of truth and the release gate; the GUI is a thin shell over the same core commands. (This signal is read downstream by tests/obs/setup-project specialists.)
- **Determinism discipline:** seeded RNG + `current_thread` runtime guarantee "same scenario + seed ⇒ same stream shape"; wall-clock journal stamps come from `std::time::SystemTime`/`Instant`, never tokio's virtual clock, preserving journal-relative SLO math.
- **Verdict/error wall:** the cross-cutting rule that verification outcomes are typed values and `Result::Err` is reserved for harness faults applies in every seam crate, so the report can classify outcomes by `match` rather than by catching errors.
- **Trust boundary:** Conductor runs entirely on the loopback dev host with no inbound listener of its own — it is a gRPC/MCP *client*, not a server. Its outbound surfaces are OTLP/gRPC egress to `127.0.0.1:4317` (`:4318` unused) and an MCP read-back session to a Pulse server it launches as a `tokio::process::Command` child over piped stdio — console-suppressed on Windows — trusting that child's stdout as the read-back source. The single deliberate exception is the port-occupier fault scenario, which intentionally *binds* `:4317` to exercise Pulse's reaction — the only case where a SHIPPED Conductor binary opens a port. The dev-only webview a11y legs — the routine `--e2e` arm, the operator-local `a11y:driven` arm and the operator-local `sr*` screen-reader suites — additionally spawn tauri-driver / the native WebDriver, which bind loopback `4444`/`4445` for the harness's lifetime and are gone with it (§Occupied Resources — Ports); the screen-reader suites additionally spawn the host NVDA named by `CONDUCTOR_NVDA` and a fixed-argv PowerShell window-activation script, neither of which opens a listener (measured 2026-09-02). There are no secrets, no `DATABASE_URL`, and no cloud credentials (the SQLite path is a local file).
- **Scope law:** "no scenario without a P-ID" and the stated non-goals (not a load-tester, no Pulse process management, no automation of **PULSE's** UI — its visual claims ride the operator checklist; driving Conductor's OWN webview is in-scope and ships as THREE suite families (four `wdio` suites) over ONE WebdriverIO + tauri-driver stack — the dev-only `--e2e` self-verify routine arm, the operator-local `a11y:driven` driven arm and the operator-local screen-reader leg (`sr` / `sr-empty` / `sr-error`, NVDA's own speech log as the driver on the Windows dev host) — never a second automation stack) are guards against feature creep; the complete `coverage-matrix.md` (every capability in the SUT capability manifest, zero gaps) is the definition of done.

## Project Intent

- **Product type:** Desktop control-panel app (Tauri 2) over a headless-drivable Rust core — a scenario-driven OTLP fault-injection and verification harness that drives a live Pulse instance through its claimed capabilities (the SUT capability manifest's accepted set) on a deterministic seeded timeline and verifies each reaction within its SLO (programmatically via MCP read-back where one exists, via an operator checklist for visual claims).
- **Scale intent:** Personal — solo developer, local dev host, no cloud, no multi-tenancy; runs next to a real Pulse instance on the dev host.
