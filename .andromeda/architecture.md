## Design Philosophy

- **Determinism under a seed** — the timeline engine runs on a `current_thread` tokio runtime with zero work-stealing, so the same scenario + seed always produces the same emission stream shape; reproducibility is a property the architecture enforces in the runtime flavor, not a convention bolted on later.
- **Headless-drivable core, thin shells** — all engine logic lives in runtime-agnostic library crates that both `scripts/agent-run.sh` (the source of truth) and the optional Tauri 2 GUI call identically; the CLI/headless path is the release gate and the GUI is convenience only. "Identically" holds for every deterministic-posture scenario; a scenario declaring the real-model L4 posture (2026-09-22) runs headless only, by design — `conductor run` alone evaluates the gate under the scenario's declared posture, while `conductor suite` and the GUI keep the deterministic gate and record it `Blocked` (§Standard Contracts — Readiness gate).
- **Compiler-enforced module seams** — the modular monolith is realized as a crate-per-seam Cargo workspace where `Cargo.toml` dependency edges *are* the architecture and a forbidden cross-seam dependency simply will not compile.
- **Outcomes are values, errors are harness faults** — verification verdicts (`Pass`/`Fail`/`CalibrationRegion`) and report states (`Pass`/`Fail`/`ManualCheck`/`KnownResidual`/`Blocked`) are typed return values; `Result::Err` is reserved strictly for Conductor's own failures (config parse, transport down, MCP unreachable), so the report can correctly classify a model-backed SUT's behavior by matching on types rather than catching exceptions.
- **Journal-relative ground truth** — every SLO is measured as `read_back_observed_at − journal_emitted_at` against an on-disk JSONL emission journal, never wall-clock-from-test-start; file artifacts are the agent-parseable ground truth and the embedded SQLite index is a thin convenience layer over them.

## Established Decisions

- **[Language / Runtime] Rust 2024 + tokio 1.52.3:** Pinned by brief for Pulse-consistency; tonic/prost require a tokio reactor and the deterministic phase scheduler maps cleanly to `tokio::time` for exact gap/silence/ramp timing.
- **[Async Runtime Flavor] tokio `current_thread`, core-owned:** Zero work-stealing makes emission ordering a deterministic function of the seed; throughput headroom is irrelevant because load-testing is an explicit non-goal (Pulse prior art saturated ~10k spans/s). `#[tokio::main(flavor = "current_thread")]` on the CLI path; hand-built `Builder::new_current_thread()` owned by the core under Tauri so Tauri's own multi_thread runtime stays the GUI shell's concern.
- **[Determinism RNG] rand_chacha `ChaCha8Rng` seeded via `seed_from_u64`:** The timeline scheduler's sole source of non-determinism is a seedable `ChaCha8Rng` (rand_chacha 0.9 + rand_core 0.9), seeded `seed_from_u64(scenario.seed)`; ChaCha8's algorithm is stable across platforms and crate versions, so the same seed reproduces the same emission-stream shape on any host — `StdRng` (no cross-version stability guarantee) was rejected for exactly this reason. The seed materially shapes timing (bounded per-gap jitter), and a transition's `elapsed_ms` is a deterministic cumulative sum of effective gaps, never a clock read.
- **[OTLP Emission Strategy] opentelemetry-proto 0.32.0 raw types over the SDK exporter:** The `opentelemetry-otlp` exporter is a near-deal-breaker — it offers no control over fingerprint identity, severity boundaries, or root-vs-child error placement and spawns its own batch tasks on the runtime. Raw message structs give byte-level control, which fault injection requires; this is the single most consequential fork in the build.
- **[Backend Framework] None (no web framework):** Conductor is a gRPC client + MCP client + Tauri IPC host, not a server; it exposes no HTTP/network surface of its own, so Axum/Actix and REST/GraphQL/tRPC are all out of scope.
- **[Database] rusqlite 0.38.0 with `bundled` SQLite, synchronous:** Quiz I pinned file artifacts + a thin SQLite index; rusqlite keeps the storage seam synchronous (no async-runtime entanglement) and `bundled` yields a self-contained cross-platform build with JSON1 for indexing fingerprint arrays. sqlx (async-first) and SeaORM (ORM over-scope) were rejected.
- **[ORM] None — raw SQL:** `runs.db` is a small fixed set of hand-written tables of run metadata (`runs`, the scenario-grained run index; `run_envelope`, the run-level envelope standing; `run_check`, the per-check index keyed `(run_id, scenario, check_index)`), each added additively under `CREATE TABLE IF NOT EXISTS`; an ORM's entity/migration machinery is weight with no payoff for hand-written append + a handful of cross-run SELECTs + one run-scoped teardown. That teardown is `RunsDb::delete_run` (2026-09-06) — three LITERAL `DELETE … WHERE run_id = ?1` statements over `runs` / `run_check` / `run_envelope` in one transaction, rusqlite bound parameters, idempotent, and never `format!`-assembled even over a hard-coded table list (security-plan §Security Anti-Patterns → Input). The seam is its sole implementation: the `conductor cleanup <run_id>` verb is the only caller and the harness shells issue no SQL of their own.
- **[MCP Read-Back Client] hand-rolled line-delimited JSON-RPC (rmcp removed 2026-06-27):** The read-back client (`conductor-verify/src/jsonrpc.rs` + `client.rs`) speaks JSON-RPC directly over the sidecar's stdio — `initialize` (capturing the server's `protocolVersion` for negotiation) + `tools/list` + `tools/call` — returning the **raw `serde_json::Value` result**. rmcp 1.7.0 was the original choice (typed SDK + version negotiation) but was **removed** when proven against the live sidecar: Pulse's MCP *server* is itself hand-rolled JSON-RPC (`crates/mcp-server/src/jsonrpc.rs`) and **non-MCP-compliant for `tools/call`** — it returns the raw tool payload as the JSON-RPC `result` (no `{content:[…]}` envelope), which rmcp's typed `call_tool` deserializes into `ServerResult` and rejects as `UnexpectedResponse` on *every* live call (rmcp exposes no raw-result escape). A hand-rolled client is therefore the faithful match to Pulse's actual wire format; version negotiation reduces to reading the `initialize` result's `protocolVersion`, the contract manifest still pins `2024-11-05`, and the preflight gate still guards a strict-newer mismatch.
- **[Validation Library] serde 1.0.x + garde 0.22.1:** garde (the modern rewrite of `validator`) expresses scenario bounds declaratively next to the serde structs — `range` rules for simple bounds (a bounded error fraction, shipped as `EmissionShape::Error { error_percent: u32 }` ∈ 0..=100 — an integer percent, not an f64, so `PhaseSpec`/`Scenario` keep `Eq`; non-negative durations, sane ramp factors) and `#[garde(custom)]` field validators for the rest; cross-field invariants spanning distinct fields (p50≤p95≤p99 ordering, severity-mix sums, the fault ⇒ `occurrences = 0` silence rule `fault_phases_are_silent`) use garde's `Context` pattern or a field-level `custom` one altitude up (the fault rule sits on `Scenario::phases`, like `no_duplicate_pids` on `p_ids`), since garde 0.22.1's `custom` is field-level only (no container-level custom) — with no async or web-framework coupling. **A THIRD route exists, and its boundary is structural:** the one-altitude-up `custom` covers only an invariant CONTAINED WITHIN the lifted field (`fault_phases_are_silent` needs `phases` alone), because a field-level `custom` receives `(&field, &())` and can see no SIBLING field. An invariant spanning a field and its sibling therefore cannot be a garde validator at all under 0.22.1 — it ships as a plain load-path method invoked from `Scenario::from_toml_str`, the shape `Scenario::check_capabilities` already uses, `Scenario::check_budgets` (`budget_ms` ≤ its scenario's own `slo_tier` deadline) joined, and `Scenario::check_checklist` (a declared `[[checklist]]` may not sit beside a non-empty `expected` — the checklist renders only on the operator-checklist path a checks-bearing scenario never takes) now joins. **A nested spec field must `dive`, never `skip`** — a `skip`ped nested struct deserializes unvalidated because garde never descends into it. **Pinned 0.22.1**, not the originally-chosen 0.23.0: its `garde_derive 0.23.0` proved absent from the registry, so 0.23.0 + the `derive` feature is unbuildable. validator (predecessor) and serde_valid (JSON-Schema niche) were rejected.
- **[Scenario Config Format] TOML on disk via the `toml` crate (0.9):** scenario config files under `scenarios/` are declarative TOML, serde-deserialized and bounds-checked with garde at load. The load-error mapping is **three-way**: `Scenario::from_toml_str` → `CoreError::Config` on a parse failure OR on a non-garde load-path check failure (`check_budgets`, `check_capabilities`, `check_checklist`), and `CoreError::Validation` only on a garde failure — because `Validation` is pinned `#[from] garde::Report` and structurally cannot carry a hand-written message. All three are harness faults on the `Result::Err` side of the verdict/error wall. TOML was chosen over JSON (the only other candidate; serde_json was already present) for hand-author ergonomics + inline comments across the per-P-ID scenario files — a P4 user decision. The `toml` crate is audit/deny-clean; serde_json remains the run-report-envelope / JSONL-journal serializer.
- **[Accepted Capability Set] a versioned SUT capability manifest, not a compile-time constant:** which Pulse P-IDs a scenario may name is **data** — `contracts/pulse-capabilities.toml`, read and bounds-checked at load (same `toml` + serde stack, no new dependency). Validation is two-layered: garde's `pid_format` asserts the `P-NNN` **shape** only, and `Scenario::check_capabilities` asserts **membership** against the manifest, applied by `Scenario::from_toml_str_with(&str, &CapabilityManifest)` at every load site that takes a `&CapabilityManifest` — the binary edges (`conductor-cli::paths`, `conductor-tauri::commands`) and the `conductor-core` catalog loaders that carry the manifest through (`list_scenarios(dir, &manifest)` for identity-only summaries, `load_catalog(dir, &manifest)` for the whole `Scenario` where a gate needs the phases a summary drops); the set is whatever takes that parameter, never a count. A malformed / absent / unparseable manifest is a **harness fault** (`CoreError`, `Result::Err`) carrying a named reason — never `Blocked` (a blocked row needs `run_id`/`seed`/`scenario`/`p_ids`/`slo_tier`, none of which exist at manifest-load time) and never a silent widening. The **accepted set** is data; the **coverage classification** stays code-native (`coverage_matrix()` in `conductor-core`, a no-runtime-IO `static`), and `check_sut_drift` asserts set-equality between the two — deliberately a two-source comparison, which sourcing the classification from the manifest would collapse into a self-check. So re-aiming at a newer Pulse release is a manifest edit **plus** a matching classification row: an accepted id with no row (or a classified id the manifest no longer accepts) is a `CoreError::SutDrift`, never a silent gap. **A second integrity gate sits beside it on a different axis:** `check_sut_drift` asks whether every accepted capability is *classified*, while `check_scenario_backing` asks whether every capability classified `Auto` — the mode that claims Conductor both drives the stimulus and asserts the reaction — actually has a scenario naming it. A capability can pass the first and fail the second, because classification is a statement of intent and a scenario is what makes it true. The `UNBACKED_AUTO` pin records the `Auto` claims no scenario yet backs, held to exact-set equality against the committed catalog (a new unbacked claim, a pin a scenario now covers, or a pin that lost its `Auto` classification are each a `CoreError::UnbackedCoverage`), so the ledger can only shrink under compulsion. Only `Auto` participates — `DriveObserve` is operator-confirmed by definition, and `StaticOnly` / `NotConductors` are deliberately not Conductor's to drive. `Scenario::from_toml_str(&str)` and `PId`'s shape are unchanged — garde's `dive` propagates `Context`, so threading the accepted set through garde would have forced a context onto `PId`/`PhaseSpec`/`EmissionSpec`/`ExpectedCheck` and changed `PId`'s public API.
- **[Error Handling] thiserror 2.0.18 in seam crates + anyhow 1.0.104 at edges, plus a type-level verdict/error wall:** The report's states require *matching on error variants* — "MCP tool absent" → `Blocked`, "transport refused" → harness error, "wrong incident" → `Fail` — so verification outcomes are VALUES (`Verdict`/`ReportState`), never Rust errors; `Result::Err` is reserved for harness failures only. `tonic::Status` codes and MCP error responses are first-class verification inputs. anyhow lives only in `conductor-cli` / `#[tauri::command]` edges.
- **[Module Boundaries] Crate-per-seam Cargo workspace:** In Rust, crates are compiler-enforced visibility boundaries; one workspace with a runtime-agnostic `conductor-core` plus the seam crates `conductor-timeline`/`conductor-emit`/`conductor-faults`/`conductor-verify`/`conductor-report` (+ `conductor-cli` bin and the `conductor-tauri` bin) makes a forbidden cross-seam dependency fail to compile, gives per-seam `cargo test -p` (and, with the qualifier below, `cargo build -p`), ships a single deployable, and mirrors Pulse's `crates/…` layout. The compiler enforces; cargo-modules/cargo-rail only audit. **The forbidden-edge property is compiler-enforced and unqualified; the standalone per-seam BUILD now holds for every member, measured rather than gate-enforced.** Workspace feature unification can mask a feature a crate uses but declares only in `[dev-dependencies]`, so a crate compiles in the workspace and in `cargo test -p` while failing alone. The standalone sweep takes the nine members each on its OWN targets — `--lib` for the seven library crates, `--bins` for `conductor-cli` and `conductor-tauri`, which have no lib target and would false-red under a uniform `--lib` — every one exit 0, measured twice (builder and operator). `--all-targets` is deliberately NOT the sweep form: it re-unifies dev-dependencies, which is the exact masking the sweep exists to catch. The caveat: no CI job builds a member standalone, so the property is measured-at-a-chunk rather than gate-enforced, and a future dev-only feature declaration could reintroduce it unnoticed.
- **[Workspace / Core Structure] Runtime-agnostic core library + CLI bin + Tauri bin:** This is the structural decision that makes "headless-drivable" real — engine logic lives in a core usable outside Tauri, and both `agent-run` and Tauri commands call it, enforcing the headless/CLI/GUI split at compile time.
- **[Real-time Strategy] Tauri 2 IPC `Channel` for in-app live updates only:** Streams live counters / target status backend→frontend without per-message JSON overhead; FCM/APNs/web-push are irrelevant on a local tool, and Conductor must NOT emit native OS toasts because those are Pulse behavior it observes via the operator checklist.
- **[Message Broker] N/A:** Single-process modular monolith; inter-module flow is in-process Rust calls / `tokio::sync::mpsc` channels at most — no Kafka/NATS/Redis. The only queue-like surface is the OTLP gRPC stream to Pulse, which is the SUT, not Conductor's infrastructure.
- **[Deployment] Local `cargo build --release` + `scripts/agent-run.sh`:** Headless is the source of truth, co-located with Pulse (which binds loopback `:4317` only, ruling out remote/containerized execution); the Tauri 2 bundler — the host `tauri-cli` dev-tool, which no lockfile resolves — produces the GUI artifact as convenience, not a release gate. No cloud / container / serverless.

Each is its own named step with no `continue-on-error` and no `if:`, each opening its `run` with a presence guard on its subject that emits a `::error::` annotation and exits 1 so an absent subject fails loudly rather than passing vacuously, then invoking the specific nextest target (`-p conductor-report --test coverage_gate` · `-p conductor-core --test scenario_audit_gate` / `secret_scan_gate` / `workflow_env_gate`). Re-listing a gate's assertion in shell would be a second copy that drifts, so the gate IS the Rust test and the step is its presence-guarded invocation. ## Conventions

**Interface surfaces (three pinned, no network API of Conductor's own):**
- **Outbound emission:** OTLP over gRPC to `127.0.0.1:4317` via tonic 0.14.6 / tonic-prost 0.14.6; OTLP wire format built from opentelemetry-proto raw types. OpenTelemetry Semantic Conventions are the shared vocabulary (`service.name`, span `Status.Code=ERROR`, exception span events with `exception.type`/`message`/`stacktrace`, log `SeverityNumber` at boundaries); W3C Trace Context propagates across emulated service edges.
- **Inbound verification:** MCP read-back via a hand-rolled line-delimited JSON-RPC client over the sidecar's stdio (rmcp removed — Pulse's `tools/call` is non-MCP-compliant); a version-pinned contract manifest + `initialize` preflight gate, with the **blocked** report state on mismatch.
- **Internal core↔UI:** Tauri 2 `#[tauri::command]` request/response for start/stop/picker actions; `Channel` for streaming live counters. REST / GraphQL / tRPC are N/A.

**Error handling:** Typed `thiserror` enums per seam crate (e.g. `EmitError`, `VerifyError`, `ContractMismatch`, `ConfigError`); `anyhow` only at `conductor-cli` / `#[tauri::command]` edges. A type-level verdict/error wall separates verification outcomes from harness failures: `enum Verdict { Pass, Fail, CalibrationRegion }` and `enum ReportState { Pass, Fail, ManualCheck, KnownResidual, Blocked }` are returned as `Ok(...)`; `Result::Err` means a harness fault (config parse, transport down, MCP unreachable). Read-back transport/decode/JSON-RPC errors fan out into `VerifyError` variants (`Transport`/`Protocol`/`Decode`/`JsonRpc` — blocked/fail/harness-error); garde's validation `Report` becomes a `ConfigError` harness-failure class via `#[from]`. `tonic::Status` codes and MCP error responses are first-class verification inputs, not panics.

**Naming patterns:** snake_case Rust source files and identifiers (per Rust convention); crates named `conductor-<seam>` (kebab-case crate names, snake_case module paths); scenarios keyed by Pulse capability P-ID, drawn from the SUT capability manifest's accepted set — "no scenario without a P-ID". On-disk artifacts use kebab-case Markdown filenames (e.g. `coverage-matrix.md`, run report) and per-run JSONL journals.

**Config conventions:** Declarative scenario config (no scenario DSL) deserialized with serde and bounds-checked with garde at load; validation co-located with the serde structs in their owning seam crates, diving into nested spec structs rather than skipping them. Durations are non-negative; an error fraction is bounded (shipped as an integer `error_percent` ∈ 0..=100); ramp factors validated sane; latency targets enforce p50≤p95≤p99 ordering and severity-mix sums. A phase's emission shape is declared data — `EmissionSpec { signal, occurrences, shape }`, where `occurrences: 0` is a deliberate silence window and the shape selects its emit-primitive family. A phase may also declare a FAULT for its window — the optional `[phases.fault]` table (`PhaseSpec.fault: Option<FaultSpec>`, serde default absent, garde `dive`) carrying the closed `FaultKindSpec::PortOccupier` kind (an unknown kind is a parse error, never an inferred default), under the scenario-level invariant that a fault-declaring phase is a silence window (`fault_phases_are_silent`: fault ⇒ `occurrences = 0` — during a port-occupier hold nothing real listens on the egress target). An `[[expected]]` check may additionally declare `budget_ms` — optional integer milliseconds (`#[serde(default)]`, garde `range(min = 1, max = MAX_BUDGET_MS)`, the ceiling DERIVED from `SloTier::Tier90s.deadline_ms()` rather than re-pinned as a literal) — the sub-tier deadline that check is graded against; absent means it inherits its scenario's tier. Because the rule spans `expected` and its sibling `slo_tier`, it is checked at load by `Scenario::check_budgets()` rather than by garde (§Established Decisions [Validation Library]). No committed scenario TOML declares one. A scenario may additionally declare `[[checklist]]` — an array-of-tables of `ChecklistItem { induced, observation }` (`#[serde(default)]`, garde `dive`, both halves `length(min = 1, max = MAX_CHECKLIST_TEXT)` with `MAX_CHECKLIST_TEXT = 200`, a dialog row's display bound) carrying the operator-checklist rows a hold renders; `HoldPoint` carries the same vector so the hold projects them to its shell. Because that rule spans `checklist` and its sibling `expected`, it too is checked at load — by `Scenario::check_checklist()`, which rejects a `[[checklist]]` declared beside a non-empty `expected` (the checklist renders only on the operator-checklist path, which a checks-bearing scenario never takes). Exactly two committed scenarios declare it: `halo-hue-encoding` and `halo-breathing-encoding`.

**Data model conventions (SQLite / `runs.db`):** Raw SQL, no migration framework; primary index keyed by `run_id` (with `seed`/`scenario`) per the Run-History decision — no synthetic UUID/serial PK is introduced. Timestamps are stored as journal-relative values whose source of truth is the JSONL journal; wall-clock stamps for the journal come from `std::time::SystemTime`/`Instant` (never tokio's virtual clock, which would break journal-relative SLO math). Column types are fixed on first write (no migration framework to coerce later): on `runs`, `latency_ms` is INTEGER milliseconds (NULL for blocked rows); `journal_emitted_at`/`read_back_observed_at` are stored as TEXT RFC-3339 (the JSONL envelope's wire form), while the integer-millisecond value the SLO math consumes is the separate `latency_ms` INTEGER column; `slo_tier` is a closed TEXT enum over exactly `<5s`/`<20s`/`<90s`. Nullability is qualified PER TABLE: on `run_check` both `latency_ms` and `deadline_ms` are INTEGER **NOT NULL** — a blocked or declare-only check emits no row at all rather than a NULL one — and `budget_ms` is INTEGER NULL when the check inherits its scenario's tier. Fingerprint arrays are stored as a JSON1 TEXT array of fingerprint strings and indexed via SQLite JSON1.

## Cross-cutting Patterns

- **Config management:** Local files + environment variables only — declarative scenario config files (serde + garde, no DSL), a pinned MCP contract manifest file, and the Pulse-side `ANDROMEDA_PULSE_MCP_ENABLED` + `ANDROMEDA_PULSE_DATA_DIR` env flags (the latter propagated to the spawned sidecar so it reads the live Pulse's corpus). Conductor's own configuration handles live under the reserved `CONDUCTOR_*` env namespace (`CONDUCTOR_RUNS_DIR`, `CONDUCTOR_SCENARIOS_DIR`, `CONDUCTOR_CONTRACT_MANIFEST`, `CONDUCTOR_SEED`); precedence is files over env defaults, and CLI flags over env. No secrets manager and no cloud config (local-only tool, no credentials).
- **Development Style:** **agent-driven** — the headless `scripts/agent-run.sh` path is the source of truth and the release gate; the GUI is a thin shell over the same core commands. (This signal is read downstream by tests/obs/setup-project specialists.)
- **Determinism discipline:** seeded RNG + `current_thread` runtime guarantee "same scenario + seed ⇒ same stream shape"; wall-clock journal stamps come from `std::time::SystemTime`/`Instant`, never tokio's virtual clock, preserving journal-relative SLO math.
- **Verdict/error wall:** the cross-cutting rule that verification outcomes are typed values and `Result::Err` is reserved for harness faults applies in every seam crate, so the report can classify outcomes by `match` rather than by catching errors.
- **Trust boundary:** Conductor runs entirely on the loopback dev host with no inbound listener of its own — it is a gRPC/MCP *client*, not a server. Its outbound surfaces are OTLP/gRPC egress to `127.0.0.1:4317` (`:4318` unused) and an MCP read-back session to a Pulse server it launches as a `tokio::process::Command` child over piped stdio — console-suppressed on Windows — trusting that child's stdout as the read-back source. The single deliberate exception is the port-occupier fault scenario, which intentionally *binds* `:4317` to exercise Pulse's reaction — the only case where a SHIPPED Conductor binary opens a port. The dev-only webview a11y legs — the routine `--e2e` arm, the operator-local `a11y:driven` arm and the operator-local `sr*` screen-reader suites — additionally spawn tauri-driver / the native WebDriver, which bind loopback `4444`/`4445` for the harness's lifetime and are gone with it (§Occupied Resources — Ports); the screen-reader suites additionally spawn the host NVDA named by `CONDUCTOR_NVDA` and a fixed-argv PowerShell window-activation script, neither of which opens a listener (measured 2026-09-02). A THIRD outbound surface exists in CI ONLY — re-described 2026-09-17, not retired, and the surface COUNT is unchanged: the `a11y` job's one-shot HTTPS fetch of the version-pinned msedgedriver (§Occupied Resources — Ports, operator-ratified 2026-09-17; it replaced the WebView2 Evergreen bootstrapper fetch admitted 2026-09-08 and made floor-conditional 2026-09-12, which retired with its install step). It is taken on every a11y run rather than conditionally, and is nonetheless the narrower crossing, because its version derives from the image's own runtime reading instead of floating always-latest. It is reached by no shipped Conductor binary and by no dev-host harness leg, so the loopback-only claim holds unchanged for every shipped and local path. There are no secrets, no `DATABASE_URL`, and no cloud credentials (the SQLite path is a local file).
- **Scope law:** "no scenario without a P-ID" and the stated non-goals (not a load-tester, no Pulse process management, no automation of **PULSE's** UI — its visual claims ride the operator checklist; driving Conductor's OWN webview is in-scope and ships as THREE suite families (four `wdio` suites) over ONE WebdriverIO + tauri-driver stack — the dev-only `--e2e` self-verify routine arm, the operator-local `a11y:driven` driven arm and the operator-local screen-reader leg (`sr` / `sr-empty` / `sr-error`, NVDA's own speech log as the driver on the Windows dev host) — never a second automation stack) are guards against feature creep; the complete `coverage-matrix.md` (every capability in the SUT capability manifest, zero gaps) is the definition of done.

## Project Intent

- **Product type:** Desktop control-panel app (Tauri 2) over a headless-drivable Rust core — a scenario-driven OTLP fault-injection and verification harness that drives a live Pulse instance through its claimed capabilities (the SUT capability manifest's accepted set) on a deterministic seeded timeline and verifies each reaction within its SLO (programmatically via MCP read-back where one exists, via an operator checklist for visual claims).
- **Scale intent:** Personal — solo developer, local dev host, no cloud, no multi-tenancy; runs next to a real Pulse instance on the dev host.
- **Growth model:** Modular monolith — one deployable harness with hard, compiler-enforced module seams (timeline engine · emission primitives · fault helpers · verification/MCP read-back · run report · control panel).
- **How new functionality is added:** New scenarios are added as declarative config keyed to a Pulse P-ID (no scenario without a P-ID); new module seams are added as new workspace crates with explicit `Cargo.toml` dependency edges. Downstream scopes are added via `/andromeda-scope-arch`, inheriting the conventions in this document.
- **Template patterns:** N/A — single harness, not a fleet of services.
