## Backend Framework Comparison

This is not a web-backend project. It is a **headless-drivable Rust core** (timeline engine + emission + verification) with a thin Tauri 2 GUI shell, driven equally from `scripts/agent-run.sh`. The brief pins **Rust 2024 + tokio**; the real fork is *how to structure the async core*, not which web framework. No Axum/Actix/web-server option is in scope (Conductor exposes no HTTP/network service of its own — it is a gRPC *client* + an MCP client).

- **tokio (1.48.x, crates.io, actively maintained — the de-facto Rust async runtime)** — *Pinned by brief; current.* Fits: tonic/prost require a tokio reactor; the timeline engine's deterministic phase scheduler maps cleanly to `tokio::time` (interval/sleep_until) for exact gap/silence/ramp timing; `tokio::time::pause()`/auto-advance is available for deterministic tests of the scheduler itself. Caveat: wall-clock emission journal must be stamped from `std::time::SystemTime` / `Instant`, **not** tokio's virtual clock, or journal-relative SLO math (`read_back_observed_at − journal_emitted_at`) breaks. No deal-breaker.
- **Core-as-library + binary split (Cargo workspace; `lib` crate + `bin` CLI + Tauri `bin`)** — Tauri's own architecture supports the Rust core being a plain library "used outside of Tauri projects" ([tauri.app/concept/architecture](https://v2.tauri.app/concept/architecture/)). Fits the brief's "UI is a thin shell over the same commands": engine logic lives in a runtime-agnostic core crate; both `agent-run` CLI and Tauri commands call it. This is the structural decision that makes "headless-drivable" real — recommended to settle in Quiz II.
- **Single-threaded vs multi-threaded tokio flavor** — `current_thread` runtime gives the most reproducible emission ordering under a seed (no work-stealing nondeterminism); `multi_thread` is needed only if emission throughput to :4317 saturates one core. Given the non-goal ("NOT a load-tester; bounded typical/high only; 50k+ spans/s excluded"), `current_thread` or a small fixed worker pool is the determinism-favoring default. **Trade-off the user owns** (see summary).

## Module Boundary Enforcement

Quiz I growth model = **modular monolith with hard module seams**: timeline engine · emission primitives · fault helpers · verification/MCP read-back · run report · control panel. Rust enforces this at compile time — the question is *how hard* to draw the seams.

- **Cargo workspace, one crate per seam (recommended)** — In Rust, "crates are module boundaries with enforced visibility, and the compiler won't let you accidentally depend on something you shouldn't" ([40tude modular-monolith series](https://www.40tude.fr/docs/06_programmation/rust/025_modular_monolith/modular_monolith_06.html)). One workspace, crates like `conductor-timeline`, `conductor-emit`, `conductor-faults`, `conductor-verify`, `conductor-report`, plus `conductor-cli` and the Tauri bin → single deployable (monolith), independent `cargo build -p` / `cargo test -p` per seam, and `Cargo.toml` dependency edges *are* the architecture (a forbidden cross-seam dep simply won't compile). Strongest enforcement, matches the brief's "hard module seams" literally, and mirrors Pulse's own `crates/…` layout (Pulse-consistency mandate).
- **Single crate + `mod` + `pub(crate)` visibility** — Lighter: one crate, seams as modules with disciplined `pub`/`pub(crate)`. Cheaper to start but boundaries are advisory-by-convention (a `mod` can reach a sibling's `pub(crate)` item) — weaker than crate seams, and doesn't give per-seam independent test/build. Acceptable only if you want minimal initial ceremony.
- **Tooling (optional, not a substitute):** `cargo-modules` visualizes the actual module/dependency graph for review; `cargo-rail` ([github.com/loadingalias/cargo-rail](https://github.com/loadingalias/cargo-rail)) adds graph-aware testing/orchestration for multi-crate workspaces. These *audit* boundaries; the compiler *enforces* them — reach for them only if the workspace grows enough to need dependency-graph visibility.

## Key Trade-offs Summary

1. **OTLP emission strategy: `opentelemetry-proto` raw types (manual `ExportTraceServiceRequest`/`ResourceSpans`/`Span`/`Status` over tonic) vs the `opentelemetry-otlp` SDK exporter — the stakes: whether Conductor can do its job at all.** `opentelemetry-otlp` 0.32.0 ([docs.rs](https://docs.rs/opentelemetry-otlp/latest/opentelemetry_otlp/)) is built to *export SDK-generated spans from real instrumentation* — it gives you almost no control over root-vs-child error placement, synthesized stacktraces, line-variant-identical fingerprints (amended P-017c), exact `SeverityNumber` at the 17-boundary, or deterministic silence. `opentelemetry-proto` 0.32.0 (released 2026-05-08, features `gen-tonic` + `trace`/`metrics`/`logs`) exposes the raw OTLP message structs you build by hand and ship via the generated `TraceServiceClient`/`LogsServiceClient` — full control of every byte, which is exactly what fault-injection requires. Every Rust/Go synthetic generator (otel-loadgen, telemetrygen, otelgen) and Pulse's own `load_profiles.rs` prior art uses this raw path. **Strong recommendation to take `opentelemetry-proto`-raw; the SDK is a near-deal-breaker for the spec's emission primitives.** This is the single most consequential fork in the build.

2. **tokio runtime flavor: `current_thread` (determinism-favoring) vs `multi_thread` — the stakes: reproducibility-under-seed vs emission headroom.** The brief demands "same scenario + seed ⇒ same stream shape"; single-threaded scheduling removes work-stealing nondeterminism in emission ordering. Since load-testing is an explicit non-goal (bounded typical/high only), throughput rarely justifies multi-thread. Picking `current_thread` (or a small fixed pool) up front avoids a later determinism bug hunt.

3. **Storage access layer: rusqlite 0.38 (sync, raw SQL, `bundled`) vs an ORM (SeaORM 2.0 sync) — the stakes: altitude match for a one-table index.** Quiz I already pinned "file artifacts + thin SQLite index, synchronous, append-mostly." rusqlite keeps the seam synchronous and dependency-light; an ORM adds entity/migration machinery with no payoff for `runs.db`. **Sub-decision the user must ratify: bump the brief's stale `rusqlite 0.31` to current 0.38.0** (bundled SQLite 3.51.1, JSON1 included) — a free correctness/maintenance win.

4. **Workspace shape: crate-per-seam Cargo workspace vs single-crate `mod` boundaries — the stakes: compiler-enforced vs convention-enforced module seams.** The brief's "hard module seams" + Pulse-consistency (`crates/…`) point to a multi-crate workspace where forbidden cross-seam deps *won't compile* and each seam tests/builds independently. Single-crate is cheaper to start but makes boundaries advisory. This also determines the headless-core/CLI/Tauri-bin split that makes "agent-driven, UI-as-thin-shell" real.

5. **Error model split: thiserror 2.0 (typed, in seam crates) + anyhow 1.0 (erased, at binary edges) — the stakes: whether the report can correctly classify outcomes.** Conductor's report states (pass / fail / manual-check / known-residual / **blocked**) require *matching on error variants* — "MCP tool absent" → blocked, "transport refused" → harness error, "wrong incident" → fail. Typed errors in the library make this a `match`; erased errors collapse the distinction. The thiserror-in-lib / anyhow-in-bin split rides on top of the workspace decision (#4).
