## Domain Overview

This project sits at the intersection of three established domains: **synthetic telemetry generation**, **fault injection / chaos engineering**, and **observability verification (alert/detection testing)**. Conductor is a *verification harness* that drives a real, running observability/AIOps tool (Pulse) by emitting precisely-shaped OpenTelemetry data (OTLP traces, metrics, logs) on a deterministic timeline, injecting the fault patterns Pulse claims to detect, and then asserting that the correct incident surfaced within its SLO — programmatically via an MCP read-back channel where one exists, and via an operator checklist for visual claims. The core problem is *test coverage for the dynamic layer of an observability product*: static unit tests can't prove that "a 3.5× error-rate ramp produces a candidate incident within 2s of 30s persistence." That requires driving live signal through the system and checking the reaction.

Existing products and tools that occupy adjacent parts of this space:

- **telemetrygen** (OpenTelemetry Collector Contrib) — the canonical CLI for generating synthetic OTLP logs/metrics/traces over gRPC/HTTP to test collectors and pipelines; supports rate limiting, batching, durations. The closest "official" analog to Conductor's emission core, but it has no scenario engine, no verification, no determinism guarantees.
- **otelgen** (krzko/otelgen) — a more feature-rich synthetic OTLP generator: multi-signal (traces with span events/links, metrics incl. exponential histograms, logs with severity + trace correlation), gRPC/HTTP, `--rate`/`--duration`, "single" vs "multi" trace scenarios. The nearest architectural cousin to Conductor's emission primitives — but still a generator, not a verifier.
- **Chaos Mesh / LitmusChaos / Gremlin / Steadybit / AWS Fault Injection Simulator** — chaos-engineering platforms that *inject faults* (network latency/loss, CPU/IO stress, pod kills) and use observability metrics to judge pass/fail. They inject at the infrastructure layer (Kubernetes/host) and verify resilience; Conductor injects at the *telemetry* layer (shaped OTLP) and verifies *detection logic*. Litmus and the OTel Demo both have OpenTelemetry integration on their roadmaps/in use.
- **Prometheus alert-rule unit testing (`promtool test rules`) / Sloth** — the established pattern for *verifying detection logic* before it ships: synthetic time-series series in, assert which alerts fire and when. Conceptually the closest to Conductor's "expected-outcome block + SLO window" assertion model, but operates offline on PromQL rules rather than driving a live, model-backed system.
- **OpenTelemetry Demo "Load Generator" / flagd feature-flag fault injection** — the reference pattern for emitting representative app telemetry and toggling failure modes to exercise an observability backend end-to-end.

The system-under-test (Pulse) is an **AIOps / anomaly-detection incident tool**: dynamic baselines, error-rate and latency-regression detection, restart/silence detection, fingerprint-based deduplication, severity tiering, and (notably) an LLM/model-interpretive layer for hypotheses and severity choice — which is exactly why Conductor splits assertions into deterministic (hard pass/fail) vs model-interpretive (calibration-region, report-for-human).

## Common Approaches

**Architecture patterns.** Tools in this space are overwhelmingly **local, single-binary CLIs** (telemetrygen, otelgen) or **operator/controller-based platforms** for the Kubernetes-native chaos tools (Chaos Mesh, Litmus). The dominant verification-harness pattern is a **headless-drivable core + thin presentation shell** — the same shape this brief specifies (headless engine + `agent-run` script + a thin UI over the same commands). For verification specifically, the recurring pattern is **"emit a controlled signal → wait → read back the system's reaction → assert against an expected-outcome spec with a time window"** — identical in spirit to promtool's `input_series → exp_alerts` model, generalized to a live system.

**Determinism.** The high-end pattern here is **Deterministic Simulation Testing (DST)** — abstract wall-clock time, seed the RNG, and guarantee that the same scenario + seed reproduces the same event trace, so failures are reproducible and explorable across seeds (used at Antithesis, Datadog, Aiven/Kafka, S2.dev for async Rust). Conductor's "deterministic under a seed; same scenario + seed ⇒ same stream shape" is a direct application of this idea to telemetry emission, paired with a **wall-clock emission journal** as the recorded ground truth (the left side of every SLO check).

**Interaction models.** Three coexist: (1) **CLI / headless** for automation and CI; (2) **declarative config files** describing scenarios/experiments (Chaos Mesh CRDs, Litmus ChaosEngine YAML, promtool YAML) rather than a bespoke DSL — matching Conductor's "declarative config + built-in catalog, no scenario DSL" stance; (3) **a minimal control GUI / dashboard** layered on top. For an AI-driven readback channel, the emerging model is an **MCP server** exposing the system's query surface to agents (Datadog, OneUptime, Grafana all ship MCP servers that let agents "list incidents / get incident details / pull traces") — which is exactly the channel Conductor consumes via `query_incident_list` / `retrieve_report` etc.

**Data flow.** Generator shapes telemetry (per-service span rate, error fraction, latency distribution, exception fingerprint, log severity, silence) → exports OTLP/gRPC to the ingest port → system-under-test ingests, baselines, detects → harness polls the read-back channel and/or prompts an operator → run report classifies each check.

## Technology Landscape

**Languages/Runtimes.** The synthetic-telemetry and observability-tooling space is dominated by **Go** (telemetrygen, otelgen, the OTel Collector, Chaos Mesh, Litmus — Go is the lingua franca of CNCF observability). **Rust** is a credible and growing second: `opentelemetry-rust` is mature, and Rust is the language of choice for several DST projects (S2.dev, Resonate) and high-reliability single-binary tooling. The brief pins **Rust 2024 + tokio** for Pulse-consistency — defensible, though it means more emission plumbing is hand-rolled vs Go's batteries-included generators.

**Frameworks.** For the emission/transport core: **`opentelemetry-rust` + `opentelemetry-otlp`** with the **`grpc-tonic`** feature (tonic/prost gRPC) is the standard Rust path to OTLP/4317 — exactly the stack the brief names. **`tokio`** for the async timeline. For the desktop control surface: **Tauri 2** (Rust backend + native webview frontend) is the mature 2025/2026 choice for lightweight local-first developer GUIs (sub-MB binaries, no bundled browser) — and aligns with the "thin shell over the same headless commands" design. Note: per the output template, the *web frontend framework / CSS / component library* inside the Tauri webview is design-specialist territory and not decided here.

**Data storage.** Harnesses of this kind are **file-based / embedded**, not server-DB: scenarios as declarative config files; the **emission journal** and **run report** as on-disk artifacts (JSON/JSONL/Markdown are the norm — promtool uses YAML; chaos tools emit JSON reports; the brief specifies a Markdown coverage matrix and run report). If any structured run history is wanted, an embedded store (e.g. SQLite) is the usual ceiling — but most tools in this space stay file-only.

**Key libraries/services.** OTLP wire format = `opentelemetry-proto` via prost; the **OpenTelemetry Semantic Conventions** (esp. `service.name`, span `Status.Code=ERROR`, exception span events with `exception.type`/`message`/`stacktrace`, log `SeverityNumber` and its boundaries) are the shared vocabulary that makes shaped telemetry meaningful to the SUT. **W3C Trace Context** propagation across emulated service edges is the standard for multi-service attribution. The read-back layer rides the **Model Context Protocol** (Anthropic, Nov 2024; broad adoption through 2025; now under the Agentic AI Foundation / Linux Foundation) — increasingly the standard way observability tools expose incidents/telemetry to agents.

**Deployment.** Distribution in this space is **single self-contained binary** (Go `go install`, Homebrew, distroless Docker; Rust `cargo`/release binary) for the CLI core, plus a **platform-native desktop bundle** for the GUI (Tauri produces Windows/macOS/Linux installers). The brief scopes deployment to **local dev host only** — no cloud, no multi-target — consistent with the "runs next to a real instance on the dev host" norm for verification harnesses.

## Recent Trends

- **MCP as the read-back / agent interface for observability** is the standout 2025–2026 shift: Datadog, Grafana, OneUptime, IBM Instana all shipped MCP servers exposing incidents/metrics/traces to agents (Datadog's went GA March 2026). Using a tested MCP tool surface as the *verification* channel (as Conductor does) is right on this trend; instrumenting/monitoring MCP servers themselves with OpenTelemetry is a parallel emerging concern.
- **Deterministic Simulation Testing has gone mainstream** for reliability-critical systems (Antithesis commercializing it; Datadog targeting ~500 seeds/component; native DST tooling for async Rust). Seeded, reproducible, time-abstracted scenarios are now an expected rigor bar, not exotic.
- **OTLP is effectively the convergence point**: gRPC on **:4317** and HTTP on **:4318** are the de-facto standard endpoints; OTLP is increasingly accepted natively by backends (e.g. Google Cloud Monitoring), reducing the need for vendor exporters. Pinning gRPC-only loopback :4317 is conventional.
- **AIOps anomaly detection has shifted from static thresholds to dynamic baselines** (statistical baselines, Prophet/ARIMA, Random Cut Forest / Isolation Forest), with first-class **"quiet windows" / deploy-suppression** to cut false positives 40–70% — which is precisely the class of behavior (baseline convergence, suppression, restart/silence handling) Conductor is built to exercise. Verifying these *probabilistic* detectors is pushing the field toward **calibration-region assertions and human-in-the-loop reporting** rather than exact-value pass/fail.
- **Chaos engineering is integrating OpenTelemetry** to make experiments "scientific" (instrument the blast radius, judge experiments on observability signals) — Litmus has roadmap items to add span attributes/events and act as an OTel collector. The boundary Conductor draws (telemetry-layer fault injection + detection verification, *not* infra-layer chaos, *not* a load-tester) is a coherent and less-crowded niche than general chaos tooling.

## Considerations for This Project

- **Determinism vs wall-clock SLOs is the central tension.** The timeline engine must be reproducible under a seed (stream *shape*), yet every assertion is against a *wall-clock* SLO window ("candidate ≤2s after 30s persistence"). These pull in opposite directions: real network/ingest jitter, GC pauses, and the SUT's own polling cadence make exact timing non-deterministic. The emission journal as recorded ground truth is the right mitigation, but the user will need to decide how much timing slack/tolerance bands to allow — and DST's "abstract physical time" trick is *not* available here because Pulse runs in real time as a black box.
- **Verifying a model-backed (LLM) detector cannot use exact-match assertions.** Pulse has model-interpretive outputs (severity choice, hypothesis quality, root-vs-deep weighting). The brief's assertion-policy split (deterministic = hard fail; interpretive = calibration-region + report-for-human) matches the industry direction, but the user will need to define *where* each P-ID's boundary sits and how wide the calibration region is — a genuinely hard, judgment-heavy classification, and the dividing line is itself a spec decision.
- **The read-back channel is a hard dependency with real preconditions.** Programmatic verification relies on Pulse being built with the non-default `mcp-server` feature + a runtime env flag, and on the MCP tool surface (`query_incident_list`, `retrieve_report` with `degraded_mode`, etc.) being stable. Anything the MCP surface doesn't expose necessarily falls to the operator checklist — so the *auto vs drive+observe* split in the coverage matrix is gated by what Pulse's MCP actually returns, not by what's theoretically observable. MCP/JSON-RPC surfaces also evolve fast (governance just moved to the Linux Foundation) — a versioning/compatibility risk.
- **"Shaped" telemetry is deceptively hard to get semantically right.** Hitting target p50/p95/p99 per operation, controlling exception *fingerprints* to be identical across line-variants but different across type/frame-variants, placing errors at root vs child spans, and crossing a specific log-`SeverityNumber` boundary all require correct, convention-faithful OTLP construction — and the SUT's detection only triggers if the conventions match what it keys on. Sample-count floors (50 for latency, 10 for error-rate) mean scenarios must emit *enough* volume in the window or the SUT legitimately won't react — a common, confusing false-negative source.
- **Scope discipline is a stated feature, and the easy failure mode is feature creep.** The "no scenario without a P-ID" scope law and the "not a load-tester / no Pulse process management / no UI automation" non-goals are deliberate guards against turning a verification harness into a general chaos/load platform. The complete `coverage-matrix.md` (all 60 P-IDs classified, zero gaps) is the actual definition of done — so the up-front classification work (seeded from the audit verdict tables) is as load-bearing as the emission engine itself, and the known-residual concept (P-032 expected to fail until a future fix) needs to be a first-class report state from day one, not bolted on.
