## Patterns to follow
- `Verdict` enum surfaces only `Pass`, `Fail`, and `CalibrationRegion` (the two-state probabilistic split); returned as `Ok(Verdict)`, never an error variant.
- `ReportState` enum contains the full five-state run-outcome vocabulary: `Pass`, `Fail`, `ManualCheck`, `KnownResidual`, `Blocked` — each with distinct semantic meaning (ManualCheck = operator-checklist; Residual = pre-accepted; Blocked = failed precondition).
- Status-rendering contract: both enums expose a text label accessor (for display) + an ASCII status-prefix accessor (`[PASS]`/`[FAIL]`/`[HOLD]` for CalibrationRegion/ManualCheck/KnownResidual contexts `/[BLOCKED]`) used by CLI to ensure status survives piping.
- Serde round-trip to canonical PascalCase names (`"Pass"`, `"Fail"`, `"CalibrationRegion"`, `"ManualCheck"`, `"KnownResidual"`, `"Blocked"`) exactly matching the run-report envelope.

## Anti-patterns to avoid
- DO NOT merge `CalibrationRegion` into `Fail` — the layout assigns it its own ANSI 179 hold color and `[HOLD]` prefix; it is a distinct third Verdict outcome.
- DO NOT make status representation color-only — type must expose text label + ASCII prefix so CLI output is parseable and survives piping/`NO_COLOR`.
- DO NOT allow `Blocked` or `ManualCheck` or `KnownResidual` to map to red/failure color in desktop or CLI — each has its own neutral or accent color (hollow ring, checkbox, muted dashed dot, ANSI 60/146/246 respectively).
