# a11y extract

## Relevance
Partial — connection-lifecycle scenarios define auto-measurable timing windows and state transitions but carry no new UI surfaces or interactive components.

## Constraints
- Per a11y-plan §1: CLI surface (`conductor run`) is not-assertable; only the desktop-webview is assertable (no a11y scope for new scenario TOML).
- Per a11y-plan §4 Critical Paths: must-be-accessible paths are operator pause go/no-go, run-report view, scenario/suite picker, operator-checklist — scenario config does not create these paths; they pre-exist.
- Per a11y-plan §1 A11y Scope Summary: auto-measurable legs (timing windows: Receiving ≤1s, ReceiverFailed ≤2s, Idle/Stalled boundaries) are expressed declarative `expected` blocks; visual/UX half (lifecycle badge / hue) routes to operator checklist.
- Per a11y-plan §3 Structured violation JSON schema: artifacts fold into obs Section 6 envelope; no new ARIA violations from TOML config authoring.
- Per a11y-plan §6 State color tokens: six lamps are `Pass`/`HOLD`/`Fail`/`Blocked`/`Manual`/`Residual` with text label + glyph (SC 1.4.1); scenario outcomes must map cleanly to these six states.
- Per a11y-plan-amendments §2026-06-21: `verdict==CalibrationRegion` ⇒ HOLD lamp regardless of `state`; scenario `expected` blocks must respect this verdict-first precedence.

## Patterns to follow
- Per a11y-plan §1 Requirement source of truth + §4 Critical Paths: scenario `expected` blocks express WCAG SC timing windows (SC 2.1.1 Keyboard, SC 2.4.3 Focus Order reachable through the existing operator checklist UI); reuse the `error-baseline-spike.toml` structure.
- Per a11y-plan §3 Structured violation JSON schema: `state` field in run-report envelope maps connection-lifecycle outcomes (Listening/Receiving/Idle/Stalled/ReceiverFailed) to the six assertion states; follow the state-naming crosswalk table (§6).
- Per a11y-plan §6 State color tokens: every scenario outcome is announced via `aria-live` on the verdict lamp; manual operator checklist must render (not downgrade to Fail if paused).

## Anti-patterns to avoid
- Per a11y-plan §11 Visual: NEVER downgrade in-progress connection states to Fail lamp on the desktop-webview; real prose ("Receiving…" / "Stalled…") + the correct verdict/state pair must reach screen readers.
- Per a11y-plan §11 Screen Reader: NEVER drop virtual-scrolled rows (coverage matrix during live run) from the a11y tree; all P-IDs reachable/announceable (SC 1.3.1, SC 4.1.2).
- Per a11y-plan §11 SLO: NEVER use retry-once for a11y checks; a11y violations must hard-fail (zero-WCAG-AA-violations invariant per §10).

## Contract bindings
- obs ↔ a11y: scenario `expected` outcomes fold into obs Section 6 Run-report envelope (`verdict` / `state` enum fields); verdict-first lamp precedence (amendment 2026-06-21) enforced in the run-report-envelope-serializer, not scenario config.
- tests ↔ a11y: fixture round-trip test (`cargo nextest`) validates scenario TOML deserialize + `PhaseTimeline` generation; a11y does not add new tests (auto-measurable timing is assertion-free; operator checklist is manual).

## Acceptance criteria contributions
- (a11y) Connection-lifecycle scenario TOML deserialize + garde validation rounds trip cleanly; expected-outcome blocks express timing windows (Receiving ≤1s, ReceiverFailed ≤2s, Idle/Stalled thresholds per pulse-capability-spec.md).
- (a11y) Scenario outcomes (Listening/Receiving/Idle/Stalled/ReceiverFailed) map cleanly to the six lamp display labels (Pass/HOLD/Fail/Blocked/Manual/Residual) with text + glyph (SC 1.4.1 not-color-alone).
- (a11y) Desktop-webview run-report view announces connection-lifecycle state changes via `aria-live` (verdict lamp + phase-line HOLD flip per §4 Critical Paths); no scenario config breaks existing lamp layout or SR announcements.
