## Relevance
Partial — the chunk builds the headless agent-run harness (shell orchestration + artifact reads), which touches 4 of 7 security-plan threat boundaries (input validation, error handling, dependency security, logging); does not implement core crypto/auth/API surfaces.

## Constraints
1. **Command-spawn hardening:** The harness must **never** pass operator-supplied values (e.g., `ANDROMEDA_PULSE_DATA_DIR`) into argv or shell commands when invoking `conductor-cli` subprocesses. Validate argument-injection metacharacters before any spawn (security plan §Anti-Patterns § Input, citing CVE-2026-30623).
2. **Environment-path validation:** The harness must invoke `conductor-cli run` / `suite` / `report` with paths resolved from `CONDUCTOR_RUNS_DIR` / `CONDUCTOR_SCENARIOS_DIR` / `CONDUCTOR_CONTRACT_MANIFEST` that are canonicalized + bounds-checked by the `conductor-cli` edge (security plan §Input Validation, outside harness scope but a prerequisite for safe pass-through).
3. **Readiness Blocked state distinction:** The `boot` subcommand must surface the MCP preflight outcome as the distinct `Blocked` state (not silently downgraded to pass/fail) when preflight fails — mismatch on protocol version, missing required tools, failed canary round-trip, or keychain-read-while-write fault (security plan §Anti-Patterns § Universal, citing Standard Contracts readiness gate).
4. **Error sanitization at the harness edge:** When the harness parses `conductor-cli` exit codes or artifact reads from `runs.db` / JSONL, it must **not** expose absolute filesystem paths or internal seam-crate struct names to stdout/stderr or agent-readable output. Emit only `[PASS]`/`[FAIL]`/`[HOLD]`/`[BLOCKED]` ASCII prefixes + verdict/state/identity fields (run_id, seed, scenario, p_ids) (security plan §Error Handling, scope artifact sanitization).
5. **Deterministic run artifacts:** When `status` or `logs` reads from `runs.db` / JSONL journals, the harness must never mutate or corrupt the ground-truth artifacts. Clock source for any new harness-emitted journal entries must be `std::time::SystemTime`/`Instant`, not tokio virtual clock (security plan §Anti-Patterns § Logging, citing determinism discipline).
6. **Dependency audit gate integration:** The harness scripts (`.sh` / `.ps1`) may invoke `cargo nextest run --profile ci` or equivalent; they must succeed only if `cargo-audit` ≥ 0.22 (installed 0.22.1) has run green upstream. No bypass of the audit gate; CI build fails on advisory hit (security plan §Dependency Security, citing SLA).
7. **Bash/shell parity for CLI injection:** Both `.sh` (POSIX bash) and `.ps1` (PowerShell) implementations of the five commands must enforce identical input-validation + spawn-hardening, especially for argument-injection metacharacters in `CONDUCTOR_*` overrides and Pulse-side `ANDROMEDA_*` flags. Parity is a security control: one platform must not accidentally relax the constraint the other enforces (security plan §Anti-Patterns § Code Patterns, citing rmcp STDIO design flaw).

## Patterns to follow
1. **Orchestration-only, no re-implementation:** The harness is a thin wrapper over `conductor-cli` verbs + `cargo nextest`; it shells out to those binaries rather than re-implementing engine logic. All validation (path canonicalize, env-var bounds-check, input-validation garde) is the responsibility of the `conductor-cli` edge, not the harness. This keeps the threat model scoped and reuses the `conductor-cli` validation gate.
2. **Artifact-read-only for status/logs:** The `status` and `logs` subcommands read from the persisted `runs.db` (SQLite index) and per-run JSONL journals without requiring a live Pulse or mutating state. This allows post-mortem analysis and supports the "status without live service" use case (security plan § Data Protection — no sensitive data stored, only synthetic test telemetry).
3. **Preflight readiness gate:** The `boot` subcommand exercises the MCP `initialize` protocol negotiation (version `2024-11-05`, required-tool presence, data-dir canary round-trip) + OTLP egress liveness check as a **prerequisite** to scenario emission. Mismatch or transport failure surfaces as `Blocked`, **not** a silent downgrade (security plan § Anti-Patterns § Universal, readiness gate).
4. **Idempotent cleanup:** The `cleanup` subcommand is safe to invoke repeatedly (e.g., on-failure cleanup in CI) and must **not** corrupt live artifacts when nothing is running. It releases the port-occupier if held and prunes ephemeral per-run artifacts per policy; repeated invocations are no-ops (security plan § Threat Model Summary — the port-occupier `:4317` bind is the sole deliberate bind and is cleaned up deterministically).

## Anti-patterns to avoid
1. **Never interpolate `ANDROMEDA_PULSE_DATA_DIR` or any operator value into argv/shell:** Pass it strictly via `.env(...)` builder (if the harness invokes the sidecar directly — deferred to `conductor-cli`); reject argument-injection metacharacters before any spawn. The rmcp STDIO command/argument-injection flaw (CVE-2026-30623) can be exploited via shell-interpreted strings (security plan § Anti-Patterns § Input).
2. **Never silently downgrade failed preflight to pass/fail/manual-check:** The `boot` subcommand must surface version mismatch, missing required tools, failed canary, or keychain fault as the distinct `Blocked` state with the named precondition string. Silent downgrades corrupt the release gate's decision-making (security plan § Anti-Patterns § Universal).
3. **Never leak absolute paths or struct names in harness output:** The harness `status` / `logs` / error output must expose only artifact identity fields (`run_id`, `seed`, `scenario`, `p_ids`) and verdict/state strings (`[PASS]`, `[FAIL]`, `[BLOCKED]`). Absolute paths (canonicalized `CONDUCTOR_*` directories, `ANDROMEDA_PULSE_DATA_DIR`) and internal enum names (`ConfigError`, `VerifyError`) must be sanitized before the harness prints to stdout/stderr (security plan § Error Handling, artifact sanitization).

## Contract bindings
- **agent-run harness ↔ conductor-cli verbs:** The harness invokes `conductor run` / `suite` / `report` as subprocesses; consumes their exit-code + stdout contract, which is the responsibility of ch1 (core verbs). The harness does not re-implement verdict logic; it relies on `conductor-cli` input validation (path canonicalize) and error contracts.
- **agent-run harness ↔ test-plan & verification-harness.md:** The five-command discipline (`boot` / `run` / `status` / `cleanup` / `logs`) and exit-code contract are defined in test-plan §3 and `.claude/rules/verification-harness.md`; the harness is the realization of that contract.
- **agent-run harness ↔ MCP preflight (conductor-verify):** The `boot` subcommand calls the MCP `initialize` gate (protocol negotiation, tool presence, canary); failure surfaces as `Blocked`. The gate is implemented by `conductor-verify` (core readiness logic); the harness surfaces its outcome distinctly.

## Acceptance criteria contributions
1. (security) Both `.sh` and `.ps1` reject argument-injection metacharacters in operator-supplied path overrides before any subprocess spawn (grep verifies no bare `$ANDROMEDA_PULSE_DATA_DIR` interpolation into argv or shell strings in the harness).
2. (security) The `boot` subcommand surfaces the MCP preflight outcome as the distinct `Blocked` state (exit code + `[BLOCKED]` prefix) when the preflight fails; status-only reads from `runs.db` never require a live Pulse.
3. (security) The harness `status` / `logs` output exposes only artifact identity + verdict strings (`[PASS]`, `[FAIL]`, `[HOLD]`, `[BLOCKED]`); grep confirms no absolute filesystem paths or seam-crate internal names leak to stdout/stderr.
4. (security) The harness scripts validate all `CONDUCTOR_*` path handles at the `conductor-cli` edge (not re-implemented in shell); this is delegated to ch1 but accepted as a prerequisite for safe orchestration.
