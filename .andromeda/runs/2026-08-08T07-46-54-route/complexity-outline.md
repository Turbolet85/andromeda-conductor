## Project signals (from arch + input)

- **Product type:** Desktop control-panel app (Tauri 2) over a headless-drivable Rust core — a scenario-driven OTLP fault-injection + verification harness driving a live Pulse (arch §Project Intent).
- **Surfaces in current scope:** 2 — CLI/headless (`conductor-cli` `agent-run`, the release gate) + Tauri 2 desktop control panel (React 19 webview). **Both already shipped in 0.1.0**; 0.2.0 extends and proves them, it does not build them.
- **Crates / modules:** 9 workspace members — `conductor-core` / `-timeline` / `-emit` / `-faults` / `-verify` / `-report` / `-run` / `-cli` / `-tauri` (arch §Occupied Resources).
- **Capabilities (Established Decisions count):** 21 items in arch §Established Decisions — all realized in 0.1.0; 0.2.0 amends two of them (Read-Back Dependency Posture, Timing-Tolerance Model) rather than adding new ones.
- **Standard Contracts:** 5 — MCP preflight readiness gate, OTLP-egress liveness equivalent, run-report envelope, timestamp formats, live update `Channel` (arch §Standard Contracts).
- **Cross-cutting concerns:** 6 — config management, agent-driven development style, determinism discipline, verdict/error wall, trust boundary, scope law (arch §Cross-cutting Patterns).
- **Security tier (cross-input):** Minimal — local-only loopback tool, no network service of its own, no secrets (`.claude/rules/security.md`, security-plan §Threat Model).
- **Project signals from input.md:** agent-driven development style (headless is the release gate); scope law "no scenario without a P-ID"; the four matrix-delegated timing claims (P-025/P-027/P-037/P-045) are first-class requirements; and input.md's own "0.1.0 done" clause — end-to-end proof against a real Pulse across five families + one severity-lifecycle pass — is **inherited unmet** and is this version's centre of gravity.
- **Existing Scopes:** None (arch §Existing Scopes).

**Version-specific signal (0.2.0):** this is a completion-and-proof version over a working 9-crate harness, not a greenfield build. Its keystone is an *external* one — the SUT advanced 22 capabilities (P-061..P-082) during a 41-day pause while Conductor's P-ID type still hard-rejects anything above P-060 — so re-aiming at the real SUT precedes every proof chunk (intent §1, §8).

## Calibration outcome

- **Hierarchy depth:** 3 levels (epoch → sub-block → chunk)
- **Reasoning:** 2 in-scope surfaces × 9 workspace crates, with all 21 arch §Established Decisions and 5 §Standard Contracts already realized in 0.1.0, means most epochs decompose straight to chunks (depth 1); only the two densest — SUT re-aim (8 concerns) and verification surfaces (7 concerns) — need one intermediate sub-block level, which is what puts the tree at 3 rather than 2.

### Adjustments applied (optional)

- **+1 epoch: sizing discipline after 0.1.0's Part-B monolith.** Intent §1 records that one 0.1.0 route entry swallowed five scenario families, the emit/extract framework and the live `ready: true` proof, and asks explicitly for "a sizing gate that will not let a Part-B-sized monolith through again" (intent §1, §4 F8 sequencing note). The live proof is therefore split across **Epoch 3** (the five families) and **Epoch 4** (severity lifecycle + the delegated timing budgets) instead of carried as one epoch.

_No other adjustments: security tier is Minimal, arch carries no v2/v3 deferred-feature markers, and the project is single-platform desktop (the Linux+xvfb constraint on the a11y legs is an execution-environment gate recorded in Notes, not a multi-platform-native signal)._

## Notes for Phase 1 synthesis

**Hard sequencing (from intent §5 and §8):**

- **Epoch 1 precedes every live-proof chunk.** Intent §8 is explicit: "a proof aimed at a stale capability set is not a proof." No Epoch 3/4 chunk may land before the SUT re-aim.
- **v2-17 + v2-18 open Epoch 2 and gate everything live.** Intent §4 F10 names the two-launch check (repo root vs marker-less temp dir) as "the first action of this version" — its verdict decides whether a **Pulse-side chunk** gates the live legs. This is an **external prerequisite**, not Conductor work: Conductor's own deliverable is detection + a named precondition, never a fix (intent §5 new non-goal).
- **v2-08 (dispatcher) + v2-09 (extraction) precede all family proofs.** They replace `coarse_emit` and the `"incidents-listed"` placeholder respectively; every Epoch 3/4 family reads through them. `execute_scenario`'s signature is preserved (intent F6).
- **v2-10 (live `ready: true`) gates the family proofs** — it is the first green live preflight and the evidence anchor for everything after it.
- **v2-19 precedes v2-20**, and if Phase 1 splits them across chunks the plan must state out loud that **Pulse P-075 stays open until both land** (intent §4 F12).

**Reuse discipline (do NOT re-author — intent §3, §4 F14, F15):**

- The **canary bridge** (`conductor-run::emit_canary` → poll `query_incident_list` → assert via `retrieve_telemetry_slice.fingerprint_refs`) shipped in 0.1.0 Part A and is CI-green — Epoch 2 reuses it.
- The **a11y harness** (`ui/wdio.conf.ts` + `ui/test/a11y/*.e2e.ts`) and its real-webview specs shipped at `2026-06-27-desktop-a11y-harness-setup` — Epoch 5 **runs** them, does not re-author them. The deterministic `tauri::test` mock-runtime command tests and the test-plan Path-7 parity checks already landed (10/10) — do not redo them.
- The **`ci.yml` obs-gate scaffold** from `2026-06-27-obs-ci-conformance-gate` (`shell: bash` gate step with jq/grep assertions + `::error::` annotation + non-zero exit, plus `actions/upload-artifact@v4` `if: always()`) is the pattern v2-24 extends.

**Execution-environment gates:**

- **Live legs are operator-gated** (`workflow_dispatch` / local invocation), **never a CI gate** — CI has no Pulse. Determinism goldens and stub-backed tests remain the CI-side coverage. This drives the matrix `method` for every Epoch 2/3/4 live capability (`dynamic-external`).
- **v2-22 / v2-24 are display-gated (Linux+xvfb)** and are *not* Windows-doable, unlike the rest of the version. Phase 1 should keep them separable so a Windows session is never blocked on them.

**Cross-cutting constraints:**

- The `v2-NN` (Conductor's own) and `P-NNN` (Pulse's) id spaces must stay visibly separate — Pulse P-IDs appear only inside acceptance criteria, `coverage.rs` and scenario configs (intent §6). v2-21 is discharged by route itself.
- v2-06/v2-07's load envelope bounds scenario design **for every later epoch** — the SUT's DuckDB append path stalls after ~10 min of sustained 10k/s storm under deterministic L4, so storm profiles authored in Epoch 3 must stay inside it.
- v2-28 (stale `rmcp` wording) is housekeeping that must ride a chunk already touching `test-plan.md` / `tests-summary.md` / `verification-harness.md` — Phase 1 should attach it rather than mint a chunk for it. Same for v2-32 in Epoch 6.
