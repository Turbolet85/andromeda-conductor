# security extract

## Relevance
Partial — a local, offline artifact-vs-artifact consistency check inside `conductor-core`; touches the already-registered capability-manifest input boundary, the verdict/error wall, and artifact-hygiene rules, but adds no auth, secret, network, subprocess, or dependency surface.

## Constraints
- The check MUST read the accepted set through the existing `CapabilityManifest::load` / `accepts` path and MUST NOT add a second parse, re-derivation, or hardcoded id/count of the accepted set — the manifest is the registered validated-at-load input boundary (per security-plan.md §Input Validation, pinned-MCP-contract-manifest row; amendment 2026-08-08-sut-capability-manifest).
- No new `CONDUCTOR_*` env handle or operator-supplied path may be introduced for locating either artifact; the manifest stays on its fixed `default_path` resolved through the shipped `resolve_under` traversal guard (per security-plan.md §Input Validation, env-var-path-handles row; §Security Anti-Patterns → Input, first ban).
- A drift condition MUST surface as a harness-side typed failure (`thiserror` enum in the seam crate, collapsed to `anyhow` only at the `conductor-cli` edge), never as a `Verdict` / `ReportState` value and never as a panic (per security-plan.md §Error Handling, internal-logging + error-format paragraphs; §Security Anti-Patterns → Universal, no-panic-on-malformed-input ban).
- The drift failure message MUST carry only capability ids plus manifest identity metadata (`sut_version`, `captured_at`) — no absolute host paths (canonicalized `CONDUCTOR_*` dirs, manifest path), no internal seam-crate struct/field names (per security-plan.md §Error Handling, run-report-artifact-sanitization paragraph; §Security Anti-Patterns → Logging, third ban).
- If a manifest read/parse fault occurs while running the check, the surfaced error MUST carry `e.kind()`-grade detail only and never the filesystem path (per security-plan.md §Input Validation, as amended 2026-08-08-sut-capability-manifest).
- Zero new dependencies are expected for an in-crate comparison; any crate added anyway must land with `cargo audit` + `cargo deny check` green and a committed, un-drifted `Cargo.lock` (per security-plan.md §Dependency Security, Pinning + CI integration; §Security Anti-Patterns → Universal, lock-drift ban).
- The check must not open, copy, or read Pulse's `corpus.db` or query a live Pulse — it is an offline read of committed artifacts only (per security-plan.md §Security Anti-Patterns → Data Protection, corpus.db ban; §Data Protection, out-of-scope paragraph).

## Patterns to follow
- Fixed-path artifact resolution via `resolve_under` (the shipped traversal guard used by the manifest and the agent-mode log path) rather than any new path input (per security-plan.md §Input Validation).
- Typed `thiserror` error enum inside `conductor-core`, type-erased to `anyhow` only at the binary edge — mirrors `ConfigError` / `VerifyError` (per security-plan.md §Error Handling).
- Identity-fields-only reporting, as already applied to `<run_id>.md` and `runs.db` rows: name the entity (ids, `sut_version`, `captured_at`), not the host layout (per security-plan.md §Error Handling, artifact sanitization).
- Deterministic, committed-artifact-only inputs — same tree ⇒ same result, matching the determinism discipline that keeps ground-truth artifacts trustworthy (per security-plan.md §Security Anti-Patterns → Logging, clock-source ban rationale).
- CI gate reuse: any new check step lands in the existing `.github/workflows/ci.yml` build/nextest/clippy pipeline alongside the cargo audit/deny jobs, not a new workflow (per security-plan.md §Dependency Security, CI integration).

## Anti-patterns to avoid
- NEVER reintroduce a hardcoded P-ID range or a second hardcoded capability count as the check's reference universe — the accepted set is data, and a compile-time duplicate re-creates the blind spot the gate exists to close (per security-plan.md §Security Anti-Patterns → Input, "NEVER deserialize scenario config without garde validation at load" boundary-is-the-source discipline; §Input Validation, manifest row).
- NEVER let a malformed/absent manifest panic or silently pass the check as "no drift" — an empty or unreadable input must become a loud typed failure, never a false pass-as-empty (per security-plan.md §Security Anti-Patterns → Input, empty-canary ban; §Security Anti-Patterns → Universal, no-silent-downgrade ban).
- NEVER emit the manifest's absolute path, the workspace root, or internal struct names into the drift message, CI log, or any run artifact (per security-plan.md §Security Anti-Patterns → Logging, second and third bans).

## Contract bindings
- **Tests** — the drift check is the CI security-relevant gate; it binds to tests §CI Integration (one workflow, drift check as a job alongside the existing cargo-audit/cargo-deny jobs) per security-plan.md §Dependency Security (CI integration).
- **Architecture** — the P4 open question (hard gate now vs. surfaced-but-non-gating until `v2-03`) is an arch/scope decision; security constrains only that whichever form is chosen must not silently downgrade a detected drift to "pass" (per security-plan.md §Security Anti-Patterns → Universal, no-silent-downgrade ban).
- **Observability** — if the drift result is emitted through the self-observation log, the message must stay identity-fields-only under the same sanitization rule as run artifacts (per security-plan.md §Error Handling, artifact sanitization).

## Acceptance criteria contributions
- (security) The drift failure output, captured from a red run on the current tree, contains the 22 drifted ids plus `sut_version` and `captured_at`, and contains no absolute path, no workspace root, and no seam-crate struct/field name — grep-verifiable (per security-plan.md §Error Handling, run-report-artifact-sanitization; §Security Anti-Patterns → Logging, third ban).
- (security) `grep` over the chunk's diff shows no literal P-ID range, no hardcoded accepted-set count, and no second read/parse of `contracts/pulse-capabilities.toml` — the accepted set enters only via `CapabilityManifest::load` / `accepts` (per security-plan.md §Input Validation, manifest boundary row, as amended 2026-08-08-sut-capability-manifest).
- (security) A missing / empty / malformed manifest makes the check fail loudly as a typed `Result::Err` at the harness edge — it neither panics nor returns "no drift", and the surfaced error carries `e.kind()`-grade detail without the path (per security-plan.md §Error Handling; §Security Anti-Patterns → Universal, no-panic + no-silent-downgrade bans; §Input Validation as amended 2026-08-08).
- (security) The drift result never appears as a `Verdict` or `ReportState` value — a drift is a harness fault only (per security-plan.md §Error Handling, verdict/error-wall paragraph).
- (security) `cargo audit` exit 0 and `cargo deny check advisories bans sources licenses` ok, with `Cargo.lock` un-drifted and committed (trivially green if no dependency is added) (per security-plan.md §Dependency Security, CI integration + Pinning; §Security Anti-Patterns → Universal, lock-drift ban).
