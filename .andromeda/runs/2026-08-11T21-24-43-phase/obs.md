## Relevance
relevant — the dispatcher sits directly on the `timeline.execute` / `emit.batch` self-obs seam and owns the `emission_count` attribute obligation.

## Constraints
- **No OTel SDK, exporter, or meter for self-observation** — the dispatcher drives `conductor-emit`'s PRODUCT OTLP path (`:4317`) only; self-obs stays `tracing`-JSON to stdout/file. The invariant is behavioral (dormant transitive `opentelemetry`/`opentelemetry_sdk` in the tree is not a violation) (per obs-plan §3 OTel SDK init, §11 Telemetry Strategy / Universal).
- **`timeline.execute` must carry `phase_count` AND `emission_count`** as span attributes; the shipped span (`crates/conductor-timeline/src/scheduler.rs:34`) has only `phase_count`, so this chunk closes the gap (per obs-plan §4 Critical Path 1 required span attributes).
- **Bounded span-name set** — any span the dispatcher opens must already be a member (`timeline.execute*`, `emit.batch`, `emit.logs_batch`, `scenario.run`, `fault.silence`/`ramp`/`port_occupier`) or a new low-cardinality `{module}.{operation}` name; never a per-phase-name or per-scenario span name (per obs-plan §4 span naming, §11 Spans/Traces).
- **Field-name allowlist is the gate for span attributes too** — `conductor-core::redact::ALLOWLISTED_FIELDS` drops any non-allowlisted attribute silently at the processor stage; `emission_count`/`phase_count` are already members (`redact.rs:42-43`), any new shape attribute (`batch_index`, `p_id_count`, `path_type`, `severity_level`, …) is not until added there. Single-location ownership — no second scrub site (per obs-plan §11 PII Scrubbing).
- **Hot-path instrumentation discipline** — no span-per-emission and no `info`-level line per emission inside the dispatch loop; per-record detail is `trace`/`debug` gated by `RUST_LOG=conductor_timeline=debug` (opt-in) (per obs-plan §6 Log levels / per-module levels, §11 Telemetry Strategy + Logs).
- **Emission counting is a span/JSON field, not an instrument** — Minimal tier has no metrics backend; do not introduce a counter/histogram to satisfy the count obligation (per obs-plan §5, §11 Metrics).
- **Wall-clock for timestamps, seeded/`tokio::time` for shaping** — journal stamps stay `std::time::SystemTime`; the tokio virtual clock is banned for stamps even though fault/ramp timing is `tokio::time`-gated under `current_thread` (per obs-plan §11 Project-specific bans, §4 fault-injection spans). If the fork extends `EmissionSpec`, garde validation on scenario deserialization is non-optional (range/cross-field: error fraction ∈ [0,1], p50≤p95≤p99, severity-mix sum) (per obs-plan §11 Project-specific bans).

## Patterns to follow
- **Egress spans already exist below the dispatcher** — `crates/conductor-emit/src/client.rs:67` (`emit.batch`, `emission_count`) and `:104` (`emit.logs_batch`, `record_count`). The dispatcher fans out over already-instrumented calls; its per-phase count aggregates those, it does not re-instrument them (per obs-plan §4 auto-instrumentation table).
- **Span topology already fixed by the prior chunk** — `scenario.run` opens at the composition root (`conductor-run::execute_scenario`) and `timeline.execute` nests beneath it; report-seam spans are run-scoped siblings correlated by `run_id`, not descendants (per obs-plan §4 CP1 Cleanup).
- **Two self-obs line variants over one base set** — event line, and span-lifecycle line adding `span` / `span_event` (`new`|`close`) / optional `parent` plus allowlisted attributes on the `new` record. `JsonObsLayer` (`crates/conductor-core/src/obs.rs`) implements `on_event` + `on_new_span` and **no `on_record`** — this is the CARRY trap named in scope.md; a late `Span::current().record(...)` for `emission_count` vanishes silently (per obs-plan §3 Log format / two record shapes).
- **Deferred-family attribute vocabulary is pre-specced** — `batch_index`/`fingerprints_in_batch` (fingerprint-storm), `path_type` (restart-suppression), `severity_level`/`phase` (severity-lifecycle), `fault_type`/`fault_duration_ms`/`fault_start_offset_ms` (faults, children of `timeline.execute`). The dispatcher's extensibility slot should land on these names rather than inventing new ones (per obs-plan §4 per-scenario paths + fault-injection spans).

## Anti-patterns to avoid
- Adding an OTel SDK / meter provider / `tracing-opentelemetry` / W3C `traceparent` to count or correlate emissions — re-introduces batch tasks that break `current_thread` determinism and pollutes the PRODUCT stream; correlation is `run_id` (per obs-plan §11 Telemetry Strategy, Metrics, Spans/Traces).
- High-cardinality or per-emission spans (e.g. a span named after `storm-same-fp-6x`, or one span per OTLP record) — over-instrumenting the hot path and busting the bounded name set (per obs-plan §11 Spans/Traces + Telemetry Strategy).
- Unstructured stderr or `info`-per-emission logging from the dispatch loop, and any line missing `run_id` (per obs-plan §11 Logs).

## Contract bindings
- **obs ↔ tests harness (test-plan §3)** — test-plan §3 OWNS the JSONL line format; the span-lifecycle variant is a lateral bind. Changing `timeline.execute`'s attribute set, or implementing `on_record` (new line shape / amended `new` record), is a two-sided change and must be reflected on both sides (per obs-plan §3 two record shapes; amendment 2026-08-10 span-lifecycle variant).
- **obs ↔ security (redaction)** — new dispatcher field names route through the single-location `conductor-core::redact` allowlist; no second scrub site, `Display`-not-`Debug` at the `anyhow` edge (per obs-plan §11 PII Scrubbing).
- **obs ↔ CI (§9)** — the `logs/agent-latest.jsonl` conformance gate asserts the §3 self-obs BASE schema (`timestamp_ms`/`level`/`target`/service-identity/`run_id`), not the §6 envelope; new dispatcher lines must not break it (per obs-plan §9 Log conformance check).

## Acceptance criteria contributions
- `timeline.execute` emits both `phase_count` and `emission_count` **on an actual JSONL span-lifecycle line** (asserted on the emitted record, not merely present in `fields(...)`), with the resolution of the `on_record`-vs-compute-before-open fork stated explicitly (per obs-plan §4 Critical Path 1 + §3 two record shapes).
- Every span name the dispatcher opens is a member of the bounded set, and every new span attribute / log field name is present in `conductor-core::redact`'s allowlist and observed on the line (a dropped field is a fail) (per obs-plan §11 Spans/Traces + §11 PII Scrubbing).
- No OTel SDK init, exporter, or metrics instrument is added for emission counting; self-obs remains stdout/file JSON with zero OTLP export (per obs-plan §3 OTel SDK init + §11 Metrics/Universal).
- Dispatch-loop logging stays off `info` per emission (`trace`/`debug`, `RUST_LOG`-gated) and `logs/agent-latest.jsonl` still passes the §9 base-schema + no-absolute-host-path conformance gate (per obs-plan §6 Log levels + §9 Log conformance check).
