## Relevance
Relevant — the chunk moves a constant that test call sites assert, and its live leg IS the harness `boot` preflight command test-plan §3 owns.

## Constraints
- The live leg's outcome is binary and must be recorded as such: `boot` readiness is stdout JSON `{"ready": true}`; `ready:false` ⇒ dependent scenarios report `state="Blocked"` with the named precondition string, never silently downgraded to pass/fail/manual-check (per test-plan §3 → 5-command implementation → `boot`). This is the spec-side form of the scope's directive 2 ("never stretched"); `blocked` is a reported envelope state, not a non-zero process exit (per test-plan §11 § E2E).
- The `boot` poll budget must be DERIVED, never a literal — two budgets: the in-process `CONDUCTOR_PREFLIGHT_TIMEOUT` raised to `contracts/pulse-run-contract.toml` `[incident_formation].min_canary_poll_seconds` (which must outlast Pulse's L3 digest cadence), and the `agent-run.{sh,ps1}` wall-clock wrapper derived per invocation as `warmup_ms/1000 + poll + margin`; a missing contract term is hard exit 2, a lowered env value clamps up to the floor (per test-plan §3 → `boot` → Timeout). Scope host-precondition 4 binds to exactly this; whether the shipped wrapper still derives correctly after the count rises is research's question.
- The live-Pulse leg is an operator/local gate (`workflow_dispatch` or `scripts/agent-run.sh`), NOT a CI gate; CI runs the rmcp-stub legs only (per test-plan §9 → Live-Pulse scenarios, restated as a ban in §11 § CI). Raising the constant must therefore leave the stub-backed CI legs green on their own terms.
- A stub-leg green does NOT prove the raised count forms a Tier-1 incident: the rmcp stub canary proves MCP wiring only, and Pulse's reaction may never be faked as a CI verdict (per test-plan §11 § Test Strategy). The incident-formation claim is live-leg-only evidence.
- The raise must stay a bounded threshold correction, not a load escalation — bounded "typical/high" P-060 profiles only, saturation is explicitly out of Conductor's scope (per test-plan §11 § Test Strategy, §10 § Performance budgets). The scope's `pulse-load-envelope.toml` premise sits on this line.
- Quality gates remain binding through the change: coverage `--fail-under-lines 60` (≥60% lines / ≥50% branch / ≥70% fn), zero-flakiness with nextest `retries` unset, and `cargo audit --deny warnings` + `cargo deny check` green with a committed un-drifted `Cargo.lock` as build-failure conditions (per test-plan §10 → Build failure conditions, §9 → Supply-chain audit). The PREREQ's "do not raise the floor / no `deny.toml` ignore / no CI edit" is compatible with §4's Tool-version policy (external CLIs are reference floors, not pins) — but whether an advisory-DB parse failure counts as the gate being non-green is research's question, not something the plan pre-decides.
- Goldens are committed and CI runs fail-don't-write; the seeded stream families (`replay__*` · `pacing__*` · `dispatch_wire__*`, one file per family × seed under `<crate>/tests/snapshots/`) plus the envelope/journal goldens are the inventory to check against the scope's "no golden pins the canary count" premise (per test-plan §7 → Seed strategies → Golden artifacts).

## Patterns to follow
- Per-seam fast iteration then the aggregate gate: `cargo nextest run -p conductor-run` for the touched crate, `cargo nextest run -E 'test(<name>)'` for one call site, and the full `run` aggregate (nextest `--profile ci` + `cargo test --workspace --doc` + `cargo clippy --workspace --all-targets -- -D warnings`) for the gate (per test-plan §3 → `run` → Test selection / CI stage selectors). `crates/conductor-run/tests/canary_wire.rs` is crate-local `tests/` — the in-crate integration home per test-plan §2 → Test directory conventions.
- Drive the live leg through `scripts/agent-run.{sh,ps1} boot` (the wrapper that derives the budget, identical semantics across both shells) rather than a bare `conductor preflight` invocation (per test-plan §3 → Bootstrap phases → 5-command-discipline-wire).
- Read evidence from the two DISTINCT artifacts without conflating them: the per-run emission journal `runs/<run_id>.jsonl` (SLO ground truth + Run-report envelope) versus the self-obs stream (`logs/agent-latest.jsonl`), whose event-line variant is any `tracing` record at whatever level obs-plan §11 assigns — the `debug`-level wire witness lives there (per test-plan §3 → Log format → "Self-obs stream is a distinct artifact"). The scope's "missing `emit.batch` line = leg-never-ran" trap is a self-obs-stream read, not a journal read.
- Record the leg's result machine-parseably: `jq -e '<predicate>' runs/<run_id>.jsonl` or a bound-parameter `SELECT` of the `runs.db` row over the 11 envelope fields — there is no HTTP status endpoint (per test-plan §3 → `status` + Status endpoint shape).
- Table-driven call-site variants use rstest `#[rstest]`/`#[case]` rows over a seeded `#[fixture]`, not duplicated literal bodies (per test-plan §4 → Fixture pattern at unit level, §7 → Fixture library).

## Anti-patterns to avoid
- Never accept a re-baselined snapshot via `cargo insta review` — insta runs CI/assert mode, fail-don't-write; if a golden turns out to pin the canary count, it is regenerated deliberately, never interactively (per test-plan §7 → Golden artifacts, §11 § Universal).
- Never re-hardcode a fresh literal at the test call sites — assert against the constant / the stated margin arithmetic, per the plan's own "never a literal" derivation discipline and the de-hardcode precedent in the amendment history (per test-plan §11 § Unit "brittle assertions against fixture-internal values", §3 `boot` Timeout).
- Never skip or relax a quality gate to land the change — no retry-once for a flaky live leg, no lowered coverage bar, no "just this once" on the audit gate (per test-plan §11 § Quality, § CI).

## Contract bindings
- tests ↔ obs: test-plan §3 → Log format is the SOURCE OF TRUTH for the JSONL format and obs-plan §3 derives from it; the self-obs event line (incl. the `debug` wire witness the leg reads) and the emission-journal envelope are two schemas that must not be conflated (per test-plan §3 → Bootstrap phases → log-format-bind-with-obs).
- tests ↔ arch/contracts: `boot`'s derived budgets read `contracts/pulse-run-contract.toml` `[incident_formation].min_canary_poll_seconds`; the harness owns the derivation, the contract term itself is arch's (per test-plan §3 → `boot` → Timeout).
- tests ↔ security: the sidecar spawn path may pass `ANDROMEDA_PULSE_DATA_DIR` only via `.env(...)`, never into argv, with a fixed hard-coded program path — an existing negative-test obligation the live leg's env wiring must not route around (per test-plan §11 § Mocking, §5 → MCP `initialize` preflight readiness gate). Scope precondition 3 (`ANDROMEDA_PULSE_MCP_ENABLED` reaching the sidecar only by inheritance) sits on this boundary.
- tests ↔ security § Dependency Security: `cargo audit` + `cargo deny` run as one Supply-chain stage in the same workflow (per test-plan §9 → Pipeline structure).

## Acceptance criteria contributions
- `cargo nextest run -p conductor-run` passes with the `canary_wire.rs` call sites following the constant, and the full aggregate gate (workspace nextest `--profile ci` + `--doc` + clippy `-D warnings`) is green with nextest `retries` unset (per test-plan §3 → `run`, §10 → Zero-flakiness budget).
