# obs extract

## Relevance
Relevant — the chunk's own discriminator between LEAD A (empty ids) and LEAD B (composition/nesting shape) is self-observation output that obs-plan §6 already mandates on the `emit.batch` boundary, and the chunk changes the canary path inside instrumented crates (`conductor-emit`, `conductor-run`).

## Constraints
- The `emit.batch` boundary log must carry the wire-shape witness — observed span count, the count of spans a receiver would skip for a missing `trace_id`/`span_id`, and the distinct event / event-attribute KEY NAMES of the outbound request (names only, never values, ordered so the same batch renders identically) — alongside batch index, emission count, result status (per obs-plan §6 Boundary-call wrappers). Whether the canary's emit path already routes through that instrumented span (vs. composing its own exports outside it) is research's question, and it is the same question as the chunk's LEAD A/B discrimination.
- The witness must be emitted at `debug` inside the existing `#[instrument]` span and carried on the already-allowlisted `message` field, requiring no new allowlist entry (per obs-plan §6; §11 Logs bans `info` on a hot path).
- Any span attribute must be a name in `conductor-core::redact::ALLOWLISTED_FIELDS` — the processor stage drops any other field, so a new dedicated attribute (e.g. a "spans-missing-ids" count) emits nothing unless allowlisted (per obs-plan §4 Required-span-attributes constraint; §11 PII Scrubbing).
- Self-obs span names must stay inside the bounded set (`scenario.run`, `timeline.execute*`, `emit.batch`, `emit.logs_batch`, `verify.readback*`, `report.generate`, `db.insert_run`, `fault.*`, `tauri.command.*`), `{module}.{operation}`-shaped, with no high-cardinality names — no per-fingerprint, per-span-id or per-export-request span name (per obs-plan §11 Spans/Traces; §2 naming conventions).
- No OTel SDK may be initialized or used for self-observation, and no self-observation OTLP may be exported — not to `:4317` (the PRODUCT fault stream) and not to `:4318` (dead per arch). The only OTLP Conductor speaks is the product stream the canary/emit path sends AT Pulse (per obs-plan §3 OTel SDK init; §11 Universal). This binds any temptation to "add a debug exporter" to diagnose the gap.
- `conductor-emit` is instrumented at the **outbound gRPC call boundary only** — Pulse-side receipt is not Conductor's instrumentation surface, and Pulse MCP is boundary-only (Conductor observes read-back responses and SLO timing, never Pulse internals) (per obs-plan §1 Instrumentation scope). Pulse's `buffer.tick` trio is therefore external ground truth read from the SUT, not Conductor telemetry.
- Capturing the witness on the live leg requires the ADDITIVE form `RUST_LOG=info,conductor_emit=debug`; a bare per-target directive REPLACES the default and darkens every other `info` crate, and neither form may be set for a run that also executes the test suite (per obs-plan §3 Per-module log levels).
- Malformed/empty transport or read-back input on the preflight path must yield `blocked` (a typed `Ok(...)` verification value), never a panic, and every panic must be captured structurally (per obs-plan §11 Error Reporting; §10 zero-unlogged-panics).

## Patterns to follow
- The `verify.readback` key-set witness (observed key set of each raw tool result, names only, on the `message` field) is the receiving-side twin the `emit.batch` witness was modelled on — same shape, same rationale (a reader that degrades to empty makes divergence indistinguishable from emptiness) (obs-plan §6).
- `conductor-emit` uses a manual span around the tonic client call — no auto-instrumentation (obs-plan §4 Auto-instrumentation per surface table).
- Self-obs lines come in two variants over one base set: the event line, and the span-lifecycle line adding `span` / `span_event` (`new` | `close`) / optional `parent` plus the span's allowlisted attributes on `new` — so a §4 span materializes as quotable evidence lines (obs-plan §3 two record shapes).
- Adding a conforming, low-cardinality member to the bounded span-name set is the established route when a genuinely new egress operation ships (precedent: `emit.logs_batch`) (obs-plan §11 bounded set).
- Live-leg evidence capture is agent-mode JSONL (`logs/agent-latest.jsonl`) plus sanitized stderr, agent-parseable via `jq`/`serde_json` (obs-plan §3 Log file location / Snapshot–paste-to-AI).

## Anti-patterns to avoid
- Never introduce an OTel SDK, exporter, or `tracing-opentelemetry`/W3C trace context for self-observation while debugging the wire — it breaks `current_thread` determinism and pollutes the PRODUCT stream (obs-plan §11 Telemetry Strategy / Spans / Universal).
- Never add a metrics instrument (counter/histogram) to tally skipped or emitted spans — Minimal tier has no metrics backend; diagnostics are JSON field/log assertions (obs-plan §11 Metrics; §5).
- Never emit per-span or per-export diagnostic detail at `info`, and never as unstructured stderr text — hot-path detail is `debug`/`trace`, structured JSON only (obs-plan §11 Logs).

## Contract bindings
- **obs ↔ tests harness:** test-plan §3 owns the JSONL self-obs line format; obs-plan §3 records the base set + span-lifecycle variant it must stay reconciled with. `crates/conductor-run/tests/canary_wire.rs` asserts wire shape against Conductor's OWN collector, while the §6 `emit.batch` witness is the runtime record of what actually went on the wire — the two are complementary, and a change to what the canary emits touches both.
- **obs ↔ security:** the field-name allowlist + value scrub live single-location in `conductor-core::redact`; the witness records key NAMES only, never values, and no absolute host paths may reach logs or artifacts (obs-plan §11 PII Scrubbing).
- **obs ↔ CI (§9):** the `logs/agent-latest.jsonl` conformance gate validates the §3 self-obs base-line schema (`timestamp_ms`/`level`/`target`/service identity/`run_id`) and no absolute host paths; new witness lines must satisfy it.
- **obs ↔ SUT boundary (§1):** Pulse is boundary-only; any Pulse-side counter cited as evidence is read from the parked Pulse repo/telemetry, not produced by Conductor's obs stack.

## Acceptance criteria contributions
- The canary's OTLP egress produces an `emit.batch` boundary log carrying the wire-shape witness — span count, receiver-skip count for missing `trace_id`/`span_id`, and distinct event / event-attribute key names (names only, ordered) — at `debug` on the `message` field (per obs-plan §6 Boundary-call wrappers). Whether the canary path currently reaches that instrumented span at all is research's question.
- No new self-obs span name outside §11's bounded set, and no new span attribute that is absent from `conductor-core::redact::ALLOWLISTED_FIELDS` (a non-allowlisted attribute emits nothing) (per obs-plan §11 Spans/Traces + §4 Required-span-attributes constraint).
- No OTel SDK initialized for self-observation and no self-obs OTLP export on any port (`:4317` product-only, `:4318` dead) after the change (per obs-plan §3 OTel SDK init + §11 Universal).
- The witness-capturing live leg is reproducible with `RUST_LOG=info,conductor_emit=debug` (additive form; bare per-target directive fails the CLI's own agent-mode self-obs test), and the agent-mode JSONL still passes the §9 base-schema + no-absolute-path conformance gate (per obs-plan §3 Per-module log levels + §9 Log conformance check).
