## Relevance
Relevant — the chunk changes a pure seam function (`conductor-emit::fingerprint`), re-pins the unit/integration tests and any golden carrying a literal fingerprint, moves `Cargo.toml`/`Cargo.lock` (supply-chain gate), and its DoD item 5 is the harness `boot` readiness signal.

## Constraints
- The fingerprint derivation is unit-tier work: it is a pure seeded function of the `conductor-emit`/`conductor-faults` class, and per-seam `cargo nextest run -p conductor-<seam>` is the bulk of the suite (per test-plan §2 pyramid Unit row + §4 "What unit tests cover" — conductor-emit / conductor-faults bullets). Egress liveness stays off the unit tier.
- The supply-chain gate is binding and non-waivable once the tree is no longer zero-delta: `cargo audit --deny warnings` + `cargo deny check` (advisories/licenses/bans/sources) green, with a committed un-drifted `Cargo.lock`, is a build-failure condition (per test-plan §9 Pipeline "Supply-chain audit" row + §10 Build failure conditions). The scope's 21st-pin deferral rests on a "no dependency delta" basis that a landed hashing dep removes — whether the deferral can still stand is research's question.
- Determinism is a hard bar with a zero-retry flakiness budget: same scenario+seed must reproduce an identical stream shape, and nextest `retries` must stay 0 (per test-plan §1 Coverage triggers "property-test (determinism discipline)" + §10 Zero-flakiness budget). A derivation change must not introduce any input the seed does not control.
- Golden artifacts are committed and CI runs fail-don't-write: the seeded stream goldens live per-crate under `<crate>/tests/snapshots/`, one file per test-file family × seed (`replay__*` · `pacing__*` · `dispatch_wire__*`), and `cargo insta review` is banned as an authoring step (per test-plan §7 Golden artifacts row). Whether any committed golden currently carries a literal fingerprint value is research's question.
- A failed preflight precondition must surface as a named reported state, never a silent downgrade: `ready:false` ⇒ every dependent scenario reports `state="Blocked"` with the named precondition string, and an empty/malformed canary round-trip ⇒ `blocked`, never false-pass-as-empty (per test-plan §3 `boot` Readiness signal + §5 Cross-module patterns / query_incident_list bullet).
- Pulse's reaction may not be faked as a CI verdict — the rmcp stub proves MCP wiring only; the live read-back leg is an operator/local `workflow_dispatch` gate, never a CI gate (per test-plan §11 Test Strategy stack-specific ban + §9 Live-Pulse scenarios). The chunk's "aligned derivation" claim therefore needs the live leg, not a stub-affirmed assertion.
- Coverage stays at the Minimal floor — `cargo llvm-cov nextest --fail-under-lines 60` over the workspace, and lowering the bar to pass is banned (per test-plan §10 Coverage thresholds + §11 Quality).

## Patterns to follow
- Table-driven rstest `#[rstest]` + `#[case]` rows for variant matrices — the natural shape for re-pinning the P-017 `FingerprintVariant` identity triple (path-insensitive / line-insensitive / type-sensitive / frame-sensitive) after the input moves to the rendered stacktrace (per test-plan §4 Fixture pattern + §7 Fixture library).
- Canonical-serialization goldens locked by exact-string `assert_eq!` at the unit tier, with insta reserved as the E2E journal-golden mechanism (per test-plan §4 conductor-report bullet, as amended 2026-06-16) — the established shape for pinning a new literal derivation value.
- `conductor-run`'s cross-process tests use assert_cmd `Command::cargo_bin` + `assert_fs::TempDir` with `.env("CONDUCTOR_RUNS_DIR", …)`, asserting exit code + envelope row + journal (per test-plan §6 cli driver row + §3 Test data bootstrap / Per-test isolation).
- `boot` is `conductor preflight --json` with readiness signal `{"ready": true}` under two derived budgets — the in-process canary poll (`CONDUCTOR_PREFLIGHT_TIMEOUT` clamped up to `[incident_formation].min_canary_poll_seconds`) and the `agent-run.{sh,ps1}` wrapper derived as `warmup_ms/1000 + poll + margin`; a missing contract term is a hard exit 2 (per test-plan §3 `boot`).
- Preflight/verdict mapping is unit-tested against an rmcp in-process stub (`ready:false ⇒ blocked`, `degraded_mode ⇒ KnownResidual`, empty canary ⇒ `blocked`) — the CI-runnable leg for any change to what the canary precondition compares (per test-plan §4 conductor-verify bullet + §8 What to mock).

## Anti-patterns to avoid
- Never merge or `cargo build --release` without audit + deny green and an un-drifted committed `Cargo.lock` (per test-plan §11 CI stack-specific) — squarely engaged by the hashing dep landing as a normal dep.
- Never test implementation details — assert the public seam API and observable behavior, not private helpers (per test-plan §11 Unit). Governs the `Fnv1a` helper's tests: if the helper is retained, its tests must not pin a derivation promise the shipped signature no longer makes.
- Never regenerate goldens through an interactive accept UI (`cargo insta review`) — CI/assert mode only, fail-don't-write (per test-plan §11 Universal + §7 Golden artifacts row).

## Contract bindings
- test-plan §3 Status endpoint shape / Log format ↔ obs-plan §3: `fingerprints` is a required field of the Run-report envelope and of every JSONL journal line, serialized identically into `runs.db`, the Markdown report, and the journal. test-plan §3 is the SOURCE OF TRUTH for that format and obs derives from it — so if the derivation change alters what populates `fingerprints` (width, rendering, count), the harness-greppable schema side must be reconciled, not just the emit-side function. Whether the current code writes the raw 16-hex value or a prefix into that field is research's question.
- test-plan §3 `boot` ↔ the chunk's DoD item 5: "a live leg reaches `ready:true`" IS the harness boot readiness signal, gated on the live-Pulse prerequisites (`mcp-server` feature + `ANDROMEDA_PULSE_MCP_ENABLED` + matching `ANDROMEDA_PULSE_DATA_DIR`) that §9 keeps off CI.
- test-plan §9 Supply-chain audit stage ↔ security-plan §Dependency Security: the audit/deny tools are reference floors, not exact pins — any install that runs the gate green satisfies it (per test-plan §4 Tool-version policy).
