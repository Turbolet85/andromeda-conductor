# obs extract

## Relevance
Relevant — this chunk drives obs-plan's Critical Path 2 (fingerprint-storm) end to end and adds a new evidence-read surface (SUT log harvest) that obs rules govern.

## Constraints
- The fingerprint-storm run must carry the must-trace chain `scenario.run` → `timeline.execute_fingerprint_storm` → `emit.batch` (per P-ID cohort) → `verify.readback_fingerprints` → `report.generate` with the per-span attributes named there (`p_id_count`/`batch_count`; `batch_index`/`fingerprints_in_batch`; `mcp_tool`/`latency_ms`/`fingerprints_read_back_count`) (per obs-plan §4 Fingerprint-storm scenario + §1 Critical paths row 2). `fingerprints_read_back_count` is required to be a COUNT of what read-back returned, never an emitted-vs-read-back match — the plan records that match as not computable. Whether the shipped code already emits this chain/attributes is research's question.
- Any span attribute the chunk wants to record (harvested `severity_hint`, `occurrence_count`, fingerprint prefix, incident count) must be a name in `conductor-core::redact::ALLOWLISTED_FIELDS`, or the processor stage drops it and the attribute emits nothing; non-allowlisted evidence must ride the allowlisted `message` field instead (per obs-plan §4 Required-span-attributes constraint + §11 PII Scrubbing).
- Span names are a bounded set (`scenario.run`, `timeline.execute*`, `emit.batch`, `emit.logs_batch`, `verify.readback*`, `report.generate`, `db.insert_run`, `fault.*`, `tauri.command.*`); a new log-harvest seam must follow `{module}.{operation}` and its name joining that set is a plan amendment, not a free choice (per obs-plan §11 Spans / Traces + §2 Naming conventions).
- The log-harvest read of `{data_dir}/logs/agent-latest.jsonl.<date>` is governed by the redaction mandate: no absolute host-file paths (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace paths) and no internal struct names may reach logs, the run-report, or `runs.db`; redaction is required at the processor stage, not the sink (per obs-plan §11 Logs + §11 PII Scrubbing, §9 Log conformance check).
- Each MCP tool result's observed KEY SET must be logged once per pass on the `verify.readback*` boundary — key names only, never values, on `message` — because the extraction readers degrade to empty on an unrecognized shape rather than erroring (per obs-plan §6 Boundary-call wrappers). The chunk's CARRY to diff `retrieve_report` / `retrieve_telemetry_slice` key sets against the pinned baseline rests on this witness existing; whether both tools' passes already emit it is research's question.
- SLO recalibration is bounded: `latency_ms` = `read_back_observed_at − journal_emitted_at` in wall-clock `std::time` (never tokio's virtual clock), `slo_tier` is the closed enum `<5s | <20s | <90s`, and the assertion happens at report-generation time as a JSON field check — not a histogram instrument (per obs-plan §5, §10 Performance budgets, §11 Project-specific bans).
- The run-report envelope is the 11-field record owned by test-plan §3 (obs derives, does not re-author); for this scenario `fingerprints` is specified as a populated array while the 2026-08-16 amendment records read-back-side fingerprints as always `[]` under deterministic L4 — reconciling which side populates the envelope field is research's question (per obs-plan §6 Log Coverage + §3 Log format JSON schema).

## Patterns to follow
- Boundary-witness pattern: emit the shape/wire witness inside the *existing* `#[instrument]` span on the `message` field rather than adding new attributes — `verify.readback` key-set witness at `info`, `emit.batch` wire-shape witness at `debug` (per obs-plan §6 Boundary-call wrappers).
- Two record shapes: the per-line self-obs stream (`timestamp_ms`/`level`/`target`/service identity/`run_id`, plus span-lifecycle variant with `span`/`span_event`/`parent`) is distinct from the scenario-result run-report envelope; a harvest assertion targets one, not both (per obs-plan §3 Log format JSON schema, "two record shapes").
- Manual instrumentation only at seams — no auto-instrumentation for the MCP client, gRPC emit, or rusqlite; `#[tracing::instrument]` spans rendered as JSON log events, correlation by `run_id` and never a `traceparent` (per obs-plan §4 Auto-instrumentation table + §3 Correlation).
- Additive `RUST_LOG` form `info,{crate}=debug` when opting into the `conductor_emit` debug witness; a bare per-target directive replaces the default and blacks out the rest of the stream, and neither form may be set for a run that also executes the test suite (per obs-plan §3 Per-module log levels).
- The coverage roll-up's auto term carries a derived `(N unbacked)` qualifier read from `conductor_core::UNBACKED_AUTO`, qualifying the auto count rather than joining the mode breakdown — the P-074 pin removal moves this number, and a reader must not treat the qualifier as a fifth mode (per obs-plan §4 Coverage-matrix completeness gate, denominator semantics).

## Anti-patterns to avoid
- Never introduce an OTel SDK or export any self-observation OTLP — not to `:4317` (the PRODUCT fault stream) and not to `:4318`; a live-Pulse leg makes self-obs export tempting and it is banned on determinism + recursion grounds (per obs-plan §11 Telemetry Strategy + §11 Universal).
- Never log at `info` in the hot path — a storm scenario's per-emission/per-record detail belongs at `debug`/`trace` behind the additive `RUST_LOG` opt-in (per obs-plan §11 Logs).
- Never persist absolute host paths, SUT log content values, or internal struct names into Conductor artifacts (journal, run report, `runs.db`) — key/field NAMES only for shape evidence (per obs-plan §11 Logs + PII Scrubbing).

## Contract bindings
- obs ↔ tests: the run-report envelope + JSONL log format are OWNED by test-plan §3; obs §3/§6 reproduce it and must realign to the owner, never the reverse. The pinned key-diff baseline test (`conductor-verify/tests/readback.rs`) is the tests-side consumer of the obs §6 key-set witness.
- obs ↔ security: redaction is single-location in `conductor-core::redact` (field-name allowlist + host-file-path value scrub + `Display`-not-`Debug` at the `anyhow` edge), applied at the processor stage (per obs-plan §11 PII Scrubbing).
- obs ↔ core/arch: the coverage-matrix gate's attributes are manifest-derived and its auto qualifier reads `conductor_core::UNBACKED_AUTO` — the same pin `check_scenario_backing` gates, which this chunk edits (per obs-plan §4 Coverage-matrix completeness gate).

## Acceptance criteria contributions
- The live leg's self-obs lines show the fingerprint-storm span chain with `verify.readback_fingerprints` carrying `mcp_tool`, `latency_ms` and `fingerprints_read_back_count` as a returned-count (not a match count) (per obs-plan §4 Fingerprint-storm scenario).
- Both `retrieve_report` and `retrieve_telemetry_slice` passes emit an observed-key-set witness line (names only, on `message`) that is diffed against the pinned baseline before any measured verdict from this family is trusted (per obs-plan §6 Boundary-call wrappers).
- No log line, journal row, or `runs.db` row produced by the leg — including anything derived from the harvested SUT log file — contains an absolute host-file path or a non-allowlisted field name (per obs-plan §11 Logs + PII Scrubbing, §9 Log conformance check).
- Any recalibrated `slo_tier` stays within the closed enum `<5s | <20s | <90s` and the `latency_ms ≤ threshold` check is evaluated at report-generation time from wall-clock `std::time` stamps (per obs-plan §10 Performance budgets + §5).
