## Relevance
Relevant — this chunk executes a critical path the plan names verbatim (fingerprint-storm E2E) plus its unit/read-back/coverage-gate legs.

## Constraints
- The live-Pulse leg is an operator/local gate by construction (`workflow_dispatch` / `scripts/agent-run.sh`), never a CI gate; CI runs the rmcp-stub legs only, so everything this chunk lands in nextest must be green with no live Pulse (per test-plan §9 CI Integration → Live-Pulse scenarios, and §11 CI).
- The stub canary proves MCP *wiring* only — Pulse's reaction may never be faked as a CI verdict; the fingerprint reaction is a live/local-gate assertion (per test-plan §11 Test Strategy).
- `blocked` / `ManualCheck` / `KnownResidual` / `CalibrationRegion` are reported envelope states, NOT non-zero process exits; only a hard `Fail` exits non-zero. Model-interpretive claims must be `CalibrationRegion` report-for-human, never hard-failed — this governs how a re-calibrated `slo_tier`/token expectation is asserted (per test-plan §3 `run` exit-code semantics + §11 E2E).
- No scenario without a Pulse P-ID, and the coverage gate's scenario-backing leg asserts exact-set equality in BOTH directions over `UNBACKED_AUTO` (`Auto` only, unit-tier, CI-runnable) — so it fails on a pinned id a scenario now covers (pin rot) exactly as on a new unbacked claim (per test-plan §6 Coverage-matrix completeness gate → Scenario-backing leg, §11 Universal).
- Artifacts (envelope, `runs.db` row, JSONL journal, Markdown report) MUST NOT leak absolute host paths or internal seam-crate struct names; the plan requires this be enforced by the insta golden plus a negative test on the journal, with the field-allowlist/redaction layer owned by obs (per test-plan §3 Status endpoint shape + §3 Log format + §3 bootstrap `log-format-bind-with-obs`). Whether a log-harvest reader of a SUT-owned file already satisfies this is research's question.
- Synchronization is on explicit signals — envelope `state`, a JSONL journal line, an element role/`aria-live`, or an exit code — never `sleep(N)`; and no real network in tests beyond the loopback gRPC/MCP stubs (per test-plan §11 E2E + §11 Universal). A pre-leg line-count slice of a SUT log is a harvest boundary, not a substitute for a signal wait.
- Zero-flakiness budget: a flake is quarantined and root-caused, `retries` stays 0; coverage gate `--fail-under-lines 60` (per test-plan §10 Quality Gates).

## Patterns to follow
- The §6 fingerprint-storm E2E scenario shape is already specified: `boot` ready → `conductor run fingerprint-storm --seed <s>` under `CONDUCTOR_RUNS_DIR` → `assert_fs::TempDir`, with assertions on exit code, per-P-ID `verdict`/`state` rows in `runs.db` (bound-parameter `SELECT`), the envelope `fingerprints` field, and read-back within SLO; `TempDir` drop is cleanup (test-plan §6 Scenario: Fingerprint-storm).
- Unit tier for the derivation/doc-comment work: `conductor-emit` OTLP struct + encoding and `conductor-faults` fingerprint generators are pure seeded functions tested crate-locally under `#[cfg(test)]` with `cargo nextest run -p conductor-<seam>`; same seed ⇒ same shape (test-plan §4 What unit tests cover). The scope's `relative_path_is_fingerprint_significant` pin sits at exactly this tier.
- Read-back stub legs are split per the current §5: `query_incident_list` carries the canary (an incident opened AFTER the emission stamp ⇒ proceed; empty corpus, only-older incidents, or a missing stamp ⇒ `blocked`) with fresh/stale/stamp-absent legs, while `retrieve_telemetry_slice` / `retrieve_report` are per-check extraction where readers degrade to empty and never panic (test-plan §5 Cross-module patterns). The key-diff baseline the CARRY names lives at this stub tier — a divergence lands as a finding plus a stub test.
- Fixtures: declarative serde+garde scenario config one-per-P-ID under `scenarios/`, valid + invalid matrices; goldens in two committed families — envelope/journal (redacting `run_id`/`journal_emitted_at`/`read_back_observed_at`) and seeded stream goldens per test-file family × seed under `<crate>/tests/snapshots/` (`replay__*` · `pacing__*` · `dispatch_wire__*`), CI fail-don't-write (test-plan §7 Seed strategies). Whether the shipped `scenarios/fingerprint-storm.toml` variant mix feeds any committed `dispatch_wire__storm_stream_seed_*` golden — i.e. whether re-shaping the mix forces a golden regeneration — is research's question.
- Harness `status`/`logs`/`cleanup` mechanics for the live leg: read the `runs.db` row via bound-parameter SQL or `jq -e` over `runs/<run_id>.jsonl`; `cleanup` is idempotent and must not touch Pulse (test-plan §3 5-command implementation).

## Anti-patterns to avoid
- Never run the live-Pulse scenario as a CI gate and never fake Pulse's reaction as a CI verdict (test-plan §11 CI + §11 Test Strategy).
- Never escalate the storm into a load/saturation test — bounded "typical/high" profiles only; 50k+ spans/sec is Pulse's own suite (test-plan §11 Test Strategy).
- Never accept a changed golden through `cargo insta review`'s interactive UI, never add a retry, and never lower the coverage bar to get the leg green (test-plan §11 Universal + §11 Quality).

Two collision risks for this chunk's log-harvest strand: (a) §3 already declares the self-obs stream (`logs/agent-latest.jsonl`) a DISTINCT artifact from the per-run emission journal (`runs/<run_id>.jsonl`, the SLO ground truth) — the SUT's `{data_dir}/logs/agent-latest.jsonl.<date>` shares that stem and must not be conflated with either; (b) any new witness line Conductor emits is a self-obs line under §3's two variants and §11's level policy.
