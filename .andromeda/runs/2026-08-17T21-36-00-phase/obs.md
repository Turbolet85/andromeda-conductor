## Relevance
Partial — the chunk is domain/test/doc re-alignment, but it redraws the meaning of the Fingerprint-storm must-trace path's fingerprint attributes and envelope field, and it leans on the no-absolute-host-path artifact-hygiene mandate obs owns.

## Constraints
- The Fingerprint-storm critical path's span set and attribute NAMES are fixed: `scenario.run` → `timeline.execute_fingerprint_storm` (`p_id_count`, `batch_count`) → `emit.batch` (`batch_index`, `fingerprints_in_batch`) → `verify.readback_fingerprints` (`mcp_tool`, `latency_ms`, `fingerprints_read_back_count`) → `report.generate`. Redrawing same-fp membership changes what `fingerprints_in_batch` counts but must not rename or drop the attributes (per obs-plan.md §4 Fingerprint-storm scenario). Whether the code already emits this set is research's question.
- The Run-report envelope's `fingerprints` field must be present but MAY BE EMPTY — it is fed solely from Pulse's `fingerprint_refs`, pinned `[]` under deterministic L4. Storm identity must be evidenced by `fingerprints_read_back_count` and the test-only harvest surface, never by a populated envelope array (per obs-plan.md §4 Fingerprint-storm Required log fields). This bounds where `storm_harvest.rs` may take its grading input.
- Every span attribute must be a name in `conductor-core::redact::ALLOWLISTED_FIELDS`; the processor stage drops any other field, so a new attribute for variant class / normalization axis emits nothing unless allowlisted or carried on the allowlisted `message` field (per obs-plan.md §4 Required-span-attributes constraint).
- Span names are a bounded set (`scenario.run`, `timeline.execute*`, `emit.batch`, `emit.logs_batch`, `verify.readback*`, `report.generate`, `db.insert_run`, `fault.*`, `tauri.command.*`); no new span name may be introduced for fingerprint or variant derivation (per obs-plan.md §11 Spans / Traces).
- Fingerprint generation is named as an inner-loop hot path that must be profiled before any span is added, and hot paths must never log at `info` (per obs-plan.md §11 Telemetry Strategy + §11 Logs).
- No absolute host path and no internal struct name may reach a log line, `runs/<run_id>.jsonl`, or `runs.db`; masking of absolute host-FILE paths is single-location in `conductor-core::redact` (per obs-plan.md §11 Logs + §11 PII Scrubbing). The chunk's `stacktrace_carries_no_absolute_host_path` invariant is the emit-side expression of this requirement; its exact reach is research's question.
- `emit.batch`'s wire-shape witness must stay `debug`-level, KEY NAMES only (never values), ordered so the same batch renders identically, carried on the already-allowlisted `message` field (per obs-plan.md §6 Boundary-call wrappers).

## Patterns to follow
- Witness-on-`message`: both the `verify.readback` key-set witness and the `emit.batch` wire-shape witness record shape evidence as ordered key names on the allowlisted `message` field rather than as new attributes — the established way to record derivation evidence without an allowlist change (obs-plan.md §6 Boundary-call wrappers).
- Two record shapes: the self-obs base line (`timestamp_ms`, `level`, `target`, service identity, `run_id`, plus the span-lifecycle variant carrying `span`/`span_event`/`parent`) versus the 11-field Run-report envelope written by the report seam. Storm evidence lands in different places depending on which shape carries it (obs-plan.md §3 Log format JSON schema, two record shapes).
- `{module}.{operation}` span naming via `#[tracing::instrument]`, rendered as JSON log events — no OTel SDK for self-observation, no W3C trace context; correlation is `run_id` (obs-plan.md §2 Naming conventions + §3 OTel SDK init / Correlation).
- `report.generate`'s boundary log records final verdict + state + fingerprint count — the count whose meaning this chunk's redesign changes (obs-plan.md §6 Boundary-call wrappers).
- Wall-clock only (`std::time::SystemTime`/`Instant`) for journal timestamps and latency math, never tokio's virtual clock — applies if storm phase timing is touched (obs-plan.md §11 Project-specific bans + §5).

## Anti-patterns to avoid
- Never add a per-fingerprint or per-variant span, and never put a raw fingerprint hex into a span name or attribute — high-cardinality naming plus hot-path over-instrumentation (obs-plan.md §11 Spans / Traces + §11 Telemetry Strategy).
- Never let an absolute host path, backtrace file path, or internal struct name ride out in a rendered stacktrace that reaches logs / run report / `runs.db` (obs-plan.md §11 Logs + §11 PII Scrubbing).
- Never re-point storm evidence at the envelope `fingerprints` array as if it were populated, and never define an attribute as a match between an emitted fingerprint and a read-back one — that match is not computable (obs-plan.md §4 Fingerprint-storm scenario).

## Contract bindings
- obs ↔ tests: the 11-field Run-report envelope (including `fingerprints`) is OWNED by test-plan §3; obs §3/§6 reproduce it and align to tests, not vice versa. Any change to what `fingerprints` means must land on the tests side and be mirrored, not authored, here (obs-plan.md §3 Log format JSON schema / §6 Log Coverage).
- obs ↔ tests harness/CI: §9's log conformance gate reads `logs/agent-latest.jsonl`, asserting the §3 self-obs base schema and no absolute host-file paths in any field — the gate that would catch a stacktrace-borne path leak from this chunk (obs-plan.md §9 Log conformance check).
- obs ↔ security: the redaction layer's absolute-host-file-path anchor plus field-name allowlist and `Display`-not-`Debug` at the `anyhow` edge is the shared surface with security's Logging & Monitoring rules (obs-plan.md §11 PII Scrubbing).
