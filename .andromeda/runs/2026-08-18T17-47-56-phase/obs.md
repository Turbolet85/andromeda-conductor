# obs extract

## Relevance
Relevant — this chunk is an evidence-producing live leg: it exercises §4 Critical Path 1 end-to-end, writes the §6 Run-report envelope, harvests self-obs JSONL, and re-calibrates `slo_tier` against measured `latency_ms`.

## Constraints
- Self-observation stays `tracing` + `tracing-subscriber` JSON only for the whole leg — no OTel SDK init, no self-obs OTLP export to `:4317` or `:4318`; the only OTLP this leg speaks is the PRODUCT fault stream `conductor-emit` sends to Pulse (per obs-plan §3 OTel SDK init, §11 Universal).
- Two record shapes must not be conflated in the evidence: the per-line self-obs base set (`timestamp_ms`, `level`, `target`, `service.name`/`.version`, `deployment.environment`, `run_id`) in `logs/agent-latest.jsonl`, vs the 11-field Run-report envelope in `runs/<run_id>.jsonl` + `runs.db` written by the report seam (per obs-plan §3 Log format JSON schema — "two record shapes", §6 Log Coverage).
- `latency_ms` must be `read_back_observed_at − journal_emitted_at` in wall clock (`std::time::SystemTime`), never tokio's virtual clock; `slo_tier` is the closed enum `<5s | <20s | <90s`, and the SLO check is a JSON field assertion at report-generation time — never a histogram instrument (per obs-plan §5 Metric Coverage, §10 Performance budgets, §11 Project-specific bans).
- The leg's span set is bounded and pre-specified: `scenario.run` → `timeline.execute` → `emit.batch` → `verify.readback` (/`verify.readback.observe` on the degraded pass) → `report.generate` → `db.insert_run`, with `report.generate`/`db.insert_run` as run-scoped SIBLINGS correlated by `run_id`, not descendants; no new span name outside the bounded set (per obs-plan §4 Critical Path 1 + Cleanup, §11 Spans/Traces).
- Boundary-call must-log events are required on this path: `verify.readback` records tool name + `latency_ms` + error + canary result + the observed KEY SET of each raw tool result (names only, on the allowlisted `message` field, for `query_incident_list`/`retrieve_report`/`retrieve_telemetry_slice`/`mark_incident_resolved`); `emit.batch` records the wire-shape witness at `debug`. Whether the shipped code already emits the key-set witness for `retrieve_report` and `retrieve_telemetry_slice` is research's question (per obs-plan §6 Boundary-call wrappers).
- Any SPAN attribute must be a name in `conductor-core::redact::ALLOWLISTED_FIELDS` or the processor stage drops it; envelope extras (e.g. `degraded_mode_response`) are written by the report seam and governed differently (per obs-plan §4 Known-residual required-span-attributes heading).
- Redaction is mandatory on everything this chunk retains as evidence — no absolute host-file paths (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace paths) in harvested slices, `leg-verdict.md`, journal rows, or `runs.db`; struct names are excluded by the field-name allowlist + `Display`-not-`Debug` at the `anyhow` edge, while the allowlisted `target` module path is preserved (per obs-plan §11 Logs + PII Scrubbing).

## Patterns to follow
- Span-lifecycle self-obs lines: the custom layer emits `span` + `span_event` (`new`|`close`) + optional `parent` + allowlisted attributes on `new`, so a §4 span materializes as greppable JSONL lines — the mechanism by which harvested leg evidence can show the span tree (per obs-plan §3 two record shapes).
- The established key-set witness shape (`query_incident_list returned keys [items, next_cursor, total]`, names only, on `message`) is the template to reuse for the two readers this family reaches first with a non-empty corpus (per obs-plan §6 Boundary-call wrappers).
- Agent-mode as a read-only trigger: `agent_mode = flag || CONDUCTOR_AGENT_MODE env-set`, exported by the operator's launching shell, never written by Conductor; forces JSON-only to `logs/agent-latest.jsonl` — aligned with the scope's five-item operator recipe (per obs-plan §3 Logging stack, agent-mode flag).
- Additive `RUST_LOG=info,{crate}=debug` when the leg needs the `emit.batch` `debug` witness — a bare per-target directive REPLACES the default and darkens every other target; never set either form for a run that also executes the test suite (per obs-plan §3 Per-module log levels).
- Ramp/baseline phases: `fault.ramp` is declarative phase data (`EmissionShape::Ramp`) opened from the caller-supplied per-phase hook, created-but-NOT-entered so `emit.batch` keeps `timeline.execute` as parent, at `info`, with `ramp_factor` as the signed normalized slope −1.0..1.0 (per obs-plan §4 Fault-injection spans).

## Anti-patterns to avoid
- Never add an OTel SDK/exporter or W3C trace context (`traceparent`, `tracing-opentelemetry`) to correlate this leg — correlation is `run_id`; cross-surface parity is the `runs.db` envelope comparison (per obs-plan §11 Telemetry Strategy + Spans/Traces).
- Never emit unstructured stderr or a raw multi-line panic/backtrace into the harvested evidence, and never leak absolute host paths or non-allowlisted field names into the leg artifacts (per obs-plan §11 Logs + Error Reporting).
- Never promote a hot-path witness to `info` or introduce a high-cardinality span name (per-scenario-instance, per-fingerprint) for this leg (per obs-plan §11 Logs "no info in hot path" + Spans bounded set).

## Contract bindings
- obs ↔ tests: test-plan §3 OWNS the JSONL envelope + self-obs line format; obs derives and must not re-author it (per obs-plan §3 Log format JSON schema, §6 Log Coverage). The scope's pinned key-set baseline lives on the tests side (`conductor-verify/tests/readback.rs`) and is fed by obs's §6 witness — a one-sided change to either breaks the bind.
- obs ↔ security: the redaction layer is single-location in `conductor-core::redact`, applied at the processor stage (not the sink), and covers journal write + report generation + `runs.db` insert (per obs-plan §11 PII Scrubbing).
- obs ↔ CI/security supply-chain: `cargo-audit` red flag is listed among obs's build/deploy failure conditions (per obs-plan §10 Build/deploy failure conditions), so the chunk's audit/deny PREREQ result reports into that gate — the floor-raising decision itself is security's, and the scope forbids CI edits here.
- obs ↔ CI: §9's log-conformance and zero-unlogged-panics gates read CI artifacts; the live leg is operator-gated (scope Boundaries), so those gates bind only the deterministic unit/golden additions this chunk may make (per obs-plan §9 CI Integration).

## Acceptance criteria contributions
- Each leg's `runs/<run_id>.jsonl` row and `runs.db` row carries the complete 11-field Run-report envelope (`journal_emitted_at`, `read_back_observed_at`, `run_id`, `seed`, `scenario`, `p_ids`, `verdict`, `state`, `latency_ms`, `slo_tier`, `fingerprints`), with `fingerprints` permitted to be empty (per obs-plan §6 Log Coverage + §4 Fingerprint-storm Required log fields).
- The re-calibrated `slo_tier` holds as a report-generation-time field assertion `latency_ms <= threshold_for(slo_tier)` against the measured wall-clock delta, with no histogram instrument added (per obs-plan §5 Metric Coverage + §10 Performance budgets).
- The `verify.readback` boundary log records the observed key set (names only, on `message`) for `retrieve_report` and `retrieve_telemetry_slice` on the first non-empty-corpus pass, diffable against the pinned baseline (per obs-plan §6 Boundary-call wrappers).
- Harvested Pulse slices, `leg-verdict.md`, journal rows and `runs.db` rows contain no absolute host-file paths and no non-allowlisted field names, and the leg produces zero unstructured `^thread.*panicked` lines — a malformed read-back/transport input yields `blocked`, never a panic (per obs-plan §11 Logs/PII Scrubbing/Error Reporting + §10 Zero unlogged panics).
