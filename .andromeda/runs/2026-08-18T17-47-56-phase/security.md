## Constraints
- The `cargo audit` deferral is an **advisory-DATABASE fault**, not a tool fault: the remedy is a bounded wait with the audit↔deny overlap **VERIFIED green** (`cargo deny check advisories bans licenses sources`), never a floor raise, never a `deny.toml` ignore, never a CI edit (per security-plan §Dependency Security, two-fault split). The scope's PREREQ restates this; the plan is the authority for it.
- If the scope's "[inferred] no new dependencies" premise falsifies, a dependency delta MAY land under the red audit **only** on a deny check verified green over the NEW `Cargo.lock`, and the deferral must be re-pinned stating the changed basis ("no dependency delta" stops being available as a reason) (per security-plan §Dependency Security, 2026-08-16 admission condition).
- The leg's operator recipe requires `ANDROMEDA_PULSE_DATA_DIR` (a fresh data dir per leg, per scope §2) to be passed strictly via the `.env(...)` builder with argument-injection metacharacters rejected before `TokioChildProcess` spawn, and `andromeda-pulse-mcp` spawned as a fixed hard-coded program path — never operator-chosen, never interpolated into argv or a shell (per security-plan §Input Validation, `ANDROMEDA_PULSE_DATA_DIR` row; §Anti-Patterns → Input/Code Patterns). Whether the shipped spawn path already enforces the metachar reject is research's question.
- Read-back child stdout stays a bounded, non-panicking decode: JSON-RPC errors / decode faults map to `VerifyError::{JsonRpc,Decode,Transport}` through the verdict/error wall, and an empty or unparseable result must never read as a false pass (per security-plan §Input Validation, MCP read-back child-stdout row; §Anti-Patterns → Universal). This binds directly to the scope's key-set-witness/diff step — a shape change at the readers must degrade to `blocked`/empty, never to a satisfied assertion.
- Every one of the FIVE named preflight preconditions must surface as its own distinct `blocked` precondition string with its named cause — never a silent downgrade to pass/fail/manual-check and never the generic corpus-empty string (per security-plan §Anti-Patterns → Universal). This chunk's leg is the first to reach the readers with a non-empty corpus, so the constraint bears on how a non-empty-but-wrong-shape read-back is classified.
- Run-report artifacts (`<run_id>.md`, `runs.db` rows, `runs/<run_id>.jsonl` journals) and the harvested `agent-latest.jsonl` slices retained as this chunk's evidence must carry verdict/state/identity fields only — no absolute host paths (the canonicalized `CONDUCTOR_*` dirs, `ANDROMEDA_PULSE_DATA_DIR`) and no internal seam-crate struct names (per security-plan §Error Handling, run-report artifact sanitization; §Anti-Patterns → Logging). This applies to the committed `evidence/leg-verdict.md` too, since it is cross-host-shared ground truth.
- Any scenario-TOML movement under the re-calibration clause (check shapes, `slo_tier`) stays inside the garde boundary: `[phases.emission]` `kind` REQUIRED whenever the table exists, `occurrences` bounded by `MAX_OCCURRENCES`, per-shape cross-field rules, and every nested spec field annotated `dive` — never `skip` (per security-plan §Input Validation, scenario-config row; §Anti-Patterns → Input).

## Patterns to follow
- Typed-error-to-`anyhow`-only-at-the-edge: `thiserror` enums stay inside the seam crates; type erasure happens only at the `conductor-cli` binary edge, with `tonic::Status` codes and MCP error responses treated as first-class typed verification inputs rather than panics (per security-plan §Error Handling).
- Verdict/error wall: `Result::Err` reserved strictly for harness faults (transport down, MCP unreachable, config parse); verification outcomes stay typed VALUES returned as `Ok(...)` (per security-plan §Error Handling). The scope's "retires to declare-only, never a vacuously-passing `Absent`" disposition is the same never-false-pass discipline in the check layer.
- Fixed-path manifest resolution with no `CONDUCTOR_*` override handle, via `resolve_under`, with read faults carrying `e.kind()` only and never the path — the established pattern for `contracts/pulse-*.toml` and the model for any new fixed-path read (per security-plan §Input Validation, committed SUT-facing manifests row).
- `ANDROMEDA_PULSE_L4_DETERMINISTIC` as a declaration-only read: Conductor tests only whether its OWN environment declares it; the value never becomes a path, argv element, or log value, and an absent declaration surfaces as an unmet contract term naming both candidate causes, never as a claimed measurement of `pulse-app` (per security-plan §Input Validation). The scope's operator recipe sets this flag in the launching shell, so the read side must stay declaration-only.
- Bound rusqlite parameters for all `runs.db` writes (`run_id` / `seed` / fingerprint-JSON1), never `format!`-built SQL (per security-plan §Input Validation, `runs.db` row; §Anti-Patterns → Input) — relevant because this chunk persists new run rows as evidence.

## Anti-patterns to avoid
- NEVER paper over the red audit: no `deny.toml` ignore for RUSTSEC-2026-0244, no floor raise (unexecutable — no released tool can read the DB), no CI edit, no silent accept (per security-plan §Dependency Security).
- NEVER let a malformed child/transport input panic or a preflight failure silently downgrade — the read-back path routes faults through the verdict/error wall, and every unmet precondition gets its own `blocked` string (per security-plan §Anti-Patterns → Universal).
- NEVER have Conductor's code directly open, copy, or exfiltrate Pulse's plaintext `corpus.db`, and never persist its content into Conductor artifacts — corpus access is via MCP read-back ONLY (per security-plan §Anti-Patterns → Data Protection). The scope reads Pulse source read-only and harvests `agent-latest.jsonl` slices; the corpus itself stays untouched by production code.

- **Dependency gate ↔ tests §CI Integration:** the audit/deny re-check is the existing single CI security gate; the scope forbids CI edits, so the gate's shape stays owned by tests while its pass/fail semantics stay mine (per security-plan §Dependency Security, CI integration).
