# obs extract

## Relevance
Relevant — this chunk is obs-plan Critical Path 4 verbatim ("Severity-lifecycle full pass observing auto-resolve + resolution summary"), so its live leg is the first measurement of a must-trace path the plan mandates.

## Constraints
- The family's must-trace chain is mandated as `scenario.run` → `timeline.execute_severity_lifecycle` → `emit.batch` (per severity transition) → `verify.readback_auto_resolve` → `verify.readback_resolution_summary` → `report.generate`, with attributes `phase_count` on the timeline span, `severity_level` + `phase` on each batch, `auto_resolve_triggered`, `summary_received` (per obs-plan §4 "Scenario: Severity-lifecycle full pass…", restated in §1 critical-paths table). Whether the code already builds this family-specific chain is research's question — the directly analogous restart-suppression chain was measured never-built and retired (see amendment history).
- A span attribute must be a name in `conductor-core::redact::ALLOWLISTED_FIELDS` or the processor stage drops it, so an unlisted attribute emits nothing (per obs-plan §4 Required-span-attributes constraint; §11 PII Scrubbing). Whether `auto_resolve_triggered` / `summary_received` / `severity_level` / `phase` / `phase_count` are allowlisted today is research's question — this is the exact disqualifier class that retired `degraded_mode_requested` / `response_received`.
- Two record shapes are governed differently: the eleven-field Run-report envelope plus the scenario extras `lifecycle_phase` ("escalation"/"plateau"/"resolution") and `severity_choice_calibrated` (boolean) are written by the report seam, while span attributes are governed by the allowlist (per obs-plan §3 "Two record shapes", §6 Additional scenario-specific fields).
- Verdict semantics for this family are split: severity *choice* is required to grade CalibrationRegion and lifecycle *timing* hard Pass/Fail (per obs-plan §1 CP4 row + §4 Required log fields). The chunk's premise that severity choice may be structurally ungradeable under deterministic L4 lands directly on this mandate.
- SLO is a JSON field assertion, not an instrument: `latency_ms = read_back_observed_at − journal_emitted_at` in wall-clock `std::time` (never tokio's virtual clock), against the CLOSED tier enum `<5s | <20s | <90s`, asserted at report-generation time (per obs-plan §5, §10, §11 project-specific bans). P-060's gradeability matters here because Pulse's own 120s idle lifecycle exceeds the top tier — whether a lifecycle leg's measured latency can land inside the closed enum is a measurement question for research.
- The MCP read-back boundary log must carry tool name (`query_incident_list` / `retrieve_report` / `retrieve_telemetry_slice` / `mark_incident_resolved`) + `latency_ms` + error + canary-check result + the observed KEY SET of each raw tool result, key names only, on the allowlisted `message` field (per obs-plan §6 Boundary-call wrappers). This is the mechanism that makes an as-yet-unexercised `mark_incident_resolved` legible instead of indistinguishable from an empty corpus.
- Correlation is the `run_id` field plus plain `tracing` span nesting; no W3C trace context, no OTel SDK for self-observation, no OTLP export of self-obs on any surface (per obs-plan §3 Correlation, §3 OTel SDK init, §11 Spans/Universal).

## Patterns to follow
- Bounded span-name set uses the `verify.readback*` and `timeline.execute*` wildcards, so the family's names conform without adding a bounded-set member (per obs-plan §11 Spans).
- A §4 span materializes as evidence via the self-obs span-lifecycle line variant — `span`, `span_event` (`new`|`close`), optional `parent`, and the span's allowlisted attributes on the `new` line only (per obs-plan §3 "Two record shapes"). Attributes not computable at span-open are therefore unwitnessable as attributes; the established substitute is a `message`-field witness at the appropriate level (per obs-plan §4 Fault-injection spans, `fault.port_occupier` precedent).
- Root `scenario.run` opens per-scenario at the composition root and closes when the scenario returns; `report.generate` and `db.insert_run` are run-scoped SIBLINGS correlated by `run_id`, not descendants (per obs-plan §4 CP1 Cleanup) — a leg's span-tree evidence should be read that way, not as one root containing everything.
- Evidence trail shape follows the prior live proofs: per-leg journal + `runs.db` rows read as the eleven-field envelope, with the §3 self-obs base line (`timestamp_ms`/`level`/`target`/service identity/`run_id`) on every line of `logs/agent-latest.jsonl` (per obs-plan §3, §9 Log conformance check).
- Fault-span lifecycle is `info` (not `debug`) so spans are visible under the default INFO filter; per-target `RUST_LOG` REPLACES the default, so always the additive form `info,{crate}=debug`, and never set it for a run that also executes the test suite (per obs-plan §6 log-levels note, §3 per-module levels).

## Anti-patterns to avoid
- NEVER log at `info` in the per-record inner loop of the per-severity-transition emit path; use `debug`/`trace` gated by the additive `RUST_LOG` form (per obs-plan §11 Logs).
- NEVER introduce a high-cardinality span name (e.g. per-incident-id or per-severity-value) or an attribute outside the redaction allowlist to carry the new lifecycle evidence (per obs-plan §11 Spans / PII Scrubbing).
- NEVER add an OTel SDK, `tracing-opentelemetry`, `traceparent`, or any self-obs OTLP export to observe the live leg — the only OTLP is the PRODUCT fault stream to `:4317` (per obs-plan §11 Telemetry Strategy + Universal).

## Contract bindings
- obs ↔ tests: the Run-report envelope schema is OWNED by test-plan §3; obs derives and must not re-author it. Any envelope change here (e.g. retiring or concretizing `lifecycle_phase` / `severity_choice_calibrated`) is the one-sided change D-tests-obs-harness guards, so it must move on both sides (per obs-plan §3 Log format JSON schema, §6 Log Coverage).
- obs ↔ tests (harvest tier): where a family claim is ungradeable from Conductor's own envelope, the established route is grading at the harvest tier over Pulse's own tracing lines, fed by obs's boundary key-set witness (per obs-plan §4 Restart-suppression scenario, §6 Boundary-call wrappers).
- obs ↔ security: no absolute host paths / internal struct names in journal, run-report, `runs.db`, or committed leg evidence — value scrub masks host-FILE paths, field-name allowlist plus `Display`-not-`Debug` at the `anyhow` edge keeps struct names out (per obs-plan §11 Logs + PII Scrubbing, citing security-plan §2).
- obs ↔ arch: the deterministic-L4 read-back posture (L4-authored fields are fixture constants) is what determines whether a severity read-back field can vary with the input tier (per obs-plan §4 Fingerprint-storm bullet, same posture).

## Acceptance criteria contributions
- (obs) Each mandated CP4 span and attribute is either observed on the leg's emitted self-obs lines (span-lifecycle `new`/`close` records with allowlisted attributes) or recorded as measured-absent with the measurement — never a vacuous green, never a silently skipped critical-path span (per obs-plan §4 Severity-lifecycle scenario + §11 Spans "NEVER skip spans on critical paths").
- (obs) The leg's read-back boundary log carries, for every tool the family calls including `mark_incident_resolved`, the tool name + `latency_ms` + result + the observed key set (names only, on `message`), so a field-name divergence is distinguishable from an empty corpus (per obs-plan §6 Boundary-call wrappers).
- (obs) Leg evidence conforms to both record shapes: every `logs/agent-latest.jsonl` line carries the §3 self-obs base set (`timestamp_ms`, `level`, `target`, `service.name`/`service.version`/`deployment.environment`, `run_id`), and each journal/`runs.db` row carries the eleven-field envelope with `latency_ms` computed wall-clock journal-relative against the closed `slo_tier` enum (per obs-plan §3 Log format JSON schema + §5/§10 SLO invariants).
- (obs) Committed evidence (per-leg journal, `runs.db` rows, leg-verdict.md) is redaction-clean — no absolute host-file paths (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace paths), no non-allowlisted Debug-dumped field names; the allowlisted `target` module path is preserved, not scrubbed (per obs-plan §11 Logs + PII Scrubbing, §9 Log conformance check).
