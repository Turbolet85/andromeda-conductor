# tests extract

## Relevance
Relevant — v2-19's `method: unit` makes this chunk almost entirely a test-domain deliverable (config→verdict→envelope round-trip proven at unit tier), and it touches the envelope/`runs.db`/journal shapes test-plan §3 owns.

## Constraints
- Unit tier carries this chunk: the per-seam `cargo nextest run -p conductor-<seam>` layer is the bulk and E2E stays capped at the 7 critical paths — no new E2E path, no live-Pulse leg for a `unit`-method capability (per test-plan §2 pyramid, §11 Test Strategy). `cargo test -p <crate>` (full, non-doc) is a standing runner-portability gate beside nextest (per test-plan §4).
- Latency must be measured/stamped from `std::time::SystemTime`/`Instant`, never tokio's virtual clock; §11 requires a golden test to catch a paused-clock leak into the ground-truth artifact, and §8 permits the virtual clock for scheduling only (per test-plan §11 Test Data, §8 What to mock).
- No real-elapsed-wall-clock assertions: drive `tokio::time::advance` under `start_paused = true` and assert scheduled ordering/shape (per test-plan §11 Unit).
- This is representation, NOT a perf budget: §10 sets Performance budgets N/A (no perf-budget trigger) and §11 bans escalating to load/saturation to exercise timing — sub-5s budget checks are contract assertions, not enforced timing gates (per test-plan §10, §11 Test Strategy).
- §3 requires the Run-report envelope (`latency_ms` + `slo_tier` among its fields) be serialized *identically* into the `runs.db` row, the JSONL journal, and the Markdown report, one JSON object per line, `serde_json`/`jq -e` parseable, with no host paths or internal struct names; §3 also names `latency_ms`/`slo_tier` as `status`-polled fields — so whichever per-check shape lands (open fork 1) must hold across all three sinks and stay pollable (per test-plan §3 Status endpoint shape + Log format).
- The budget-≤-tier bound is a garde cross-field invariant, which §1's security-vector/property-test trigger requires be covered by load-time negative tests plus a property test over the `#[garde(custom)]` rules — and explicitly requires catching a nested spec field annotated `skip` rather than `dive` (rules that exist but never execute) (per test-plan §1 Coverage triggers, Vector 2).
- Any `runs.db` read/write for a new column or row shape uses rusqlite bound parameters — never `format!`/concatenated SQL — asserted by a negative/static test; fixtures stay self-bootstrapping (in-memory `runs.db` per test, committed scenario TOMLs, no developer-seeded DB) (per test-plan §11 Integration, §7).

## Patterns to follow
- Canonical-serialization golden: lock the envelope/journal line shape with exact-string `assert_eq!` at unit tier (the `verdict.rs`/`report_state.rs`/`scenario.rs` pattern); insta stays the E2E journal-golden mechanism, redacting `run_id`/`journal_emitted_at`/`read_back_observed_at`, CI fail-don't-write, never `cargo insta review` (per test-plan §4 conductor-report bullet, §7 Golden artifacts).
- Table-driven rstest: `#[fixture]` for the seeded generator, `#[rstest]` + `#[case]` rows for the garde valid/invalid config matrix and per-P-ID catalog rows, `#[once]` for in-memory `runs.db` schema (per test-plan §4 Fixture pattern, §7).
- Crate-local `#[cfg(test)] mod tests` inside each `conductor-<seam>` source file (crate-local `tests/` only for slower in-crate integration), snake_case test fns (per test-plan §4 Conventions, §2 directory/naming).
- proptest strategies with `proptest-regressions/` persistence for the cross-field invariant space (per test-plan §1 property-test trigger, §7 Randomized data).
- Module↔DB coverage uses rusqlite `open_in_memory()` per test; `assert_fs::TempDir` file DB only for the cross-process leg (per test-plan §5 boundary table, §7).

## Anti-patterns to avoid
- Never stabilize a timing assertion with `sleep(N)`, a retry, or a nextest `retries` knob — flaky is quarantine-and-fix at the cause, and a runner-dependent result is in that class (per test-plan §10 Zero-flakiness, §11 E2E/CI/Quality).
- Never assert on implementation details or fixture-internal values — assert the Run-report envelope contract (per test-plan §11 Unit).
- Never hard-code the tier deadline literals in new assertions where the tier's own rule is the source; the de-hardcode precedent requires naming the SET/rule so the assertion does not re-stale (per test-plan §1 amendment precedent 2026-08-08/09, §6 Selector strategy).

## Contract bindings
- **tests §3 ↔ obs-plan §3 (log format).** test-plan §3 is the declared SOURCE OF TRUTH for the JSONL format; obs derives its envelope from it. Adding/reshaping a per-check latency field is a lockstep §3 ↔ obs-plan §3 amendment (the D-tests-obs-harness class), and §3's *two-site* companion is §1 Critical Paths 1–4 + their §6 scenario twins, which each mandate "`latency_ms` recorded against the declared `slo_tier`" — a one-sided apply leaves the retired shape standing (two-site rule, established at the 2026-08-18 error-baseline re-base).
- **tests ↔ obs (redaction allowlist).** §3's bootstrap `log-format-bind-with-obs` assigns the field-allowlist/redaction layer to obs and requires tests to assert that boundary via a negative test on the journal (no host paths, no struct names) — so `conductor-core::redact` admitting any new field name is obs's call, tests' assertion.
- **tests ↔ obs (stream separation).** The self-obs stream and the per-run emission journal are distinct artifacts whose schemas must not be conflated (§3); a per-check latency field belongs to the envelope side. Whether the code today emits any latency value on a self-obs line is research's question.
- **tests ↔ security.** §11 Integration's bound-parameter-SQL ban cites the security plan's `runs.db` anti-pattern; §1's Vector-2 trigger is the load-time garde negative-test mandate.
- **tests ↔ arch.** The envelope is an arch Standard Contract and `slo_tier` is arch's closed TEXT enum — tests assert the shape arch fixes; the choice between row-per-check and per-check sub-structure (scope open fork 1) is arch's to cite, tests' to golden-lock.
