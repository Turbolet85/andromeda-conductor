# arch extract

## Relevance
Relevant — arch owns the pinned interface-surface set, the journal-relative timing model that `budget_ms` grades, the report-envelope states these four scenarios must land in, and the crate placement for any new reader.

## Constraints
- Latency is defined as `read_back_observed_at − journal_emitted_at` and nothing else; `budget_ms` is a sub-tier deadline on THAT quantity via `ExpectedCheck::effective_deadline_ms(tier)`, with the tier deadline as a ceiling (per architecture.md §Established Decisions [Timing-Tolerance Model]). This is the arch rule that decides the chunk's second open premise: a Pulse-internal frontend/render duration is not the quantity the field grades, so binding one to the other would contradict the model rather than merely be imprecise.
- Conductor's interface surfaces are pinned at THREE — OTLP/gRPC egress, inbound verification via the hand-rolled JSON-RPC MCP read-back over the sidecar's stdio, and internal Tauri command/`Channel` (per architecture.md §Conventions "Interface surfaces (three pinned…)"). A programmatic reader of Pulse's `tracing` stream would be a FOURTH inbound surface and a change to the stated trust boundary (Conductor trusts exactly one child's stdout as its read-back source, per §Cross-cutting Patterns "Trust boundary") — an arch-level decision, not an implementation choice.
- Scope law bans UI automation and Pulse process management outright (per architecture.md §Cross-cutting Patterns "Scope law"), which is binding on the three webview-sourced observables; and "no scenario without a P-ID" means every scenario stays keyed to a P-ID in the manifest's accepted set (§Established Decisions [Accepted Capability Set]).
- A scenario with zero `[[expected]]` checks lands `verdict: null` / `state: "KnownResidual"` by either route (degraded read-back, or the post-green-preflight auto-resolve residual), while a checks-bearing scenario whose read-back cannot carry its checks — and every read-back call failure — lands `Blocked` with a named precondition, never a silent downgrade (per architecture.md §Standard Contracts "Run report envelope" + §Established Decisions [Read-Back Dependency Posture]). Whether these four TOMLs currently carry `[[expected]]` checks is research's question; the constraint fixes what each choice makes them land as.
- A blocked or declare-only scenario emits ZERO `CheckRecord` rows / zero `run_check` rows (per architecture.md §Standard Contracts "Per-check record" + §Occupied Resources on-disk artifacts). So the harvest-tier option and the per-check persistence surface named in the chunk's "surfaces touched" are mutually exclusive for a given scenario.
- Verdicts and report states are typed VALUES; `Result::Err` is reserved for harness faults (per architecture.md §Cross-cutting Patterns "Verdict/error wall"). "This observable reaches no read-back surface" must therefore surface as a state, never an error.
- Coverage-mode changes are gated in two directions: `check_sut_drift` holds manifest-accepted ⇄ code-native classification to set-equality, and `check_scenario_backing` holds the `UNBACKED_AUTO` pin to exact-set equality, so an `Auto`→`DriveObserve` re-classification (the chunk's third open premise) must move the pin in lockstep or raise `CoreError::SutDrift` / `CoreError::UnbackedCoverage` (per architecture.md §Established Decisions [Accepted Capability Set]). Where the four P-IDs sit today is research's question.

## Patterns to follow
- **Declare-only family + harvest tier.** architecture.md §Standard Contracts records seven families shipping zero `[[expected]]` "because no read-back surface can carry them under deterministic L4", with the live claims graded at the harvest tier — the precedent shape for exactly this chunk's structural finding.
- **Transcribed-SUT-record artifact with honesty-typed terms.** The `contracts/*.toml` manifests carry `sut_version` / `captured_at` / `provenance`, resolve through a fixed `default_path()` + `resolve_under`, and the run contract types each term by what Conductor can honestly know — `shell-declaration` (can block) / `asserted` / `declared-not-observable` (recorded, never blocking, because blocking would claim a measurement) (per architecture.md §Occupied Resources `contracts/pulse-run-contract.toml`). This is the existing shape for a real SUT-side value with no read-back surface.
- **`budget_ms` → `effective_deadline_ms` + load-path cross-field check.** Optional integer ms, `#[serde(default)]`, garde `range` with the ceiling DERIVED from `SloTier::Tier90s.deadline_ms()`, and the sibling-spanning `budget_ms ≤ slo_tier` rule checked by `Scenario::check_budgets()` at load rather than by garde (per architecture.md §Conventions "Config conventions" + §Established Decisions [Validation Library]). All four budgets (1s–5s) are sub-tier, so the machinery is expressible; the open question is semantic, not mechanical.
- **`route_read_back` / `ReadBack {Graded, AutoResolved, Blocked}`** as the crate-private routing seam in `conductor-run` (per architecture.md §Established Decisions [Read-Back Dependency Posture]).
- **Crate-per-seam placement with explicit `Cargo.toml` edges** — scenario/spec types in `conductor-core`, read-back + verdict in `conductor-verify`, journal/report/`runs.db` in `conductor-report`, composition in `conductor-run`; a genuinely new seam is a new workspace crate, not a module smuggled into an existing one (per architecture.md §Established Decisions [Module Boundaries] + §Project Intent "How new functionality is added").

## Anti-patterns to avoid
- Any design that requires driving Pulse's GUI/webview, or starting/stopping `pulse-app`, to make an observable fire — both are stated non-goals (per architecture.md §Cross-cutting Patterns "Scope law").
- Adding a `CONDUCTOR_*` env handle (or any new env var) for a new contract/artifact path — the three SUT manifests deliberately have NO override handle and resolve from a fixed path through `resolve_under` (per architecture.md §Occupied Resources, Environment variables + the manifest bullets).
- Grading a value Conductor did not measure, or downgrading an unmeasurable check to pass/fail/manual-check instead of the named `Blocked`/`KnownResidual` state (per architecture.md §Established Decisions [Read-Back Dependency Posture] + §Probabilistic-Assertion Policy).

## Contract bindings
- **Trust boundary ↔ security:** option (b) (a Pulse-`tracing`-stream reader) adds an ingestion surface outside the pinned three, so arch's §Cross-cutting "Trust boundary" is the arch half of the security domain's input-boundary/spawn review.
- **Run-report envelope + `CheckRecord` ↔ tests / obs:** the eleven-field envelope and nine-key `CheckRecord` are arch-owned shared shapes riding the JSONL journal, `run_check`, and the Markdown report (§Standard Contracts); test fixtures and obs redaction bind to those shapes.
- **Verdict-first lamp precedence ↔ design / a11y:** `Verdict → ReportState` default mapping is arch-owned (§Probabilistic-Assertion Policy); the report's lamp rendering binds to it.
- **Capability manifest + classification gates ↔ tests:** `check_sut_drift` / `check_scenario_backing` are arch-locked invariants the test gate executes if the four P-IDs' mode changes.

## Acceptance criteria contributions
- (arch) Any latency graded through `budget_ms` / `effective_deadline_ms` is the journal-relative `read_back_observed_at − journal_emitted_at` value; no Pulse-internal duration is bound to that field (per architecture.md §Established Decisions [Timing-Tolerance Model]).
- (arch) Conductor's inbound verification surface remains the MCP read-back session over the spawned sidecar's stdio — no fourth ingestion surface lands without an explicit arch decision recorded as an amendment (per architecture.md §Conventions "Interface surfaces" + §Cross-cutting Patterns "Trust boundary").
- (arch) Each of the four scenarios lands a state consistent with its check count: zero `[[expected]]` ⇒ `verdict: null` / `KnownResidual` with zero `run_check` rows; any retained check with no read-back surface ⇒ `Blocked` with a named precondition, never pass/fail/manual-check (per architecture.md §Standard Contracts "Run report envelope" + "Per-check record").
- (arch) Code lands in the existing `conductor-{core,verify,run,report}` crates or a newly registered workspace member with explicit `Cargo.toml` edges, and any coverage-mode change for P-025/P-027/P-037/P-045 keeps `check_sut_drift` + `check_scenario_backing` green (per architecture.md §Established Decisions [Module Boundaries] + [Accepted Capability Set]).
