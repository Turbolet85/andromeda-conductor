## Constraints
- test-plan §5 (Cross-module patterns → `mark_incident_resolved`) currently mandates that tool's coverage as tool-presence + typed-response schema **against the stub only**, recording no production call site and no live exercise. This chunk's live lifecycle leg supersedes that mandate, so §5's bullet is the expected amendment target; whether a production caller exists today is research's question (the scope's measured premise says none at `crates/conductor-verify/src/client.rs:148`).
- test-plan §6 + §1 Critical Paths require a **live** claim about Pulse's reaction to grade at the HARVEST tier — `crates/conductor-run/tests/*_harvest.rs` at the `conductor-run` unit tier, on the operator/live gate, pinning verbatim leg captures — not as in-scenario `[[expected]]` checks. This is the precedent the seven declare-only families set and is the plan-side answer to the chunk's `[inferred]` "harvest test vs. new scenario TOML" premise.
- test-plan §3 (`run`, exit-code semantics) + §1 (assertion-policy split) require exit 0 = all checks Pass and non-zero ONLY on a hard `Fail`; `Blocked`/`ManualCheck`/`KnownResidual`/`CalibrationRegion` are reported envelope states. The DECLINED arm's JSON-RPC error must therefore land as a typed `Verdict`/`ReportState`, never a process-failure exit.
- test-plan §5 (OTLP egress liveness / read-back extraction) draws the verdict/error wall: a genuine transport fault surfaces as `Result::Err` (harness fault, security Vector 5), while malformed/negative read-back **degrades, never panics**. A declined write is a graded outcome, not a harness `Err`.
- test-plan §9 (Live-Pulse scenarios) + §11 Test Strategy require the live leg to stay an operator/local gate (`workflow_dispatch` / `scripts/agent-run.{sh,ps1}`), never a CI gate; CI runs the rmcp-stub legs only.
- test-plan §3 (`boot`) + §5 (MCP `initialize` preflight, pinned `contracts/` manifest, `query_incident_list` canary) require the canary round-trip to observe an incident opened AFTER the emission stamp — empty corpus, only-older incidents, or a missing stamp ⇒ `Blocked`, never silently downgraded. A leg that resolves the canary's own incident must be checked against this gate (the chunk's `[inferred]` ordering/isolation premise) and against the required-tool-presence assertion that names `mark_incident_resolved`.
- test-plan §10 (Zero-flakiness budget) forbids nextest `retries` and classes a runner-dependent result as a determinism break; §11 E2E forbids `sleep(N)` for synchronization — a post-resolve re-read must wait on an explicit signal (envelope `state`, journal line, active-set count), not a wall-clock nap.

## Patterns to follow
- Harvest-tier test shape: a `crates/conductor-run/tests/<family>_harvest.rs` file asserting verbatim Pulse log lines at the `conductor-run` unit tier (`storm` → `baseline` → `restart` → `pii` → `connection` → `severity` precedent, test-plan §6 per-scenario Verification signals).
- rmcp stub legs for the arm that cannot be induced live: in-process duplex transport for verdict/typed-response logic, `TokioChildProcess` test-binary for the spawn/`.env()` path (test-plan §5 Drivers, §8 Mocking-libraries table); this is the CI-runnable half.
- Live-leg invocation recipe: `SCENARIO=<name> scripts/agent-run.{sh,ps1} run` with a fresh data dir, `--seed` appended ONLY when `SEED` is explicitly set (TOML-declared seed governs otherwise), `CONDUCTOR_RUNS_DIR` → `assert_fs::TempDir` (test-plan §3 `run`, §6 Restart-suppression Steps, §7).
- Declare-only row shape, if the leg needs a scenario TOML rather than a harvest test: exit 0, `verdict` null, `state="KnownResidual"`, non-Blocked, `latency_ms` against the declared `slo_tier` (test-plan §6 scenarios).
- Mis-pairing pinned as a negative test: test-plan §6 Severity-lifecycle already requires that pairing a creation with the FIRST active-set drop (which is the preflight canary's own resolution) be pinned as a negative test — the same hazard the chunk's canary-perturbation premise names.

## Anti-patterns to avoid
- NEVER fake Pulse's reaction as a CI verdict — the rmcp stub canary proves MCP wiring only (test-plan §11 Test Strategy, stack-specific). An applied-arm-live + declined-arm-by-stub split must be recorded as exactly that, never as a live claim for the arm that never fired.
- NEVER treat `Blocked`/`ManualCheck`/`KnownResidual`/`CalibrationRegion` as a non-zero process exit (test-plan §11 E2E, stack-specific) — the declined arm included.
- NEVER add a scenario without a Pulse P-ID (test-plan §11 Universal, project-specific) — applies if the leg lands a `scenarios/` TOML rather than a harvest test.
