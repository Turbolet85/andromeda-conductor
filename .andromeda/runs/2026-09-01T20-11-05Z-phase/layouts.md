# layouts extract

## Relevance
Relevant — the chunk's assertion surface targets the desktop-webview console (HOLD dialog, operator-checklist rows, not-color-alone pairing, focus order/restoration), all of which layout-templates.md owns structurally; only the coverage-view *layout* work is out (scope §Boundaries, `v2-30`).

## Constraints
- The desktop-webview is a single-station console: no router, no routes, no deep links, no breakpoints — the four "screens" (idle / live / HOLD / report) are one frameless window in different **run states** (per layout-templates.md §Surface: desktop-webview → Primary screens, §IA notes). A spec cannot navigate to make the HOLD subject exist; only driving run state can. This is the structural reason the chunk's "driven leg where the subject IS present" is the only path to a non-vacuous assertion.
- The operator-pause go/no-go is a shadcn `AlertDialog` (Radix) over a dimmed console, focus **trapped**, visible `color-focus` ring, controls behind it inert, 200ms fade entrance (per layout-templates.md §Component — Hero / signature section; §Wireframe — Run console (HOLD)). Whether the shipped dialog already restores focus to its invoker on Escape/Abort is research's question.
- Checklist rows render **between Body and Actions as a sibling of the dialog's `Description`, never nested inside it** (the Description is the described-by target; interactive rows read as flat prose there), present only when the hold declares `[[checklist]]` items; Space toggles a focused row; the unticked roll-up is a `role=status` (per layout-templates.md §Component — Operator-checklist; §Component — Hero / signature section).
- Status is never color-alone anywhere on this surface: matrix lamp always paired with its verdict/state text, Mode-cell label always rendered, footer count tokens each paired with their label, active picker item carries a `border-emphasis` edge so focus is never color-only (per layout-templates.md §Component — Primary content block 1; §Component — Footer; §Component — Primary navigation). The chunk's "not-color-alone is a path, not decoration" invariant is this rule.
- The lamp set is **closed at six** and none of `Blocked` (hollow ring, `count-blocked`, measurement cells `—`/null), `ManualCheck` (neutral `status-manual` checkbox glyph) or `KnownResidual` (muted dashed ring) may be rendered red or collapsed into `Fail` (per layout-templates.md §Component — Primary content block 2). This is the structural basis of the already-passing Blocked-vs-Fail distinctness spec.
- `alert()` / `confirm()` / `prompt()` are never used — the styled `AlertDialog` is the **only** modal; Chromium context menu / devtools / text-selection on non-text elements are suppressed (per layout-templates.md §IA notes). A keyboard-trap-escape spec therefore has exactly one modal shape to assert.
- Icon-only titlebar window controls (Lucide minimize/close) must each carry an accessible name, and the focus ring must be visible on every interactive control with a keyboard equivalent for every hover affordance (per layout-templates.md §Component — Header; §Component — Primary navigation). Whether the shipped titlebar already satisfies this — a plausible home for the one uncaptured axe violation — is research's question.
- Responsive breakpoints are **N/A** for this surface (desktop-bound; per layout-templates.md §Decisions Log → Responsive breakpoints), so no breakpoint-conditional assertion belongs in this leg.

## Patterns to follow
- **Run-state transition as the only navigation**: pick scenario/suite (`Command`/`Select`) → Start → live heartbeat → operator-pause hold → report (per layout-templates.md §Component — Primary navigation). The driven leg that raises a real hold follows this sequence, not a route change.
- **Keyboard-first register already templated**: start / stop / proceed / abort each bound to a shortcut exposed through the Radix primitives; Space toggles a focused checklist row; OS shortcuts keep working (per layout-templates.md §Component — Primary navigation; §Component — Operator-checklist). Affordance-level keypress assertions map onto existing bindings rather than new ones.
- **Proceed disables and shows an in-flight state** during the async committed step (per layout-templates.md §Component — Hero / signature section) — a driven spec pressing Proceed will encounter this transient state and must not read it as a trap.
- **Role/text-addressable pairing**: because every lamp, count token and Mode cell renders its text label, role/text/aria-live selectors (the chunk's selector invariant) have a stable structural target (per layout-templates.md §Component — Primary content block 1; §Component — Footer).
- **Empty states are prose, never gray skeletons** — "No run yet — pick a scenario/suite to begin", "No scenarios loaded" (per layout-templates.md §Component — Primary content block 1 / block 2). The idle-console axe baseline is scanned against real prose, not placeholder blocks.

## Anti-patterns to avoid
- Do not nest interactive checklist rows inside the dialog's `Description` to make a spec's selector easier — the sibling placement is mandated (per layout-templates.md §Component — Operator-checklist).
- Do not introduce a second modal shape, a native `alert`/`confirm`, a route, or a breakpoint to make an absent subject reachable (per layout-templates.md §IA notes; §Component — Primary navigation).
- Do not resolve a lamp with flashing/blink/pulse, add a seventh lamp state, or tint an out-of-scope/qualifier state with `status-fail`/`count-blocked` (`count-blocked` shares its hex with `text-muted`, so a plain dim reads as `Blocked`) (per layout-templates.md §Component — Primary content block 1 (Mode cell); §Component — Primary content block 2).

## Contract bindings
- **Focus order / focus trap → a11y-plan §3/§5/§6** (the chunk's named binding contract): layouts fixes the structural position (dialog over dimmed console, trapped, ring visible, controls inert); a11y derives SC 2.4.3 reading-order match, Escape-dismiss and focus-restoration conformance.
- **Not-color-alone → a11y contrast/color pairs**: layouts guarantees the text label exists beside every color signal (§Component — Primary content block 1, §Component — Footer); a11y derives the contrast ratios and the WCAG mapping.
- **Reduced-motion → design §Motion**: the count-tint transition is dropped under reduced-motion preference and lamps resolve motionless (§Component — Header; §Decisions Log → Motion trigger placement) — the agent-driven reduced-motion leg asserts against that behavior, not against a layouts-owned token.
- **Cross-surface mirror**: the desktop lamp/token set maps 1:1 by name to the cli ANSI set (§IA notes → Multi-surface coordination), so a token-distinctness change on the webview has a cli counterpart.

## Acceptance criteria contributions
- (layouts) The operator-pause dialog renders as the single `AlertDialog` over the dimmed console with focus trapped, a visible `color-focus` ring, and the console controls inert behind it (per layout-templates.md §Component — Hero / signature section).
- (layouts) When the hold declares `[[checklist]]` items, rows render between Body and Actions as a sibling of the dialog's `Description` — never nested — with Space toggling a focused row and the unticked roll-up exposed as a status roll-up (per layout-templates.md §Component — Operator-checklist).
- (layouts) Every status conveyor asserted by the leg pairs color with text — matrix lamp + verdict text, footer count token + label, Mode-cell label — with `Blocked` a hollow ring and `KnownResidual`/`ManualCheck` never rendered red (per layout-templates.md §Component — Primary content block 1 / block 2 / §Component — Footer).
- (layouts) The HOLD subject is reached by driving run state through the single frameless window (idle → live → HOLD), not by a route, URL or breakpoint; each icon-only titlebar control carries an accessible name (per layout-templates.md §Surface: desktop-webview → Primary screens, §IA notes, §Component — Header).
