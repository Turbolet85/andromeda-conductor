## Relevance
Partial — the chunk adds one new `#[tauri::command]` (an IPC boundary the plan governs) plus dependency-gate PREREQs; no auth/secret/PII surface is involved.

## Constraints
- The new read-only `#[tauri::command]` projecting `RunsDb::get_envelope` sits on the Tauri IPC trust boundary (backend↔bundled webview, in-process, not network-exposed) per security-plan.md §Threat Model Summary (Attack surface: Tauri IPC vector); it must not be promoted into any inbound listener — security-plan.md §Security Anti-Patterns → Universal requires no inbound network listener of Conductor's own in shipped binaries.
- security-plan.md §Security Anti-Patterns → Code Patterns requires a minimal deny-by-default Tauri capabilities file allowing ONLY the actual commands plus the one live-counter `Channel`. This chunk adds a seventh command to the enumerated set (`list_scenarios`, `coverage_matrix`, `unbacked_auto`, `run_report`, `start_run`, `stop_run` per scope.md), so the capabilities allowlist must be extended in lockstep — whether the repo's capabilities file is command-enumerated or permissive today is research's question.
- The command's return value crosses the `#[tauri::command]` boundary, which security-plan.md §Error Handling names as an "external" surface: returns and their error arm must be sanitized — no absolute host paths (canonicalized `CONDUCTOR_*` dirs, `ANDROMEDA_PULSE_DATA_DIR`), no stack traces, no internal seam-crate struct/field names. Same mandate restated in §Security Anti-Patterns → Logging (bullet 2) and → API (bullet 1).
- `EnvelopeStatus` reaching the webview is envelope/run-metadata, i.e. self-generated synthetic run data per security-plan.md §Threat Model Summary (Data classification: test-telemetry / run-metadata) — no PII, credential, or corpus content may ride the new projection; §Data Protection and §Security Anti-Patterns → Data Protection forbid persisting or exfiltrating Pulse corpus content into Conductor surfaces.
- Any `RunsDb` read backing the new command must use rusqlite bound parameters, never `format!`/concatenated SQL — security-plan.md §Input Validation (`runs.db` writes row) and §Security Anti-Patterns → Input. Whether `RunsDb::get_envelope` already binds its `run_id` parameter is research's question.
- The `run_id` argument arriving from the webview is IPC-supplied input; security-plan.md §Input Validation requires validation at ALL system boundaries. Note the plan's boundary table does not enumerate an IPC-argument row today, so the applicable rule is the general boundary mandate plus the §Error Handling sanitization rule — an unknown/absent `run_id` must return a typed, path-free error, never a panic (§Security Anti-Patterns → Universal: no malformed input may panic).
- PREREQ 2 discharge is governed by security-plan.md §Dependency Security (advisory-DATABASE fault bullet): the remedy for the RUSTSEC-2026-0244 duplicate-advisory fault is a bounded wait with `cargo deny check advisories bans licenses sources` VERIFIED green — never a floor raise, never a `deny.toml` ignore, never a CI edit. Any npm dependency delta (scope.md notes `package.json` script-only changes to date) additionally requires `npm audit --omit=dev` clean per §Dependency Security (Frontend (npm) supply chain).

## Patterns to follow
- Typed `thiserror` enums inside the seam crate collapsing to `anyhow` only at the `#[tauri::command]` edge — the shipped error pattern per security-plan.md §Error Handling; the existing six commands are the in-repo precedent to mirror.
- Read-only projection over an existing validated `RunsDb` method rather than a new storage path — keeps the new surface inside the already-governed `runs.db` boundary (security-plan.md §Input Validation, `runs.db` row).
- The `blocked`/absent-measurement convention: security-plan.md §Error Handling states a `blocked` row populates only identity fields with measurement fields JSON `null`. The new command's `Option&lt;EnvelopeStatus&gt;` absence arm and the coverage rows' "not yet run" arm should render as an explicit distinct state, never as a fabricated or defaulted value.
- Existing deny-by-default Tauri capabilities authoring (per §Security Anti-Patterns → Code Patterns) as the place any new command is registered.
- The dev-only driver stack (`wdio.conf.ts`, `CONDUCTOR_MSEDGEDRIVER` `UNSAFE_PATH` guard, repo-derived resolved program, array-form argv, `4444`/`4445` harness-lifetime listeners) is used AS-IS per scope.md boundaries; security-plan.md §Input Validation (`CONDUCTOR_MSEDGEDRIVER` row) and §Security Anti-Patterns → Code Patterns rule (b) already cover both driver arms, so adding specs requires no new boundary work.

## Anti-patterns to avoid
- NEVER ship a Tauri command without extending the minimal deny-by-default capabilities file — a permissive default exposes unintended IPC (security-plan.md §Security Anti-Patterns → Code Patterns).
- NEVER surface absolute host paths, internal struct/field names, or stack traces through the new command's return or error arm, nor through the new webview banner text (security-plan.md §Security Anti-Patterns → Logging, → API).
- NEVER resolve the deny/audit PREREQ by a `deny.toml` ignore, a floor raise, or a CI edit; NEVER assume the deny overlap ran green without capturing its true exit code (security-plan.md §Dependency Security, advisory-DATABASE fault bullet).

## Contract bindings
- CI security gate binds to tests §CI Integration — the `cargo audit` / `cargo deny` PREREQ discharge in scope.md's Definition of Done item 3 is one gate inside the existing workflow, not a separate pipeline (security-plan.md §Dependency Security, CI integration; §Bootstrap phases dep-security-ci-gate).

- (security) The new `#[tauri::command]` is enumerated in the Tauri capabilities allowlist; no permissive/default-allow entry is introduced (per security-plan.md §Security Anti-Patterns → Code Patterns).
