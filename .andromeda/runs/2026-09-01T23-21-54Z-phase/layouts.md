## Constraints
- The coverage matrix row anatomy is fixed left-to-right: status-lamp glyph → scenario label → P-ID (Data role) → Mode → slo_tier → latency_ms; a live verdict lamp occupies the existing lamp column, not a new cell (per layout-templates.md §Component — Primary content block 1). Whether the shipped `CoverageMatrix.tsx` row order already matches this is research's question.
- The lamp set is closed at six report/verdict states — filled dot (`Pass`/`CalibrationRegion`/`Fail`) · hollow ring `Blocked` · neutral checkbox `ManualCheck` · muted dashed dot `KnownResidual` — and the plan requires every lamp be paired with its status text so state is never color-only (per layout-templates.md §Component — Primary content block 2). Half 1 must join into that closed set, never extend it.
- The not-yet-run treatment is an EMPTY/absence state, and layout-templates.md §Component — Primary content block 1 requires absence states render as prose in the `text-tertiary` register ("No scenarios loaded"), never a gray placeholder/skeleton — the "no run record" row must read as an explicit textual state, not a dimmed failure.
- `Fail` renders as a motionless `status-fail` lamp and `Blocked` renders `—`/null in measurement columns and is *never* red; non-result states are never downgraded to `Fail` (per layout-templates.md §Component — Primary content block 2 "Distinct non-result states"). This is the layout rule that makes DoD-1's "not-yet-run distinct from failed" a placement/treatment requirement, not just a color choice.
- The load-envelope qualifier rides OUTSIDE the lamp column as a run-level caption with an always-rendered ASCII/DOM text label, in the recessive `status-residual` register, omitted entirely when in-envelope or exempt (per layout-templates.md §cli Output structure `conductor run` + §cli Component — Primary content block 2). layout-templates.md documents this shape only for cli/Markdown; the desktop-webview §Component — Primary content block 2 currently templates no envelope banner, so Half 2 adds a webview region the plan has not yet templated — the plan's cross-surface rule (§IA notes "adapted not forked") requires the webview banner mirror the cli caption's shape, not invent a new one.
- Lamps resolve **motionless** over a single `motion-micro` color transition — never flashing, no pulse/blink/glow (per layout-templates.md §Component — Primary content block 2 and §Decisions Log "Motion trigger placement"). Live per-row lamp resolution is exactly the case this rule governs.
- The desktop surface has no router, no routes, no breakpoints — the four "screens" are one frameless window in different run states (per layout-templates.md §Surface: desktop-webview Primary screens + §IA notes). Live lamps and the envelope banner are run-state changes within the single console, not new views.

## Patterns to follow
- **Mode-cell out-of-scope precedent** — a non-lamp classification rendered in the recessive `--status-residual` tint with an always-rendered text label, deliberately not `--status-fail`/`--count-blocked` because reusing any lamp-set token would read as a verdict (per layout-templates.md §Component — Primary content block 1, Mode cell). The scope names this precedent for Half 2's banner; it is the plan's own authority for the treatment.
- **Indented-detail-line precedent** — the `Blocked` precondition string and the `KnownResidual` "expected until {named fix}" note render as `text-tertiary` Body lines beneath their P-ID row, adding no column and no bracket label (per layout-templates.md §Component — Primary content block 2 + §cli Component — Primary content block 2 per-check detail region). Reusable if the join needs to surface which run a row's lamp came from.
- **Header-strip roll-up** — the coverage matrix header strip carries manifest-derived counts (Data role, `color-id-cyan`) and tallies every classification value summing to the row count (per layout-templates.md §Component — Primary content block 1). If live lamps introduce a measured/unrun tally, it belongs in that existing strip, and any count must be derived, never a literal (per the repeated de-literalization amendments below).
- **Dense single-row-per-P-ID list, virtual-scrolled** — `color-raised-1` container, `radius-md`, `border-subtle` row dividers, row padding `space-md`, no shadows; explicitly NOT a KPI-card grid (per layout-templates.md §Component — Primary content block 1). Lamp wiring must not change row density or container shape.
- **Cross-surface mirroring, adapted not forked** — the same status tier and roll-up shape render on all three surfaces (Markdown artifact · cli · webview) by token name (per layout-templates.md §IA notes "Multi-surface coordination" and §cli Primary screens `conductor coverage`). Half 2 is the webview leg of an already-shipped cli/Markdown shape.

## Anti-patterns to avoid
- Do not introduce a seventh lamp state or a new bracket/status label for either the not-yet-run treatment or the envelope banner — the lamp set is closed at six and the envelope is a run-level qualifier outside the lamp column (per layout-templates.md §Component — Primary content block 2 and §cli Component — Primary content block 2).
- Do not render a run-state signal color-only, and do not use a gray skeleton/placeholder for the unrun row — every state pairs a glyph with its text, and empty states are prose (per layout-templates.md §Component — Primary content block 1 "Empty" and §Component — Primary content block 2).
- Do not add flash/pulse/blink when a lamp resolves live, and do not turn the matrix into a KPI-card grid or add shadow depth (per layout-templates.md §Component — Primary content block 1 and §Decisions Log "Motion trigger placement"; borders-only depth per §Decisions Log "Key layout choices").

## Contract bindings
- **Lamp text pairing → a11y**: layout-templates.md §Component — Primary content block 2 requires each verdict/state change be announced; the concrete live-region attribute is derived by the a11y specialist, and the chunk's a11y proof rides the existing `--e2e` leg (scope §Boundaries).
- **Envelope banner text label → a11y/NO_COLOR**: the always-printed ASCII/DOM label rule in layout-templates.md §cli Component — Primary content block 2 is stated as a layout requirement from which NO_COLOR / screen-reader compliance derives.
- **`status-residual` token → design**: layout-templates.md references color by token name only (§Notes); the hex and both theme values live in the design-system plan / `tokens.css`, not here.
- **Coverage roll-up counts → the manifest/`unbacked` prop contract**: layout-templates.md §cli Primary screens requires every roll-up number be manifest-derived and identical on all three surfaces (webview receives it as a prop from the backing command, never mirrored in TypeScript) — binds any new matrix tally to the Tauri command edge, not to frontend computation.
- **Responsive breakpoints**: none — layout-templates.md §Decisions Log states N/A for this desktop-bound single-station console.

- (layouts) Each coverage row's lamp renders in the existing status-lamp column (leftmost cell of the dense P-ID row), paired with its status text, and the row's Mode / slo_tier / latency_ms cells keep their documented left-to-right order (per layout-templates.md §Component — Primary content block 1).
- (layouts) A capability with no run record renders an explicit `text-tertiary` prose/absence treatment, distinct in glyph AND text from the `Fail` lamp, and no non-result state is rendered in the `status-fail` register (per layout-templates.md §Component — Primary content block 2 "Distinct non-result states").

- (layouts) Lamps resolve motionless over a single `motion-micro` color transition — no flash, blink, pulse, or entrance animation on the live update (per layout-templates.md §Component — Primary content block 2 and §Decisions Log "Motion trigger placement").
