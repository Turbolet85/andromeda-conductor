# design extract

## Relevance
Partial — the chunk authors a screen-reader pass spec (a document + evidence record, not new UI), but the must-announce list is derived directly from design-system §Component Patterns 1 / 4 / 6 / 7, so the design plan supplies the *authoritative target* for what each state's nodes and labels are supposed to be.

## Constraints
- The four run states the spec covers map onto design-mandated titlebar behavior: design-system §Component Patterns 1 requires that on hold the count's value **freeze** (not blank, not keep running), the phase line flip to "HOLD — operator pause", and `aria-live="assertive"` announce the flip — the assertive announcement is a design requirement, not merely an a11y one. Whether the shipped `Titlebar.tsx` already announces exactly that phrase is research's question.
- design-system §Brand Identity requires the signature to be the **absence** of motion (the frozen count "shows where it stopped"). The spec's expected-NVDA-speech for `hold` must therefore describe a *static, frozen* count value, not a ticking or progressing one; a spec row that expects a running/animating readout contradicts the signature.
- design-system §Component Patterns 4 requires every verdict/report-state lamp to be "always paired with text (`Pass`/`CalibrationRegion`/`Fail`/`Blocked`/`Manual`/`Residual`) + `aria-live` announcement". Whether the shipped `StatusLamp.tsx` carries a live region (scope premise 3 says it does not) is research's question — the design plan states the live-region announcement as a *requirement*, which is what makes an unannounced lamp a recordable gap rather than an as-designed outcome.
- design-system §Component Patterns 6 requires distinct, non-collapsing states in the run-report: empty = "No run yet — pick a scenario/suite to begin" prose in `--text-tertiary`, in-progress = "Run in progress" prose in `--text-secondary`, **never a gray skeleton placeholder and never downgraded to a red `Fail`**. The spec's must-announce prose for `idle`/`live` is bounded by this mandate; where shipped prose differs (scope premise 2), the divergence is a finding, and which string ships is research's question.
- design-system §Component Patterns 7 requires the operator-checklist footer to "surface the unticked count so an incomplete manual pass is never mistaken for a finished run" — so the roll-up is a *required* announced item, and the dialog-site vs report-site parity question (scope premise 4) is a real design contract, not an implementation detail.
- design-system §Iconography requires that "every status lamp is paired with a text label … every icon-only titlebar/lamp control carries an `aria-label`" — this fixes the expected accessible names for the min/close titlebar controls and mandates the lamp glyph be decorative-with-text rather than the sole signal.
- design-system §Anti-Patterns / Rejected Defaults ("Conflating 'no result yet' with 'failed'") forbids the terminal/`Blocked`/in-progress states from reading as `Fail`; the spec must include a must-announce row proving `Blocked` announces its named precondition string and does not speak as an error.

## Patterns to follow
- **Component Pattern 1 (frameless titlebar + paused-count)** — the announcement source for `idle`/`live`/`hold`/`aborted`: phase line (IBM Plex Sans 600/18px) + count (JetBrains Mono 500/28px, tabular-nums), assertive live region on the flip, `aria-label`ed 16px Lucide min/close. This is the node inventory the spec's per-state rows should enumerate for the titlebar.
- **Component Pattern 4 (verdict / report-state lamp)** — the closed six-state set with its paired text labels; the spec's expected-speech strings for matrix/report rows should be built from these exact labels, and the lamp resolves motionless (150ms color transition), so nothing on the row is a timing-dependent announcement.
- **Component Pattern 6 (run-report view)** — the terminal sub-state of `idle`: `ManualCheck` rows expand into the operator-checklist, `KnownResidual` rows carry the "expected to fail until {named fix}" note. Both are text the spec should list as must-announce, since they exist specifically so a state never silently reads as `Fail`.
- **Component Pattern 7 (operator-checklist)** — the `ManualCheck` render: induced state + expected observation as a ticked yes/no, Space toggles a row (keyboard-first), unticked-count roll-up in the footer. The keyboard-first rule means the spec's "action or key sequence" column has a real key path for every checklist row.
- **Component Pattern 2 (operator-pause dialog)** — `role="alertdialog"`, focus trapped, visible `--color-focus` ring, Proceed/Abort actions; the `hold` state's dialog announcements derive from this pattern.

## Anti-patterns to avoid
- Do not let the spec assert or imply any motion-based signal (pulse / blink / flash / animate-to-100%) as an expected announcement or observation — design-system §Motion Hard limits bans all of these, and §Rejected Defaults bans the flashing-red `Fail`; the freeze is the event.
- Do not write expected-speech rows that collapse "no result yet" into "failed" (design-system §Rejected Defaults) — `idle`-with-report, in-progress, and `Blocked` each need their own distinct expected phrase.
- If any attribute-level remedy is pulled into scope at P5 (scope §Boundaries), it must not introduce raw hex/px/ms literals or new colors — design-system §Tokens declares the 34-token `:root` contract as binding-by-name (see the `--motion-heartbeat` and `@theme`→`:root` amendment precedents below).

## Contract bindings
- **design ↔ a11y**: the assertive live-region flip (§Component Patterns 1) and the lamp `aria-live` announcement (§Component Patterns 4) are the design-side statement of what a11y-plan §3 / §4 require the spec to test; the SC mapping (4.1.3 / 4.1.2 / 1.3.1) belongs to a11y, the node-and-label inventory to design.
- **design ↔ a11y §Use of Color (SC 1.4.1)**: §Iconography's "every status lamp paired with a text label" is the not-color-alone binding — the spec's expected-speech text is exactly the text label that discharges it, so a lamp whose label is absent fails both domains at once.
- **design ↔ a11y §Animation (SC 2.3.3)**: §Motion requires all transitions be dropped under `prefers-reduced-motion: reduce`; if the operator runs NVDA with reduce-motion active, the count-tint transition is suppressed and only the frozen *value* + label flip remain announceable — the spec should not depend on a transition being observable.
- **design ↔ layouts**: per-screen placement/focus order for these nodes is the layouts distiller's; this extract supplies only the component/token/label side.

## Acceptance criteria contributions
- (design) The spec's `hold` rows describe a count value that is **frozen in place** (not blanked, not still running) with the phase line reading "HOLD — operator pause" (per design-system §Brand Identity Signature element + §Component Patterns 1).
- (design) Every lamp-bearing must-announce row in the spec names the paired text label from the closed six-state set (`Pass`/`CalibrationRegion`/`Fail`/`Blocked`/`Manual`/`Residual`) as the expected speech, never the color or glyph alone (per design-system §Component Patterns 4 + §Iconography).
- (design) The spec carries distinct rows for empty / in-progress / `Blocked` / terminal-with-report such that none is specified as announcing as a `Fail` or as an unlabelled placeholder (per design-system §Component Patterns 6 + §Rejected Defaults "Conflating 'no result yet' with 'failed'").
- (design) Any in-scope attribute-level remedy introduces no hardcoded hex/px/ms values and no new color or motion token — token-by-name only (per design-system §Surface: desktop-webview / Tokens).
