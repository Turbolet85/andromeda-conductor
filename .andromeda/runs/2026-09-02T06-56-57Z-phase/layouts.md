## Constraints
- The four run states are **one surface in different run states, not four routes** — no router, no breakpoints, no back/forward, no deep links; and `alert()`/`confirm()`/`prompt()` are never used, the styled `AlertDialog` being the only modal (per layout-templates §Primary screens, §IA notes). The spec's stimulus recipe must therefore express state transitions inside one frameless window, and the HOLD state's announced node is the styled dialog, not a native browser dialog.
- The titlebar requires three zones — phase line (left), count (center), window controls (right) — with the tick→frozen flip **announced to assistive tech**, an accessible name on each icon-only control, and an explicit **abort** behavior (count stops, dims to `count-blocked`) (per layout-templates §Component — Header, §Signature placement #1). Note for the scope's plan-vs-shipped finding: layouts *does* name an abort state even where a11y-plan's four-state naming omits it.
- Non-result states are never downgraded to Fail and each carries its own **real prose**: report Empty "No run yet — pick a scenario/suite to begin", In-progress "Run in progress"; matrix Empty "No scenarios loaded", plus the "Not yet run" absence cell distinguished by TEXT never tint alone (per layout-templates §Primary content block 1, §Primary content block 2). These are TARGET prose; scope `[inferred] 2` records the shipped strings differ — which prose the shipped DOM renders is research's question.
- Every lamp is required to be **paired with its status/verdict text**, and each verdict/report-state change is required to be announced, with a11y deriving the live-region attribute (per layout-templates §Primary content block 1, §Primary content block 2). Whether `StatusLamp.tsx` already carries any live region (scope `[inferred] 3`) is research's question.
- The Operator-checklist is **one primitive in two contexts** — dialog-site (rows between Body and Actions, rendered as a **sibling of the dialog's `Description`**, never nested, because the Description is the described-by target and interactive rows read as flat prose there) and report-site — with Space toggling a focused row and the unticked roll-up announced (per layout-templates §Component — Operator-checklist, §Component — Hero / signature section). This is the layouts-side framing for scope `[inferred] 4`.
- The go/no-go dialog's focus contract: shadcn/Radix supplies the trap + Escape but **not** restoration for this Channel-opened (Trigger-less) dialog — restoration is contract-borne via a `restoreFocusTo` accessor in `onCloseAutoFocus`, and the invoking control must stay focusable using `aria-disabled`, never the native `disabled` attribute (per layout-templates §Component — Hero / signature section).
- A pinned single-line **footer status strip** is required, carrying `conductor` · seed · run phase, the verdict roll-up and an unticked-ManualCheck count, each token paired with its label (per layout-templates §Component — Footer). Scope `[inferred] 5` reports no such node in the `App.tsx` render tree — whether the footer ships at all is research's question, and its absence is a layouts-side finding for wrap, not a phase edit.

## Patterns to follow
- Derive each state's must-announce row set from the **documented region order** in the per-state wireframes — titlebar → control row → coverage matrix → run-report card → footer (per layout-templates §Wireframe — Run console (idle) / (HOLD) / §Wireframe — Run report (terminal)) — rather than re-enumerating regions from scratch.
- Use the documented keyboard register for the spec's "action or key sequence" column: every interactive control has a keyboard equivalent, a visible `color-focus` ring, an active picker item carrying a `border-emphasis` edge (focus never color-only), and Space toggling a checklist row (per layout-templates §Component — Primary navigation, §Component — Operator-checklist).
- Text-always-renders discipline: status/mode labels always print so state survives NO_COLOR / mono / piping (per layout-templates §Primary content block 1 Mode cell, §Component — Footer) — this is the layouts-side reason each lamp exposes speakable text.
- "Adapted per surface, never forked" for cross-surface conventions (per layout-templates §IA notes Multi-surface coordination, §Primary content block 2 run-level qualifier) — the SR spec is the desktop-webview leg only; the cli's `[PASS]`/`[HOLD]` prefixes are that surface's leg, matching the scope's CLI exclusion.
- Doc-vs-shipped divergences are corrected through wrap's amendment flow, not by phase (the 2026-09-01 coverage-row-anatomy correction precedent) — consistent with this chunk's record-as-finding posture.

## Anti-patterns to avoid
- Do not frame the four states as routes/pages or add per-breakpoint rows: the surface is desktop-bound with no responsive breakpoints (per layout-templates §Primary screens, §Decisions Log — Responsive breakpoints N/A).
- Do not accept a gray skeleton/placeholder as an empty state — empty states are required to be real prose (per layout-templates §Primary content block 1 "Empty", §Primary content block 2 "Empty"); a placeholder that reads as blank is a recorded finding, not the target.
- Do not nest the dialog's checklist rows inside `Description`, and do not use native `disabled` on the invoking Start control (per layout-templates §Component — Hero / signature section) — either changes what the HOLD rows can announce and whether focus can be restored.

## Contract bindings
- **layouts ↔ a11y**: layouts states announcement as a *behavioral* requirement (announce the HOLD flip, verdict changes, the unticked roll-up; accessible names on icon-only controls; visible focus ring; status never color-alone); a11y derives the concrete attributes and conformance (per layout-templates §Notes). The spec's "node carrying it (role + accessible name + live-region mechanism)" column is exactly that a11y leg.
- **layouts §Component — Hero ↔ a11y modal pattern**: trap + Escape from the primitive, restoration contract-borne via `restoreFocusTo`; focus order/keyboard equivalence binds to a11y SC 2.4.3.
- **layouts ↔ design §Motion**: the count-tint transition and dialog fade are dropped under reduced-motion (per layout-templates §Component — Header, §Decisions Log — Motion trigger placement) — relevant only if the operator's NVDA pass runs with reduced-motion enabled; the freeze itself (absence of motion) is not motion-gated.
- **layouts §Surface: cli — Primary screens ↔ tests harness**: `--e2e` is named as the cross-surface stage that builds the release bundle and drives the webview console; the chunk's stimulus recipe (release bundle built `--features tauri/custom-protocol`) is a manual launch, not that stage, and scope forbids touching the harness.
