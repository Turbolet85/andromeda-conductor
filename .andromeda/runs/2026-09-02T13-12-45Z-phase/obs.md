# obs extract

## Relevance

## Constraints
- Cross-surface parity is an envelope comparison, never a trace correlation: obs-plan.md §4 (Both-surface parity) and §3 (Correlation) require the two runs be matched by `(scenario, seed)` with a **per-surface `run_id`** — there is no shared trace, no `traceparent`, and artifact identity is explicitly not parity.
- The envelope is the eleven-field Run-report record (obs-plan.md §3 Log format JSON schema; `read_back_observed_at` added per the 2026-06-16 amendment). Of those eleven, `run_id` (§3 format `YYYY-MM-DDTHH-MM-SS-<suffix>`), `journal_emitted_at`, `read_back_observed_at` and `latency_ms` are per-run wall-clock/identity values (§5 defines `latency_ms = read_back_observed_at − journal_emitted_at`, wall-clock) — a whole-row equality assertion across two separate runs contradicts §5's own measurement definition. Whether the shipped comparison is field-scoped is research's question.
- One journal file carries **two report-seam line shapes** — the envelope and the finer-grain per-check `CheckRecord` — and obs-plan.md §3 (two record shapes) requires a typed parse to discriminate them; a declare-only or blocked scenario emits no check line at all. A parity reader that treats "the journal" as homogeneous will mis-compare.
- Every `#[tauri::command]` handler must open a MANUAL `tracing::info_span!("tauri.command.<name>").entered()` guard — never the `#[tracing::instrument]` attribute, which does not stack with the command macro — across the enumerated EIGHT handlers including `run_envelope` (obs-plan.md §1 desktop-webview row, §4 auto-instrumentation table). Names stay inside §11's bounded `tauri.command.*` set. Whether `run_envelope` already carries the guard is research's question.
- The envelope READ path (`conductor_run::read_envelope` over `RunsDb::get_envelope`) must log a boundary-call `info!` carrying `run_id` plus the outcome **on the allowlisted `message` field**, inside the caller's `tauri.command.*` span, and mint **no `db.*` read span** (obs-plan.md §6 Boundary-call wrappers; §11 bounded span-name set carries `db.insert_run` alone and is deliberately not widened). A field name outside `conductor-core::redact::ALLOWLISTED_FIELDS` is dropped at the processor stage, so a dedicated `incident`/`envelope` attribute would emit nothing (§4 Required-span-attributes constraint).
- The Tauri self-obs sink NAME is fixed and its DIRECTORY rides `CONDUCTOR_RUNS_DIR` — `<runs_dir.parent()>/logs/conductor-tauri.jsonl` (obs-plan.md §3 Log file location). A parity harness pointing both surfaces at one `assert_fs::TempDir` therefore relocates the Tauri backend's log file to that temp dir's PARENT, and a new/changed a11y suite runs dir relocates it again; the plan's landing-site enumeration must stay honest.
- Self-obs is JSON on stderr or a file — never stdout, never pretty (obs-plan.md §3 Logging stack, §11 Logs; the 2026-08-22 21-site correction). A subprocess (`assert_cmd`) leg asserting on the CLI's self-obs stream must read stderr; stdout is the CLI PRODUCT render.

## Patterns to follow
- Span tree for the Tauri arm: `tauri.command.start_run` (root) → `scenario.run` with the same attributes as the CLI arm (`run_id`, `seed`, `scenario`, `p_ids`); `report.generate` and `db.insert_run` are run-scoped SIBLINGS correlated by `run_id`, not descendants (obs-plan.md §4 Both-surface parity + CP1 Cleanup).
- A §4 span materializes as assertable JSONL: the custom layer emits a span-lifecycle line adding `span`, `span_event` (`new` | `close`), optional `parent`, and the span's allowlisted attributes on `new`, over the same self-obs base set (`timestamp_ms`/`level`/`target`/service-identity/`run_id`) — obs-plan.md §3 two record shapes. This is the mechanism a DOM/parity test would assert against, not an implicit trace.
- Boundary-call witness idiom: put non-allowlisted detail (key sets, incident ids, outcomes) on the allowlisted `message` field rather than minting a new attribute (obs-plan.md §6 Boundary-call wrappers — the `verify.readback` key-set witness, the `mark_incident_resolved` id, the `emit.batch` wire-shape witness at `debug`).
- Rust-gate telemetry handling: cargo-nextest JSON output and `logs/agent-latest.jsonl` are uploaded CI artifacts; clippy warnings ride structured stderr (obs-plan.md §9 Pipeline integration), with the zero-unlogged-panics grep gate over the same artifact (§9, §10).
- `RUST_LOG` discipline for any leg that also runs the suite: a bare per-target directive REPLACES the default, so use `info,{crate}=debug`, and never set either form for a run that also executes the test suite — the env reaches the runner's child processes (obs-plan.md §6 per-module log levels).

## Anti-patterns to avoid
- NEVER add W3C trace context / `tracing-opentelemetry` / a `traceparent` to make the two surfaces "correlate" for the parity proof — obs-plan.md §11 (Spans / Traces) and §3 Correlation name the `runs.db` envelope comparison as the parity mechanism; adding it re-introduces the banned SDK.
- NEVER mint a span name outside the bounded set — in particular no `db.*` read span for the `run_envelope` read and no new name for a fixture seeder's `run_envelope` insert (obs-plan.md §11 Spans / Traces; §6 DB READ bullet records this as an explicit operator ruling).
- NEVER let an absolute host path reach a committed artifact or log line, and note the MEASURED channel outside the three redaction sites: the flagless sidecar spawn (`conductor-verify/src/spawn.rs:80`) publishes the sidecar's absolute exe path as a foreground console-pane title; the `CREATE_NO_WINDOW`-class fix is route-owned, not shipped (obs-plan.md §11 PII Scrubbing + Project-specific bans). A live-Pulse leg re-enters that channel and its evidence must be scrubbed at capture.

## Acceptance criteria contributions
- (obs) The parity assertion compares the deterministic envelope fields (`verdict`/`state`/`seed`/`scenario`/`p_ids`/`slo_tier`) and explicitly does NOT require equality of `run_id`, `journal_emitted_at`, `read_back_observed_at` or `latency_ms`, which are per-run wall-clock/identity values (per obs-plan.md §4 Both-surface parity, §5 Metric Coverage).
- (obs) Each surface's run writes its own `<run_id>.jsonl` whose scenario-result line carries the full eleven-field envelope, and any reader of that file discriminates the envelope from the per-check `CheckRecord` by typed parse rather than by line position (per obs-plan.md §3 Log format JSON schema / two record shapes).
- (obs) The `run_envelope` command path opens the manual `tauri.command.run_envelope` span and its rusqlite READ emits a boundary `info!` carrying `run_id` plus the outcome on the allowlisted `message` field, with no `db.*` read span introduced (per obs-plan.md §6 Boundary-call wrappers, §4 Span / Trace Coverage).
- (obs) The rust gate leg produces zero unstructured panic lines (`^thread.*panicked`) in `logs/agent-latest.jsonl` or stderr, and no committed artifact from the parity or live-Pulse leg contains an absolute host path (per obs-plan.md §9 CI Integration, §11 PII Scrubbing).
