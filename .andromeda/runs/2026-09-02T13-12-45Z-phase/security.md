# security extract

## Relevance
Partial — no new production boundary is proposed, but the chunk drives four existing ones (Tauri IPC `run_id`, the shared `CONDUCTOR_RUNS_DIR` handle, `runs.db` writes, and — only if the live fork is taken — the MCP sidecar spawn + preflight), plus artifact/evidence hygiene on everything it commits.

## Constraints
- The parity proof and the banner proof both drive `#[tauri::command]` `run_report`/`run_envelope` with a caller-supplied `run_id`; security-plan.md §Input Validation (Tauri IPC row) requires that id be resolved through `resolve_under` against the resolved runs dir before any read (absolute or `..` REJECTED, never clamped), every returned `Err` to cross the edge through `sanitize_error`, and an unknown id to be an absence (`Ok(None)` / empty list), never a panic or a fabricated value. Whether the shipped commands already satisfy this is research's question — the boundary row was added as documentation of pre-existing practice (see amendment 2026-09-01-live-per-p-id-verdict-lamps), not as a new mandate.
- The parity proof points BOTH shells at one `CONDUCTOR_RUNS_DIR`; security-plan.md §Input Validation (env-var path handles row) requires `std::fs::canonicalize` + an explicit type/existence check at the `conductor-cli` edge before any `runs.db`/journal write, and §Security Anti-Patterns → Input bans using that handle without it. Whether both entry paths (CLI and the Tauri shell's own resolution) already apply it is research's question.
- Every `runs` / `run_envelope` write this chunk adds or seeds must use rusqlite bound parameters — security-plan.md §Input Validation (`runs.db` writes row) and §Security Anti-Patterns → Input ban string-formatted SQL outright, even for self-generated synthetic content. This binds the fixture seed of an `EnvironmentSuspect` row as much as the parity envelope rows.
- Everything this chunk persists or commits — `<run_id>.md`, `runs.db` rows, the two JSONL journals, any `evidence/` record, and the msedgedriver PREREQ `--version` confirmation — must carry verdict/state/identity fields only, with no absolute host path (canonicalized `CONDUCTOR_*` dirs, `ANDROMEDA_PULSE_DATA_DIR`, the operator's driver path, a fresh Pulse data dir) and no internal seam-crate struct name (per security-plan.md §Error Handling, run-report artifact sanitization; §Security Anti-Patterns → Logging, which explicitly covers the committed `evidence/` tree).
- If P4 resolves the fork toward the LIVE Pulse leg, the sidecar spawn must keep its hardened form: a fixed hard-coded program NAME resolved through the inherited `PATH`, with the operator's fresh `ANDROMEDA_PULSE_DATA_DIR` passed strictly via the `.env(...)` builder after argument-injection metacharacter rejection — never interpolated into argv or a shell (per security-plan.md §Input Validation, `ANDROMEDA_PULSE_DATA_DIR` row; §Security Anti-Patterns → Code Patterns rule (a)). That same rule records the console-window-suppression duty as a MEASURED, route-owned defect that is not yet shipped; the live leg will re-encounter the host-path disclosure pane, and remediation is the Epoch-6 entry the scope excludes, so this chunk records rather than fixes it.
- On the live leg, a failed preflight must surface as the distinct `blocked` state with its own named precondition string (one of the five named preconditions), never a silent downgrade to pass/fail/manual-check and never a false pass-as-empty read-back (per security-plan.md §Security Anti-Patterns → Universal; §Input Validation, MCP child stdout row). Concretely: an unreachable or empty read-back must not be allowed to present as an over-envelope classification for the banner subject.
- The v2-28 sweep must not re-open the security master's read-back description — security-plan.md §Threat Model Summary and §Input Validation already describe the hand-rolled line-delimited JSON-RPC client with rmcp removed (2026-06-27), and that reconciliation cascaded to `.claude/rules/security.md` + `.claude/docs/security-summary.md`. Whether either distillation still carries a present-tense rmcp claim at HEAD is research's question; any such site is in the sweep's scope and is a security-domain doc, not a `.andromeda/` master.

## Patterns to follow
- The `resolve_under` + `sanitize_error` pair in `crates/conductor-tauri/src/commands.rs`, proven at the mock-runtime IPC tier (`tauri::test`), is the shipped shape for a `run_id`-taking command — the parity and banner work should ride the existing read path rather than open a second one (per security-plan.md §Input Validation, Tauri IPC row, which notes app-defined commands are NOT capability-ACL-gated, so this row and not the capabilities file governs them).
- Host-tool path handles are validated at the wdio edge, not in Rust: existence + `isFile` + shell-metacharacter rejection before the spawn, the value used only as an array-form argv element (or, for NVDA, the guarded program), and unset-or-not-a-file ⇒ the leg SKIPS at exit 0 with a host-path-free precondition (per security-plan.md §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row; §Security Anti-Patterns → Code Patterns rule (b)). The PREREQ version confirmation should be recorded in that same host-path-free style — the handle name and the version, not the value.
- Committed SUT-facing manifests resolve through a fixed `default_path()` + `resolve_under` with deliberately NO `CONDUCTOR_*` override; if the live leg needs warm-up / canary-poll budgets, they come from the validated fixed-path run contract (which clamps a lowered `CONDUCTOR_PREFLIGHT_TIMEOUT` UP to the contract floor), never from an operator-steerable handle (per security-plan.md §Input Validation, committed SUT-facing manifests row).
- The verdict/error wall: typed `VerifyError::{JsonRpc,Decode,Transport}` and `ConfigError` stay inside the seam crates as harness faults (`Result::Err`), while verification outcomes stay typed VALUES returned as `Ok(...)`; `tonic::Status` codes and MCP error responses are first-class typed inputs, never panics (per security-plan.md §Error Handling; §Security Anti-Patterns → Universal).
- The dev-only driver stack's harness-lifetime `127.0.0.1:4444` / `:4445` listeners sit OUTSIDE the inbound-listener ban, which is scoped to Conductor's shipped binaries — the banner leg reusing that one stack stays inside the carve-out (per security-plan.md §Security Anti-Patterns → Universal; §Threat Model Summary, port-bind vector).

## Anti-patterns to avoid
- NEVER build the parity comparison or the `run_envelope` fixture seed with `format!`/concatenated SQL — bound parameters only (per security-plan.md §Security Anti-Patterns → Input).
- NEVER let the operator's fresh Pulse data dir, the named msedgedriver path, or a canonicalized `CONDUCTOR_RUNS_DIR` reach a committed evidence record, run report, `runs.db` row or journal (per security-plan.md §Security Anti-Patterns → Logging).
- NEVER resolve the seeded-vs-live fork by staging a row directly in Pulse's `corpus.db` file — corpus access is the MCP tool surface only (read-back plus the `mark_incident_resolved` write); direct file staging to induce a SUT state is the explicitly banned route (per security-plan.md §Security Anti-Patterns → Data Protection).

## Contract bindings
- Artifact/evidence hygiene binds to obs (host-path/PII scrubbing in self-observation output) and to tests (fixtures and committed evidence carry no real host path) — the same scrub rule is asserted by the harness, not by security code.
- The Tauri IPC boundary row binds to tests' mock-runtime IPC tier (`tauri::test`): the `resolve_under` + `sanitize_error` proof lives in the tests harness, alongside the `assert_cmd` CLI leg over the shared `assert_fs::TempDir` DB.
- The CI security gate (`cargo-audit` / `cargo-deny`, `npm audit --omit=dev`) binds to tests §CI Integration as a job in the ONE workflow — the chunk's `nextest` + `clippy` gate is the tests domain's; the audit/deny leg is security's and is additive to it.

## Acceptance criteria contributions
- Both parity legs reach `runs.db` only through the resolved runs dir (`resolve_under` before any read; absolute / `..` rejected, never clamped), and every `Err` returned by `run_report` / `run_envelope` is sanitized — no absolute path, no seam-crate struct name (per security-plan.md §Input Validation).
- No `format!`/string-concatenated SQL in any `runs` or `run_envelope` write added or seeded by this chunk — rusqlite bound parameters, grep-verifiable (per security-plan.md §Security Anti-Patterns → Input).
- Every artifact the chunk commits (evidence record, run report, `runs.db` row, journal, PREREQ version confirmation) greps clean of absolute host paths and internal seam-crate struct names (per security-plan.md §Security Anti-Patterns → Logging).
- If any Cargo or npm dependency delta lands, `cargo deny check advisories bans licenses sources` is VERIFIED green over the NEW `Cargo.lock` (the advisory-DATABASE fault keeps `cargo audit` red; a floor raise is not the remedy) and `npm audit --omit=dev` reports 0 production vulnerabilities (per security-plan.md §Dependency Security).
