# arch extract

## Relevance
Relevant — the chunk's central question ("which package owns the test, and what dependency edge guarantees the `conductor` binary") is a workspace-boundary/dependency-graph decision, which is arch's domain.

## Constraints
- **The dependency graph IS the architecture.** architecture.md §Established Decisions [Module Boundaries] pins crate-per-seam where `Cargo.toml` dependency edges are the compiler-enforced seam. A test that reaches a sibling package's build output with no edge declaring it is therefore an architectural gap, not a test-config detail; any new edge (dev-dep, artifact-dep, or relocation) is an arch-registered change, not an incidental fix.
- **Layering: bins are the top; shared machinery sits below both.** §Occupied Resources — Crate names locks `conductor-run` as "the run composition root library … sitting above the seams and below both bins, shared by them", with `conductor-cli` and `conductor-tauri` as the two bins. A form that makes one bin's package depend on the other bin's package inverts that layering and needs escalation rather than silent adoption; the sanctioned home for anything both bins need is `conductor-run`.
- **The toolchain pin is locked.** §Stack and Technologies + §Inherited Defaults pin Rust 2024 / cargo 1.85 / MSRV 1.94.1 (stable, `rust-toolchain.toml`), and §Infrastructure Patterns — Build system builds on stable cargo. A candidate form requiring a nightly-only cargo feature (`-Z bindeps` artifact-dependencies) would require changing a locked inherited default — an arch decision the chunk may not make on its own.
- **Frontend-bundle build order gates every `conductor-tauri` compile.** §Infrastructure Patterns — Build system requires `npm run build` (`ui/dist`) before ANY workspace `cargo build`/`nextest`/`clippy` that compiles `conductor-tauri`, because `tauri::generate_context!` resolves `build.frontendDist` at COMPILE time. A mutation run rebuilds `conductor-tauri` once per mutant, and a FRESH-target-dir gate compiles it cold — whether the unmutated-tree baseline and the mutants scratch tree satisfy this prerequisite (`ui/dist` is git-ignored per §Occupied Resources — Frontend asset subtree) is research's question, not something this extract can attest.
- **CI is build+test only, and CI has no Pulse.** §Established Decisions [CI/CD] + §Infrastructure Patterns — CI/CD approach pin GitHub Actions to `cargo build` / nextest / clippy, with any dynamic proof needing a live Pulse as an operator/local gate. A relocated or newly-created test target joins the CI nextest set by default, so it must stay hermetic (no live Pulse, no `:4317` egress, no sidecar resolved through `PATH` — §Occupied Resources — Service/process names records `PATH` as a spawn-resolution input).
- **Supply-chain surface is arch-registered.** §Infrastructure Patterns — Build system requires `cargo deny` green with every accepted advisory/license exception naming its crate AND dependency path inline in `deny.toml`; §Stack and Technologies is the registry every new external crate lands a row in. An escargot-style form admits new packages and must clear both.
- **Namespace and naming discipline.** §Conventions — Naming patterns pins snake_case Rust source files and `conductor-<seam>` kebab-case crate names; §Occupied Resources — Interface routes reserves the `conductor-*` crate prefix, and §Occupied Resources — Environment variables reserves `CONDUCTOR_*` for any new configuration handle (which must then be registered there).

## Patterns to follow
- **Integration-test targets under the composition root.** architecture.md already names `tests/` targets living in `conductor-run` — `conductor-run/tests/lifecycle_harvest.rs` (§Established Decisions [Read-Back Dependency Posture]) and `crates/conductor-run/tests/envelope_fixture.rs` (§Occupied Resources — Environment variables). That is the established shape for a test whose reach exceeds one bin.
- **Harness-set, test-read env handle (the third handle class).** `CONDUCTOR_E2E_SEED_DIR` per §Occupied Resources — Environment variables: SET by the harness, READ only by an integration test, never by a shipped binary, and a **no-op when unset** so an ordinary `cargo nextest`/`cargo test` never writes into the repository. The template if binding the CLI needs a handle rather than a graph edge.
- **Skip-at-exit-0 precondition guard.** `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` (§Occupied Resources — Environment variables): a missing host-side prerequisite makes the arm SKIP at exit 0 with a host-path-free precondition string plus a recipe, never a hard failure — the precedent for a test arm whose prerequisite cannot be guaranteed by the graph.
- **New-dependency registration at wrap.** §Stack and Technologies row + inline-justified `deny.toml` entry naming crate and dependency path (§Infrastructure Patterns — Build system); the blake3/`arrayref` BSD-2-Clause precedent is the shape.
- **Two thin shells over one core.** §Design Philosophy ("headless-drivable core, thin shells") is the premise the parity assertion under test encodes; per the chunk scope only the test's *binding to the CLI binary* (and possibly its location) is in play, not that premise.

## Anti-patterns to avoid
- **Relying on a build artifact no dependency edge guarantees.** Depending on `target/debug/conductor.exe` having been produced by a sibling package is precisely what §Established Decisions [Module Boundaries] refuses — the edge, not the artifact, is the contract.
- **Unregistering the graph.** Landing a new workspace member, a new bin↔bin edge, or a new external package without the corresponding §Occupied Resources / §Stack registration (the `conductor-run` 9th-member precedent shows a workspace member is a tracked occupied resource).
- **Widening locked defaults to fit a test.** Moving off the pinned stable toolchain for a nightly cargo feature (§Stack, §Inherited Defaults), opening any new listener (§Cross-cutting Patterns — Trust boundary: no inbound listener of Conductor's own in shipped binaries), or introducing a configuration handle outside the `CONDUCTOR_*` namespace (§Occupied Resources — Environment variables).

## Contract bindings
- **arch ↔ tests:** the crate identity `-p conductor-tauri` that test-plan §4's mutation discipline targets is arch's locked workspace-member name (§Occupied Resources — Crate names); and the `ui/dist`-before-cargo build order (§Infrastructure Patterns — Build system) is a precondition of the mutation tier's unmutated-tree baseline and of any fresh-target-dir gate.
- **arch ↔ security:** the chunk's dependency-delta basis rides `cargo deny` green over the new lock, whose accepted advisory/license set and inline justifications are arch-owned in `deny.toml` (§Infrastructure Patterns — Build system, which also separates the green `cargo deny` from the externally-red `cargo audit`).
- **arch ↔ tests/CI:** §Established Decisions [CI/CD] bounds what a newly-created test target may require — a target added to the nextest set must not need a live Pulse, `:4317`, or the sidecar on `PATH`.

## Acceptance criteria contributions
- (arch) The test lands in one of the locked workspace members (`conductor-tauri` / `conductor-cli` / `conductor-run`); no unregistered workspace member or crate-name outside the `conductor-*` prefix appears (per architecture.md §Occupied Resources — Crate names).
- (arch) Whatever binding form wins builds on the pinned stable toolchain — Rust 2024 / cargo 1.85 / MSRV 1.94.1, no nightly-only cargo feature (per architecture.md §Stack and Technologies + §Inherited Defaults).
- (arch) Any new dependency edge or external package is registered — a §Stack row where new, `cargo deny` green over the new lock with each exception naming its crate and dependency path (per architecture.md §Infrastructure Patterns — Build system).
- (arch) The mutation tier's unmutated-tree baseline and the fresh-target-dir gate satisfy the frontend-bundle build order (`ui/dist` present before any cargo compile of `conductor-tauri`); whether the current invocations already do is research's question (per architecture.md §Infrastructure Patterns — Build system).
