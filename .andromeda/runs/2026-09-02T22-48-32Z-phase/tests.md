# tests extract

## Relevance
Relevant — this chunk is entirely test-infrastructure (mutation instrument, runner portability, test-target placement), all governed by test-plan §4/§9/§10/§11.

## Constraints
- The mutation instrument's run discipline is mandated, not optional: workspace-root-resolved `-f` full crate paths, `--test-tool=nextest` REQUIRED, gitignored `mutants.out/` output, and **`Found 0 mutants to test` is a NO-OP, never a pass** (per test-plan §4 Unit Test Strategy → Mutation instrument). The audit's own invocation already satisfied this, so the abort must be closed at the unmutated-tree baseline, not at the invocation.
- The mutation verdict is read from the **tallies** in `mutants.out/` (`missed.txt` empty + every named survivor present in `caught.txt`), never from the process exit code — which §4 requires be treated as uninformative in BOTH directions (exit 0 on a silent no-op; non-zero reflecting surviving/timeout CLASSES on a run that fully met acceptance) (per test-plan §4 → Mutation instrument).
- Acceptance is **disposition of every NAMED survivor** — killed, or classified accepted-deliberate against a cited standing rule — and explicitly NOT a numeric `--fail-under` threshold; the score moves only as a consequence (per test-plan §10 Mutation-survivor disposition). This matches the chunk's own boundary and forbids substituting a number for the disposition.
- The mutation run is an **operator/local instrument, never a blocking CI stage**, scoped per-chunk to the crates that chunk touched — §9's stage table is CI's complete inventory, not a chunk's (per test-plan §9 Scoped mutation audit).
- **Runner portability is a standing gate**: the suite must be green under BOTH `cargo nextest run -p <crate>` and `cargo test -p <crate>` (full, non-doc). A test green under one runner and red under the other is a determinism break to fix at the cause, in the zero-flakiness class — never a runner to pin to, never masked by `retries` or `--test-threads=1` (per test-plan §4 Framework + §10 Zero-flakiness budget). Whether the shipped `conductor-tauri` suite currently satisfies this on a fresh target dir is research's question — §4 states it as a requirement, and the fresh-tree arm the scope names is the un-measured half.
- §11 Integration mandates that a test must NOT depend on nextest's per-test process for a property the shared-process runner cannot supply; the prescribed remedy is a **test binary of its own** (`tests/*.rs` gives each file its own process under `cargo test`, and nextest is already process-per-test, so one file per such test holds under BOTH runners) (per test-plan §11 Integration). This is the plan-side reason a `tests/` target is a legitimate form — but §11 does not adjudicate whether it resolves `CARGO_BIN_EXE_conductor`, which is research's question.
- Whatever form wins, the parity claim's shape is fixed by §5: both surfaces driven into ONE `assert_fs::TempDir` file `runs.db` under a non-default `CONDUCTOR_RUNS_DIR`, comparing the two PERSISTED envelopes field-by-field (never each against a literal), with `assert_cmd` `Command::cargo_bin` named as the CLI-subprocess driver for that leg (per test-plan §5 Driver(s) + Cross-module patterns → Cross-surface parity). A relocation must preserve that shape.

## Patterns to follow
- **Own-test-binary relocation** — §11 Integration's prescribed remedy for a test whose isolation needs cannot be met in a shared `#[cfg(test)]` module: move it to its own `tests/*.rs` file, which holds under both runners (per test-plan §11 Integration).
- **Zero-lock-cost opt-in gating** — §9 records `conductor-run/tests/lifecycle_live.rs` behind `[features] live-pulse = []`, an EMPTY feature declaring no dependency, so it adds zero package nodes and leaves `Cargo.lock` byte-unchanged; `stub-server`-gated `preflight_spawn.rs` is the in-repo precedent. If the chosen binding needs an opt-in, this is the established shape (and §9 requires such a leg to owe its OWN `cargo clippy -p <crate> --features <feat> --all-targets -- -D warnings`, since a gated file is invisible to the default lint pass).
- **Crate-local test placement convention** — `#[cfg(test)] mod tests` inside the source file for unit logic, crate-local `tests/` for slower in-crate integration; snake_case `fn` naming under `#[test]`/`#[tokio::test]` (per test-plan §4 Conventions + §2 Test directory + naming conventions).
- **Cross-process fixture/teardown shape** — `assert_fs::TempDir` per cross-process test, cleanup by `TempDir` drop, `CONDUCTOR_RUNS_DIR` as the sandbox handle (per test-plan §5 Setup/teardown lifecycle + §6 Both-surface parity Cleanup).
- **Machine-parseable acceptance output** — nextest's stable `NextestExitCode` (100 test-fail / 101 build-fail / 4 NO_TESTS_RUN) is the agent-readable signal for the test gate; a build-level abort is 101, distinct from a failure (per test-plan §2 Agent-runnable invariants).

## Anti-patterns to avoid
- NEVER treat the mutation run's exit code as the verdict, and NEVER accept `Found 0 mutants to test` (or "tested 0") as a pass — both are explicitly banned readings (per test-plan §4 → Mutation instrument).
- NEVER resolve a runner-dependent result by pinning to one runner, adding nextest `retries`, or serializing with `--test-threads=1` — that hides a shared-state/determinism defect instead of removing it at the cause (per test-plan §10 Zero-flakiness budget + §11 Integration/Quality/CI).
- NEVER promote the mutation run to a blocking CI stage, and NEVER merge or `cargo build --release` without `cargo audit --deny warnings` + `cargo deny check` green over a committed, un-drifted `Cargo.lock` (per test-plan §9 Scoped mutation audit + §11 CI).

## Contract bindings
- **tests ↔ security** — the dependency-delta basis for any new test-time dependency (escargot, or a new dev-dep edge) is security-plan's PACKAGE-COUNT basis plus `cargo deny` green over the NEW lock; test-plan §9/§10 binds the CI/quality side of the same fact (`cargo audit --deny warnings` + `cargo deny check` green, `Cargo.lock` committed and un-drifted, toolchain ≥ 1.94.1).
- **tests ↔ arch/route (verification matrix)** — `v2-25`'s `ref` names the parity test by source path; test-plan does not own `verification-matrix.json`, so if the test relocates, repairing that ref is a route/wrap-owned reconcile item, not a test-plan mandate.
- **tests ↔ obs** — untouched by this chunk: §3's 5-command surface, the `status` disk read, and the envelope/JSONL shapes must remain unchanged so §3 ↔ obs-plan §3 continue to agree (per test-plan §3). Any form that altered `CONDUCTOR_RUNS_DIR` handling or a harness command would re-open that binding.

## Acceptance criteria contributions
- (tests) `cargo mutants -p conductor-tauri --test-tool=nextest` (workspace-root `-f` paths, `--output` to a gitignored dir) completes against a PASSING unmutated tree with tested > 0, and the verdict is read from the `mutants.out/` tallies — `missed.txt` empty and every named survivor present in `caught.txt` — never from the exit code; a `Found 0 mutants to test` result is a no-op, not a pass (per test-plan §4 Unit Test Strategy → Mutation instrument).
- (tests) Every NAMED survivor for `conductor-tauri` ends killed or classified accepted-deliberate against a cited standing rule; no numeric `--fail-under` threshold is introduced (per test-plan §10 Mutation-survivor disposition).
- (tests) The parity test — wherever it lands — is green under BOTH `cargo nextest run -p <crate>` and `cargo test -p <crate>` on a FRESH target dir, with no runner pin, no `retries`, and no `--test-threads=1` (per test-plan §4 Framework runner-portability gate + §10 Zero-flakiness budget).
- (tests) `cargo clippy --workspace --all-targets -- -D warnings` is green over any new `[[test]]` target (plus its own `--features`-scoped clippy invocation if the target is feature-gated), and `cargo audit --deny warnings` + `cargo deny check` are green over a committed, un-drifted `Cargo.lock` (per test-plan §9 CI Integration pipeline + Live-Pulse/gated-leg lint rule + §10 Build failure conditions).
