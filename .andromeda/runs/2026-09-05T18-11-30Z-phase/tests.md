## Constraints
- **Disposition rule, not a score.** Every NAMED survivor in a chunk's mutation run ends either killed or classified accepted-deliberate against a cited rule; the accepted set is a SET recorded in §12, each member with its own citation, and a new acceptance EXTENDS that roster rather than contradicting it. Explicitly NOT a numeric `--fail-under` threshold — the score moves as a consequence, never as the acceptance (per test-plan §10 Mutation-survivor disposition). This governs W1's 41, W3's two timeouts, and W2's six.
- **Read-out gate, never the exit code.** Gate on the tallies in `mutants.out/`: `missed.txt` holding EXACTLY the run's accepted-deliberate survivors (empty only when none is accepted, since such a survivor by construction survives) plus every other named survivor present in `caught.txt`. The exit code carries no verdict in EITHER direction (a measured exit 3 on a fully-accepted run; a non-zero reflects surviving/timeout CLASSES), and `Found 0 mutants to test` is a NO-OP never a pass. `-f` resolves from the **workspace root** — a package-relative path under `-p` silently matches nothing; `--test-tool=nextest` is REQUIRED (per test-plan §4 Mutation instrument). W2's file-scoped `--file crates/conductor-core/src/obs.rs` re-run and W1/W3/W4a's per-unit re-runs all inherit this.
- **Mutation is an operator/local instrument, never a blocking CI stage**, run per-chunk against the crates the chunk touched — and §9's stage table is CI's complete inventory, not a chunk's (per test-plan §9 Scoped mutation audit). So the mutation evidence is chunk-acceptance evidence, not a new pipeline stage.
- **Runner portability is a standing gate.** The suite must be green under BOTH `cargo nextest run` and `cargo test -p <crate>`; only the shared-process runner exposes a test relying on nextest's per-test process for isolation, and a runner-dependent result is a determinism break to fix at the cause, never a runner to pin to (per test-plan §4 Framework + §10 Zero-flakiness). Binding on W5, which changes the test-binary topology.
- **Test placement.** Crate-local `#[cfg(test)] mod tests` inside each `conductor-<seam>` source file is the sanctioned unit home, with crate-local `tests/` for slower in-crate integration (per test-plan §4 Conventions and §2 Test directory conventions) — which is exactly the shape W5's split rule names. §11 Unit still bans asserting on private fns / internal struct fields, so a relocated test must keep asserting observable seam behavior (envelope / verdict / state / rendered output), not internals.
- **Zero-flakiness, including host-dependence.** No `retries`; a flake is quarantined and fixed at the root cause (per test-plan §10 Zero-flakiness). §12's 2026-09-04 precedent rejects a kill that lands host-dependently — "a roster is an enumerated set that must mean the same thing on every host" — which is the governing rule for W1's `[inferred]` `stdout_color` / `stderr_color` `IsTerminal` question and for any wall-clock bound W3 introduces.
- **Supply-chain gate.** `cargo audit --deny warnings` + `cargo deny check` (advisories/licenses/bans/sources) green, committed un-drifted `Cargo.lock`, toolchain ≥ 1.94.1, `tauri` ≥ 2.10.3 — a build-failure condition, and §11 CI bans merging or `--release` without it (per test-plan §9 Supply-chain audit stage + §10 Build failure conditions). W6's two-step probe sits on this.
- **Tool versions are floors, not pins** — the external-CLI tools named in §4 (cargo-nextest, cargo-llvm-cov, cargo-mutants) are reference floors; any install that runs the gate green satisfies it (per test-plan §4 Tool-version policy). The scope's jscpd 5.0.16 / cargo-mutants versions read as reproducibility choices under this rule, not as pins the plan mandates.

## Patterns to follow
- **rstest table-driven `#[case]` rows** for a discriminating input matrix (per test-plan §4 Fixture pattern + §7 Seed strategies) — the natural shape for W2's boundary-date set (epoch / month end / leap day / year edge), one case per date, so each arithmetic swap fails a named case rather than one fused assertion.
- **Exact-string `assert_eq!` unit goldens** for canonical rendered shapes, with insta reserved as the E2E/journal-golden mechanism in CI/assert mode, never `cargo insta review` (per test-plan §4 conductor-report bullet + §7 Golden artifacts). This is the pattern for W1's content assertions on the `[PASS]` / `[FAIL]` / `[HOLD]` / `[BLOCKED]` prefixes and caption/summary text, and for W4b's shared coverage formatter.
- **Own test binary per process-global-singleton consumer.** `cargo test` gives each `tests/*.rs` its own process and nextest is already process-per-test, so one file per such test holds under BOTH runners (per test-plan §11 Integration). Directly shapes W4c: a shared `tests/common/` *module* is fine, but `canary_obs_witness.rs` must not be folded into a sibling binary.
- **Bounded, injected time rather than real waits** — `#[tokio::test(flavor = "current_thread", start_paused = true)]` + `tokio::time::advance`, with DI of the stdio transport into the hand-rolled JSON-RPC client rather than runtime patching (per test-plan §2 Agent-runnable invariants + §8 Mocking libraries / Anti-monkey-patching). W3's "bounded await on the `connect_transport` duplex" should reach for this before a real-clock timeout.
- **Accepted-deliberate entries carry a cited rule and an evidence home** — the ledger enumerating the set is the citation home referenced from §12 (per test-plan §10 + §12 mutation-instrument entry, whose four members each name a rule and a chunk `evidence/` path). W1's new cli roster and W3's accepted timeout (if any) follow this shape.

## Anti-patterns to avoid
- **NEVER rely on nextest's per-test process to isolate a test from a process-global, first-install-wins singleton** (`conductor_core::init_observability` is the shipped case) — a per-test `TempDir` sink does not isolate it, and serializing (`--test-threads=1` / a profile knob) hides the defect instead of removing it (per test-plan §11 Integration). Binding on W4c and on any W5 test that moves into a new binary.
- **NEVER add retries or lower a gate to pass** — no nextest `retries` > 0, no lowering `--fail-under-lines 60`, no skipping a quality gate "just this once" (per test-plan §11 Quality + §10). A bounded await in W3 that flakes is a defect to fix, not a retry.
- **NEVER merge or `cargo build --release` without `cargo audit --deny warnings` + `cargo deny check` green and a committed un-drifted `Cargo.lock`** (per test-plan §11 CI, stack-specific). W6 closes a deferral against this ban — a RED at take-up or wrap is a new event, not a re-pin.
