## Relevance
Relevant — the chunk's deliverable is a test/gate over the artifact test-plan §3 owns (the run journal), plus a CARRY on the §3 `cleanup` verb.

## Constraints
- The journal's subject is TWO report-seam row shapes, and a typed parse must DISCRIMINATE them — the envelope line targeted specifically, never asserted over every line — per test-plan §3 Log format (Agent parsing), restated at §2 Agent-runnable invariants and §6 (headless scenario Verification signal). A `CheckRecord` line judged against envelope keys is a false negative by that rule.
- The no-absolute-host-path / no-internal-struct-name property is already MANDATED as a negative test on the journal, not new scope: test-plan §3 Log format (Required fields) and §3 Bootstrap phases → `log-format-bind-with-obs` require this plan to assert that boundary via a negative test; §3 Status endpoint shape adds that artifacts must not leak them. Whether such a negative test already exists at HEAD, and whether shipped rows already conform, are research's questions (the chunk's open questions 3 and 4).
- The envelope's field set and the per-check grain are contract, not gate-extensible — per test-plan §3 Status endpoint shape (per-check detail is a separate finer grain, "never an extension of the envelope"). A gate requiring a shape change is a finding, matching the chunk's own boundary.
- The gate must be hermetic and CI-safe: a live-Pulse leg is never a CI gate and is operator/local only (per test-plan §9 Live-Pulse scenarios + §11 CI), and no real network beyond the sanctioned loopback set (per §11 Universal).
- Any journal the gate reads must come from the sanctioned provenance SET — seeded generation, rstest fixtures, or a crate-local `tests/fixtures/` artifact seeded through the production reader/writer — and a committed fixture must carry its MEANING under test via a production round-trip; "developer pre-populates `runs.db`" stays banned (per test-plan §7 Self-bootstrapping requirement).
- Reported states are not process failures: `Blocked` / `ManualCheck` / `KnownResidual` / `CalibrationRegion` never map to a non-zero exit (per test-plan §11 E2E, stack-specific). A hermetic Blocked-run producer therefore exits 0 — the gate must go red on schema/redaction violation, not on the row's state.
- CARRY (`cleanup`): teardown must cover every table a run writes — `runs`, `run_check`, `run_envelope` — via BOUND parameters, be idempotent, and be verified by file-absence plus `SELECT count(*)` = 0 on each of the three (per test-plan §3 5-command `cleanup`, body + Idempotency + Verification). The bound-parameter rule is also a standing ban with a mandated negative/static test (per §11 Integration, stack-specific) — the shells' `sqlite3` interpolation is the tension the chunk must state rather than discover.

## Patterns to follow
- Envelope/journal assertion mechanism split: exact-string `assert_eq!` for the canonical line shape at unit tier; insta as the E2E journal-golden mechanism with `run_id`/timestamp redaction; insta in CI/assert (fail-don't-write) mode only (per test-plan §4 `conductor-report` bullet, §7 Golden artifacts, §5 Run report envelope bullet, which already pairs the golden with an artifact-sanitization assertion).
- Machine-parseable gate output: nextest `NextestExitCode` / `ci`-profile JUnit for a Rust-test home, `jq -e` over the journal for a shell/CI-step home (per test-plan §2 Agent-runnable invariants and §3 `status` command body).
- Existing producer precedent for the gate's subject: the `--e2e` leg seeds its own subject by invoking the `conductor-run` `envelope_fixture` test target under `CONDUCTOR_E2E_SEED_DIR`, writing through the production writer `conductor_run::persist` and throwing rather than seeding silently (per test-plan §3 CI stage selectors + §7). This is the plan-side candidate answer to the chunk's open question 2.
- Per-test isolation for a producer that writes run artifacts: `assert_fs::TempDir` + repo-relative `CONDUCTOR_RUNS_DIR` (a verb writing nothing sets the handle NOT AT ALL) (per test-plan §3 Test data bootstrap → Per-test isolation).
- Gate placement pattern: a CI stage whose non-green is a build failure, with §9's stage table stated as CI's complete inventory (per test-plan §9 Pipeline structure + Build failure conditions).

## Anti-patterns to avoid
- Conflating the self-obs stream schema with the per-run emission journal, or re-asserting/widening the existing self-obs gate — the two schemas "must not be conflated" (per test-plan §3 Log format → Self-obs stream is a distinct artifact).
- Building `runs.db` SQL by `format!`/string concatenation, or hand-populating `runs.db` as a fixture (per test-plan §11 Integration, stack-specific, and §7 / §11 Test Data) — both bear directly on the CARRY's two added deletes.
- Relying on nextest's per-test process to isolate a test from the process-global first-install-wins `init_observability` singleton; the remedy is a test binary of its own, never serializing (per test-plan §11 Integration, stack-specific).

## Contract bindings
- tests §3 Log format ↔ obs-plan §3: test-plan §3 is the SOURCE OF TRUTH for the journal format and obs derives its product-side envelope from it — "format break = harness break" — while the field-allowlist / redaction layer is the one piece owned by obs downstream, with this plan asserting that boundary via a negative test (per test-plan §3 Bootstrap → `log-format-bind-with-obs`). Standing discipline in this plan's amendment history: any §3 edit states explicitly whether §3 ↔ obs-plan §3 still agree.
- tests ↔ security: the artifact-sanitization mandate and the bound-parameter SQL rule are security-sourced and land in this plan as test obligations (per test-plan §3 Status endpoint shape, §1 closing note "artifact-sanitization discipline folds into the Run-report envelope golden tests", §11 Integration).
- tests §3 `cleanup` ↔ the harness contract file the scope cites (`.claude/rules/verification-harness.md` 5-command `cleanup`): the scope reports both already name all three tables, so this chunk's CARRY is the code half only.

## Acceptance criteria contributions
- The gate discriminates the two journal row shapes — envelope lines judged against the envelope's declared fields, `CheckRecord` lines against their own — and no assertion parses every line as one shape (per test-plan §3 Log format, Agent parsing).
- A negative assertion over both row shapes of `runs/&lt;run_id&gt;.jsonl` finds no absolute host path and no internal struct name, mirroring the single source of the host-path notion rather than minting a second (per test-plan §3 Log format, Required fields + §3 Bootstrap `log-format-bind-with-obs`).
- The gate runs from a hermetically produced journal (no live Pulse, loopback-only) and a seeded violation makes the build RED under the standing build-failure conditions, green-with-a-note being a fail (per test-plan §9 Build failure conditions + §9 Live-Pulse scenarios / §11 CI).
- (CARRY) `cleanup` verification passes with `SELECT count(*)` = 0 on `runs`, `run_check` and `run_envelope` plus journal/report file-absence, and a re-run against a clean state is a no-op (per test-plan §3 5-command `cleanup`).
