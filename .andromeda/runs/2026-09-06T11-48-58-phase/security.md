## Constraints
- The run journal is a governed ground-truth artifact: security-plan §Security Anti-Patterns → Logging requires that run-report artifacts — naming `<run_id>.md`, `runs.db` rows **and JSONL journals** — plus committed evidence records carry verdict/state/identity fields only and leak no absolute host paths (canonicalized `CONDUCTOR_*` directories, `ANDROMEDA_PULSE_DATA_DIR`) nor internal seam-crate struct names. This is the mandate the chunk's gate enforces; whether every shipped journal row already satisfies it is research's question (the scope's own open question 4).
- security-plan §Error Handling ("Run-report artifact sanitization") states the same duty positively and fixes the **blocked-row shape**: a `blocked` row populates only identity fields plus the named precondition string, with measurement fields JSON `null`. A schema-completeness assertion that treats a null measurement field as a missing key would contradict this mandate; the gate's completeness notion must be key-presence-with-null-allowed for those fields, not value-presence. Whether the shipped writer emits nulls vs. omitting keys is research's question.
- security-plan §Bootstrap phases (`error-sanitization-wire`) requires exactly this artifact-hygiene property as a wired boundary control, and §Security Anti-Patterns → Logging pairs "absolute host path" with "internal seam-crate struct name" as two distinct leaks. The scope records that the shipped host-path anchors do NOT flag `::` module paths — so the struct-name half is a SEPARATE assertion, not a free rider on the host-path check; whether either is covered at HEAD is research's question.
- CARRY / SQL surface: security-plan §Input Validation (`runs.db` writes row) and §Security Anti-Patterns → Input require **rusqlite bound parameters** — never `format!`/concatenated SQL — for `run_id`/`seed`/fingerprint writes in the `conductor-report` storage seam. That row's subject is the rusqlite seam; the plan carries **no boundary row for `sqlite3`-CLI statements in the harness shells**, so the two added `DELETE`s inherit no plan-sanctioned control other than the shells' existing `valid_run_id` / `Test-RunId` gate, which must remain applied to both. Whether that gap owes a plan amendment is a wrap-time question, not a licence to add an ungated interpolation.
- security-plan §Security Anti-Patterns → Logging bans writing journal/report wall-clock stamps from tokio's virtual clock (`SystemTime`/`Instant` only). This binds whichever hermetic journal producer P3 selects for the gate (open question 2): a paused-clock tokio test that mints journal rows would violate the ban and corrupt the ground-truth artifact the gate then judges.
- security-plan §Input Validation (env-var path handles row) + §Security Anti-Patterns → Input hold the `CONDUCTOR_*` path-handle namespace to three settled classes with class-specific controls (shipped-binary reader ⇒ `canonicalize` + bounds-check at the CLI edge; wdio-read host-tool ⇒ existence + `isFile` + metacharacter guard; test-binary-read constant ⇒ no-op when unset). The scope's "no new handle" boundary keeps that obligation closed; a fourth handle would owe both a new boundary row and its class's control.
- security-plan §Dependency Security requires `cargo audit` green and, for any dependency delta, `cargo deny check advisories bans licenses sources` VERIFIED green over the **new** `Cargo.lock`, with any new license/advisory taking the documented `deny.toml` accepted-exceptions mechanism (justifying comment) — never a silent accept. Applies if the gate pulls in a JSON-schema or assertion crate.

## Patterns to follow
- The CI obs-gate shape the scope cites (`.github/workflows/ci.yml:112-160`) — produce the artifact hermetically, then assert over it — is also the plan's sanctioned CI form: §Dependency Security ("CI integration") mandates adding steps to *the existing* workflow that already runs build/nextest/clippy, i.e. one workflow gaining a job/step, not a second workflow.
- Single-sourced redaction: the scope's `conductor-core::redact::is_host_path_token`, already mirrored by the CI obs-gate anchors, is the one host-path notion; §Security Anti-Patterns → Logging defines that class as the canonicalized `CONDUCTOR_*` directories + `ANDROMEDA_PULSE_DATA_DIR`, so the gate should bind to the shipped source rather than mint a second regex that could drift from the ban's scope.
- Scrub-then-write for committed records: security-plan §Input Validation (screen-reader speech-log ingest row) ships the precedent — host-path tokens rewritten to `<host-path>`, the row gaining a `security_finding`, asserted by a hygiene grep over the committed record. If this chunk commits a journal fixture or an evidence excerpt, that is the governing pattern.
- `resolve_under` against the resolved runs dir before any read of a `run_id`-class string, with an absolute candidate or `..` REJECTED (never clamped), per §Input Validation (`#[tauri::command]` IPC arguments row) — the shipped pattern for turning a run id into a journal path, should the gate resolve one.
- Read faults carry `e.kind()` only, never the path (§Input Validation, committed SUT-facing manifests row) — the plan's artifact-hygiene idiom for a file-read failure message, applicable to the gate's own "journal missing/unreadable" arm.

## Anti-patterns to avoid
- NEVER let a run-report artifact or a committed evidence record carry an absolute host path or an internal seam-crate struct name (§Security Anti-Patterns → Logging) — including any journal excerpt the gate's failure output writes into a committed record.
- NEVER build `runs.db` SQL by string concatenation/`format!` in the rusqlite seam (§Security Anti-Patterns → Input); the CARRY's two added shell `DELETE`s must not become a second interpolation class that skips the shells' existing run-id gate.
- NEVER paper over a real signal from a red gate — §Dependency Security's audit discipline ("never a `deny.toml` ignore … never a silent accept" for a transient fault; distinguishing cases "is what keeps a red gate honest") is the plan's stance the scope's open question 4 inherits: a red first run is a finding, not a licence to soften the assertion.

## Contract bindings
- **Host-path / redaction notion ↔ obs-plan**: the gate mirrors the same `conductor-core::redact` source the self-obs conformance gate uses; the security ban (§Security Anti-Patterns → Logging) and obs's scrubbing schema must name one host-path class, not two.
- **CI security gate ↔ tests §CI Integration**: per §Dependency Security ("CI integration"), the build-failing home belongs in the single existing workflow alongside the obs gate and the `cargo audit`/`cargo deny` steps — one workflow, gates as jobs/steps.
- **Fixture hygiene ↔ tests**: if P3 chooses a committed journal fixture (open question 2), §Security Anti-Patterns → Logging binds it — synthetic, host-path-free, struct-name-free, since it becomes an agent-parseable record shared across hosts.
- **Harness shells ↔ test-plan**: the CARRY's verification extends count-zero to all three tables; the security-relevant half is that both added statements stay behind `valid_run_id` / `Test-RunId` (§Security Anti-Patterns → Input, by extension of the bound-parameter ban's intent).
