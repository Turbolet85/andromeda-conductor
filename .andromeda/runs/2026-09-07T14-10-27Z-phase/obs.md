# obs extract

## Relevance
Relevant — the chunk's core mandate ("redacted, service-tagged JSON aligned to the obs-owned format", emitted from a CI gate) sits directly on obs-plan §3/§6 (format + identity + redaction) and §9 (CI integration).

## Constraints
- **Tier is Minimal — no SDK, no exporter, no metrics.** The gate's output must be stderr/file/console JSON only; introducing an OTel SDK, a meter, or any network OTLP export for a11y results is banned on every surface including the webview frontend (per obs-plan.md §1 Obs Scope Summary, §3 OTel SDK init, §11 Universal).
- **"The obs-owned format" is TWO record shapes, and the chunk must resolve which one it means.** §3 Log format JSON schema splits the self-obs base line (`timestamp_ms` · `level` · `target` · `service.name` / `service.version` / `deployment.environment` · `run_id`) from the eleven-field Run-report envelope (`journal_emitted_at` … `fingerprints`). a11y-plan §3 reproduces the ELEVEN-FIELD ENVELOPE verbatim as its violation schema while separately requiring service-identity tagging — so the chunk's "service-tagged JSON aligned to the obs-owned format" spans both shapes. Pinning the artifact to one shape without mixing them is required (per obs-plan.md §3 Log format JSON schema, two record shapes).
- **No new top-level fields.** §3's per-scenario extension point stands but has no known instance (its only ever-named one retired 2026-09-06); §6's additional-scenario-specific-fields list is empty. a11y's own contract folds axe rule-id + WCAG-SC tag + selector into `fingerprints[]` precisely to avoid new keys (per obs-plan.md §3 Log format JSON schema, §6 Log Coverage).
- **"Required" means KEY PRESENCE, not non-null.** The five measurement fields are `Option` and serialize as JSON `null`; a typed parse cannot distinguish absent from null, so key presence is asserted separately by a conformance gate (per obs-plan.md §6 Required fields).
- **Redaction has a specific shape and is Rust-side.** The value scrub masks absolute host-FILE paths (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace file paths) → `<redacted>`; internal struct names are excluded by the field-name allowlist plus `Display`-not-`Debug` at the `anyhow` edge — never blanket `::`-token redaction, and the allowlisted `target` module path is preserved, not a leak. The three enumerated application sites are all Rust (`conductor-core::redact` layer, report-write, runs.db insert); §11's standing warning is that the enumeration bounds only the sites it names. **Whether the web-plane (wdio/TS) a11y harness applies an equivalent host-path scrub — the Rust redact layer cannot reach it — is research's question** (per obs-plan.md §11 Logs, §11 PII Scrubbing).
- **CI artifacts are mandatory and must be agent-parseable; the gate fails the build on violation.** §9 requires the log file + machine-readable test output uploaded as CI artifacts with GitHub default (14-day) retention, downloadable + `jq`-parseable; on schema violation the CI check is marked FAIL (build gated). §10 lists the log conformance gate among build/deploy failure conditions (per obs-plan.md §9 Telemetry artifact handling + Log conformance check, §10 Build / deploy failure conditions).
- **CI resource attributes are specified.** `deployment.environment` = `dev` on all branch builds, plus `ci.run.id` (`github.run_id`) and `git.commit.sha` (`github.sha`); service identity is never hardcoded — `env!("CARGO_PKG_*")` with `$CONDUCTOR_SERVICE_NAME` / `$CONDUCTOR_ENV` override (per obs-plan.md §9 CI-specific resource attributes, §3 Service identity, §11 Universal).

## Patterns to follow
- **The existing §9 log-conformance gate is the template for a new JSONL gate:** read the artifact, validate the per-line schema, assert no absolute host-file paths, FAIL the check on violation. The 2026-06-27 amendment records that this gate asserts the §3 self-obs base schema — not the envelope — for `logs/agent-latest.jsonl`; a run-journal envelope gate is separately specified (per obs-plan.md §9 Log conformance check).
- **Detail that has no allowlisted field rides the `message` field, key names only, never values.** §6's boundary-call wrappers use this for the read-back key-set witness and the `emit.batch` wire-shape witness precisely because a non-allowlisted field name is dropped at the processor stage (per obs-plan.md §6 Boundary-call wrappers).
- **Service-identity + `run_id` on every line; envelope/result fields only on the scenario-result record.** The custom `tracing-subscriber` layer exists because stock `fmt().json()` cannot emit constant identity fields flat at top level (per obs-plan.md §3 Log format JSON schema).
- **The Tauri backend self-obs sink follows `CONDUCTOR_RUNS_DIR`:** file name `conductor-tauri.jsonl` fixed, directory = `<runs_dir.parent()>/logs/` — measured per a11y suite at `runs/logs/` (routine `--e2e` + `sr-empty`), `runs/driven/logs/`, `runs/sr-leg/logs/`. Any CI artifact-upload path must follow the suite's handle, not a literal project-root `logs/` (per obs-plan.md §3 Log file location).
- **`obs-ci-gate-wire` is the established bootstrap shape:** machine-readable test output + CI artifact upload of the JSONL (per obs-plan.md §3 Bootstrap phases).

## Anti-patterns to avoid
- Never wire an OTel SDK, `tracing-opentelemetry`/W3C `traceparent`, a metrics instrument, or any network OTLP export (`:4317` or `:4318`) into the a11y gate or its artifact path — recursion + `current_thread` determinism guard; correlation is the `run_id` field (per obs-plan.md §11 Telemetry Strategy, §11 Spans/Traces, §11 Universal).
- Never leak absolute host paths or internal struct names into the uploaded artifacts; never scrub only at the sink stage, and never hardcode the scrub in a single location (per obs-plan.md §11 Logs, §11 PII Scrubbing).
- Never lose the telemetry artifacts, and never leave the gate's verdict human-review-gated or non-machine-parseable — every signal needs an agent-readable consumption path (per obs-plan.md §11 CI, §11 Universal).

## Contract bindings
- **obs ↔ a11y (two-sided, the primary bind for this chunk):** obs §3/§6 owns the eleven-field envelope; a11y-plan §3 reproduces it verbatim as the violation schema and narrows (state = `Fail` when `violations.length > 0`; axe id/impact/tags/target folded into `fingerprints[]`). The 2026-06-16 amendment established that an envelope change lands on both masters together. This bind answers the chunk's open question 3.
- **obs ↔ a11y (identity tagging):** a11y-plan `:85`, `:202`, `:282`, `:476` require artifacts tagged `service.name` (`conductor-tauri` / `conductor-ui`) + `deployment.environment` (+ `ci.run.id` / `git.commit.sha`) "per obs Section 3" — obs-plan §3 Service identity and §9 CI-specific resource attributes are the authoritative side.
- **obs ↔ tests harness:** obs §9's artifact set (nextest JSON + `logs/agent-latest.jsonl`) is the CI-side twin of the tests harness contract; a11y-plan routes results out through tests' 5-command `logs` surface. Whether the new a11y job emits through that surface, and whether it uploads the suite's `conductor-tauri.jsonl`, is research's question.
- **obs ↔ security:** §11's sidecar-spawn ban is a cross-master citation of security-plan; the 2026-08-20 and 2026-09-04 amendments both record that it must move on both sides together.

## Acceptance criteria contributions
- (obs) The gate's violation artifact carries exactly the eleven envelope keys with no new top-level field, `state` = `Fail` when violations exist, and required asserted as KEY PRESENCE rather than non-null (per obs-plan.md §6 Log Coverage — Required fields / §3 Log format JSON schema).
- (obs) Every line/artifact the gate emits carries service identity (`service.name` / `service.version` / `deployment.environment`) + `run_id`, and under CI additionally `deployment.environment` = `dev`, `ci.run.id`, `git.commit.sha`, with identity resolved via env override rather than hardcoded (per obs-plan.md §9 CI-specific resource attributes / §3 Service identity).
- (obs) No absolute host-file path (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace paths) and no non-allowlisted / `Debug`-dumped field name appears in any artifact the job uploads or in the `conductor-tauri.jsonl` the suite produces; an allowlisted `target` module path is explicitly NOT a violation (per obs-plan.md §9 Log conformance check / §11 Logs).
- (obs) The job's telemetry artifacts — the suite's `<runs_dir.parent()>/logs/conductor-tauri.jsonl` plus the structured result JSON — are uploaded as CI artifacts, `jq`-parseable, and the CI check is FAIL/build-gated on schema or host-path violation; a run that produced no artifact must be distinguishable in the emitted JSON from a run that produced zero violations (per obs-plan.md §9 Telemetry artifact handling + Log conformance check / §11 CI "never lose telemetry artifacts" — bears on scope open questions 1 and 2).
