Partial — the WebDriver/WebView2 session mechanism is outside obs, but the a11y job's telemetry artifacts (obs-plan §9), the violation-record shape (§3), the Tauri self-obs sink location (§3), and host-path hygiene across probe refs and diagnostic captures (§11) all bind this chunk.

## Constraints
- obs-plan §9 (CI Integration → artifact table) registers the a11y violation record `runs/a11y/&lt;run_id&gt;.jsonl` as a CI artifact of the `a11y` job — uploaded via `actions/upload-artifact@v4` with `if-no-files-found: warn`, with conformance asserted **in-job** by `journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y`. A green job must exercise that row; whether the workflow at HEAD already wires all three parts is research's question.
- obs-plan §3 (Log format JSON schema → extension point) requires that record to carry the eleven envelope keys PLUS the §9 resource tags `service.name` (`conductor-ui`) and `deployment.environment` — 13 top-level keys locally, 15 under CI where `ci.run.id` + `git.commit.sha` join them — and requires the gate to assert key PRESENCE, closed sets and host-path freedom, never key exclusivity (that is what lets one gate serve both record shapes).
- obs-plan §9 (CI-specific resource attributes) requires `deployment.environment` = `dev` on branch builds, `ci.run.id` from `${{ github.run_id }}`, `git.commit.sha` from `${{ github.sha }}`. Any probe-ref edit or remedy that rewrites the a11y job's env block must preserve these three; whether the current job sets them is research's question.
- obs-plan §9 (Log conformance check) + §11 (Logs) require no absolute host-file path (drive-letter `X:\`, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace file paths) in any conformance-checked field. This is the obs-side twin of the chunk's binding probe-ref hygiene rule, and it bears directly on hypothesis 2: a `$RUNNER_TEMP`-derived `WEBVIEW2_USER_DATA_FOLDER` is a runner absolute path that must not reach a committed record or an uploaded conformance-checked artifact.
- obs-plan §3 (Log file location → Tauri backend) requires the backend self-obs sink at `&lt;runs_dir.parent()&gt;/logs/conductor-tauri.jsonl` — file NAME fixed, DIRECTORY riding `CONDUCTOR_RUNS_DIR`, stderr only as an open-failure fallback. Under the a11y job's `CONDUCTOR_RUNS_DIR=runs/a11y` that resolves to `runs/logs/`. Presence-vs-absence of that file is the backend-side witness of whether the Tauri process ever reached obs init under the driver; whether the job captures or uploads it is research's question.
- obs-plan §10 (Always-required SLO invariant) + §9 (Zero-unlogged-panics gate) require every panic to be captured as a structured `tracing::error!` event, with the gate grepping `^thread.*panicked` in `logs/agent-latest.jsonl` + stderr. The CARRY excludes app crash by measurement, but any probe that does surface a crash must produce a structured capture, not a raw backtrace.
- obs-plan §6 (Log levels mapping) governs **Conductor's own** stream only (`error` = unrecoverable, `warn` = recoverable). The decisive `session not created` line is wdio's, outside that mapping — no obs level semantics licence treating its `WARN` as non-decisive.

## Patterns to follow
- The a11y violation record is an already-registered instance of the §3 envelope extension point and the §9 artifact table (per obs-plan §3, §9) — extend/read that shape rather than authoring a new diagnostic record format for probe evidence.
- Boundary-witness pattern (per obs-plan §6 Boundary-call wrappers): where a consumer degrades to empty/ambiguous rather than erroring, log the observed KEY SET / wire-shape witness so "divergent" is distinguishable from "empty". Directly analogous to this chunk's failure mode, where "no session created" and "no spec output" present alike — the second SR-chunk fix (wdio RED output reaching the job log) is the same principle already applied.
- Allowlist escape hatch (per obs-plan §4 Coverage-matrix gate re-base and §6): any field name outside `conductor-core::redact::ALLOWLISTED_FIELDS` is dropped at the processor stage, so diagnostic detail rides the allowlisted `message` value rather than a new attribute name — the disqualifier that retired `degraded_mode_requested` and the coverage-gate attribute set.
- Sink-location-rides-`CONDUCTOR_RUNS_DIR` (per obs-plan §3 Log file location): the per-suite landing sites (`runs/logs/`, `runs/driven/logs/`, `runs/sr-leg/logs/`) are the established way to locate an a11y leg's backend log — never the bare project-root literal.
- Machine-parseable CI artifact + `jq` parse as the agent-access path for every uploaded telemetry artifact (per obs-plan §9 artifact table).

## Anti-patterns to avoid
- NEVER leak absolute host paths in logs, run-report artifacts or uploaded diagnostics (per obs-plan §11 Logs, §11 PII Scrubbing) — and §11 PII Scrubbing's standing warning explicitly holds that the three redaction application sites do NOT bound every host-path channel, which is exactly the class this chunk's probe trees, driver verbose logs and `a11y-session-diag` captures fall into (outside `conductor-core::redact` entirely).
- NEVER lose telemetry artifacts (per obs-plan §11 CI) — the diagnostic steps' `continue-on-error` / `if: always()` and the `if-no-files-found: warn` upload must survive any probe edit, so a RED probe iteration still yields its evidence rather than dying before upload.
- NEVER add a browser OTel SDK, a network OTLP exporter, or an export to `:4317`/`:4318` to the webview leg while diagnosing (per obs-plan §11 Universal + §1 desktop-webview row) — frontend self-obs is console JSON only; the recursion guard is not relaxed for diagnostics.

## Contract bindings
- **obs ↔ a11y:** the violation record at `runs/a11y/&lt;run_id&gt;.jsonl` is authored by the a11y gate but its key set is obs's envelope + §9 resource tags (per obs-plan §3 extension point, §9 artifact table).
- **obs ↔ tests harness:** `journal_conformance` is the tests-side gate; test-plan §3 owns the journal format, obs §3 reproduces it, and the gate's "key presence, not non-null / never exclusivity" semantics are what let one gate serve both the scenario record and the a11y record (per obs-plan §3, §6 Required fields).
- **obs ↔ security:** host-path/PII scrubbing binds security §Logging &amp; Monitoring at the redaction config (per obs-plan §11 PII Scrubbing); the chunk's probe-tree hygiene rule is the same invariant applied to a channel outside Conductor's redaction sites.
- **obs ↔ CI platform:** `ci.run.id` / `git.commit.sha` / `deployment.environment` are sourced from GitHub Actions contexts (per obs-plan §9 CI-specific resource attributes).

## Acceptance criteria contributions
- (obs) On a green a11y job, the violation record `runs/a11y/&lt;run_id&gt;.jsonl` uploads as a CI artifact and in-job `journal_conformance` passes under `CONDUCTOR_RUNS_DIR=runs/a11y` (per obs-plan §9 CI Integration — artifact table).
- (obs) That record carries the eleven envelope keys plus `service.name` = `conductor-ui` and `deployment.environment`, with `ci.run.id` + `git.commit.sha` joining them under CI (15 top-level keys), asserted as key PRESENCE and closed sets, never key exclusivity (per obs-plan §3 Log format JSON schema — extension point).
- (obs) No absolute host-file path (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`) appears in any pushed probe tree, uploaded diagnostic artifact, or conformance-checked record — including any `$RUNNER_TEMP`-derived `WEBVIEW2_USER_DATA_FOLDER` value if hypothesis 2 is taken (per obs-plan §9 Log conformance check + §11 Logs / PII Scrubbing).
- (obs) Every probe iteration, green or red, still uploads its diagnostic artifacts — the `if: always()` isolation step and the `a11y-session-diag` upload survive each edit (per obs-plan §11 CI "NEVER lose telemetry artifacts").
