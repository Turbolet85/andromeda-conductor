## Constraints
- The chunk lands no workspace-crate code: `.github/workflows/` is the registered home for GitHub Actions and the nine-member crate roster is closed here — no new member, no crate edge (per architecture.md §Infrastructure Patterns directory tree · §Occupied Resources Crate names). The scope's "no scenario, crate or contract change" is consistent with this.
- The `a11y` job's `runs-on: windows-2025` label is **explicitly pinned rather than floating, so a `-latest` move cannot change the Edge driver the leg resolves from the image**; an install step must not alter the label or the Windows-runner premise (per architecture.md §Infrastructure Patterns — Build system · §Established Decisions [CI/CD]).
- A CI gate that can report success by skipping is banned — that is the stated reason `CONDUCTOR_A11Y_STRICT` exists (an unresolved handle exits NON-ZERO under an affirmative declaration, and strictness is an ADDED arm over the existing guards, never a relaxation) (per architecture.md §Occupied Resources — `CONDUCTOR_A11Y_STRICT`). Whether the `a11y` job already declares it affirmatively is research's question.
- Any env name a committed workflow SETS or READS must be registerable under one of the recorded handle-class bases and makes **no `CONDUCTOR_*` namespace claim** — that namespace is reserved for handles over artifacts/concepts arch itself defines (per architecture.md §Occupied Resources — Environment variables). The registered `WEBVIEW2_USER_DATA_FOLDER` / `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` pair's registered lifetime is explicitly "that one `continue-on-error` diagnostic step"; an install step that changes machine-wide runtime state sits outside that recorded lifetime and needs its own registration at wrap.
- Runner-process variables must be resolved in the **step shell**, never through `${{ env.* }}` — that expression context holds only workflow/job/step declarations, and resolving `EDGEWEBDRIVER` there yielded an empty base and a literal `\msedgedriver.exe` (per architecture.md §Occupied Resources — `EDGEWEBDRIVER`).
- The absorbed PREREQ gates are governed by Build system: `cargo nextest` is the pinned runner driven through the **zero-retry `ci` profile** in `.config/nextest.toml` (no retries mask flakes — the determinism invariant), and `tauri-build`'s `generate_context!` resolves `build.frontendDist` (`ui/dist`) at COMPILE time, so `npm run build` / `ensure_frontend` MUST precede any workspace `cargo build`/`nextest`/`clippy` that compiles `conductor-tauri` (per architecture.md §Infrastructure Patterns — Build system).
- The riding supply-chain pin is measured the arch way: both runners green over the un-drifted lock, and the advisory-db checkout's `git status --porcelain` is read BEFORE any parse failure is classified external (per architecture.md §Infrastructure Patterns — Build system).
- No shipped Conductor binary gains a network surface from this work — Conductor exposes no HTTP/network service of its own and its only sanctioned bind is the port-occupier fault; a bootstrapper download is CI-runner-scoped only (per architecture.md §Cross-cutting Patterns — Trust boundary · §Stack Backend framework N/A).

## Patterns to follow
- The `EDGEWEBDRIVER` step's precondition shape: print the handle **NAME plus a boolean** (`Test-Path`), never the path/value, and exit non-zero when it does not resolve — the model a signature gate should copy (architecture.md §Occupied Resources — `EDGEWEBDRIVER`).
- Diagnostic-vs-gate separation as already recorded: the WebView2 session-isolation step is `continue-on-error` and decides nothing, and its two handles are set-then-cleared within that one step so probe (b) sees unmodified behaviour (architecture.md §Occupied Resources — WEBVIEW2_* pair).
- Claims recorded with run ids and an owning route entry: [CI/CD] states the a11y job is RED "as measured at runs 34157101273 · 34158355397 · 34160378753 · 34162118841", names what it reached and what it did not, and names the owner — the shape this chunk's verdict record should take either way (architecture.md §Established Decisions [CI/CD]).
- Validated-at-the-edge, array-form, fixed-argv invocation with no shell interpolation of an operator/host-supplied path — the shared `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` handling pattern (architecture.md §Occupied Resources — Environment variables).
- Windows-runner checkout discipline: `.gitattributes` is treated as a gate-correctness control because every CI job runs on a Windows runner where `core.autocrlf=true` is the norm (architecture.md §Infrastructure Patterns — Build system).

## Anti-patterns to avoid
- Green-by-suppression: a **gate** step gaining `continue-on-error`, or an unresolved handle skipping at exit 0 while the job claims strictness (architecture.md §Occupied Resources — `CONDUCTOR_A11Y_STRICT`).
- Reintroducing a floating runner label for the `a11y` job — the explicit `windows-2025` pin is what holds the image's driver/runtime axis still (architecture.md §Infrastructure Patterns — Build system).
- Reading `--all-targets`' ban as applying here: it is banned only in the standalone **per-member** build sweep (it re-unifies dev-dependencies, the exact masking that sweep catches) — the PREREQ's workspace `cargo clippy --workspace --all-targets` is a different command and is not covered by that ban (architecture.md §Established Decisions [Module Boundaries]).

## Contract bindings
- **arch ↔ tests/obs:** `runs/a11y/&lt;run_id&gt;.jsonl` is asserted by `conductor-run`'s `journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y` — the eleven-field run-report envelope plus obs resource tags, **13 top-level keys locally, 15 under CI** (`ci.run.id` + `git.commit.sha`), key-PRESENCE not key-exclusivity (architecture.md §Occupied Resources — On-disk artifacts · §Standard Contracts Run report envelope). §Infrastructure Patterns — CI/CD approach requires the conformance gate and the artifact upload to be described as job WIRING that has never executed in CI; if the 152+ probe carries the job past session creation, that characterisation becomes amendable at wrap — whether the run actually reaches those stages is what the probe measures.
- **arch ↔ security:** the env-handle registry is arch's, but the signature-gate's own discipline (validate before execute, never interpolate a downloaded path into a shell) is security-plan's; arch only requires that whatever the workflow sets/reads be registerable and namespace-clean (architecture.md §Occupied Resources — Environment variables).
