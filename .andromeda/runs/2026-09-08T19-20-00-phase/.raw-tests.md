# tests extract

## Relevance
Relevant — this is a CI-workflow chunk touching the `a11y` job that test-plan §9 owns, plus a non-deferrable workspace test/lint gate absorbed from the prior chunk's PREREQ.

## Constraints
- The `a11y` job's GATE step must never carry `continue-on-error`; only the pre-existing *diagnostic* steps may. Per test-plan §9 (Pipeline structure → E2E webview row), "a gate that can report success by skipping or erroring is the thing the strict arm exists to forbid" — so a runtime-install step placed on the gate path inherits the gate rule, and a failed/unsigned install must fail the step rather than warn-and-proceed (which also satisfies the scope's signature-gate requirement in test-domain terms).
- The mandatory Test Commands are the §9 stage commands, not chunk-scoped variants: Lint = `cargo clippy --workspace --all-targets -- -D warnings` (+ `cargo fmt --check`), Unit = `cargo nextest run --workspace --profile ci` (per test-plan §9 Pipeline structure; §3 `run` CI stage selectors records that `--unit` ⇒ the nextest leg ONLY — doctest and clippy are separate §9 stages, never folded into `--unit`).
- The supply-chain gate rides in the **bare** form: `cargo audit` + `cargo deny check` green over a committed, un-drifted `Cargo.lock`, per test-plan §9 (Supply-chain audit row) and §11 CI. The `--deny warnings` variant was retired plan-wide (see amendment history below) — a chunk re-adding it re-breaks the gate by construction.
- The `a11y` job must stay Pulse-free: test-plan §11 CI (stack-specific) bans running any live-Pulse leg as a CI gate, and §9 (Live-Pulse scenarios) confines the live legs to `workflow_dispatch`/`scripts/agent-run.{sh,ps1}`/feature-gated targets/`a11y:driven`. The chunk's "No Pulse dependency" boundary is the same rule stated from the plan side.
- CI jobs are identified BY NAME, never by `ci.yml` line coordinates — test-plan §9 (Matrix builds, OS bullet) states coordinates "move as the workflow grows". The scope names `:263` / `:314` / `:337-352`; anchoring the new step's placement by *step name* rather than line number is what §9 requires.
- A green must not be manufactured by repetition: test-plan §10 (Zero-flakiness budget) forbids nextest `retries` &gt; 0 and classes a runner-dependent result as a determinism break "to fix at the cause, never a runner to pin to". If the endpoint opens only intermittently under 152+, that is a recorded conditional measurement, not a pass.
- Whatever the probe measures must be recorded as a member of the measured runtime × driver **PAIR set** that §6 (Drivers per surface → desktop-webview Mode cell) and §9 (Matrix builds) already carry — never as a substituted fresh literal. §9 currently frames "whether installing WebView2 Runtime 152+ in-job changes it" as OPEN and owned by a follow-up route entry, so this chunk's result is the datum those sites are waiting on (whether the shipped `ci.yml` already prints the runtime version before and after is research's question).

## Patterns to follow
- The a11y job's existing step shape per test-plan §9 (E2E webview row): `agent-run.ps1 run --e2e` → the reused `journal_conformance` gate over `runs/a11y` → `actions/upload-artifact@v4`, plus `continue-on-error` DIAGNOSTIC steps and an `if: always()` `a11y-session-diag` upload. The step set is explicitly open (amended 2026-09-07), so a new install step joins it without contradicting the plan.
- Capture-then-print, then assert the PRINTED verdict rather than the process exit — test-plan §3 (`run` → `--e2e` CI stage selectors). The same clause records that a PowerShell caller setting `$PSNativeCommandUseErrorActionPreference = $true` preempts the capture-then-print and destroys the verdict; a new PowerShell step in this job must not reintroduce that setting into the gate path.
- Evidence-by-artifact: the `if: always()` diag upload (§9 E2E row) is the established mechanism for making a probe's decisive output readable off the runner — the `[diag] (a)` line and the before/after registry version belong there.
- Measured-set naming over literals: §6's Mode cell already records passing/failing pairs as sets (and §9's Matrix builds states the hosted-image finding as *driver-independent*, measured at runtime 151.0.4129.101). Extending that set is the shipped pattern for a new measurement.

## Anti-patterns to avoid
- NEVER skip quality gates "just this once" and NEVER lower/suppress a gate to pass the build (test-plan §11 Quality) — a `continue-on-error` on any gate step, or a signature check that warns and proceeds, is that ban.
- NEVER merge or release-build without `cargo audit` + `cargo deny check` green and an un-drifted committed `Cargo.lock` (test-plan §11 CI, stack-specific).
- NEVER ignore or retry a flaky result (test-plan §11 CI + §10) — quarantine and fix at the cause; no nextest `retries`.

## Contract bindings
- **tests §3 ↔ obs-plan §3** — the harness log-format/envelope bind. test-plan §3 requires that the five-command surface, the `status` disk read and the envelope/JSONL shapes stay untouched; §3 also records `runs/a11y/&lt;run_id&gt;.jsonl` as a SEPARATE shape deliberately outside the harness's non-recursive `"$RUNS_DIR"/*.jsonl` glob. A CI-only chunk owes no change here — the requirement is that it introduce none.
- **tests §9 a11y CI gate ↔ a11y-plan** — the a11y assertions run inside this same `a11y` job (`--e2e` → `accessibility.e2e.ts`, `CONDUCTOR_A11Y_STRICT` strict arm per §9/§1); whether the runtime change makes the axe/token assertions reachable is the a11y domain's claim, gated by this job's plumbing.
- **tests §9/§11 supply-chain ↔ security-plan** — `cargo audit` + `cargo deny check` are the shared workflow gate the standing external-decay pin rides.

- (tests) No step on the `a11y` job's gate path carries `continue-on-error`, and the job reports RED while the cause is open (per test-plan §9 Pipeline structure → E2E webview row; §11 Quality).
