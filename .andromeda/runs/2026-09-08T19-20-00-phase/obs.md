## Constraints
- The `a11y` job is a registered obs telemetry surface: obs-plan §9 (CI Integration → telemetry-artifact table) requires `runs/a11y/<run_id>.jsonl` uploaded via `actions/upload-artifact@v4` (`if-no-files-found: warn`) **and** conformance asserted in-job by `journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y`. A step inserted ahead of the diagnostics must leave both intact and must not land between the record-producing step and its assertion (per obs-plan §9).
- obs-plan §11 (Obs Anti-Patterns → CI) requires that telemetry artifacts are never lost and that the zero-unlogged-panics + log-conformance gates are never skipped — "all CI runs must pass `cargo-nextest` + log conformance + panic-hook verification". This is the obs-side backing for the PREREQ's mandatory `cargo nextest` / `cargo clippy`: obs's gate set is not suspendable by a chunk's source-delta size (per obs-plan §11 CI).
- obs-plan §9 (Log conformance check) requires every checked line to carry the §3 self-obs base schema (`timestamp_ms`, `level`, `target`, `service.{name,version}`, `deployment.environment`, `run_id`) and to carry **no absolute host-file path** (drive-letter `X:\`, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`) in any field. An install step introduces new runner-absolute paths (download dir, bootstrapper, registry values) into the job; nothing reaching a conformance-checked artifact may carry them (per obs-plan §9 + §11 Logs).
- obs-plan §3 (Log file location) requires the Tauri backend to write `conductor-tauri.jsonl` under `<runs_dir.parent()>/logs/` **unconditionally**, with stderr only as an open-failure fallback and the directory riding `CONDUCTOR_RUNS_DIR`. If probe (a)'s bare-app launch starts the backend, that file is a required app-liveness witness independent of `DevToolsActivePort` — decisive for this chunk's "app stayed alive but no endpoint" reading. **Whether the existing probe step already produces, captures or uploads that file is research's question** (per obs-plan §3 Log file location).
- obs-plan §3 (Log format JSON schema → extension point) + §9 (CI-specific resource attributes) require the a11y violation record to carry the eleven envelope keys **plus** `service.name` (`conductor-ui`) and `deployment.environment`, joined under CI by `ci.run.id` (`${{ github.run_id }}`) and `git.commit.sha` (`${{ github.sha }}`) — 13 keys locally, 15 under CI. If the 152+ runtime lets the routine arm reach a session and emit a record for the first time under CI, that key set is the shape required (per obs-plan §3 + §9).
- obs-plan §10 (Build / deploy failure conditions) names an unlogged panic and a conformance violation as build-failing conditions; obs-plan §11 (SLO) forbids soft, non-enforcing budgets. A gate step made non-failing erases a declared failure condition — obs's independent backing for the chunk's own no-`continue-on-error` boundary (per obs-plan §10 + §11 SLO).

## Patterns to follow
- **Diagnostic-vs-gate separation is already obs's own model** — §9 gates (log conformance, zero-unlogged-panics) FAIL the build, while §9's pipeline-stage table treats clippy output as agent-readable annotation. `continue-on-error` on a diagnostic is consistent with that split; on a gate it is not (per obs-plan §9 + §11 CI).
- **In-job assertion before artifact upload** — the a11y gate's shipped shape (assert with `journal_conformance` in-job under a scoped `CONDUCTOR_RUNS_DIR`, then upload with `if-no-files-found: warn`) is the established pattern for adding anything to this job; new steps precede the record-producing step rather than splitting that pair (per obs-plan §9 artifact table).
- **Agent-readable one-line output** — obs-plan §2 (Agent-readable invariants) and §11 (Universal) require every signal to have a machine-parseable consumption path with no human-review-gated reading; the before/after runtime-version prints and the `[diag] (a)` verdict line should stay greppable single lines so the run log alone establishes which major ran (per obs-plan §2 + §11 Universal).
- **Panics surface structured, not raw** — obs-plan §9 (Zero-unlogged-panics gate) greps `^thread.*panicked` in `logs/agent-latest.jsonl` + stderr; a bare-app launch on the runner that dies must appear as a `tracing::error!` JSON event, not an unstructured backtrace (per obs-plan §9 + §11 Error Reporting).

## Anti-patterns to avoid
- Never suppress or drop an obs CI gate or its artifact to get a green job — `NEVER lose telemetry artifacts` and `NEVER skip zero-unlogged-panics gate` (per obs-plan §11 CI).
- Never let a runner-absolute path reach a conformance-checked artifact or the committed evidence file; obs-plan §11 (PII Scrubbing) carries a standing warning that the three redaction application sites **do not bound every host-path channel** — a diagnostic or probe-verdict echo is exactly that class (per obs-plan §11 PII Scrubbing + §11 Logs).
- Never reach for a browser-side exporter, OTel JS SDK or `:4318` to observe the webview while chasing the DevTools endpoint — frontend self-obs is console JSON only; the only OTLP Conductor speaks is the PRODUCT stream at `:4317` (per obs-plan §11 Universal + §3 OTel SDK init).

## Contract bindings
- **obs §9 ↔ a11y plan** — the a11y violation record is a11y-emitted into obs's structured format; §9 owns its artifact handling + resource tags, a11y owns the violation content. Both sides describe the same `runs/a11y/<run_id>.jsonl`.
- **obs §9 ↔ tests §3** — `journal_conformance` is the tests-owned gate asserting key PRESENCE, closed sets and host-path freedom (never key exclusivity, which is what lets one gate serve both the 11-key scenario record and the 13/15-key a11y record); obs §3 reproduces the format the test plan owns. The PREREQ's mandatory `cargo nextest` also feeds the §9 cargo-nextest JSON artifact row.
- **obs §11 ↔ security plan** — the host-path / sidecar-spawn bans are cross-cited on both sides and must move together if either is amended.
