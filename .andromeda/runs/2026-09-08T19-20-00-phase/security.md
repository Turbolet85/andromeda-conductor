## Constraints
- The signature check must be a **terminal gate**, not an advisory line: a non-`Valid` / non-Microsoft-signer `Get-AuthenticodeSignature` result must stop the step with a non-zero exit *before* the bootstrapper executes. The plan's governing shape is the never-silently-downgrade discipline — a failed precondition surfaces as its own distinct blocking state, never degraded to a pass (per security-plan §Security Anti-Patterns → Universal, never-silently-downgrade bullet), and the same `a11y` job's existing CI arm already sets the precedent of **exiting non-zero rather than skipping at exit 0** (per §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row, CI-producer clause).
- The fetch is the project's first **non-loopback egress** in a job step: TLS verification must stay on and the URL must be HTTPS — no `-SkipCertificateCheck`, no plaintext `http://` (per §Security Anti-Patterns → Data Protection, "NEVER disable TLS verification or downgrade to plaintext on any surface that is ever promoted beyond loopback"). Whether any existing `a11y` step already performs a non-loopback fetch is research's question (the only fetch I see is loopback).
- Executing the downloaded bootstrapper is a **spawn**: fixed program at a workflow-derived path, fixed silent-install argv, never assembled into a shell string, never `Invoke-Expression`, nothing operator-supplied anywhere in the vector (per §Security Anti-Patterns → Code Patterns rule (b), whose "in every form an operator-supplied VALUE appears only as a separate element of an array-form argv" universal binds every governed form).
- Rule (b) is a **verbatim count of governed forms** (currently five) that goes stale on every addition; whether a CI-step installer execution is a sixth governed form — i.e. a boundary widening requiring registration — is a wrap-time Expected-amendment question, never a phase edit (per §Security Anti-Patterns → Code Patterns; amendment `2026-09-06-run-report-envelope-conformance-gate`).
- The standing supply-chain pin rides this chunk: `cargo audit` green **and** the `cargo deny check advisories bans licenses sources` overlap green over an **undrifted, committed `Cargo.lock`** (per §Security Anti-Patterns → Universal, audit-green + no-lock-drift bullets; §Dependency Security, CI integration). The scope declares no crate change, so the "new dependency under a red audit" conditional stays disarmed (regime CLOSED per §Dependency Security).
- If the audit goes red, the **`git status --porcelain` probe on the local `${CARGO_HOME:-$HOME/.cargo}/advisory-db` checkout PRECEDES** classifying the failure as external; never a `deny.toml` ignore, never a CI edit, never a silent accept (per §Dependency Security, two-external-decay-faults block as re-adjudicated 2026-09-05).
- The chunk's committed `chunks/{marker}/evidence/` verdict must carry **no absolute host path** (drive letter, `%APPDATA%`, `/Users`, `/home`) and no internal seam-crate struct name — committed evidence records are named explicitly in the ban and are agent-parseable ground truth shared across hosts (per §Security Anti-Patterns → Logging; §Error Handling, run-report artifact sanitization). Whether the existing `[diag]` lines the verdict will quote are already path-free is research's question.
- The added step must not become a second producer or reader of `CONDUCTOR_MSEDGEDRIVER`, and must leave the existing precondition arm and the `wdio.conf.ts` `UNSAFE_PATH` guard byte-unchanged — the plan records `wdio.conf.ts` as the **sole reader and sole guard site**, with the CI arm an ADDED arm and never a relaxation (per §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row).

## Patterns to follow
- Handle-named boolean precondition idiom already in this job at `D:/dev/projects/conductor/.github/workflows/ci.yml:290-298` — prints `[precondition] CONDUCTOR_MSEDGEDRIVER: resolved` / `NOT RESOLVED` and exits 1, i.e. **handle NAME + state, never the resolved path**. The install/signature step's own output should mirror it (signer, status, version — not the download path).
- The versions diagnostic at `ci.yml:263-283` reads the EdgeUpdate registry key and prints a **version string only**; version strings are outside the host-path ban, so the required before/after runtime-major observable can be printed as-is.
- Diagnostic-vs-gate separation is already expressed structurally: `continue-on-error: true` appears only on the two diagnostic steps (`ci.yml:265`, `ci.yml:315`). The install + signature steps are gates and must carry neither `continue-on-error` nor `-ErrorAction SilentlyContinue` around the signature evaluation.
- Supply-chain gate shape already in the same workflow at `ci.yml:86-90` (`cargo audit`; `cargo deny check`) — the two-tool overlap §Dependency Security mandates; the chunk's mandatory gates ride these existing steps rather than new ones.

## Anti-patterns to avoid
- A signature check that logs a warning and proceeds (or is wrapped so it cannot fail the step) — that is exactly the silent-downgrade class (per §Security Anti-Patterns → Universal).
- Disabling certificate validation or fetching the bootstrapper over plaintext HTTP (per §Security Anti-Patterns → Data Protection).
- Building the download or install invocation as an interpolated shell string / `Invoke-Expression` rather than a fixed program with a fixed argv (per §Security Anti-Patterns → Code Patterns rule (b)).
