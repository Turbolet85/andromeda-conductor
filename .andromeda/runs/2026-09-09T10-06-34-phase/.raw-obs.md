## Relevance
Partial — the fmt gate itself is build-time and explicitly Not-instrumentable (per obs-plan §1 Obs Scope Summary, instrumentation-scope row "cargo build / CI/CD pipeline"), so obs contributes preservation constraints on `.github/workflows/ci.yml` and on the instrumented source the pass rewrites, not new instrumentation.

## Constraints
- The fmt gate requires no spans, logs, or metrics of its own: obs-plan §1 (instrumentation-scope table, `cargo build / CI/CD pipeline` row) classes the GitHub Actions pipeline Not-instrumentable — build-time verification that "does not run at runtime". A formatting check is in the same class as the `cargo build` / nextest / clippy steps already listed there.
- obs-plan §9 CI Integration places a fmt check in the existing **Lint / typecheck** pipeline stage (the row that today names `cargo clippy` warnings → stderr → CI annotations for agent parsing). The scope's open premise "which CI job hosts the fmt gate" resolves obs-side toward that stage; §9 does not mandate a separate job.
- obs-plan §9 requires the telemetry artifacts to survive every CI run — `logs/agent-latest.jsonl` on every CI job, and the a11y violation record `runs/a11y/&lt;run_id&gt;.jsonl` via `actions/upload-artifact@v4` with `if-no-files-found: warn`. A fmt step whose failure aborts a job before those uploads would breach this. Whether `ci.yml` today actually carries those uploads, and whether the fmt step would sit upstream of them, is research's question.
- obs-plan §9 requires two obs CI gates to keep running: the log-conformance check (validating the §3 self-obs base-line schema and absence of absolute host-file paths) and the zero-unlogged-panics gate (grep for `^thread.*panicked`). Adding a step must not reorder or short-circuit either. Whether the workflow already implements both is research's question.
- The pass rewrites files in the crates that carry obs surface: `conductor-verify` (110 sites — the `verify.readback*` spans and the allowlisted `mcp_tool` attribute), `conductor-emit` (51 — `emit.batch` / `emit.logs_batch`), `conductor-run` (64 — the fault-span per-phase hook and `journal_conformance`), `conductor-core` (4 — where `obs.rs`'s `JsonObsLayer` and `redact::ALLOWLISTED_FIELDS` live). obs-plan §11 (Spans / Traces) fixes the bounded span-name set and obs-plan §11 (PII Scrubbing) fixes the single-location field allowlist; a formatting-only diff must leave every one of those string literals byte-identical in meaning.
- obs-plan §10 (Build / deploy failure conditions) enumerates the gating conditions (unlogged panic, log-conformance, `cargo-audit`, `cargo-llvm-cov --fail-under-lines 60`, clippy-as-annotation). A fmt gate is an addition to that list, not a substitution for any entry — notably it does not change clippy's non-blocking-at-Minimal status.
- obs-plan §11 (Universal) requires every CI signal to have an agent-readable consumption path. `cargo fmt --check`'s `Diff in &lt;file&gt; at line N` output satisfies this from the CI log; no human-only surface may be the sole failure report.

## Patterns to follow
- **Lint-stage colocation** (per obs-plan §9, Pipeline integration table): the fmt check joins clippy in the Lint / typecheck stage, with its diff going to the job log as CI annotations for agent parsing — the same consumption model §9 already specifies for clippy.
- **In-job conformance assertion** (per obs-plan §9, artifact table, a11y row): the established in-repo shape for an obs-adjacent CI gate is an assertion run *inside* the job (`journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y`) alongside an `actions/upload-artifact@v4` upload. A new gate step should mirror that step-shape rather than invent a new job wrapper.
- **Artifact-preserving step order** (per obs-plan §9 + §11 CI): telemetry uploads are unconditional per §9 ("every CI job"); a fail-fast lint step belongs either before any artifact-producing work or after it with the upload guarded so failure does not drop artifacts.
- **Bounded-set discipline on instrumented source** (per obs-plan §11 Spans / Traces): span names are a closed enumeration (`scenario.run`, `timeline.execute*`, `emit.batch`, `emit.logs_batch`, `verify.readback*`, `report.generate`, `db.insert_run`, `fault.silence/ramp/port_occupier`, `tauri.command.*`); the Tauri handlers additionally use a manual `tracing::info_span!(...).entered()` guard because `#[tracing::instrument]` does not stack with `#[tauri::command]` (per obs-plan §1 desktop-webview row) — a formatting rewrite of `conductor-tauri` (10 sites / 2 files) must not disturb that guard form.

## Anti-patterns to avoid
- NEVER lose telemetry artifacts and NEVER skip the zero-unlogged-panics gate (per obs-plan §11 CI) — a fmt step positioned so its non-zero exit preempts the log-file / a11y-record uploads or the two obs gates violates both bans.
- NEVER let a hand-edit ride the formatting diff that renames a span, a span attribute, or an allowlist field name (per obs-plan §11 Spans / Traces bounded span-name set; §11 PII Scrubbing single-location `conductor-core::redact` ownership) — a non-allowlisted attribute name is silently dropped at the processor stage, so such a drift fails invisibly.
- NEVER route the fmt gate's own output into a telemetry artifact or the self-obs stream (per obs-plan §11 Logs / §9 log-conformance check, which fails any line carrying a drive-letter / `/home` / `/Users` host path) — rustfmt's `Diff in &lt;path&gt;` lines carry absolute host paths, acceptable in a CI step log, disqualifying inside `logs/agent-latest.jsonl` or an uploaded record.

## Contract bindings
- **obs §9 ↔ tests §9 Lint row** (`.andromeda/test-plan.md:455`, which the scope records as already naming `cargo fmt --check` beside clippy): tests owns the CI gate row; obs §9's Pipeline-integration Lint stage is the obs-side twin. The scope's ruling that `:455` is left standing and made TRUE means no obs-side edit is implied either.
- **obs §9 ↔ a11y CI gate**: the a11y job's violation record `runs/a11y/&lt;run_id&gt;.jsonl` is registered in obs §9's artifact table (upload + in-job conformance). The scope holds the a11y job's open questions out of scope; obs's binding is only that the added step must not perturb that job's upload or in-job assertion.
- **obs §11 PII Scrubbing ↔ security §Logging &amp; Monitoring**: the host-path redaction contract is cross-master and moves on both sides together (per obs-plan-amendments, 2026-08-20 and 2026-09-04 entries). A formatting-only pass over `conductor-verify/src/spawn.rs` and `conductor-core::redact` must not alter it; if the pass is truly rustfmt-byte-identical, no cascade is triggered.

## Acceptance criteria contributions
- (obs) The fmt pass leaves the bounded span-name set and `conductor-core::redact::ALLOWLISTED_FIELDS` unchanged in content — no span-name, span-attribute, or log-field string literal differs from HEAD other than by rustfmt whitespace/ordering (per obs-plan §11 Spans / Traces and §11 PII Scrubbing).
- (obs) The added CI step does not remove, reorder past, or gate out the §9 telemetry artifact uploads (`logs/agent-latest.jsonl`; `runs/a11y/&lt;run_id&gt;.jsonl` via `actions/upload-artifact@v4`) or the log-conformance and zero-unlogged-panics gates (per obs-plan §9 CI Integration and §11 CI).
- (obs) The fmt gate introduces no runtime instrumentation — no new span, no new log line, no metric instrument — consistent with the pipeline's Not-instrumentable classification (per obs-plan §1 Obs Scope Summary, instrumentation-scope CI/CD row; §11 Metrics).
- (obs) On failure the gate's report is agent-readable from the CI log alone (the `cargo fmt --check` unified diff), and that output is not written into any telemetry artifact or the self-obs JSONL stream (per obs-plan §11 Universal and §9 log-conformance host-path rule).
