# a11y extract

## Relevance
**Partial** — no WCAG criterion is triggered (the chunk is Rust-only and the `ui/` TypeScript tree that holds every DOM/ARIA/token site is explicitly out of scope), but the chunk edits `.github/workflows/ci.yml`, the file that hosts the a11y CI gate job, so a11y's CI-integration and CI-ban rules bind the added gate.

## Constraints
- The a11y routine arm's CI arrangement is job `a11y` on `windows-2025`; a11y-plan §9 (Platform) and §1 (CI integration) require that job to remain CI-wired. Adding a fmt step to `ci.yml` must not remove, reorder into, or gate that job.
- a11y-plan §11 (Anti-Patterns → CI) requires the a11y step to be fail-fast and never skipped on CI failure, with `CONDUCTOR_A11Y_STRICT` + the printed-verdict assertion as the enforcing mechanism (exit code alone is insufficient, because the leg's host-tool guard skips at exit 0). A fmt gate wired so a fmt failure suppresses the `a11y` job into a skip would defeat that mechanism. Whether the `a11y` job today declares `CONDUCTOR_A11Y_STRICT` and asserts the printed verdict is research's question.
- a11y-plan §9 (Per-pipeline-stage a11y artifacts, Lint row) records the Lint stage as `n/a` for a11y — no `eslint-plugin-jsx-a11y` lane is mandated in the Rust-first stack. A fmt gate therefore owes no a11y artifact and produces no a11y signal.
- a11y-plan §3 (CI integration → Command) and §9 (Pipeline integration) require the a11y JSON step to ride the tests' `wdio run` webview-E2E path via `agent-run run --e2e` and emit through the 5-command `logs` command. The fmt gate must stand outside that path.
- a11y-plan §1 (A11y scope) declares the desktop-webview the only assertable surface and the `conductor` verb/CLI surface not-assertable; §11 (Universal) bars treating the cli surface as a11y-assertable. Reformatting `.rs` sources — including the 10 sites in `conductor-tauri` — asserts nothing about the rendered webview DOM.
- a11y-plan §3 (Structured violation JSON schema) fixes the violation artifact at the obs §6 envelope plus resource tags (13 keys local / 15 CI), honoured by `conductor-run`'s `journal_conformance` asserting key presence. The formatting-only boundary must leave that shape byte-equivalent; whether `journal_conformance` sits among `conductor-run`'s 64 reformatted sites is research's question.

## Patterns to follow
- **Identify CI jobs by NAME, never by `ci.yml` line coordinates** — a11y-plan §3 (Configuration) states this explicitly, having been burned when the frontend job moved `:178` → `:188`. This bears directly on the chunk's open premise "which CI job hosts the fmt gate, and where in its step order": name the job, do not pin a line.
- **The existing a11y gate is the shape precedent for a workspace gate** — non-zero exit on violation, never a warning-only mode (a11y-plan §9 Pipeline integration, §11 CI). A fmt gate should be modelled the same way.
- **CI-existence claims are stated as measured, not as target** — a11y-plan §9 (Platform) distinguishes the shipped `windows-2025` arrangement from the still-absent `ubuntu-latest`+`xvfb` target. Any statement this chunk makes about `ci.yml` should carry the same distinction.
- **Reuse the one webview-automation stack** — a11y-plan §3 (tool pick) and §11 (CI) bind a11y to the tests' `@crabnebula/tauri-driver` + WebdriverIO session; a fmt gate introduces no automation stack and must not become a reason to add one.

## Anti-patterns to avoid
- Counting a lint-class gate as a11y coverage — a11y-plan §11 (CI) bans lint-only a11y: the runtime axe-core step via tauri-driver/WebdriverIO must still run and remains the only a11y catch.
- Wiring the fmt gate so it can skip or short-circuit the `a11y` job (e.g. a `needs:` chain) — a11y-plan §11 (CI) bans skipping a11y on CI failure, because a skipped-green run and a real pass are otherwise indistinguishable.
- Claiming any a11y/WCAG outcome from the formatting pass — a11y-plan §11 (Strategy) bans WCAG conformance claims without machine-verifiable axe-core/colorjs.io/WebdriverIO JSON evidence.

## Contract bindings
- **a11y ↔ tests (CI + harness):** the a11y routine arm rides tests' `wdio run` webview-E2E job and tests' binding 5-command harness (boot/run/status/cleanup/logs) per a11y-plan §3 (CI integration) and §9 (Pipeline integration). The chunk's target row `test-plan.md:455` (Lint, pairing fmt with clippy) is tests-owned; a11y's own §9 Lint row is `n/a`, so a11y neither claims nor amends that row.
- **a11y ↔ obs (violation envelope):** a11y violation artifacts align verbatim to the obs §6 log-format envelope plus obs §3 resource tags, per a11y-plan §3 (Structured violation JSON schema) — the formatting pass must not perturb the emitting code's output.

## Acceptance criteria contributions
- The `a11y` job remains present in `ci.yml` with `runs-on: windows-2025`, its trigger and step list unchanged, and is not made conditional on the new fmt gate (per a11y-plan §9 CI Integration → Platform + §1 A11y Scope Summary → CI integration).
- The `a11y` job's skip-suppression mechanism (`CONDUCTOR_A11Y_STRICT` plus the printed-verdict / expected-skip-SET assertion) is untouched by the workflow edit (per a11y-plan §11 A11y Anti-Patterns → CI).
- The new gate is referenced by job NAME rather than `ci.yml` line coordinates in the chunk's plan, report and any amendment (per a11y-plan §3 A11y Assertion Harness Contract → Configuration).
- No a11y or WCAG claim is derived from the formatting pass, and no a11y artifact is emitted or owed by the Lint stage (per a11y-plan §9 CI Integration → Per-pipeline-stage a11y artifacts, Lint row + §11 → Strategy).
