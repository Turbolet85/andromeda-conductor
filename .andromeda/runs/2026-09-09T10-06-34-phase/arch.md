# arch extract

## Relevance
Relevant — the chunk touches two arch-owned surfaces: the workspace-wide crate roster (formatting pass) and the CI workflow model (the new gate).

## Constraints
- The gate must land in GitHub Actions as a job/step that turns the job RED on violation. Per architecture.md §Established Decisions [CI/CD], CI is the build+test+clippy+a11y job set on Windows runners (the two original jobs on `windows-latest`, `a11y` on the explicit `windows-2025` label per §Infrastructure Patterns — Build system); a new gate inherits that model rather than introducing a runner class of its own.
- A CI gate that can report success by skipping is banned — arch states this rule explicitly at §Occupied Resources — Environment variables (`CONDUCTOR_A11Y_STRICT`), and the 2026-09-08 WebView2 install step is the shipped shape of it (no `continue-on-error`, no `if:`, non-zero on either arm, per §Established Decisions [CI/CD]).
- The pass must be formatting-only in the architectural sense: `Cargo.toml` dependency edges ARE the architecture (§Design Philosophy — compiler-enforced module seams; §Established Decisions [Module Boundaries]), so no edge may move and no item may cross a crate seam. The nine registered workspace members (§Occupied Resources — Crate names) are the complete set the pass may touch.
- The gate's invocation must cover every registered workspace member so it cannot go blind as members are added — §Occupied Resources — Crate names is the registry, and §Established Decisions [Module Boundaries] records the analogous failure mode (a per-member property that is "measured-at-a-chunk rather than gate-enforced" because no CI job asserts it member-by-member).
- rustfmt is a toolchain component, not a workspace dependency: §Stack and Technologies requires Rust 2024 / cargo 1.85 / MSRV 1.94.1 and §Infrastructure Patterns — Build system pins the supply-chain gates over `Cargo.lock`. A fmt gate must therefore introduce no `[workspace.dependencies]` entry, no lockfile delta, and no audit/deny surface. Whether `ci.yml`'s jobs actually resolve rustfmt through the pinned `rust-toolchain.toml` (rather than an in-workflow toolchain override) is research's question.
- §Infrastructure Patterns — Build system requires the webview bundle be built before any workspace cargo invocation that COMPILES `conductor-tauri` (the `tauri-build` `generate_context!` coupling, wired as `ensure_frontend` into the CI Rust job). A `cargo fmt` check compiles nothing, so the mandate does not reach it; whether the hosting job's step order already places `ensure_frontend` ahead of where the gate lands is research's question.
- §Infrastructure Patterns — Build system makes line-ending behaviour a gate-correctness concern, not cosmetics: every CI job runs on a Windows runner and `core.autocrlf=true` is the dev-host norm, which is why the sole `.gitattributes` rule exists for the byte-comparing coverage gate. Whether rustfmt's default newline handling makes `cargo fmt --check` checkout-invariant across dev host and runner is research's question.
- New root build-config files are registered in the §Infrastructure Patterns directory tree, never in §Occupied Resources — `rustfmt.toml` already sits there (registered 2026-09-04) beside `.gitattributes`, `Cargo.lock` and `rust-toolchain.toml`.

## Patterns to follow
- The 2026-09-07 a11y gate is the shipped precedent for adding a gate to the single `ci.yml`: one job on a pinned Windows label, plus lockstep restatement of arch's CI enumerations across five sites (§Stack CI/CD row · §Established Decisions [CI/CD] · §Infrastructure Patterns Build system · §Infrastructure Patterns CI/CD approach · §Inherited Defaults CI/CD). A fmt gate that changes what CI runs will owe the same lockstep pass.
- Runner-pinning discipline (§Infrastructure Patterns — Build system): the `windows-2025` label is pinned deliberately so a `-latest` move cannot shift a tool underneath a leg. A new gate should not float a toolchain it depends on.
- Registration bar for anything the workflow names: only a handle a SHIPPED artifact names gets registered (§Occupied Resources — Environment variables, `EDGEWEBDRIVER` / `RUNNER_TEMP` / `WEBVIEW2_*` bases). A fmt step that names no new handle registers nothing.
- Crate-per-seam layout (§Infrastructure Patterns — Directory structure): the eight crates the pass touches plus `conductor-report` are exactly the tree's `crates/` members; the pass adds, removes and renames nothing in that tree.

## Anti-patterns to avoid
- Any semantic edit riding the formatting diff that moves code across a crate seam or alters a `Cargo.toml` dependency edge — the forbidden-edge property is compiler-enforced and unqualified (§Established Decisions [Module Boundaries]).
- A gate made permissive by `continue-on-error`, an `if:` guard, or a skip path — banned per §Established Decisions [CI/CD] and the `CONDUCTOR_A11Y_STRICT` rule (§Occupied Resources).
- Introducing a new outbound target, third-party CI binary, or env handle for the gate: §Occupied Resources — Ports registers exactly one non-loopback egress (the CI-scoped Evergreen fetch, operator-ratified as a boundary widening) and §Cross-cutting Patterns — Trust boundary holds the loopback-only claim; a fmt gate reaching outside the toolchain would be a new widening requiring the same ratification.

## Contract bindings
- **arch ↔ tests** — arch owns the workflow/job model (§Established Decisions [CI/CD], §Infrastructure Patterns CI/CD approach) while test-plan §9's Lint row owns the gate's identity; the invocation shipped in `ci.yml` must be the one the test plan's row names, and the scope's boundary (`test-plan.md:455` left standing, made true) is the tests domain's call, not arch's.
- **arch ↔ security** — §Infrastructure Patterns — Build system pairs the CI job set with the `cargo deny` / `cargo audit` supply-chain measurement over an un-drifted lock; a formatting-only pass must leave `Cargo.lock` untouched so that measurement is unchanged.
- **arch ↔ all domains** — the nine locked crate names (§Occupied Resources — Crate names) are where every domain's code lives; the pass must preserve them exactly.

## Acceptance criteria contributions
- (arch) The fmt gate lives in `.github/workflows/ci.yml` on the existing Windows runner set and fails the job on violation, with no `continue-on-error`, no `if:` guard and no skip path (per architecture.md §Established Decisions [CI/CD] · §Occupied Resources — `CONDUCTOR_A11Y_STRICT`).
- (arch) The gate's invocation asserts over every workspace member listed in the crate registry, so a tenth member added later cannot escape it (per architecture.md §Occupied Resources — Crate names · §Established Decisions [Module Boundaries]).
- (arch) No new occupied resource lands: no port or egress target, no env handle, no crate, no on-disk artifact, and no `[workspace.dependencies]` / `Cargo.lock` delta (per architecture.md §Occupied Resources · §Infrastructure Patterns — Build system).
- (arch) The pass changes no `Cargo.toml` dependency edge and moves no item across a crate seam; the `crates/` tree in §Infrastructure Patterns — Directory structure is unchanged (per architecture.md §Design Philosophy · §Established Decisions [Module Boundaries]).
