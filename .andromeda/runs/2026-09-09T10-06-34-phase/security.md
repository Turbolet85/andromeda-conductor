## Relevance
Partial — no new external-input boundary, dependency, secret or spawn crossing; security's stake is (a) the pass must not perturb shipped control sites and (b) the added `ci.yml` step lands on a workflow the plan governs.

## Constraints
- The pass must leave `Cargo.lock` un-drifted and committed, and the tree must stand green under `cargo audit` + `cargo deny check advisories bans licenses sources` at wrap — the audit/deny gate is the Minimal-tier residual-risk control and binds the merge/release gate, not only dependency-changing chunks (per security-plan §Security Anti-Patterns → Universal, §Dependency Security).
- No garde annotation on a nested scenario-config spec struct may change under the pass: `dive` is the only correct annotation and `#[garde(skip)]` silently bypasses the boundary while the rules still exist (per security-plan §Security Anti-Patterns → Input, §Input Validation scenario-config row). `conductor-core` (4 sites / 2 files) and `conductor-run` (64 / 8) are in the flagged set; which files those are is research's question.
- The shipped subprocess control in `conductor-verify` must survive byte-semantically: rule (a) requires a fixed hard-coded program NAME through the inherited `PATH`, `.env(...)`-only data-dir propagation, nothing operator-supplied in argv, and the `#[cfg(windows)]` `.creation_flags(console_suppressing_flags())` console suppression held by a `#[cfg(windows)]` unit test (per security-plan §Security Anti-Patterns → Code Patterns rule (a)). `conductor-verify` carries the largest slice of the pass (110 sites / 18 files); whether `spawn.rs` is among them is research's question.
- The Tauri IPC edge must keep its `resolve_under`-before-read guard and `sanitize_error` on every returned `Err`, and the `conductor-cli` edge its `std::fs::canonicalize` + bounds-check for the `CONDUCTOR_*` path handles (per security-plan §Input Validation, `#[tauri::command]` row and env-var-path-handles row). `conductor-tauri` (10 / 2) and `conductor-cli` (7 / 1) are both in the flagged set.
- The added CI step must be a fixed toolchain program with a fixed argv — no shell-string assembly, no `Invoke-Expression`, no network-fetched program, no operator-supplied value anywhere in the vector — matching the "in every form" universal that governs `.github/workflows/ci.yml` as a spawn locus since the sixth governed form landed (per security-plan §Security Anti-Patterns → Code Patterns rule (b)).
- Inserting the fmt step must not reorder, disable or `continue-on-error` any existing gate in `ci.yml`: §Dependency Security requires the cargo-audit (+ optional cargo-deny) step to fail the build on an advisory hit, and the `a11y` job's pre-execution `Get-AuthenticodeSignature` check on the fetched WebView2 bootstrapper is the sole admitting control for the third dependency class (per security-plan §Dependency Security CI integration + third dependency class). Whether those steps exist today in `ci.yml` and in which job is research's question — the scope's own grep only established that no step mentions `fmt`.
- This chunk does NOT discharge `secret-scanning-ci-gate`; that bootstrap phase remains open with tool selection deferred, and adding an unvetted scanner alongside the fmt step is explicitly disallowed (per security-plan §Bootstrap phases, §Secret Management).

## Patterns to follow
- Fixed-program / fixed-argv job step, no operator-supplied value — the shape every governed spawn form already uses (repo-derived resolved constant, fixed OS/toolchain binary + fixed argv, env map never argv, never a shell) per security-plan §Security Anti-Patterns → Code Patterns rule (b). A bare `cargo fmt --all --check` run step matches the existing `cargo build` / nextest / clippy precedent.
- Gate steps fail the job non-zero rather than reporting success by skipping — the discipline §Dependency Security states as "build fails on advisory hit", and the same principle the plan records for the `a11y` job (an unresolved handle exits non-zero under strictness rather than skipping at exit 0) per security-plan §Input Validation `CONDUCTOR_A11Y_STRICT` row.
- ADDED arm, never a relaxation: the plan's standing shape for CI-side additions — a new gate arm ships while the existing readers/guards stay byte-unchanged (per security-plan §Input Validation `CONDUCTOR_MSEDGEDRIVER` row, CI-producer clause).
- Byte-identity against `rustfmt --config-path rustfmt.toml` as the partition proof: it is also the security evidence that no control site's semantics moved, since rustfmt reformats whitespace/ordering only and does not rewrite attributes, string literals or `cfg`-gated bodies. The chunk's own boundary ("no semantic change ships in the pass") is what keeps the control sites out of review risk.

## Anti-patterns to avoid
- NEVER resolve a formatting conflict on a garde-validated struct by changing an annotation — `dive` → `skip` looks like formatting churn and silently removes the trust boundary (per security-plan §Security Anti-Patterns → Input). If a `#[rustfmt::skip]` is added under the chunk's open premise, it is a formatting attribute only and carries no garde meaning.
- NEVER let `Cargo.lock` drift or go uncommitted through a mechanical pass — it makes the audit/deny scan non-deterministic (per security-plan §Security Anti-Patterns → Universal).
- NEVER let the pass alter an error/sanitization site so an absolute host path, a stack trace or an internal seam-crate struct name reaches `conductor-cli` stderr, a `#[tauri::command]` return, `<run_id>.md`, `runs.db` or a committed `evidence/` record (per security-plan §Security Anti-Patterns → Logging, §Error Handling).

## Contract bindings
- **CI security gate ↔ tests §CI Integration:** `ci.yml` is the single workflow hosting both the fmt gate and the security gates (cargo-audit / cargo-deny / `npm audit --omit=dev`); step placement is a tests-domain call, non-disturbance of the security steps is this domain's (security-plan §Dependency Security CI integration, §Bootstrap phases dep-security-ci-gate).
- **Artifact hygiene ↔ obs (host-path scrubbing) and a11y (committed `evidence/nvda-pass.json`):** the same sanitization sites the pass must leave semantically identical are cited by obs and a11y (security-plan §Security Anti-Patterns → Logging).
- **`a11y` job (Authenticode verification, `CONDUCTOR_A11Y_STRICT`, the `Test-Path` handle precondition):** security-relevant CI machinery in the same file, explicitly out of this chunk's scope per its own Boundaries — leave byte-unchanged.
