# arch extract

## Relevance
Relevant — this chunk drives live legs that land in arch-owned artifact contracts (run envelope, per-check record, `runs.db`, live-suite captures) and rides the readiness gate, so most of the domain's contract surface applies even though little new code lands.

## Constraints
- The readiness gate runs ONCE at suite start and gates every dependent auto scenario: on `ready:false` an auto scenario is emitted `state: "blocked"` with one of the FIVE named preconditions and identity fields only (`run_id`/`seed`/`scenario`/`p_ids`/`slo_tier`), every other envelope field JSON `null` (per architecture.md §Standard Contracts — Readiness gate). A "non-blocked verdict" for P-079 therefore presupposes a green preflight in the same invocation.
- Every leg's evidence must be the ELEVEN-field run envelope plus, for a graded check only, the nine-key `CheckRecord` (`run_id`·`scenario`·`check_index`·`kind`·`verdict`·`state`·`latency_ms`·`deadline_ms`·`budget_ms`); architecture.md §Standard Contracts — Per-check record requires a blocked or declare-only scenario to emit ZERO check records and zero `run_check` rows. Whether the shipped writer already honours that for these three scenarios is research's question.
- Report state is decided by the read-back route, not by intent: architecture.md §Established Decisions [Read-Back Dependency Posture] fixes `ReadBack {Graded, AutoResolved, Blocked}` — the auto-resolve/empty-active-list residual is confined to declare-only scenarios, the degraded read-back route to `KnownResidual` is NOT so confined, and every read-back CALL FAILURE lands `Blocked` unconditionally. `degraded` is a per-read-back property, never a mode-wide guarantee.
- Latency is journal-relative (`read_back_observed_at − journal_emitted_at`), graded against the per-check EFFECTIVE deadline (declared `budget_ms` else the tier's), and `slo_tier` stays the closed TEXT set `&lt;5s`/`&lt;20s`/`&lt;90s`; `latency_ms` is the INTEGER-ms column, the two instants TEXT RFC-3339 (per architecture.md §Established Decisions [Timing-Tolerance Model] · §Conventions Data model conventions).
- The sidecar program is a fixed NAME resolved through the inherited `PATH`, and architecture.md §Occupied Resources — Service/process names requires any operator-driven live leg to carry a `PATH` prefix resolving it as part of its firing form: a `PATH` miss returns BLOCKED in ~2ms with all four tools `absent`, at row level indistinguishable from a genuine SUT-side gate failure. `ANDROMEDA_PULSE_DATA_DIR` must be propagated to the spawned sidecar (same §, and §Cross-cutting Config management).
- Live-Pulse dynamic proof is an operator/local gate, never a CI gate — the exclusion is the live-Pulse dependency, not the end-to-end tier (per architecture.md §Established Decisions [CI/CD] · §Infrastructure Patterns CI/CD approach). Whichever wiring fork lands must keep these legs off the three CI jobs.
- Two Pulse-side handles are asserted NOT set by Conductor (`ANDROMEDA_PULSE_MCP_ENABLED`, `ANDROMEDA_PULSE_L4_DETERMINISTIC`); Conductor only READS them in its own shell as run-contract `shell-declaration` proxies / `preconditions` subjects, and `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` is the one registered handle Conductor neither sets nor reads — which posture actually booted is read from Pulse's own `triage.baseline.bootstrap_window.override` target, never from the emitting function name or the launch string (per architecture.md §Occupied Resources — Environment variables). This matches the scope's "read back from Pulse's own witness line".

## Patterns to follow
- Per-leg capture/freeze: `runs/live-suite/{leg}.jsonl` is the registered site for the `run --live` per-leg self-obs freezes — harness-owned by `scripts/agent-run.{sh,ps1}`, LEG-stemmed, moving with `CONDUCTOR_RUNS_DIR`, git-ignored, cleared at suite start by a non-recursive `rm -f …/*.jsonl` — and it exists BECAUSE `logs/agent-latest.jsonl` truncates per invocation (architecture.md §Occupied Resources — On-disk artifacts). Either wiring fork should reuse this site rather than mint a second capture mechanism.
- Preflight/precondition sequencing: `boot` runs `conductor preconditions` as a leading arm (three subjects, graded per handle by kind) and short-circuits only on a genuinely unmet subject; a satisfied environment REACHES and PAYS `CONDUCTOR_PREFLIGHT_TIMEOUT` (~47s = warm-up + poll) and emits `ReadyState` JSON — the skip is told from a failure by the absence of that JSON (architecture.md §Standard Contracts — Liveness equivalent · §Occupied Resources `CONDUCTOR_PREFLIGHT_TIMEOUT`).
- Service-identity split: the scenario dispatcher emits as `conductor` and the preflight canary as `conductor-canary`, deliberately separate because the preflight runs inside every scenario leg and Pulse keys sample counts / error-rate EWMAs per service (architecture.md §Occupied Resources — Service/process names). This is the arch-side handle for the scope's canary-vs-storm attribution question on P-079.
- Verdict-first lamp + independent `verdict`/`state`: `Verdict::default_report_state` maps `Pass→Pass` / `Fail→Fail` / `CalibrationRegion→ManualCheck`, a producer may set a context-specific state, and a calibration row renders HOLD rather than Manual (architecture.md §Established Decisions [Probabilistic-Assertion Policy]).
- Composition-root placement: `conductor-run` owns preflight + `execute_scenario` + persist + the run driver above the seams and below both bins; the harness shells issue no SQL of their own (architecture.md §Occupied Resources — Crate names · §Established Decisions [ORM]).

## Anti-patterns to avoid
- Do NOT edit the pinned `contracts/*.toml` manifests (capability manifest · load envelope · run contract · MCP contract) to move a verdict: their SUT-side terms are a transcribed SUT record with deliberately NO `CONDUCTOR_*` override handle, and the catalog gates (`check_sut_drift`, `check_scenario_backing`/`UNBACKED_AUTO`, `check_load_envelope` with its empty exemption ledger) are held to exact-set equality (architecture.md §Established Decisions [Accepted Capability Set] · §Occupied Resources — On-disk artifacts).
- Do NOT synthesize measured values for anything not measured: a blocked or declare-only scenario writes zero `run_check` rows and NULL envelope measurement fields, and cross-run latency/percentile/P-036 queries MUST exclude NULL-measurement rows (architecture.md §Standard Contracts — Readiness gate · §Occupied Resources `runs.db`).
- Do NOT add a new `CONDUCTOR_*` handle for the live-leg wiring — the live-suite capture path is deliberately handle-free and moves with `CONDUCTOR_RUNS_DIR`; nor automate PULSE's UI for the two `drive+observe` claims (architecture.md §Occupied Resources — On-disk artifacts · §Cross-cutting Patterns Scope law).

## Contract bindings
- Run envelope + `CheckRecord` shape ↔ tests harness: the same `journal_conformance` assertion is the reused gate over a runs dir (arch registers it as never a second copy of the schema) — the wrap's light-gate re-runnability question (scope Q4) lands on this binding.
- Readiness-gate precondition strings + `data_dir` redaction ↔ security/obs: every precondition string is host-path-free and the self-obs stream inherits processor-stage redaction, which the frozen `runs/live-suite/{leg}.jsonl` captures inherit too (architecture.md §Standard Contracts — Readiness gate · §Occupied Resources).
- ManualCheck / operator-checklist rows ↔ design + layouts + a11y: the checklist is a scenario-config surface (`[[checklist]]`, `ChecklistItem { induced, observation }`, projected via `HoldPoint`) which architecture.md §Conventions Config conventions records as declared by exactly two committed scenarios — none of this chunk's three — so scope Q3 ("where do ManualCheck rows and the checklist come from") is a joint arch/layouts question, and the lamp rendering is verdict-first.
- `ANDROMEDA_PULSE_*` handles ↔ security: Conductor reads but never writes them; the probe's reporting is name-only (a finding names handles, never values).

## Acceptance criteria contributions
- Each leg's evidence is the eleven-field envelope row in `runs/&lt;run_id&gt;.jsonl` plus its `runs.db` row, with ZERO `run_check` rows for the two declare-only scenarios and per-check `CheckRecord` rows only for the checks-bearing one (per architecture.md §Standard Contracts — Run report envelope / Per-check record).
- Any per-leg self-obs freeze lands at `runs/live-suite/{leg}.jsonl` — leg-stemmed, harness-owned, cleared per invocation, no new `CONDUCTOR_*` handle (per architecture.md §Occupied Resources — On-disk artifacts).
- Every reported latency is journal-relative and each row's `slo_tier` stays inside the closed `&lt;5s`/`&lt;20s`/`&lt;90s` set, with `latency_ms` INTEGER and the two instants TEXT RFC-3339 (per architecture.md §Established Decisions [Timing-Tolerance Model] and §Conventions Data model conventions).
- No live-Pulse leg is added to any CI job; the wiring stays an operator/local gate, and the leg's firing form resolves the sidecar on `PATH` so a BLOCKED row cannot be a `PATH` artefact (per architecture.md §Established Decisions [CI/CD] and §Occupied Resources — Service/process names).
