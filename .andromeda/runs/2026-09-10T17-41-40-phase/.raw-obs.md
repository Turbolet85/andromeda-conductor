## Relevance
Relevant (partial) — obs owns CARRY A (the panic-hook tests live in `conductor-core/src/obs.rs`, obs's own module) and the semantics of "a final SLO verification pass"; it adds no new spans, metrics or fields to this chunk.

## Constraints
- **Zero unlogged panics is the always-required invariant**: every panic captured by `std::panic::set_hook()`, logged via `tracing::error!(panic_msg, backtrace)` with the backtrace one-line-serialized, and converted to `anyhow::Error` at the binary edge (CLI: exit 1 + sanitized stderr) — per obs-plan §10 Always-required SLO invariant + §11 Logs. CARRY A's remedy must leave both racing tests still asserting what they pin (one error line; host-path redaction in the panic payload) and must not disturb the production installer. Whether the *release profile* preserves the hook→anyhow-edge path and a serializable backtrace (`panic`/`strip`/`debug` settings) is research's question.
- **The SLO pass is a JSON field assertion, never an instrument**: `latency_ms &lt;= threshold(slo_tier)` with the closed tier enum `&lt;5s | &lt;20s | &lt;90s` → 5000 / 20000 / 90000 ms, evaluated at report-generation time over the envelope + `runs.db` rows — per obs-plan §10 Performance budgets and §5 Metric Coverage. §11 Metrics forbids adding a histogram/meter to record it.
- **`latency_ms` is journal-relative wall clock** — `read_back_observed_at − journal_emitted_at` from `std::time`, never tokio's virtual clock, and it covers the scenario's whole emission window rather than an MCP round-trip — per obs-plan §5, §11 Project-specific bans, and the 2026-09-10 amendment. A tier verdict on the shipped artifact must be read against declared phase duration, not call latency.
- **The pass's self-obs artifact is the agent-mode stream**: `--agent-mode` (or the read-only `CONDUCTOR_AGENT_MODE` trigger Conductor reads and never writes) switches the WRITER to `logs/agent-latest.jsonl`; the format is JSON either way, one writer at a time — per obs-plan §3 Logging stack + Log file location. The §9 log-conformance gate validates that file against the §3 **self-obs base line** schema (`timestamp_ms`, `level`, `target`, `service.name`, `service.version`, `deployment.environment`, `run_id`), *not* the §6 eleven-field envelope, which lives in `runs/&lt;run_id&gt;.jsonl` — per obs-plan §9 Log conformance check.
- **Service identity is compile-time-derived and must not be hardcoded**: `service.version` = `env!("CARGO_PKG_VERSION")`, `service.name` overrideable via `$CONDUCTOR_SERVICE_NAME`, `deployment.environment` via `$CONDUCTOR_ENV` (default `local`) — per obs-plan §3 Service identity + §11 Universal. This gives the chunk's version-stamp open question an obs consequence: whichever stamp the release carries becomes `service.version` on every self-obs line of the recorded pass. The gate requires key presence, not a particular value; whether the shipped code resolves the stamp this way is research's question.
- **The no-OTel-SDK-for-self-obs invariant is behavioral and survives the release build**: no SDK may be initialized/used for self-observation, and no self-obs OTLP may be exported (`:4317` carries the PRODUCT fault stream only; `:4318` is dead) — per obs-plan §3 OTel SDK init + §11 Telemetry Strategy/Universal. The dormant transitive `opentelemetry` / `opentelemetry_sdk` crates in the tree are explicitly not a violation, and §3 records that no feature trim can shed them.
- **Host-path and struct-name freedom in every telemetry artifact** — the redaction layer masks absolute host-file paths; the allowlisted `target` module path is preserved; struct names are excluded by the field-name allowlist + `Display`-not-`Debug` at the anyhow edge — per obs-plan §9 Log conformance check + §11 Logs / PII Scrubbing. §9 already records that the fmt gate's `Diff in {file}` lines are deliberately kept out of telemetry artifacts for exactly this reason.

## Patterns to follow
- Agent-mode harness run as the evidence producer: drive the pass through `scripts/agent-run.{sh,ps1}`, yielding one `jq`/`serde_json`-parseable JSONL stream plus the run report Markdown as the paste-to-AI surface (obs-plan §3 Logging stack, Snapshot / paste-to-AI integration).
- The two-record-shapes split: self-obs base line (per `tracing` line) vs the Run-report envelope (scenario result), with the per-check `CheckRecord` as a finer grain beneath the envelope — the SLO assertion reads the envelope, the conformance gate reads the base line (obs-plan §3 Log format JSON schema, §6 Required fields).
- Conformance asserted as key PRESENCE + closed sets + host-path freedom, never key exclusivity — the property that lets one gate serve both the eleven-key scenario record and the a11y record's superset (obs-plan §3 extension-point paragraph, §9 CI Integration).
- Tauri backend sink placement rides `CONDUCTOR_RUNS_DIR` (`&lt;runs_dir.parent()&gt;/logs/conductor-tauri.jsonl`), unconditional file sink with stderr only as an open-failure fallback (obs-plan §3 Log file location) — the pattern any bundle-launch verification must be read against, since a bundled GUI has no console for the fallback.
- Existing CI gate composition to extend, not replace: log conformance + zero-unlogged-panics + nextest JSON + inline `cargo-audit`/`cargo-deny` output, with an audit red flag already listed as a build-failure condition (obs-plan §9 Pipeline integration, §10 Build / deploy failure conditions).

## Anti-patterns to avoid
- No retry-once policy for panic handling and no soft (unenforced) SLO budget — CARRY A must be fixed at the cause (serialize the two, or one shared guard), never by retry, sleep or runner pin (obs-plan §11 SLO).
- No OTel SDK, meter provider, `tracing-opentelemetry`/W3C trace context, or any self-obs OTLP export introduced by the release/bundle configuration (obs-plan §11 Telemetry Strategy / Metrics / Universal).
- No new span minted for build-time or verification-pass activity, and no widening of the bounded span-name set — the build/CI pipeline is classified Not-instrumentable because it runs at no runtime (obs-plan §1 instrumentation-scope `cargo build / CI/CD` row + §11 Spans / Traces).

## Contract bindings
- **obs ↔ tests**: test-plan §3 owns the JSONL log format, the eleven-field envelope and the harness contract; obs-plan §3/§6 reproduce it and align to it. The zero-flake bar the scope names as owning CARRY A is test-plan §10; obs contributes the invariant it defends (§10 zero unlogged panics) and the §9 gate that detects a regression.
- **obs ↔ a11y**: the a11y violation record `runs/a11y/&lt;run_id&gt;.jsonl` is a registered §9 CI artifact riding the envelope extension point (eleven keys plus resource tags), conformance asserted in-job under `CONDUCTOR_RUNS_DIR=runs/a11y` — so any CARRY C work that emits SR/a11y evidence inherits obs's key-presence and host-path-freedom requirements (obs-plan §3 extension point, §9 artifact table, §11 PII Scrubbing).
- **obs ↔ security**: the sidecar-spawn ban (fixed program name via inherited `PATH` + `.env(...)`, never a shell, never a visible console window) is a cross-master citation held on both sides; the release binary's spawn path must keep the shipped `CREATE_NO_WINDOW` suppression (obs-plan §11 Project-specific bans).
- **obs ↔ CI/supply chain**: `cargo-audit` / `cargo-deny` output is inline CI telemetry and an audit red flag is an enumerated build-failure condition, which is the same gate the chunk puts in front of `cargo build --release` (obs-plan §9 artifact table, §10 Build / deploy failure conditions).

## Acceptance criteria contributions
- The recorded final pass asserts, per graded envelope row of the shipped-artifact run, `latency_ms &lt;= threshold(slo_tier)` against 5000/20000/90000 ms at report-generation time, with no histogram or metrics backend introduced (per obs-plan §10 Performance budgets / §5 Metric Coverage).
- The pass's `logs/agent-latest.jsonl` passes the §9 log-conformance gate: every line carries the §3 self-obs base schema (`timestamp_ms`, `level`, `target`, `service.name`, `service.version`, `deployment.environment`, `run_id`) and no absolute host-file path in any field (per obs-plan §9 Log conformance check).
- Zero unlogged panics across the release run and the suite — no `^thread.*panicked` line in `agent-latest.jsonl` or stderr — and CARRY A's remedy removes the shared-hook race at the cause while both tests still assert one error line and host-path redaction of the panic payload (per obs-plan §10 Always-required SLO invariant + §9 Zero-unlogged-panics gate).
- The release artifact initializes no OTel SDK for self-observation and exports no self-obs OTLP on any surface; a dormant transitive `opentelemetry`/`opentelemetry_sdk` in the lockfile is not a violation (per obs-plan §3 OTel SDK init + §11 Universal).
