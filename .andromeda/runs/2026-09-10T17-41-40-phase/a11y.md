## Constraints
- The `conductor-cli` / `agent-run` release binary — the chunk's own release gate — is a **not-assertable** surface; a11y-plan §1 (A11y scope, `conductor-cli` entity, set-scoped over the whole `conductor` verb surface) requires that no a11y assertion be claimed of it, and §11 Universal bans treating the cli as a11y-assertable. Only the desktop-webview bundle is an assertable subject.
- If the final verification pass claims a11y coverage, a11y-plan §10 requires the **zero-WCAG-AA-violations invariant** on the four must-be-accessible paths (SC 2.1.1 / 1.4.3 / 2.4.3 baseline plus 1.4.11 / 1.4.1 / 4.1.2 / 4.1.3 / 2.1.2 / 1.3.1 / 2.4.7 / 3.3.2), with `violations.length > 0` ⇒ non-zero exit, plus the not-color-alone and reduced-motion failure conditions as build-failure triggers.
- Any CARRY C remedy is constrained by a11y-plan §10 and §11 SLO: **no retry-once policy, no soft a11y SLO** — the same bar the scope quotes from test-plan §10. The scope's own "fix at the cause" wording is consistent with the a11y ban; the ban is independent authority, not derived from it.
- The SR leg is **supplemental, never sole** (a11y-plan §3 Screen reader test pattern; §2 agent-runnable invariants; §11 Universal). CARRY C's `S3-04` sits in the NVDA pass spec, so a11y-plan §11 requires that no WCAG conformance verdict for the release rest on the SR row's outcome, and that machine output (axe-core / colorjs.io / WebdriverIO JSON) carry the claim regardless of how CARRY C resolves.
- a11y-plan §6 (Color contrast pairs → Verification; Motion tokens → Verification) and §3 (Contrast verification harness) require the 13 named token pairs to be resolved **from the compiled CSS custom properties** and the `@media (prefers-reduced-motion: reduce)` rule to be asserted **per-declaration off the compiled stylesheet**. A release-profile / bundled build must therefore keep those custom-property names and that rule resolvable — *whether the release bundle's compiled CSS already preserves them is research's question.*
- a11y-plan §9 Platform and §3 CI integration split the arms: the **routine** arm is the CI gate (job `a11y`, `windows-2025`, via `agent-run run --e2e`), while the **driven** and **`sr*`** arms are operator/local gates requiring a live Pulse / NVDA host. A "final pass" that includes CARRY C's SR subject is an operator gate by that split, not a CI one.
- a11y-plan §3 (Structured violation JSON schema), §9 (CI-specific resource attributes) and §11 SLO require every a11y artifact from this pass to tag `service.name` / `deployment.environment` (plus `ci.run.id` / `git.commit.sha` under CI) and to leak **no absolute host paths or internal seam-crate struct names** — a live constraint for release-time evidence files.

## Patterns to follow
- The tests' binding **5-command harness discipline** (boot / run / status / cleanup / logs) with a11y results surfaced through `logs` — a11y-plan §3 CI integration and §9 Pipeline integration make this the command surface a11y reuses; the chunk drives its final pass through `scripts/agent-run.{sh,ps1}`, the same surface.
- **One webview-automation stack**: `@crabnebula/tauri-driver` + WebdriverIO with axe injected via `@axe-core/webdriverio` (a11y-plan §3 tool pick). Any release-artifact verification leg reuses that session rather than attaching a new driver.
- The **NVDA pass-spec grading shape** already in use for CARRY C's evidence — speech log (`-l 12`) graded by `parse-nvda-log.ts` against the 51-row `crates/conductor-tauri/ui/test/a11y/screen-reader/nvda-pass-spec.md`, operator review transcribed into `evidence/nvda-pass.json` (a11y-plan §3 Screen reader test pattern). The chunk's `nvda-pass.live.run3-lightgate.json` is that shape.
- The **printed-verdict + `CONDUCTOR_A11Y_STRICT` enforcement mechanism** (a11y-plan §11 CI) — the exit code alone cannot distinguish a skipped-green run from a pass. This is the same mechanism the scope records as CARRY B's discharge, and it stays binding for the final pass.
- **Per-arm run budget** (a11y-plan §10 Performance budget): axe under 30s; routine arm fast/unattended; the driven arm carries a 15-minute mocha ceiling with a quiet-window precondition that costs two 12-minute runs when violated — a scheduling input for a final operator-gated pass.

## Anti-patterns to avoid
- **Never** a retry-once policy or a soft SLO for an a11y violation or a flaky SR row (a11y-plan §11 SLO) — this bans "re-run the `sr*` leg until `S3-04` announces" as a CARRY C disposition.
- **Never** skip a11y on gate failure and never let a skipped-green run stand in for a pass (a11y-plan §11 CI) — a release pass must assert the runner's printed verdict, not just a zero exit.
- **Never** claim WCAG conformance without machine-verifiable evidence aligned to the obs §6 envelope, and never let manual/SR review be the only method (a11y-plan §11 Universal, §2) — bars a release note that asserts a11y conformance from the operator's SR review alone.

## Contract bindings
- **a11y ↔ obs**: violation/ratio/keyboard JSON folds into the obs §6 log envelope; shipped shape is the eleven envelope keys plus obs resource tags (13 local / 15 CI), `fingerprints[]` one tuple **per node** (a11y-plan §3 Structured violation JSON schema; obs §3 extension point, obs §9).
- **a11y ↔ tests**: driver + harness reuse (tests §6 tauri-driver/WebdriverIO, 5-command contract), and the zero-flake bar test-plan §10 imposes on CARRY C's remedy (a11y-plan §3, §9, §10 Cross-input parallel).
- **a11y ↔ design**: contrast token pairs bind to design §Color Palette; the reduced-motion drop binds to design §Motion (Tailwind v4.1 `motion-reduce:` + `@theme` tokens) — both asserted off the compiled stylesheet the release build produces (a11y-plan §6).
- **a11y ↔ CI/arch**: a11y-plan §1 and §9 quote arch §Stack's gate-set rationale verbatim; a release chunk that alters the CI gate set would move those citations.
