# obs extract

## Relevance
Partial — the chunk ships no Rust, no spans and no self-obs lines, but it adds CI job steps and a recorded artifact, which lands squarely on obs's CI-integration, host-path-hygiene and agent-readability mandates.

## Constraints
- The CI/CD pipeline is classified **Not-instrumentable** (GitHub Actions workflow, build-time only, no runtime) per obs-plan §1 Obs Scope Summary (instrumentation-scope table, `cargo build / CI/CD pipeline` row); a probe step is therefore required to mint **no span and no `tracing` line** — §11 Spans/Traces holds the span-name set bounded and closed, so no `probe.*`-class name may be introduced.
- No absolute host-file path may appear in the probes' job-log output or in the recorded reading. obs-plan §9 CI Integration (Log conformance check) defines the anchor set the gate rejects — drive-letter `X:\`, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup` — and §11 Logs restates the ban for logs / run-report / runs.db. A policy *value* that is itself a path must be reported by presence/shape rather than verbatim to satisfy this.
- obs-plan §11 PII Scrubbing requires that a host-path channel **outside** the three `conductor-core::redact` application sites (processor-stage layer, report write, runs.db insert) be closed at its own source — its standing warning ("NEVER assume the three application sites bound every host-path channel") is explicitly unretired. A YAML workflow step reaches none of those three sites, so the scrub must be intrinsic to the probe. Whether any existing a11y-job diagnostic already scrubs inline (and how) is research's question.
- The reading must be agent-consumable without human review: obs-plan §1 (agent-driven invariant: every signal readable by an agent from a snapshot or pasted excerpt; a non-instrumentable surface gets boundary instrumentation only) plus §11 CI and §11 Universal ("NEVER use human-review-gated log analysis without machine-parseable export").
- Diagnostic output that carries host paths stays in the job log and is **not** routed into a telemetry artifact — obs-plan §9 Pipeline integration (Lint/typecheck row) states exactly this for the fmt gate's `Diff in {file}` lines, because §9's own log-conformance check would reject them. This chunk's artifact is a *committed* reading rather than a telemetry artifact, so the scrub is what makes it admissible.
- The a11y job already owns two artifact obligations obs §9 Telemetry artifact handling records — `logs/agent-latest.jsonl` (every CI job) and the a11y violation record `runs/a11y/&lt;run_id&gt;.jsonl` (uploaded `actions/upload-artifact@v4`, conformance asserted in-job under `CONDUCTOR_RUNS_DIR=runs/a11y`). §11 CI requires these not be lost; added steps must leave both paths and the in-job assertion untouched.
- obs-plan §9 Zero-unlogged-panics gate greps `logs/agent-latest.jsonl` **plus stderr** for `^thread.*panicked` and FAILs the check on a hit. Whether that grep's stderr reach includes a new diagnostic step's output in the same job — and hence whether a probe echoing such a string could trip a gate it is forbidden to decide — is research's question.

## Patterns to follow
- **Shape witness, names never values** (obs-plan §6 Boundary-call wrappers): the `verify.readback` key-set witness and the `emit.batch` wire-shape witness both record the observed KEY NAMES only, never values, ordered so the same input renders identically. This is the plan's own model for reporting what a surface exposes without publishing its contents — the applicable pattern for a policy value that is path-shaped.
- **Presence, not non-null** (obs-plan §6 Required fields): "required" means the key IS PRESENT, since a typed parse cannot distinguish an absent key from a null one. The scope's "explicitly report the absence of a key rather than omitting it" is the same discipline applied to a registry read.
- **Job-log-only diagnostic output** (obs-plan §9 Pipeline integration, fmt-gate row): agent-readable from the job log, deliberately not written into any telemetry artifact — the nearest in-plan precedent for a CI step whose output carries host-path risk.
- **CI resource attributes** (obs-plan §9 CI-specific resource attributes): `ci.run.id` (`${{ github.run_id }}`) and `git.commit.sha` (`${{ github.sha }}`) are the plan's identity fields for tying a CI-produced record back to its run — the same pair §3's extension-point paragraph records as joining the a11y record's keys under CI (15 vs 13 locally).

## Anti-patterns to avoid
- Leaking an absolute host path (or a path-shaped policy value verbatim) into the job log or the recorded reading — obs-plan §11 Logs; §9 Log conformance check.
- Producing the reading as unstructured prose only, with no machine-parseable form — obs-plan §11 Universal / §11 CI ("human-review-gated log analysis without machine-parseable export"); §11 Logs ("NEVER use unstructured stderr text … structured JSON-per-line or sanitized stderr with machine-parseable hints").
- Relying on `conductor-core::redact` to cover a workflow-step channel — obs-plan §11 PII Scrubbing's standing warning; the enumeration bounds the sites it names, never every channel.

## Contract bindings
- **obs ↔ a11y** — obs-plan §9 artifact table and §3 Log format (extension-point paragraph) bind to the a11y CI gate's violation record `runs/a11y/&lt;run_id&gt;.jsonl`; the probes live in the same `a11y` job, so obs's side of the bind is that the record's path, its upload and its in-job `journal_conformance` assertion (key presence + closed sets + host-path freedom, never key exclusivity) stay exactly as specified.
- **obs ↔ security** — obs-plan §11 PII Scrubbing / §11 Project-specific bans carry cross-master citations of security-plan's host-path and sidecar-spawn bans (the 2026-08-20 and 2026-09-04 amendments establish these move on both sides together). The scope's harness-spawn rule (b) is security's to rule on; obs's binding interest is that a spawn-shaped probe re-opens the host-path-in-window-title class §11 records as measured-and-closed.
- **obs ↔ tests** — obs-plan §9's two CI gates (log conformance, zero-unlogged-panics) consume CI artifacts; a new step in the same job shares the streams those gates read.

## Acceptance criteria contributions
- (obs) No absolute host-file path (drive-letter `X:\`, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`) appears in any new probe's job-log output or in the recorded reading; a path-shaped policy value is reported by presence/shape only (per obs-plan §9 Log conformance check + §11 Logs).
- (obs) The recorded reading is machine-parseable from a pasted excerpt with no human-review step in the path (per obs-plan §1 Agent-driven invariant + §11 Universal).
- (obs) An absent registry key or unreadable value is recorded as an explicit "absent" reading rather than omitted — the assertion is key presence, not a non-null value (per obs-plan §6 Required fields).
- (obs) The new steps mint no span, add no `tracing` line and create no new telemetry-artifact path; the a11y job's existing `logs/agent-latest.jsonl` and `runs/a11y/&lt;run_id&gt;.jsonl` uploads and the in-job conformance assertion under `CONDUCTOR_RUNS_DIR=runs/a11y` are unchanged (per obs-plan §1 instrumentation-scope CI row + §9 Telemetry artifact handling + §11 Spans bounded set).
