# a11y extract

## Relevance
Partial — the chunk adds diagnostic steps to the `a11y` job, which is a11y's own CI gate surface (a11y-plan §9 Platform, §3 CI integration), but it adds no UI surface and triggers no new WCAG criterion; a11y's authority here is over the gate's posture, artifact hygiene and platform-claim discipline, not over the probes' content.

## Constraints
- The `a11y` job's verdict must stay fail-fast and undecidable by a diagnostic: a11y-plan §11 (CI) bans skipping a11y on CI failure and requires the step be a gate, not a warning; its shipped enforcement mechanism is `CONDUCTOR_A11Y_STRICT` plus assertion of the runner's PRINTED verdict (failed-spec count, per-spec skip tally against the expected-skip SET, driven-session banner), because an exit code alone cannot distinguish a skipped-green run from a real pass. Added `continue-on-error: true` steps must not perturb that printed-verdict parsing or the expected-skip SET (per a11y-plan §11 CI; scope's own citation of "a diagnostic can never gate").
- No a11y artifact may carry an absolute host path or an internal seam-crate struct name — a11y inherits tests' Status JSON constraint (per a11y-plan §11 SLO; §3 Structured violation JSON schema, which requires node selectors be stored DOM-relative / `data-testid` and never filesystem paths). This binds both the job log and the recorded reading.
- No probe may stand up a second browser-automation stack: a11y-plan §11 (CI) requires ONE webview-automation stack (axe injected into tests' tauri-driver/WebdriverIO session, no puppeteer/CDP). A probe that launches a browser or a second driver would cross that ban as well as the scope's harness-spawn rule (b).
- CI jobs and steps must be identified BY NAME, not by `ci.yml` line coordinates — a11y-plan §3 (Configuration) states coordinates move as the workflow grows and were a measured source of stale claims.
- Readings recorded from the hosted image must not be generalized into capability claims about the measured dev-host platform SET, and vice versa: a11y-plan §9 (Platform) and §11 (CI) hold the Windows WebView2 host / Linux+`xvfb` capability statements as dated measurements distinct from the hosted `windows-2025` arrangement.
- a11y-plan §11 (Strategy, carve-out) requires the CI PROOF of the routine Operable pair be recorded as still OWED while the `a11y` job is red at WebView2 session creation; a diagnose-only chunk may not convert a probe reading into a conformance or green claim (reinforced by §11 Strategy's ban on claiming WCAG conformance without machine-verifiable evidence).
- a11y-plan §10 (SLO invariants) bans soft a11y SLOs and retry-once policies; a probe result must never become a soft signal the gate keys on, and no probe may add a retry around the gate step.

## Patterns to follow
- Host-tool handle discipline: a11y-plan §3 (Bootstrap `a11y-ci-gate-wire`, Screen reader test pattern) uses named env handles (`CONDUCTOR_MSEDGEDRIVER`, `CONDUCTOR_NVDA`) where unset ⇒ skip at exit 0, with `CONDUCTOR_A11Y_STRICT` flipping an unresolved handle to non-zero under CI — the existing precedent for "a step that reports what it finds without deciding the gate."
- Report-by-shape scrubbing: a11y-plan §3 (Structured violation JSON schema) already solves "a value that would be a host path" by recording a DOM-relative selector instead of the real location — the precedent for the scope's "a policy value that is itself a path is reported by presence/shape."
- Artifact emission through tests' 5-command contract: a11y-plan §9 (Pipeline integration) and §3 (CI integration → Command) require a11y results surface through the `logs` command, with CI artifacts uploaded via `actions/upload-artifact`.
- Resource-attribute tagging: a11y-plan §9 (CI-specific resource attributes) and §3 (Structured violation JSON schema) tag CI artifacts with `service.name` / `deployment.environment` plus `ci.run.id` / `git.commit.sha` for obs cross-correlation — the existing shape for any CI-produced a11y artifact.
- Dated, arm-scoped recording: a11y-plan §9 (E2E row) and §11 (Strategy) record runs by id, event and outcome with the arm named — the form the scope's "recorded reading" should match so the reading is not later misread as a platform capability.

## Anti-patterns to avoid
- Letting a diagnostic weaken or decide the gate — a11y-plan §11 (CI) bans a warning-shaped a11y step and bans a run that passes by skipping.
- Leaking absolute host paths or internal seam-crate struct names into any a11y artifact or log — a11y-plan §11 (SLO).
- Introducing a second browser-automation stack or driver for any probe — a11y-plan §11 (CI).

## Contract bindings
- **a11y ↔ obs §6**: a11y-plan §3 (Structured violation JSON schema) binds a11y *violation* emissions to the obs §6 envelope plus obs §3 resource tags (13 keys local / 15 under CI). Whether a diagnose-only reading artifact is inside that binding or is chunk evidence outside the harness is not settled by the plan — research's question.
- **a11y ↔ tests §6**: a11y-plan §3 / §9 require the a11y leg ride tests' one webview-automation stack and emit through the `logs` command of the binding 5-command harness contract; whether the probes sit inside that leg or beside it in the job is research's question.
- **a11y ↔ security**: the scope's harness-spawn rule (b) over `ci.yml` meets a11y-plan §11 (CI)'s one-stack ban — a probe that launches a program crosses both, so the spawn question and the stack question resolve together.
- **a11y ↔ route**: a11y-plan §11 (Strategy) names the *Hosted-runner WebView2 session* route entry as owner of the job's standing red; this chunk's readings feed that ownership, per the plan's own record.

## Acceptance criteria contributions
- (a11y) Every probe step added to the `a11y` job is diagnose-only — no gate step's outcome keys on a probe result, and the job's pass/fail remains determined by the routine arm's fail-fast verdict (per a11y-plan §11 CI).
- (a11y) The `CONDUCTOR_A11Y_STRICT` + printed-verdict assertion mechanism still enforces non-skipping after the probes are added: the failed-spec count and the per-spec skip tally against the expected-skip SET are unchanged by the new steps (per a11y-plan §11 CI). Whether that mechanism is in force in the job today is research's question.
- (a11y) Neither the job log nor the recorded reading contains an absolute host path or an internal seam-crate struct name; a path-shaped policy value is reported by presence/shape only (per a11y-plan §11 SLO + §3 Structured violation JSON schema).
- (a11y) The recorded reading identifies the job and its steps by NAME, states the run by id/event/branch/outcome, and attributes the run's red to the standing WebView2 session-creation failure rather than to this chunk — with no green or conformance claim drawn from a probe (per a11y-plan §3 Configuration, §9 Platform, §11 Strategy).
