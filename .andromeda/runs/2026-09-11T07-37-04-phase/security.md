# security extract

## Relevance
Relevant — the chunk edits `.github/workflows/ci.yml`'s `a11y` job (a governed spawn locus and the site of the third dependency class) and writes a committed `evidence/` reading, both of which security-plan.md governs directly.

## Constraints
- **Artifact hygiene binds to both surfaces.** No absolute host path and no internal seam-crate struct name may reach the job log or the committed `evidence/` record — the ban names the per-chunk `evidence/` tree explicitly, and these records are agent-parseable ground truth shared across hosts, so they carry state/identity fields only (per security-plan.md §Security Anti-Patterns → Logging; §Error Handling "Run-report artifact sanitization"). A policy value that is itself a path is therefore reported by presence/shape, never verbatim.
- **Spawn rule (b) is at SIX governed forms across THREE loci, `ci.yml` among them, and "a seventh crossing escalates again — this class never becomes routine"** (per security-plan.md §Security Anti-Patterns → Code Patterns rule (b)). A registry or process-state read constructs no child and is not a crossing; a probe that *launches a program* is. The 2026-09-09 precedent bounds this: a plain `run:` step invoking a fixed toolchain binary with fixed argv is the class of `cargo build` / `cargo audit` and is NOT counted among the six. Which side each of the three probes falls on is a P3 question.
- **The third dependency class's admitting controls must survive untouched.** The `a11y` job's WebView2 Evergreen bootstrapper is a CI-time-fetched dependency in no lockfile that `cargo audit` / `cargo deny` / `npm audit` are structurally blind to; its sole admitting control is the pre-execution `Get-AuthenticodeSignature` check (status `Valid` + `O=Microsoft Corporation`, non-zero exit before the binary runs), and §Dependency Security requires that **neither the fetch nor the install step carry `continue-on-error`** (per security-plan.md §Dependency Security, third dependency class). The chunk's new diagnostics require `continue-on-error: true`; that posture must not propagate to those two steps.
- **The runtime version float carries a stated exit condition.** Always-latest Evergreen is deliberate and temporary, bounded by "once the `a11y` job actually GATES … the runtime is pinned to a version," with an in-step floor (post-install runtime major ≥ 152, non-zero exit otherwise) holding meanwhile (per security-plan.md §Dependency Security, third dependency class). The chunk's module-version reading is *input* to that disposition; the reading must not be recorded in a way that silently retires the float or relaxes the in-step floor (the pin disposition itself is v3-02 per the scope).
- **Networking: the one non-loopback egress in the project is the CI-only bootstrapper fetch** (per security-plan.md §Threat Model Summary → Infrastructure → Networking; §CI/CD — "the supply-chain STEPS are unchanged … the audited SURFACE is not"). A probe that fetches anything over the network widens that recorded exception and is a new supply-chain surface, not a diagnostic.
- **The no-secrets invariant binds the committed reading.** Conductor owns no secrets and that invariant must hold for the whole `conductor-*` workspace (per security-plan.md §Secret Management; §Security Anti-Patterns → Secrets). Registry policy hives and process/session state are operator-machine surfaces whose value space was never enumerated, so a verbatim dump into a committed artifact is the route by which a secret-shaped or host-identifying string could first enter the tree.

## Patterns to follow
- **Handle NAME + boolean/state, never the value** — the CI arm's producer of `CONDUCTOR_MSEDGEDRIVER` already prints a handle-named `Test-Path` precondition in the step shell, reporting the handle name and a boolean and never the path (per security-plan.md §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row). This is the in-repo precedent for a `ci.yml` step reporting on a path-valued subject.
- **Scrub-on-write with a visible marker** — the speech-log ingest boundary treats untrusted third-party text by mapping any drive-letter / `%APPDATA%` / `/Users` / `/home` token to `<host-path>` and marking the row with a `security_finding`, keeping the raw artifact under gitignored `runs/` (per security-plan.md §Input Validation, screen-reader speech-log ingest row). Registry values and loaded-module paths are the same class of read-whatever-the-host-has text.
- **Report absence as a named absence, not as an error carrying a path** — committed-manifest read faults carry `e.kind()` only, never the path (per security-plan.md §Input Validation, committed SUT-facing manifests row). The scope's "explicitly reporting the absence of a key rather than omitting it" lands on this shape.
- **`<redacted>` rendering for a resolved location that must still be proven present** — the readiness gate renders `data_dir: "<redacted>"` while still attesting the handle (per security-plan.md §Security Anti-Patterns → Universal, preflight bullet).

## Anti-patterns to avoid
- NEVER let a committed `evidence/` record or the job log leak absolute host paths or internal seam-crate struct names (per security-plan.md §Security Anti-Patterns → Logging).
- NEVER add a seventh governed harness-spawn crossing as a routine addition — if a probe must launch a program in `ci.yml`, that is a boundary widening requiring operator escalation, with no playbook rule available to routinize it (per security-plan.md §Security Anti-Patterns → Code Patterns rule (b)).
- NEVER commit a secret-shaped string to the `conductor-*` workspace — a verbatim registry/environment/session dump into the reading is the plausible route (per security-plan.md §Security Anti-Patterns → Secrets).

## Contract bindings
- **Host-path scrub ↔ obs (path/value redaction in emitted records) and ↔ tests** — security-plan.md §Input Validation names the proving mechanism for the analogous committed record as a hygiene grep asserting no host path / seam-crate struct name, plus a closed-set check; this chunk's reading needs an equivalent check owned by tests, not by security prose.
- **Spawn rule (b) ↔ arch** — a seventh crossing is a boundary/capability decision escalated to the operator, not a security-local call (per security-plan.md §Security Anti-Patterns → Code Patterns rule (b)).
- **`continue-on-error` posture ↔ a11y-plan §11 (a gate must not pass by skipping) and ↔ tests §CI Integration** — the same job carries both never-`continue-on-error` supply-chain steps and always-`continue-on-error` diagnostics; the two postures must stay attached to the right steps.
- **Module-version reading ↔ dependency-version disposition (v3-02)** — the third dependency class's pin exit condition consumes this chunk's reading (per security-plan.md §Dependency Security).

## Acceptance criteria contributions
- Zero absolute host paths and zero internal seam-crate struct names in the new probes' job-log output and in the committed `evidence/` reading; any path-valued policy value appears by presence/shape or as `<host-path>`, never verbatim (per security-plan.md §Security Anti-Patterns → Logging and §Error Handling).
- The governed harness-spawn form count remains SIX: no new probe constructs a child process outside the plain fixed-program/fixed-argv `run:` class; if one must, it is escalated to the operator before it ships (per security-plan.md §Security Anti-Patterns → Code Patterns rule (b)).
- The WebView2 fetch step and the `Install WebView2 Evergreen runtime 152+ (gate)` step still carry no `continue-on-error`, still perform the `Get-AuthenticodeSignature` check before the binary runs, and still assert the runtime-major ≥ 152 floor; `continue-on-error: true` appears only on the newly added diagnostics (per security-plan.md §Dependency Security, third dependency class). Whether the workflow as committed already satisfies this is research's question.
- The `a11y` job gains no new network egress beyond the already-recorded CI-only bootstrapper fetch (per security-plan.md §Threat Model Summary → Infrastructure → Networking).
