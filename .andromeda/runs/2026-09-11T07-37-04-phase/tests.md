## Constraints
- The `a11y` job's step set is OPEN — `continue-on-error` diagnostic steps and an `if: always()` `a11y-session-diag` upload are registered beside the gate — but test-plan §9 (Pipeline structure, E2E-webview row) requires that the GATE step itself never carry `continue-on-error`, "since a gate that can report success by skipping or erroring is the thing the strict arm exists to forbid". Three added probes are diagnostics under that rule; the `run --e2e` step and the reused `journal_conformance` gate over `runs/a11y` must keep their non-`continue-on-error` posture.
- A CI job's red/green is decided only by the enumerated conditions — test failure (nextest 100/101), coverage below `--fail-under-lines 60`, clippy/fmt, `cargo audit`/`cargo deny`/lock drift (per test-plan §9 Build failure conditions and §10 Build failure conditions). A probe that returns nothing, or a reading that contradicts the expected cause, must not move the job verdict.
- CI jobs are identified BY NAME, never by `ci.yml` line coordinate, "which move as the workflow grows" (per test-plan §9 Matrix builds). Adding steps moves every downstream coordinate, so the recorded reading and any plan text must key on the job/step name.
- Artifacts MUST NOT leak absolute host paths or internal seam-crate struct names (per test-plan §3 Status endpoint shape; the boundary is asserted by a negative test, with the redaction allowlist owned by obs per §3 `log-format-bind-with-obs`). This binds the recorded reading and the job log, and matches the chunk's own artifact-hygiene constraint — a policy value that is itself a path is reported by presence/shape.
- No CI gate may run a live-Pulse leg; the sanctioned live paths are `workflow_dispatch` / `scripts/agent-run.{sh,ps1}` (incl. `run --live`) / a cargo-feature-gated target invoked directly / an npm-script wdio suite (per test-plan §11 CI, stack-specific, and §9 Live-Pulse scenarios). A registry- or process-state probe stays inside CI's stub-only envelope.
- `CONDUCTOR_A11Y_STRICT`'s two measured arms are the mandated coverage for that handle — strict + unresolved driver handle ⇒ exit 1, lax + unresolved ⇒ exit 0 with the dev-host skip preserved (per test-plan §1 Coverage triggers, Vector-1 fourth per-reader class). The chunk must leave that posture undisturbed.
- A runner-dependent result is a determinism break to fix at the cause, never a runner to pin to (per test-plan §10 Zero-flakiness budget) — which is why §6 names the hosted IMAGE (a policy or session property), not a runtime × driver pairing, as the open variable this probe set targets.

- The two diagnostics already registered in the job — "WebView2 driver + runtime versions" and the `if: always()` "WebView2 session isolation" probe — plus the `if: always()` `a11y-session-diag` upload are the shape §9's E2E row records for a diagnostic addition (per test-plan §9 Pipeline structure).
- Driver-independent probing: §6 Drivers-per-surface records the bare-app probe "with no driver in the picture at all" as the form that isolated the endpoint finding and made it byte-identical through tauri-driver and direct at `msedgedriver` (per test-plan §6 desktop-webview row).

- Probe-log observables are grepped for the TARGET string a log line actually carries, never for the emitting function name, which may appear nowhere in the log (per test-plan §9 Live-Pulse scenarios, the bootstrap-window-override precedent).
- If anything reaches the harness shells rather than `ci.yml` alone, both variants must expose identical semantics — asserted of the SCRIPTS together with the invoking environment (per test-plan §3 Bootstrap phases, `5-command-discipline-wire`).

## Anti-patterns to avoid
- Never let a diagnostic decide the gate, and never attach `continue-on-error` to a gate step or lower a quality gate "just this once" (per test-plan §9 Pipeline-structure E2E row and §11 Quality).
- Never write a new probe artifact into the harness's non-recursive `"$RUNS_DIR"/*.jsonl` glob — the a11y violation record at `runs/a11y/<run_id>.jsonl` is deliberately a separate shape outside it so `status` cannot read it as a scenario run (per test-plan §3 `run` → `--e2e` CI stage selectors).
- Never introduce a manual smoke step or human-reviewed screenshot as the evidence for the reading (per test-plan §11 Universal) — the recorded artifact must be agent-readable.
