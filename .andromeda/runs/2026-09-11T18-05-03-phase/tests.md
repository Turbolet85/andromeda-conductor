## Relevance
Relevant — the chunk edits the `a11y` CI job's step set (which test-plan owns as the E2E-webview stage), re-runs the deferred `--unit` gate, and adds an operator-local dev-host arm over the routine `--e2e` leg.

## Constraints
- The `a11y` job's diagnostic steps are diagnose-only and the GATE step is not: test-plan.md §9 (Pipeline structure, E2E-webview row) requires every diagnostic member to carry `continue-on-error` + `if: always()` while the gate step never carries `continue-on-error`, "since a gate that can report success by skipping or erroring is the thing the strict arm exists to forbid" — so a section-selectable probe invocation placed inside the isolation step inherits the diagnostic posture, and the job's verdict stays the routine arm's printed verdict (per test-plan.md §9).
- The `--e2e` leg's verdict is read from the PRINTED output, never the exit code (the handle guard is designed to skip at exit 0): zero on the `Spec Files:` failed count, a per-spec skip tally within the expected-skip SET (the two live-hold subjects; a third skip is a failure), and the `[webview2 … windows]` driven-session banner (per test-plan.md §3, `run` → CI stage selectors).
- That printed-verdict contract is asserted of the SCRIPTS **together with the invoking environment** — a PowerShell caller preempting native-command exits (`$PSNativeCommandUseErrorActionPreference = $true`) diverges the `.ps1` leg with zero script delta (per test-plan.md §3, `run` → `--e2e`, and §3 Bootstrap phases → `5-command-discipline-wire`). Arm B runs from a *different* shell (elevated), so this is the contract its reading must be taken under; whether an elevated shell profile sets that preference is research's question.
- The 5-command surface is closed at five with no new `CONDUCTOR_*` handle, port or stage selector — the `--live` precedent records exactly this discipline for a new harness branch (per test-plan.md §3, `run` → CI stage selectors). A diagnostic probe invocation must not become a sixth command or a stage selector.
- CI jobs and steps are identified BY NAME, never by `ci.yml` line coordinate, "which move as the workflow grows" (per test-plan.md §9, Matrix builds). The scope's touchpoints are given as line coordinates (`:382`–`:512`, `:513`, `:411`, `:422`); the plan and any committed record must name the steps instead.
- The PREREQ gate is the `--unit` stage leg and nothing else: `agent-run.{sh,ps1} run --unit` ⇒ `cargo nextest run --workspace --profile ci`, with `cargo test --workspace --doc` and `cargo clippy --workspace --all-targets -- -D warnings` as their own separate stages, not folded in (per test-plan.md §9 pipeline table + §3, `run` → CI stage selectors). Build-failure conditions are `NextestExitCode` 100/101 (per test-plan.md §9).
- Live-Pulse legs are never a CI gate (per test-plan.md §11 → CI, and §9 Live-Pulse scenarios). The elevated dev-host arm is the ROUTINE `--e2e` arm (no live Pulse); keeping it routine is what keeps it outside the operator-gated live SET.

## Patterns to follow
- The operator-local leg pattern, as registered for the `sr*` screen-reader family and the driven arm (per test-plan.md §6, Drivers per surface → desktop-webview): the operator supplies the *invocation and the host condition*; the machine produces the graded record from the session's own log against its action timeline, and the operator's role is REVIEW of that record. Arm B's elevated run is that shape.
- The routine arm's self-seeding subject: `seedFixtureRuns()` invokes the `conductor-run` `envelope_fixture` target under `CONDUCTOR_E2E_SEED_DIR`, writing through the production writer, and the tauri-driver spawn carries repo-relative `CONDUCTOR_RUNS_DIR=runs/e2e-fixture` (`resolve_under` rejects absolute handles); the dir is clean-re-created per session so no session's journal leaks into another's subject (per test-plan.md §3, `run` → `--e2e`, and §6 routine-arm paragraph). An elevated re-run on the same host must re-seed, not inherit residue.
- The de-literalized verdict record: the arm's sample is the SET it evidences (fully green with only the two live-hold subjects skipped), the pass tally being a moving count (per test-plan.md §6, desktop-webview row). The scope's `12 passing / 2 skipped` is a cited prior reading, not a pin to re-assert.
- Fixed-argv harness spawn: the leg-owned `activate-window.ps1` is spawned with fixed argv and the sidecar by fixed program NAME through the inherited `PATH`, never through a shell or interpolated operator value (per test-plan.md §11 → Mocking, and §6 `sr*` firing form). A section-selector parameter added to `webview2-cause-probe.ps1` follows that form.
- The measured-set discipline for host/runtime claims: readings are recorded as PAIRS/SETS with the host named, and a reading taken on one host is never generalized to another (per test-plan.md §6, desktop-webview Mode cell — the "PAIR is not the discriminator" record). Arm B's null result retires elevation only as measured on this host.

## Anti-patterns to avoid
- Never let a gate pass by skipping or erroring: the `[probe] complete: 3/3 sections` assertion must still fail on a missing section after any split, and "a context-skip is never a pass" (per test-plan.md §9 Pipeline E2E row + §6 routine-arm rule); a duplicated marker that lets one arm satisfy the gate for both is the vacuous-pass class §6 already records (the `Absent` check that "passed VACUOUSLY").
- Never introduce a manual smoke step or a human go/no-go judgment (per test-plan.md §11 → Universal). The precedent is explicit at test-plan.md §1 (Untestable zones): the applied Windows creation flag is evidenced by an operator-local leg's machine-observable, "never by a unit assertion and never by a manual smoke step". Arm B must land as a recorded reading from an agent-graded leg, not an operator attestation.
- Never bake a fresh literal for a set the code owns — neither the a11y diagnostic-step enumeration nor the arm's pass tally (per test-plan.md §9 Pipeline E2E row and §6 desktop-webview row, both de-literalized to SETs); and never weaken the gate to make the job green (per test-plan.md §11 → Quality).

## Contract bindings
- tests ↔ obs: test-plan.md §3 (Log format / Status endpoint shape) is the source of truth obs-plan §3 derives from; the a11y leg's `runs/a11y/<run_id>.jsonl` violation record is this envelope's eleven fields plus obs's resource tags, deliberately outside the harness's non-recursive `"$RUNS_DIR"/*.jsonl` glob so `status` cannot read it as a scenario run. Any CI-step or probe change must leave the envelope, the `status` disk read and the JSONL shapes untouched so §3 ↔ obs-plan §3 still agree.
- tests ↔ a11y: the a11y assertions run inside the same `a11y` job whose step set this chunk edits (per test-plan.md §9 Pipeline E2E row); test-plan owns the step posture and the printed-verdict wiring, a11y-plan owns what the specs assert.
- tests ↔ security: the probe invocation must add no new spawned program, bind, or `CONDUCTOR_*` handle (per test-plan.md §3 stage-selector rule + §11 → Mocking argv ban), which is the tests-side reading of the scope's "harness-spawn form count stays at SIX".
