# tests extract

## Relevance
Relevant — the chunk's entire modify-set is one crate-local test target (`crates/conductor-report/tests/matrix_ledger_gate.rs`), so this domain owns it end to end.

## Constraints
- The failing target sits at the crate-local `tests/` tier that test-plan §4 names for `conductor-report` (the tier the zero-unclassified assertion was re-homed to, because it must reach both `conductor_core` and `conductor_report` sides of the dependency edge); it is a CI-runnable static gate over committed artifacts — no live Pulse, no stub, no `runs.db` (per test-plan §4, §6 Coverage-matrix completeness gate).
- Ledger/matrix gates must assert by SET/property, never by a literal count or id range — test-plan §1 Critical Path 6 requires set-equality "no literal count or P-ID range", and §6 records that a static row count "is the literal-count form this same path's Verification signal forbids". A baked version prefix is the same class of literal (per test-plan §1 Critical Path 6, §6).
- A red test is a binding build-failure condition, not a dispositionable state: any test failure is `NextestExitCode` 100/101 and fails the build; `blocked`/`ManualCheck`/`KnownResidual` are envelope states of a scenario RUN, not an escape for a failing gate (per test-plan §9 Build failure conditions, §10).
- The repaired target must be green under BOTH runners — `cargo nextest run` and the standing runner-portability gate `cargo test -p conductor-report` (full, non-doc); a runner-dependent result is a determinism break to fix at the cause, never a runner to pin to (per test-plan §4 Framework, §10 Zero-flakiness budget).
- The gate's inputs are committed, read-only declarative artifacts consumed in-test; test data must be self-seeded/declarative and no test may write or normalise the artifacts it reads (per test-plan §7 Self-bootstrapping requirement, §7 Test data lifecycle). The scope's immutability of `requirements.md` is consistent with this; the plan adds that a committed input must carry its MEANING under test, not just its parseability (§7).
- A gate that can report success by skipping or emptying its subject is the failure mode test-plan §9 forbids of a gate step ("a gate that can report success by skipping or erroring is the thing the strict arm exists to forbid"); the anti-vacuity arm is therefore load-bearing and must survive the generalisation (per test-plan §9, §6 negative-arm discipline).
- The scoped mutation audit is an operator/local instrument, never a blocking CI stage and never a numeric threshold, so it is optional for this chunk's acceptance (per test-plan §9 Scoped mutation audit, §10 Mutation-survivor disposition).

## Patterns to follow
- The sibling gate in the same directory — `crates/conductor-report/tests/coverage_gate.rs` — is the shipped three-arm form test-plan §6 prescribes: load the artifact at runtime from its conventional repo path via `CARGO_MANIFEST_DIR` (never the CWD-relative default, which cannot resolve from a test binary's package-root CWD), a negative arm that removes each row IN TURN and asserts the error NAMES the dropped id, and a byte-equality arm over the committed artifact. Whether the ledger gate's scan already resolves this way is research's question (per test-plan §6).
- Set-equality asserted in BOTH directions is the plan's assertion shape for ledger-style gates, chosen so the gate fails on a new unbacked entry, on a stale pin, and on a lost classification alike (per test-plan §6 Scenario-backing leg).
- Table-driven accept/reject matrices via rstest `#[rstest]` + `#[case]` are the plan's fixture pattern for a predicate matrix — the natural home for "accepts `v{N}-{NN}`, rejects prose titles, rejects `P-NNN`" (per test-plan §4 Fixture pattern, §4 Conventions on test grouping).
- Crate-local `tests/` grouping with snake_case `#[test]` fn names namespaced by the seam crate (per test-plan §2 Test directory + naming conventions, §4 Conventions).
- Where a doc/assertion message must name a space, name the SET or the rule rather than substituting a fresh literal — the de-hardcode precedent the amendments below establish (per test-plan §6, §1 Critical Path 6).

## Anti-patterns to avoid
- NEVER replace the baked `v2-` literal with a baked `v3-` literal (or a hard-coded two-version union): that reproduces the literal-count/range form test-plan §1 Critical Path 6 and §6 forbid, and re-stales at `conductor-0.4.0` — the exact failure mode the chunk exists to end.
- NEVER reach green by weakening, deleting or making conditional the anti-vacuity assertion, nor by narrowing the directory scan — "NEVER skip quality gates 'just this once'" (test-plan §10 Quality bans) and §9's rule that a gate able to succeed by skipping is forbidden.
- NEVER quarantine-with-retry or pin to one runner: no nextest `retries`, and a test green under one runner and red under the other is a defect to remove at the cause (per test-plan §11 CI, §10).

## Contract bindings
- tests ↔ arch/catalog id-space: the gate's `no_pulse_p_id_occupies_an_id_position` arm and the `:208` message encode the separation between the version-capability id space and the SUT's Pulse `P-NNN` space, which test-plan §11 Universal (project-specific) governs from the other side ("NEVER add a scenario without a Pulse P-ID") and §6 keys the coverage-matrix selectors on ("mono P-ID tokens — the manifest's accepted set"). The generalised predicate must keep the two spaces disjoint or it breaks that binding.
- tests ↔ CI (§9): the shared gate is the Unit stage `agent-run.{sh,ps1} run --unit` → `cargo nextest run --workspace --profile ci`; this chunk's red is that stage's red (per test-plan §3 `run` CI stage selectors, §9 pipeline table).
- tests ↔ obs: none required. The change must mint no envelope, journal or self-obs line, so the §3 ↔ obs-plan §3 log-format/envelope agreement stands untouched — a test-only chunk that alters neither is the expected shape (per test-plan §3 Log format).

## Acceptance criteria contributions
- (tests) `cargo nextest run --workspace --profile ci` is green with zero failures — the gate's three arms pass and the run's failed count is 0 (per test-plan §9 Build failure conditions / §3 `run --unit`).
- (tests) The same target is green under the runner-portability gate `cargo test -p conductor-report` (full, non-doc), not nextest alone (per test-plan §4 Framework).
- (tests) The repaired predicate is asserted by property/set — no version literal baked into the gate's live path, so the `conductor-0.4.0` transition needs no edit here (per test-plan §1 Critical Path 6 and §6 Coverage-matrix completeness gate).
- (tests) A discrimination arm remains that fails LOUDLY on a vacuous required set and on a mis-admitted input (prose title, `P-NNN`) — the negative-arm and non-skippable-gate discipline (per test-plan §6 negative arm, §9 gate-step rule).
- (tests) Workspace coverage stays at or above the Minimal line gate `--fail-under-lines 60` (a test-only change adds no production lines but the gate remains binding) (per test-plan §10 Coverage thresholds).
