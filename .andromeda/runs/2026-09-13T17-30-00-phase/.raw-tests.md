## Constraints
- The mutation read-out gate is the TALLIES, never the exit code: `cargo mutants` exits non-zero for surviving/timeout CLASSES and exits 0 on `Found 0 mutants to test` (a no-op, never a pass), so acceptance reads `mutants.out/` with `missed.txt` holding EXACTLY the run's accepted-deliberate survivors and every other named survivor present in `caught.txt` (per test-plan §4 Unit Test Strategy → Mutation instrument). The run discipline is also mandated there: `-f` paths resolve from the WORKSPACE root, `--test-tool=nextest` is REQUIRED, output redirected off the repo root.
- Disposition, not score, is the acceptance: every NAMED survivor ends killed OR classified accepted-deliberate against a cited rule, the roster is the enumerated SET in §12 (a new acceptance EXTENDS it), and this is explicitly NOT a numeric threshold — "the score moves as a consequence of dispositioning named survivors, and is never itself the acceptance" (per test-plan §10 Quality Gates → Mutation-survivor disposition). This is the plan-side basis for the scope's replacement of the `≤ 8` bar.
- Roster identity is by function + COLUMN, re-measured rather than derived by line arithmetic (per test-plan §12 Test Decisions Log → the 2026-09-04/2026-09-05 re-pointings of the `declares`, class-B/C, `run_thread` members). The scope's `[inferred]` `execute.rs:95:27 → :105:17` changes the COLUMN, which §12's rule does not by itself license as a re-point — whether that mutant is the standing class-B member or a new entrant is research's question.
- A kill whose outcome depends on the HOST is banned: §12 member 4 records the `spawn.rs:116` agreement test as CONSIDERED AND REJECTED because it kills one arm or the other depending on `PATH`, and "a roster is an enumerated set that must mean the same thing on every host" (per test-plan §12 + §10 Zero-flakiness budget). - Any killing test added here must be green under BOTH runners — `cargo nextest run -p &lt;crate&gt;` AND `cargo test -p &lt;crate&gt;` — the runner-portability gate; a runner-dependent result is a determinism break to fix at the cause, never a runner to pin to (per test-plan §4 Framework + §10 Zero-flakiness budget).
- The workspace line-coverage gate stays `--fail-under-lines 60` with an enumerated exclusion list that names `conductor-verify/tests/common` by path (per test-plan §10 Coverage thresholds); whether the shipped llvm-cov invocation would also need to exclude a NEW `conductor-emit/tests/common` is research's question.

## Patterns to follow
- A crate-local `tests/common/mod.rs` shared-helper module is the plan's own named mechanism, already cited for `conductor-verify` (`stub_pulse_mcp` lives there per test-plan §4 conductor-verify bullet and §5 boundary table "Module ↔ external"). Collapsing `conductor-emit/tests/` clone pairs onto one such module follows the plan's stated directory convention: crate-local `tests/` for in-crate integration, snake_case file/fn naming (per test-plan §2 Test directory + naming conventions).
- Kill assertions go through the public seam API and the observable contract (envelope / verdict / state output), not private fns or fixture internals (per test-plan §11 Test Anti-Patterns → Unit).
- Where a survivor proves unreachable, the sanctioned outcome is a NEW roster member with its own cited rule and a citation home under the chunk's `evidence/` — the form every existing member takes (per test-plan §12, each member naming its `evidence/disposition-ledger.md` / `survivor-dispositions.md` home).
- Table-driven kills use rstest `#[rstest]` + `#[case]`; async seams use `#[tokio::test(flavor = "current_thread", start_paused = true)]` (per test-plan §4 Fixture pattern at unit level + §2 Agent-runnable invariants).
- If a kill for a stdio/spawn/observability path collides with process-global state, the remedy SET is (a) a test binary of its own, or (b) an in-module guard serializing only the tests touching the singleton — never a runner knob (per test-plan §11 → Integration, as widened 2026-09-10).

## Anti-patterns to avoid
- NEVER read a verdict off `cargo mutants`' exit code in either direction, and never treat `Found 0 mutants to test` as a pass (per test-plan §4 Mutation instrument).
- NEVER adopt a kill that is host-dependent or runner-dependent, and never serialize a shared-state defect away with `--test-threads=1` or a profile setting (per test-plan §10 Zero-flakiness budget, §11 Integration).
- NEVER assert against implementation details or fixture-internal values to make a mutant die — assert the seam's public behaviour / envelope contract (per test-plan §11 Unit).

## Contract bindings
- tests ↔ obs: the eleven-key envelope + JSONL journal shape is owned by test-plan §3 Log format / Status endpoint shape and bound to obs-plan §3; single-sourcing the assertion const is a test-side move only if the field SET is untouched.
- tests ↔ arch: §12's accepted-deliberate reasons cite architecture.md (§Occupied Resources — the fixed `:4317` endpoint and the fixed `andromeda-pulse-mcp` program name; §Design Philosophy thin shells), and §11 Integration cites arch §Established Decisions [Module Boundaries] forbidding widening a crate's public API for tests alone — so a kill requiring new `pub` visibility or a new injectable production seam is an arch-side change, not a tests-side one.
- tests ↔ wrap: the §12 roster re-pointing is an amendment to a spec master; test-plan's own header states it is not edited during phase/implement runs, so the re-point rides wrap's amendment flow (consistent with the scope's statement).
