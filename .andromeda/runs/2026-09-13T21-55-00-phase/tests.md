## Relevance
Partial — the chunk authors an outward-addressed specification artifact rather than test code, but test-plan.md governs how its hard-grade predicate must be gradeable, how a committed artifact is (or is not) pinned in-tree, and the standing workspace gates any chunk owes.

## Constraints
- The contract's "hard grade" must be phrased so a claim about **Pulse's own behaviour** grades at the **harvest tier** — Pulse's own emitted lines captured and asserted at the `conductor-run` unit tier — which is the shipped shape for every live SUT claim (`baseline` / `storm` / `restart` / `pii` / `connection` / `severity` / `lifecycle` harvests) (per test-plan.md §6 Critical path scenarios + §1 Critical paths). A predicate no harvest-tier assertion can read reproduces the unmeasurable-instrument defect in a new name.
- A reported state (`Blocked` / `ManualCheck` / `KnownResidual` / `CalibrationRegion`) is never a non-zero process exit; only a hard `Fail` is (per test-plan.md §11 E2E, stack-specific + §3 `run` exit-code semantics). The predicate must therefore say which side of the assertion-policy split a hue-budget breach lands on — a hard `Fail` (exit non-zero) or a report-for-human state.
- Pulse's reaction may never be proven by the CI stub; the stub proves MCP wiring only, and every live-Pulse leg is operator/local-gated, never a CI gate (per test-plan.md §11 Test Strategy, stack-specific + §9 Live-Pulse scenarios). A contract satisfiable by a stubbed observable would be gradeable in CI and therefore wrong by this rule.
- Live Pulse and its `corpus.db` are a flagged **untestable zone** — a third-party process Conductor cannot start or reach internally (per test-plan.md §1 Untestable zones). The contract states what Pulse must emit; it cannot mandate a Conductor-side driver for a Pulse-internal event.
- If the artifact ships as a parseable manifest under `contracts/`, the shipped `contracts/` class is Rust-read at a fixed path and bounds-checked/derived at load (pinned MCP contract manifest; `pulse-run-contract.toml` `[incident_formation].min_canary_poll_seconds` deriving both `boot` budgets, a missing term being a hard exit 2, never a silent default) (per test-plan.md §5 Cross-module patterns + §3 `boot` Timeout). Whether the new artifact acquires any in-tree reader at all is research's question.
- A committed fixture must carry its **meaning** under test — one round-trip per committed fixture through the production reader/writer/validator, so a change leaving the file parseable but semantically inert fails at `cargo nextest` (per test-plan.md §7 Self-bootstrapping requirement). This binds only if the artifact becomes a fixture consumed in-test; test-plan.md mandates no general verification duty for a committed non-Rust instrument with no reader (see amendment history).
- Scenario config files are committed declarative fixtures validated through serde + garde at load, one-per-P-ID under `scenarios/` (per test-plan.md §7 Seed strategies + §4 Scenario-config validation surface). Any header-pointer edit to `scenarios/halo-hue-encoding.toml` must leave it loading through that validator unchanged.

## Patterns to follow
- **The committed-artifact gate precedent** — `coverage-matrix.md` is gated by a crate-local `tests/` target (`conductor-report --test coverage_gate`), asserting byte-equality against a renderer plus negative arms, over an artifact LF-pinned by `.gitattributes` so the comparison is host-independent (per test-plan.md §6 Coverage-matrix completeness gate). This is the shape to reuse **if** P4 decides the contract gets an in-tree assertion.
- **Declare-only + harvest-tier re-basing** — when no read-back surface can carry a check, the scenario's `[[expected]]` checks are retired with the measurement recorded in the scenario TOML header, the row lands `verdict` null / `state="KnownResidual"` (non-Blocked), and the live claim grades hard at the harvest tier (per test-plan.md §6 scenarios for `pii-scrub` / `connection-lifecycle` / `severity-lifecycle`). The delegated hue budget's present posture (recorded, never asserted as a pass) is this same pattern; the contract is what would move it to a graded check.
- **Set-naming over literals** — assertions and prose name the SET the code owns rather than a count or a coordinate (the de-hardcoded P-ID range, the `live_leg_order`-anchored leg set, roster members keyed by description) (per test-plan.md §6 Selector strategy + §3 `--live` + §12 roster identity). A contract stating a resolution or window as a bare literal restates the class of claim these rules keep retiring.
- **Derived-budget discipline** — a budget the harness must honour is derived from a committed contract term at invocation, never restated as a flat literal, and a missing term is a hard failure (per test-plan.md §3 `boot` Timeout). Directly applicable to how a ≤2 s bound and its resolution requirement should be expressed if the artifact is machine-read.
- **Evidence provenance** — goldens and pinned captures are committed and CI runs fail-don't-write; interactive accept UIs are banned (per test-plan.md §7 Golden artifacts + §11 Universal). The mechanism pins in `delegated_timing_harvest.rs` are record, not target, and stay as they are.

## Anti-patterns to avoid
- NEVER fake Pulse's reaction as a CI verdict (per test-plan.md §11 Test Strategy, stack-specific) — the contract must not be satisfiable by a stub-emitted observable.
- NEVER lower a threshold or skip a gate to make a run pass (per test-plan.md §11 Quality) — the ≤2 s bound is not restatable more loosely, and a narrower claim substituted for the blocked one is the same move.
- NEVER use `sleep(N)` for in-test synchronisation; a wall-clock wait is legitimate only as a harness-level firing-form precondition between legs, reproducing a SUT-side transition that emits no signal (per test-plan.md §11 E2E). A contract whose window is stated as "wait N seconds then read" must survive this ban.
