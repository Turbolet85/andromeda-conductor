## Patterns to follow
- Declare-only is an already-governed config shape, not a new one — the boundary row enumerates `[[expected]]` as `Option`/`#[serde(default)]`-class optional surface, so a zero-`[[expected]]` scenario stays inside the documented boundary (per security-plan §Input Validation, scenario-config row). Follow the five-scenario precedent's shape rather than inventing a new retirement marker.
- `dive`-never-`skip` on every nested spec field is the standing annotation rule; `PhaseSpec.emission`'s historical `skip` is the recorded regression to not repeat if any struct in `scenario.rs` is reshaped (per security-plan §Input Validation; §Security Anti-Patterns → Input).
- Sibling-reading invariants ship as `Scenario::check_*()` raising `CoreError::Config` at load — a harness fault, never a verdict — because garde 0.22.1's field-level `custom` receives `(&field, &())` (per security-plan §Input Validation, scenario-config How column).
- Committed-evidence hygiene has a shipped pattern: host-path tokens scrubbed to `<host-path>` before write, with a hygiene grep over the committed record as the gate (established for `evidence/nvda-pass.json`) (per security-plan §Input Validation, speech-log ingest row; §Security Anti-Patterns → Logging).

## Anti-patterns to avoid
- NEVER mark a nested spec field `#[garde(skip)]` — garde never descends, so its rules never run and the boundary is silently bypassed while the rules still appear present (per security-plan §Security Anti-Patterns → Input).
- NEVER write a sibling-reading invariant as `#[garde(custom)]` — it would look enforced while never testing the invariant (per security-plan §Security Anti-Patterns → Input).
- NEVER let committed evidence records leak absolute host paths (canonicalized `CONDUCTOR_*` dirs, `ANDROMEDA_PULSE_DATA_DIR`, any drive-letter / `%APPDATA%` / `/Users` / `/home` token) or internal seam-crate struct names (per security-plan §Security Anti-Patterns → Logging).
