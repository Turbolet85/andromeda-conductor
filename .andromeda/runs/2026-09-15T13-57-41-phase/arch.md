## Constraints
- Scenario config is **declarative data**, serde-deserialized and garde-bounds-checked at load with no scenario DSL; `[[expected]]` is a declared config key, so retiring a block is a TOML edit under `scenarios/` — never a code path that special-cases a scenario by name (per architecture.md §Conventions — Config conventions, §Established Decisions [Scenario Config Format]).
- The scope law "no scenario without a P-ID" binds: each retired scenario must stay committed, keep its `p_ids`, and still pass membership against `contracts/pulse-capabilities.toml` via `Scenario::from_toml_str_with` at the three binary-edge load sites (per architecture.md §Cross-cutting Patterns — Scope law, §Established Decisions [Accepted Capability Set]).
- Two sibling-spanning load-path checks read `expected` and must still pass once it is emptied: `Scenario::check_budgets` (spans `expected` ↔ `slo_tier`) and `Scenario::check_checklist` (rejects a `[[checklist]]` beside a NON-empty `expected`). Whether any of the five scenarios declares `[[checklist]]` or a `budget_ms` today — and therefore whether emptying `expected` changes a load verdict — is research's question (per architecture.md §Established Decisions [Validation Library], §Conventions — Config conventions).
- A declare-only scenario has a defined landing contract: ZERO `CheckRecord` rows on all three surfaces (JSONL journal, `run_check` table, the Markdown per-check detail line) and an envelope row of `verdict: null` / `state: "KnownResidual"` by either of the two routes; every read-back call failure still lands `Blocked` unconditionally (per architecture.md §Standard Contracts — Run report envelope, Per-check record).
- The declare-only family registry in §Standard Contracts is the single enumerating home and currently states NINE families; moving it is wrap's amendment flow, and `.andromeda/` masters are read-only in this phase (per architecture.md §Standard Contracts — Run report envelope).
- `check_scenario_backing` / `UNBACKED_AUTO` holds `Auto`-classified capabilities to *a scenario NAMING them*, not to a scenario grading them — so retirement leaves the gate green by construction while weakening what an `Auto` claim means. That is exactly the "capability claimed on a widened basis" boundary the scope defers to P4/P5; the arch requirement is that no widening be asserted on this chunk's basis (per architecture.md §Established Decisions [Accepted Capability Set]).
- Pinning tests/guards land inside the locked crate-per-seam workspace (`conductor-core` · `-timeline` · `-emit` · `-faults` · `-verify` · `-report` · `-run` · `-cli` · `-tauri`); the dependency edges ARE the architecture and a forbidden cross-seam edge will not compile. Which member owns a scenario-corpus assertion is research's question (per architecture.md §Established Decisions [Module Boundaries], §Inherited Defaults — Module boundaries, §Occupied Resources — Crate names).

## Patterns to follow
- **Declare-only retirement precedent (nine prior families).** The scenario stays committed, stays validated, keeps its P-ID, and its live row grades at the harvest tier instead — the shape `fingerprint-storm` / `pii-scrub` / the connection family / the structurally-dead-assertion class already took (per architecture.md §Standard Contracts — Run report envelope).
- **Two-source integrity-gate shape for a code-native pin.** `check_sut_drift` and `check_scenario_backing` hold a code-native ledger to EXACT-SET equality against the committed catalog, failing with a typed `CoreError` variant so the ledger "can only shrink under compulsion" — the arch-native model if a minted guard must pin absence rather than presence (per architecture.md §Established Decisions [Accepted Capability Set]).
- **Sibling-spanning invariants ship as a plain `Scenario::check_*()` called from `from_toml_str`, never as a garde validator** — garde 0.22.1's `custom` is field-level only and sees no sibling field (per architecture.md §Established Decisions [Validation Library]).
- **Verdict/error wall.** A corpus/config integrity failure is a harness fault on the `Result::Err` side (`CoreError::Config` for a non-garde load-path check, `CoreError::Validation` only for a garde failure); it is never expressed as a `Verdict` or `ReportState` (per architecture.md §Cross-cutting Patterns — Verdict/error wall, §Established Decisions [Scenario Config Format]).

## Anti-patterns to avoid
- No new occupied resource for this chunk: no new workspace crate, no new `CONDUCTOR_*` env handle, no port, and no new committed `contracts/` artifact — the reserved namespace covers only handles over artifacts arch already defines (per architecture.md §Occupied Resources — Environment variables, §Cross-cutting Patterns — Config management).
- Do not edit `.andromeda/architecture.md` (or any master) in this phase — including the §Standard Contracts declare-only family registry, whose move rides wrap's amendment flow (per architecture.md §Standard Contracts; scope.md §Surfaces and contracts touched).
- Do not mint a fresh corpus-tally literal (e.g. "N live `[[expected]]` blocks") into a spec registry; the 2026-09-15 precedent deliberately named the SET rather than a count, because a count re-stales on the next retirement (per architecture.md §Standard Contracts — Run report envelope).

## Contract bindings
- **§Standard Contracts (Run report envelope + Per-check record) ↔ tests and obs:** "declare-only ⇒ zero `CheckRecord` rows, envelope `verdict: null` / `state: KnownResidual`" is the shape the run-seam journal, the `run_check` table and the report renderer all share; any test asserting a retired scenario's grading asserts against that envelope, and `run_check`'s `latency_ms`/`deadline_ms` are NOT NULL precisely because a declare-only check emits no row.
- **§Occupied Resources (crate names, LOCKED) ↔ all domains:** every pinning guard minted under CARRY 2 lives in one of the nine workspace members; the wide sweep `grep -rln "<scenario-name>" crates/` the scope mandates is a sweep over exactly that locked set.
- **§Established Decisions [Accepted Capability Set] ↔ the `v3-04` coverage claim:** `contracts/pulse-capabilities.toml` is read-only here and the two integrity gates (`check_sut_drift`, `check_scenario_backing`) are what bound what the corpus may claim — the claimability decision itself is P4/P5's, not arch's.
