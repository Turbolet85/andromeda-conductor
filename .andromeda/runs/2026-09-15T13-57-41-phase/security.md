## Relevance
partial — the chunk edits committed instances of an enumerated external-input boundary (5 scenario TOMLs) plus its pinning guards; it adds no new boundary, dependency, spawn, listener, or network surface.

## Constraints
- Scenario config is an enumerated external-input boundary whose trust boundary is TWO co-equal mechanisms together — garde `#[derive(Validate)]` `range`/`custom` co-located with the serde structs, AND the load-path `Scenario::check_*()` arm invoked from `from_toml_str` (faulting as `CoreError::Config`, a harness fault at load, never a verdict). Retiring declarations from the committed corpus must not remove, relax, or route around either mechanism on the struct shape (per security-plan §Input Validation, scenario-config row; restated §Threat Model Summary → Attack surface, config-files vector).
- `check_checklist` is required to REJECT a `[[checklist]]` declared beside a non-empty `expected` (per security-plan §Input Validation, scenario-config row). Emptying `expected` INVERTS that sibling rule's outcome for any retired scenario that also declares a `[[checklist]]` — a shape previously rejected at load becomes accepted. Whether any of the five named scenarios carries a `[[checklist]]` (and whether `HoldPoint.checklist` is in play) is research's question; scope's surfaces table asserts validation is `[inferred]` unaffected, and this is the rule that can falsify it.
- `[[expected]].budget_ms` is required to carry garde `range(min = 1, max = MAX_BUDGET_MS)` PLUS the sibling-spanning `check_budgets` rule (≤ the scenario's own `slo_tier` deadline) (per security-plan §Input Validation, scenario-config row). Removing six `[[expected]]` blocks removes carriers of that key; the rules must remain on the struct regardless of what the corpus declares. Whether any retired block carried a `budget_ms`, and whether a moving pinning test was the only exerciser of that rule, is research's question.
- `dive` is the only correct annotation on a nested spec field; `#[garde(skip)]` deserializes the struct entirely unvalidated because garde never descends into it (per security-plan §Security Anti-Patterns → Input). A guard minted under CARRY 2, or any struct change made to accommodate an empty `expected`, must not convert a dive to a skip nor construct a `Scenario` by a path that bypasses `from_toml_str`.
- NEVER add a scenario without a Pulse P-ID (per security-plan §Security Anti-Patterns → Universal). Scope holds `contracts/pulse-capabilities.toml` read-only and `p_ids` unchanged — a declare-only scenario stays a scenario under that ban, so retirement must leave each P-ID intact.
- Committed evidence records (the per-chunk `evidence/` tree) and run-report-class artifacts must carry no absolute host paths and no internal seam-crate struct names — they are agent-parseable ground truth shared across hosts (per security-plan §Security Anti-Patterns → Logging; §Error Handling, run-report artifact sanitization). The CARRY-2 wide-sweep output and the pin inventory, if committed, inherit that duty; DECLARE-ONLY header citations must stay repo-relative, never host-absolute.
- The merge/release gate requires `cargo audit` green (and recommended `cargo deny check advisories bans licenses sources`) over an un-drifted committed `Cargo.lock` (per security-plan §Security Anti-Patterns → Universal; §Dependency Security). A zero-dependency-delta chunk still runs it; if it goes red, the `advisory-db` checkout porcelain check PRECEDES classifying the fault as external (per security-plan §Dependency Security, two-external-decay-faults block).

## Patterns to follow
- The two-mechanism split: field-level bounds as garde rules beside the serde struct in its owning seam crate; any rule that must read a SIBLING field as an explicit `Scenario::check_*()` called from `from_toml_str`, because garde 0.22.1's field-level `custom` receives `(&field, &())` and structurally cannot see a sibling (per security-plan §Input Validation, How column).
- A test that PINS the load path actually invoking each `check_*()` is the mandated shape for this boundary's coverage (per security-plan §Bootstrap phases → input-validation-library-install). CARRY 2's newly minted guards should reuse that existing pinning idiom rather than inventing a second enforcement mechanism.
- Harness-fault vs verdict wall: config parse/validation failures stay `Result::Err` (`CoreError::Config`), verification outcomes stay typed `Ok` values (per security-plan §Error Handling). A declare-only scenario must still load as a validated shape — neither an error nor a fabricated verdict.
- Failure origins and read faults name the handle and the file's own name, never a resolved path (per security-plan §Input Validation, committed-manifest row; §Error Handling) — the shape to follow if a new guard emits a diagnostic naming a scenario file.

## Anti-patterns to avoid
- NEVER deserialize scenario config without validation at load, and NEVER write a SIBLING-reading invariant as `#[garde(custom)]` — it would look enforced while never testing the invariant (per security-plan §Security Anti-Patterns → Input).
- NEVER mark a nested spec field `#[garde(skip)]`: the rules exist but never run and the boundary is silently bypassed (per security-plan §Security Anti-Patterns → Input).
- NEVER let a committed artifact or evidence record leak an absolute host path or an internal seam-crate struct name (per security-plan §Security Anti-Patterns → Logging).

## Contract bindings
- Scenario-config boundary ↔ tests: the pinning tests/guards this chunk moves and mints ARE the enforcement surface for §Input Validation's load-path `check_*()` mandate, and §Bootstrap phases requires a test pinning that invocation — so the tests domain owns the harness shape while security owns the invariant.
- CI security gate ↔ tests §CI Integration: `cargo audit` / `cargo deny` are jobs of the one existing workflow, not a separate pipeline (per security-plan §Dependency Security → CI integration).
- Evidence-record hygiene ↔ obs/tests artifact rules: the host-path scrub duty on committed records is the same rule obs applies to journals/reports; no PII is in play at all (data classification: PII "none", per security-plan §Threat Model Summary).

- (security) No nested spec field's annotation moves from `dive` to `skip`, and no sibling-reading rule is introduced as `#[garde(custom)]`, in either the retirement edits or the newly minted guards (per security-plan §Security Anti-Patterns → Input).
