## Relevance
Relevant — the chunk edits committed scenario fixtures and moves/mints crate-local pinning tests, both governed by this plan's declare-only retirement discipline and its unit/CI gates.

## Constraints
- A retirement to declare-only must record its MEASUREMENT in the scenario TOML header and leave the row grading `verdict` null / `state="KnownResidual"`, non-Blocked, `latency_ms` against the declared `slo_tier` — the shape §6 requires of every prior member of this class (per test-plan §6 Scenario: Headless deterministic scenario run, Cleanup parenthetical — the `pii-scrub` / `connection-lifecycle` precedents; restated at §1 Critical paths closing note).
- Removing `[[expected]]` blocks must not change exit-code semantics: `blocked`/`ManualCheck`/`KnownResidual`/`CalibrationRegion` are reported envelope states, never non-zero process exits; only a hard `Fail` exits non-zero (per test-plan §3 `run` exit-code semantics + §11 E2E stack-specific ban).
- A retired scenario stays in the catalog carrying its Pulse P-ID — the plan requires a static assertion that every catalog scenario carries a P-ID, and bans any scenario without one (per test-plan §4 "Scenario catalog + coverage-matrix" + §11 Universal project-specific).
- The coverage-completeness gate must stay green in BOTH of its axes after the edit: `check_sut_drift` over the committed classification, and the scenario-backing leg's exact-set equality in both directions over `UNBACKED_AUTO` (`Auto` only) — a pinned id a scenario now covers, or a covered id that loses backing, are both gate failures (per test-plan §6 Scenario: Coverage-matrix completeness gate + Scenario-backing leg). Whether `check_scenario_backing` keys on a scenario's EXISTENCE or on its graded checks — i.e. whether stripping `[[expected]]` from five scenarios can move that set — is research's question.
- The edited TOMLs are members of the committed-fixture family, which the plan requires to carry their MEANING under test via a round-trip through the production validator (`Scenario::from_toml_str_with`), not merely to parse (per test-plan §7 Self-bootstrapping requirement).
- Pin moves and any newly minted guard live at the per-seam crate-local tier and must be green under BOTH runners — `cargo nextest run -p <crate>` and `cargo test -p <crate>` — since runner portability is a standing gate, and a runner-dependent result counts as a determinism break, not a runner quirk (per test-plan §4 Framework + §10 Zero-flakiness budget).
- Coverage remains gated at Minimal thresholds (line ≥ 60%, `--fail-under-lines 60` workspace-wide); crate-local `tests/` trees are excluded by one generic path regex, so a guard placed under `tests/` contributes no covered lines (per test-plan §10 Coverage thresholds).

## Patterns to follow
- The declare-only retirement series §6 already carries — `error-baseline-spike`, `fingerprint-storm`, `restart-suppression`, the five severity-family TOMLs, `pii-scrub`, `connection-lifecycle` — each retiring checks that no read-back surface can carry, with the measurement recorded in the scenario header and (where a live claim survives) a harvest-tier home at `crates/conductor-run/tests/*_harvest.rs`. This chunk authors no new checks per its own boundary, so the harvest half is not owed here; the pattern names where a live claim would have to go if one were ever wanted (per test-plan §6, all six scenario subsections).
- The plan names the vacuous-`Absent` / structural-fail-`Contains` pair explicitly as the retirement ground for the `fingerprint-storm` and `pii-scrub` members — the same two directions this chunk's six blocks split into (per test-plan §6 Scenario: Fingerprint-storm; §6 Cleanup parenthetical, `pii-scrub`).
- Gate assertions are shaped as SET equality with a per-row negative arm, never as counts — the coverage gate's three arms are the in-repo model (runtime manifest load, a negative arm removing each classified row IN TURN, byte-equality to `render()`) (per test-plan §6 Scenario: Coverage-matrix completeness gate).
- Crate-local `#[cfg(test)]` modules plus crate-local `tests/` for slower legs; snake_case `#[test]`/`#[rstest]` fn names namespaced by the seam module path; rstest `#[case]` rows for table-driven catalog matrices (per test-plan §2 Test directory + naming conventions, §4 Conventions).

## Anti-patterns to avoid
- NEVER pin a literal count as the gate — a row/block/test count is the literal-count form the coverage path's own verification signal forbids; name the SET (per test-plan §6 Coverage-matrix completeness gate; the de-hardcode precedent in the amendment history below). Scope's own "test-count movement is unpredicted" premise is consistent with this.
- NEVER write brittle assertions against fixture-internal values — a pinning guard asserting check-membership must assert the seam's public contract/envelope shape, not private struct internals (per test-plan §11 Unit).
- NEVER fake Pulse's reaction as a CI verdict — a stub-proven substitute for a retired live-Pulse token check would be exactly this ban (per test-plan §11 Test Strategy, stack-specific).
