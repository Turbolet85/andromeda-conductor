# tests extract

## Relevance
Relevant (partial) — the chunk edits committed scenario fixtures and the tests pinning their tiers/derived deadlines; no new test tier, harness command, or E2E leg is owed.

## Constraints
- Committed `scenarios/*.toml` are per-suite test fixtures, not just product config (test-plan §7 Seed strategies, "Fixture files (scenario config)" row) — an edited `slo_tier` line is a fixture edit and inherits §7's rules.
- test-plan §7 Self-bootstrapping requires every committed fixture to carry its MEANING under test — one round-trip per committed fixture through the production reader/validator (the plan names `Scenario::from_toml_str_with` for the `conductor-tauri` scenarios fixture tree), so a re-tiered file must still load AND still assert the property its consumer depends on, not merely parse.
- test-plan §4 Framework makes runner portability a standing gate: the touched crates must be green under BOTH `cargo nextest run -p &lt;crate&gt;` and `cargo test -p &lt;crate&gt;`; a runner-dependent result is a determinism break under §10, never a runner to pin to.
- test-plan §3 Log format (Agent parsing) requires the journal's per-check `CheckRecord` line to carry `deadline_ms` and `budget_ms` (budget null when the check inherits its tier) while the envelope's eleven fields stay byte-unchanged — so a tier re-declaration moves derived VALUES, not the schema. Whether the shipped code derives `deadline_ms` from the declared tier at check time (and thus which goldens move) is research's question.
- test-plan §3 Status endpoint shape lists `slo_tier` as an envelope field and §3 `status` requires the read to target the NEWEST ENVELOPE line (selected by the envelope-only `seed` key), never the file's last line — any harness-level tier assertion must read it that way.
- test-plan §7 Golden artifacts + §11 Universal require insta goldens to be committed and CI fail-don't-write, never accepted through the interactive `cargo insta review` UI — a golden carrying a re-tiered scenario's tier/deadline must be regenerated non-interactively.
- test-plan §1 fixes the tier at `Minimal (0)` and §11 Test Strategy closes E2E at the 7 critical paths, so the expected breadth here is unit/fixture-tier; no live-Pulse leg is owed (which matches the scope's "not a live-Pulse chunk" boundary).

## Patterns to follow
- Table-driven per-scenario assertions via rstest `#[rstest]` + `#[case]` over the catalog / garde matrices (test-plan §4 Fixture pattern; §3 Test data bootstrap Mechanism) — the plan's established shape for a per-scenario row assertion.
- The committed-fixture round-trip pattern named in test-plan §7: one production-path round-trip per committed fixture (plan-named members: `conductor-tauri`'s `commands::tests::the_committed_scenarios_fixture_stays_loadable` over `crates/conductor-tauri/tests/fixtures/scenarios/`, plus `crates/conductor-run/tests/lamps_fixture.rs` and `envelope_fixture.rs`).
- Static assertions over committed artifacts at the crate-local `tests/` tier, CI-runnable with no live Pulse — the `crates/conductor-report/tests/coverage_gate.rs` shape (test-plan §4 Scenario-catalog bullet, §6 Coverage-matrix completeness gate). This is the shape the SIBLING `Scenario-assertion audit gate` will take; this chunk establishes state only.
- Set/property naming over fresh literals: test-plan §6 Selector strategy and the coverage gate both forbid literal counts/ranges in assertions, preferring the derived set — apply the same discipline to any tier/duration assertion added or moved here.
- Scenario-config validation stays garde-at-load with valid/invalid fixture matrices (test-plan §4 Scenario-config validation surface; §1 Coverage trigger "security-vector-coverage / property-test") — a tier edit must not bypass load-time validation.

## Anti-patterns to avoid
- Never write brittle assertions against fixture-internal values — assert on the Run-report envelope contract (test-plan §11 Unit); a hand-copied tier literal per scenario is exactly that class.
- Never assert on real wall-clock duration in a timeline test — drive `tokio::time::advance` under `start_paused = true` and assert scheduled ordering/shape (test-plan §11 Unit, stack-specific); a scenario's summed phase duration is a declared config property, not an elapsed measurement.
- Never lower or skip a binding gate, and never accept goldens interactively (test-plan §11 Quality; §11 Universal) — coverage `--fail-under-lines 60`, clippy `-D warnings` and zero-retry flakiness stay in force for this chunk's crates.

## Contract bindings
- tests §3 ↔ obs-plan §3 (log format / envelope): `slo_tier` is one of the envelope's eleven fields and `deadline_ms`/`budget_ms` ride the `CheckRecord` line. A tier re-declaration changes VALUES only; test-plan §3 requires the envelope shape and the two report-seam line shapes to stay unchanged, so the §3 ↔ obs §3 bind must remain untouched by this chunk.
- tests ↔ arch/core: `SloTier`'s closed variant set and `deadline_ms()` are owned outside this domain and read-only per the chunk's Boundaries; tests only pin what they return (test-plan §1 conductor-core entity, §3 Status endpoint shape).
- tests ↔ the sibling route entry (`Scenario-assertion audit gate`, `verification-matrix.json#v3-06`): the re-runnable mechanical check belongs there. Per test-plan §10/§11 Quality a shipped gate is binding, so this chunk must not land a partial gate that the sibling then has to re-cut.
- tests §3 `--live` leg budgets ↔ scenario `slo_tier`: the shells' `live_leg_order` per-leg budget (e.g. `halo-hue-encoding`'s `live_leg_budget_sec 180`) and the `boot` timeout derived from `contracts/pulse-run-contract.toml` are SEPARATE budgets from a scenario's declared tier (test-plan §3 `run` CI stage selectors, `boot` Timeout) — a tier edit must not be read as moving either.

## Acceptance criteria contributions
- (tests) `cargo nextest run -p &lt;crate&gt;` AND `cargo test -p &lt;crate&gt;` both pass for every crate holding a test that pins a re-tiered scenario's tier or derived deadline — the runner-portability gate, where a runner-dependent result counts as a determinism break (per test-plan §4 Unit Test Strategy / Framework + §10 Zero-flakiness budget).
- (tests) Every edited committed scenario fixture still round-trips through the production validator and still asserts its meaning, not just its parseability (per test-plan §7 Test Data &amp; Fixtures / Self-bootstrapping requirement).
- (tests) Any insta golden carrying a re-tiered scenario's `slo_tier` / `deadline_ms` is regenerated fail-don't-write, never via the interactive accept UI (per test-plan §7 Golden artifacts row + §11 Universal).
- (tests) The Run-report envelope's eleven fields and the journal's two report-seam line shapes are unchanged by the re-tier — only values move — so the §3 ↔ obs-plan §3 log-format bind still agrees (per test-plan §3 Test Harness Contract / Log format + Status endpoint shape).
