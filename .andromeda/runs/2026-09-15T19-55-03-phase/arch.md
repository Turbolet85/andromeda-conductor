# arch extract

## Relevance
Relevant — arch owns the closed `slo_tier` set, the declarative scenario-config conventions, and the `scenarios/` on-disk catalog this chunk edits; no new surface, crate, or contract is introduced.

## Constraints
- The tier set is CLOSED and pinned in two places: `slo_tier` is "a closed TEXT enum over exactly `<5s`/`<20s`/`<90s`" on the `runs` table and rides the eleven-field run envelope — so honesty may only re-select among the three, never mint a fourth (per architecture.md §Conventions → Data model conventions; §Standard Contracts → Run report envelope).
- The tier deadline is a CEILING, and latency is journal-relative — `read_back_observed_at − journal_emitted_at`, with "the corpus observed ONCE per scenario" and a per-check effective deadline of `budget_ms` when declared else the tier's (per architecture.md §Established Decisions [Timing-Tolerance Model]). This is the plan-side ground of the scope's Premise 1; the plan states what the SLO MEASURES, not whether summed phase duration bounds it from below — whether the verify seam's arithmetic makes the tier genuinely have to hold the duration is research's question.
- A declared `[[expected]].budget_ms` is cross-checked against **that scenario's own `slo_tier`** at load by `Scenario::check_budgets()`, with the ceiling DERIVED from `SloTier::Tier90s.deadline_ms()` (per architecture.md §Conventions → Config conventions). A downward re-tier can therefore make a previously-legal budget illegal at load; the plan records that no committed TOML declares one, but whether that still holds at HEAD is research's question.
- Load-error mapping is three-way and both arms are harness faults on `Result::Err`, never a verdict or a report state: parse or non-garde load-path check failure → `CoreError::Config`, garde failure → `CoreError::Validation` (per architecture.md §Established Decisions [Scenario Config Format]; §Design Philosophy "Outcomes are values, errors are harness faults").
- The load envelope's ASSERTED terms are per-emitting-phase (`max_sustained_storm_ms` + the wire-record rate term); `max_scenario_duration_ms` is recorded but NOT asserted, and the `[[exempt]]` ledger is held at exact-set equality in both directions (per architecture.md §Occupied Resources → `contracts/pulse-load-envelope.toml`). This is the arch backing for the scope's "envelope untouched" expectation, and the reason summed duration has no gate of its own today.
- Determinism under a seed is enforced structurally: a transition's `elapsed_ms` is a deterministic cumulative sum of effective gaps, never a clock read (per architecture.md §Design Philosophy "Determinism under a seed"; §Established Decisions [Determinism RNG]). Editing `gap_ms` changes the emission-stream shape a seed reproduces — which is why the scope's remedy must move the declaration, not the duration.
- Scenario config is declarative DATA with no DSL, bounds-checked by garde at load, validation co-located with the serde structs in the owning seam crate (per architecture.md §Conventions → Config conventions; §Cross-cutting Patterns → Config management). `scenarios/*.toml` and `crates/conductor-core/src/scenario.rs` are the only placements this chunk's surfaces occupy (per §Infrastructure Patterns directory tree; §Inherited Defaults → Module boundaries).

## Patterns to follow
- **Inline-comment-bearing TOML as the hand-author surface.** TOML was chosen over JSON specifically for hand-author ergonomics + inline comments across the per-P-ID scenario files (per architecture.md §Established Decisions [Scenario Config Format]) — the stated-reason comment rides an affordance the format decision already paid for.
- **Posture recorded beside the resource it qualifies, with its measurement and any falsification in place.** The load-envelope bullet records both its asserted terms and the prediction that was measured false, so a reader can tell how far to trust it (per architecture.md §Occupied Resources → `contracts/pulse-load-envelope.toml`). Situation 1's operator-ratified honest-bucket posture belongs in that shape.
- **One shared basis between a static catalog gate and its per-run counterpart.** `check_load_envelope` and `LoadEnvelope::classify` funnel through one predicate so the gate and the run caption cannot diverge (per architecture.md §Occupied Resources → `contracts/pulse-load-envelope.toml`) — the shape the deferred v3-06 gate should take if it lands.
- **Sibling-spanning invariants ship as a load-path `Scenario::check_*()` called from `from_toml_str`, never as a garde validator** — `check_capabilities` / `check_budgets` / `check_checklist` are the existing three (per architecture.md §Established Decisions [Validation Library]). A tier-vs-phases rule spans `slo_tier` and its sibling `phases`, so it is that route by construction.
- **Closed enums reject rather than infer**: an unknown declared kind is a parse error, never an inferred default (per architecture.md §Conventions → Config conventions).

## Anti-patterns to avoid
- Widening the tier ladder or introducing a fourth `slo_tier` value / a free-form deadline — the enum is closed at the config, envelope, and `runs.db` column simultaneously (per architecture.md §Conventions → Data model conventions).
- Expressing a tier-vs-duration rule as a container-level or sibling-reading `#[garde(custom)]` validator — structurally impossible under the pinned garde 0.22.1, whose `custom` is field-level and receives no sibling (per architecture.md §Established Decisions [Validation Library]).
- Letting a dishonest or unloadable scenario surface as a verdict/report state (`Fail`/`Blocked`) — config faults sit on the `Result::Err` side of the verdict/error wall (per architecture.md §Cross-cutting Patterns → Verdict/error wall; §Established Decisions [Error Handling]).

## Contract bindings
- **arch ↔ tests/storage:** `slo_tier` is a field of the eleven-field run-report envelope AND a closed TEXT column on `runs.runs`; a re-tier changes the value landing on both surfaces, so envelope/journal conformance fixtures pinning a scenario's tier move with it (per architecture.md §Standard Contracts → Run report envelope; §Conventions → Data model conventions).
- **arch ↔ tests (per-check grain):** `run_check.deadline_ms` is NOT NULL and derives from the tier via the effective-deadline rule, with `budget_ms` NULL on inherit; the nine-key `CheckRecord` rides three surfaces (JSONL journal · `run_check` · the Markdown per-check line) (per architecture.md §Standard Contracts → Per-check record; §Established Decisions [Timing-Tolerance Model]).
- **arch ↔ a11y/obs:** the `runs/a11y/<run_id>.jsonl` violation record carries `slo_tier` `<90s` as a MAPPED, not measured, value — a scenario re-tier must not be assumed to move it (per architecture.md §Occupied Resources → On-disk artifacts).
- **arch ↔ tests (catalog gate):** `contracts/pulse-load-envelope.toml`'s asserted per-emitting-phase terms and its empty exact-set `[[exempt]]` ledger are what a phase-duration edit would disturb; a tier-only edit reaches neither (per architecture.md §Occupied Resources → `contracts/pulse-load-envelope.toml`).

## Acceptance criteria contributions
- (arch) Every committed scenario's `slo_tier` after the change is one of exactly `<5s` / `<20s` / `<90s`, and no new variant or literal deadline is introduced anywhere in config, envelope, or `runs.db` schema (per architecture.md §Conventions → Data model conventions).
- (arch) No `gap_ms` / phase-duration value changes: the emission-stream shape a given seed reproduces is byte-identical before and after, since `elapsed_ms` is a deterministic cumulative sum of effective gaps (per architecture.md §Established Decisions [Determinism RNG]).
- (arch) Every edited scenario still loads through `Scenario::from_toml_str_with` without raising `CoreError::Config` / `CoreError::Validation` — in particular any declared `[[expected]].budget_ms` still satisfies `check_budgets()` against the scenario's NEW tier (per architecture.md §Conventions → Config conventions; §Established Decisions [Scenario Config Format]).
- (arch) `contracts/pulse-load-envelope.toml` and its `[[exempt]]` ledger are unchanged and every catalog verdict is unmoved, because the asserted terms are per-emitting-phase and `max_scenario_duration_ms` is recorded-not-asserted (per architecture.md §Occupied Resources → `contracts/pulse-load-envelope.toml`).
