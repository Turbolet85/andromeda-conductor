# security extract

## Relevance
**Partial** — the chunk adds no new trust boundary, but it adds a new READER of the plan's enumerated scenario-config boundary, produces operator-visible gate output plus committed `evidence/`, and (if registered in CI) lands a step in the same workflow that hosts the supply-chain gates.

## Constraints
- The 36 committed `scenarios/*.toml` are an enumerated external-input boundary whose validation is garde `range`/`dive` **plus** the load-path `Scenario::check_*()` arm; per `security-plan.md` §Input Validation (scenario-config row) and §Security Anti-Patterns → Input, a second parse path must not stand in for that boundary — if the check parses TOML independently (a `scripts/` script), it grades the corpus but validates nothing, and the garde/`check_*()` duty stays where it is. Whether the shipped load path already asserts any part of this chunk's two outcomes (notably `check_budgets`, which already cross-checks `budget_ms` against the scenario's own `slo_tier`) is research's question.
- The canonicalize/bounds duty **binds per READER, not per handle** (§Input Validation, env-var path handles row; §Security Anti-Patterns → Input, restated 2026-09-06). A new reader that resolves the scenarios directory must either take a fixed, non-operator-steerable resolution with no new `CONDUCTOR_*` handle, or carry an explicitly recorded residual — an unrecorded reader is the drift, not the validation.
- Gate output is an operator-facing surface: §Error Handling requires sanitized external responses (no absolute host paths, no internal seam-crate struct names, no stack traces), and §Security Anti-Patterns → Logging extends the same ban to committed `evidence/` records. A failure must name the offending scenario by the handle and the file's own name, never a resolved path.
- If registration is a CI gate, §Dependency Security (CI integration) requires the build to actually fail on a hit; the plan's own CI-gate discipline records steps as carrying **no `continue-on-error`** (§Dependency Security, third dependency class). A registered gate that cannot fail the build does not satisfy "enforced by something rather than by memory".
- §Security Anti-Patterns → Code Patterns rule (b) governs six harness-spawn forms across three loci, one of which is `.github/workflows/ci.yml`; a plain `run:` step invoking a fixed toolchain binary with fixed argv is the class of the existing `cargo build`/`cargo audit`/`cargo fmt` steps and is deliberately NOT counted among the six. Anything beyond that shape — a shell string, `Invoke-Expression`, a constructed argv carrying an operator value, or a network-fetched program — would be a seventh crossing, which §Security Anti-Patterns → Code Patterns treats as a never-routine boundary widening.
- Any dependency delta (a TOML parser, a Rust dev-dep, a Python lib) requires `cargo audit` green plus `cargo deny check advisories bans licenses sources` green over the **committed, undrifted** `Cargo.lock` (§Dependency Security; §Security Anti-Patterns → Universal). Note the plan enumerates only three dependency classes — the Rust crate graph, the npm tree, and the CI-time-fetched binary — so a Python-side dependency would fall under no existing gate; whether the check introduces one is P4's fork.

## Patterns to follow
- `conductor-report --test coverage_gate` — the existing test-binary gate over committed SUT-facing data: it loads through the same bounds-checking loader but resolves the conventional repo path from `CARGO_MANIFEST_DIR` rather than `default_path()`, because a cargo test binary's CWD is its own package root (§Input Validation, committed SUT-facing manifests row). This is the closest precedent if P4 picks "a Rust test over the catalog `conductor-core` already loads".
- Fixed `default_path()` through `resolve_under` with **deliberately no `CONDUCTOR_*` override handle** — the not-operator-steerable resolution every shipped committed-manifest reader uses (§Input Validation, committed SUT-facing manifests row).
- Host-path-free failure origin: a read fault carries `e.kind()` only, and a gate's failure names the handle plus the file's own name (§Input Validation, committed manifests + env-var path handles rows).
- Explicitly recorded residual for a test-only reader of an otherwise-shipped handle, as `conductor-run/tests/journal_conformance.rs` and `envelope_fixture.rs` carry (§Security Anti-Patterns → Input; §Bootstrap phases → input-validation-library-install).
- Committed evidence carries verdict/state/identity fields only, with host-path tokens scrubbed before write — the shape §Input Validation mandates for the speech-log ingest record and §Security Anti-Patterns → Logging mandates for the whole per-chunk `evidence/` tree. Bears directly on this chunk's probe forms and its synthetic known-positive control fixture.

## Anti-patterns to avoid
- NEVER let the check's output, its committed probe/evidence records, or any minted fixture leak an absolute host path or an internal seam-crate struct name (§Security Anti-Patterns → Logging; §Error Handling).
- If the check touches any scenario-config struct: NEVER mark a nested spec field `#[garde(skip)]` (garde never descends, so the rules never run) and NEVER write a sibling-reading invariant as `#[garde(custom)]` (garde 0.22.1 sees `(&field, &())` — it would look enforced while testing nothing); sibling-spanning rules ship as a `Scenario::check_*()` from `from_toml_str` (§Security Anti-Patterns → Input).
- NEVER commit a synthetic known-positive control fixture into `scenarios/` as a scenario without a Pulse P-ID, and NEVER let `Cargo.lock` drift or go uncommitted (§Security Anti-Patterns → Universal).

## Contract bindings
- **CI security gate ↔ tests §CI Integration** — the registration surface is the same single `.github/workflows/ci.yml` that hosts `cargo audit` / `cargo deny` / `npm audit --omit=dev` / `cargo fmt --all --check`; the new gate belongs in that workflow as a job/step, not in a second workflow that routes around the existing gates (§Dependency Security, CI integration).
- **Evidence/fixture hygiene ↔ tests (fixture authoring) and obs (scrubbing cross-cuts)** — the host-path scrub and closed-set discipline are mine; the fixture's content and the probe's assertions are the tests domain's. Conductor owns no PII (§Data Protection: all data classes "none"), so this binding reduces to host-path and struct-name scrubbing, not PII redaction.
- **Where the check lands (script vs. `conductor-core` test) is an arch capability decision**, not mine; my constraints attach to whichever reader results (§Input Validation, per-READER duty).

## Acceptance criteria contributions
- (security) The check's failure output and every committed `evidence/` artifact this chunk authors contain zero absolute host paths and zero internal seam-crate struct names — grep verifies (per `security-plan.md` §Security Anti-Patterns → Logging, and §Error Handling run-report artifact sanitization).
- (security) The check's resolution of the scenario corpus introduces no new `CONDUCTOR_*` override handle and nothing operator-steerable; if a new reader of an existing path handle results, its residual is explicitly recorded per READER (per `security-plan.md` §Input Validation, committed SUT-facing manifests row + env-var path handles row).
- (security) If registered in CI, the step is a fixed-program/fixed-argv `run:` step in the existing `.github/workflows/ci.yml` with no shell string, no `Invoke-Expression`, no operator-supplied value in the vector and no `continue-on-error`, so rule (b)'s six governed harness-spawn forms do not move (per `security-plan.md` §Security Anti-Patterns → Code Patterns rule (b), and §Dependency Security CI integration).
- (security) If any dependency lands, `cargo audit` and `cargo deny check advisories bans licenses sources` both exit 0 over the committed, undrifted `Cargo.lock` (per `security-plan.md` §Dependency Security, and §Security Anti-Patterns → Universal).
