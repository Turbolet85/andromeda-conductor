# tests extract

## Relevance
Relevant — the chunk's entire deliverable (a mechanical re-runnable check, its registration surface, and its can-fail demonstration) is test-domain work at the `unit`/crate-local-`tests` tier.

## Constraints
- A static check over committed files is unit- or crate-local-`tests`-tier and CI-runnable; E2E is reserved for the 7 critical paths only, and the per-seam unit layer is the bulk (per test-plan §2 Test Strategy pyramid + §11 Test Anti-Patterns → Test Strategy).
- The check's assertions must be set-equality / enumeration against the loaded catalog, never a literal count: test-plan §6 Coverage-matrix completeness gate states outright that "a row count is the literal-count form this same path's Verification signal forbids", and §1 Critical Path 6 requires "no literal count or P-ID range". The scope's "36 scenarios" / "2 of 36" figures are therefore describable but not assertable as the gate's predicate (per test-plan §6, §1 Path 6).
- A gate that can report success by skipping, finding no subjects, or erroring is not a gate: test-plan §9 (E2E-webview row) requires the GATE step never carry `continue-on-error`, §4 Mutation instrument requires `Found 0 mutants to test` be read as a NO-OP never a pass and the verdict be taken from the tallies rather than the tool's exit code, and §6's routine-arm rule states a skip is never a pass. This is the domain form of the chunk's "demonstrated able to fail" requirement (per test-plan §9, §4, §6).
- Each probe's can-fail demonstration must be an in-suite negative arm, not an external anecdote — the shipped pattern is §6's coverage gate, which "removes each classified row IN TURN from the REAL `coverage_matrix()` and asserts `Err(CoreError::SutDrift)` naming the dropped id" (per test-plan §6 Coverage-matrix completeness gate).
- Any synthetic known-positive control fixture (the wrapped-comment gloss file CARRY 3 now requires, since no committed file carries the gloss) must come from the sanctioned committed-fixture family — a crate-local `tests/fixtures/` tree — be consumed through the production validator/reader, and carry its MEANING pinned by a production round-trip, not merely its parseability (per test-plan §7 Self-bootstrapping requirement).
- The check must be green under BOTH runners: `cargo nextest run -p <crate>` and the standing runner-portability gate `cargo test -p <crate>`; a runner-dependent result is a determinism break to fix at the cause, and no retries may be added (per test-plan §4 Framework + §10 Zero-flakiness budget).
- Registration must not add a sixth harness command. The 5-command discipline is closed at boot/run/status/cleanup/logs; an operator instrument rides either a sibling stage selector (the `--unit`/`--integration`/`--e2e`/`--live` `case`-branch form) or a standalone committed script, as `scripts/mutation-gate.py` does — which §9 records as operator-local, invoked by no CI step, adding no sixth `agent-run.{sh,ps1}` command (per test-plan §3 Test Harness Contract, §4 Mutation instrument, §9 Scoped mutation audit).
- A static or stub-tier check may not grade Pulse's reaction as a CI verdict (per test-plan §11 → Test Strategy, stack-specific). This bears directly on CARRY 2's bar fork: the *satisfiable* bar is a declarative property of committed files and is gradeable here; a *discrimination-against-own-stimulus* bar asks whether a token reaches the report because of the scenario's stimulus — a SUT-behaviour claim the plan routes to the live/operator gate, never to a CI check.

## Patterns to follow
- `crates/conductor-report/tests/coverage_gate.rs` — the in-repo precedent for exactly this shape (static gate over a committed artifact, CI-enforced, unit-tier, no live Pulse): manifest loaded at runtime via `CARGO_MANIFEST_DIR` rather than a CWD-relative default path (a test binary's CWD is its package root), plus a per-row negative arm and a byte-equality arm (per test-plan §6 Coverage-matrix completeness gate).
- `scripts/mutation-gate.py`'s committed-instrument form — fresh gitignored output dir per invocation, verdict computed from the read-out tallies rather than the wrapped tool's exit code, operator-local footing, no CI step and no sixth command (per test-plan §4 Mutation instrument, §9 Scoped mutation audit). CARRY 1's "grade every tally the claim rests on" is the same discipline §4 already states two-sidedly for that gate (`missed.txt` holding exactly the expected set AND every other named survivor present in `caught.txt`).
- The roster split — `scripts/mutation-roster.toml` as the coordinate-free EXECUTABLE form joined on a key to a prose CITATION home, neither restating the other's content (per test-plan §10 Mutation-survivor disposition). This is the plan's existing answer to the chunk's limb-(d) problem: turning an authored enumeration (`tier-ledger.md`) into something a tally comparison can consume without duplicating the reasoning.
- Committed scenario-TOML fixtures read through the production validator and pinned by a loadability round-trip — `crates/conductor-tauri/tests/fixtures/scenarios/` via `Scenario::from_toml_str_with`, pinned by `commands::tests::the_committed_scenarios_fixture_stays_loadable` (per test-plan §7 Self-bootstrapping requirement).
- `.gitattributes` LF-pinning so a committed text artifact's byte comparison is host-independent (per test-plan §1 Critical Path 6). A wrap-tolerant line-joining sweep over `scenarios/*.toml` on a Windows host is exposed to the same line-ending hazard; whether the scenario tree is already LF-pinned is research's question.

## Anti-patterns to avoid
- Never key the gate on a row/scenario count or any baked literal (36 scenarios, 2 live `[[expected]]`, 9/2/6/19 tier classes) — name the SET, since a fresh literal re-stales at the next scenario (per test-plan §6 verification signal; §1 Path 6 de-hardcode rule).
- Never ship a gate that can pass vacuously — no `continue-on-error` on the gate step, no skip-as-pass, no zero-subjects-as-clean-sweep, and no gating on a wrapped tool's exit code in place of its read-out (per test-plan §9 E2E row; §4 Mutation instrument; §6).
- Never fake Pulse's reaction as a CI verdict, and never mask a non-deterministic result with a runner knob or a retry (per test-plan §11 → Test Strategy + Integration; §10).

## Contract bindings
- **tests §3 ↔ obs-plan §3 (harness/log-format bind):** if registration touches `scripts/agent-run.{sh,ps1}`, test-plan §3 requires the five-command surface, the Run-report envelope, the `status` disk read and the JSONL journal shapes all stay unchanged so §3 and obs-plan §3 still agree — the discipline the `--live` stage flag followed. §3 further requires the two shells hold identical semantics, asserted of the scripts *together with the invoking environment* (a caller's `$PSNativeCommandUseErrorActionPreference` can diverge the `.ps1` leg at zero script delta).
- **tests §9 ↔ security §Dependency Security:** a new CI gate step joins the workflow already carrying `cargo audit` + `cargo deny check`; test-plan §9 Build failure conditions own its red/green semantics, and §9's precedent (operator-resolved at `2026-09-06-coverage-completeness-gate`) is that such a step takes NO §9 stage-table row.
- **tests §9 ↔ a11y CI gate:** the `a11y` job sets the standing rule for any gate step sharing that workflow — the gate itself never carries `continue-on-error`, only diagnostic steps do.
- **tests §4 ↔ arch catalog convention:** the "no scenario without a P-ID" static assertion over the catalog is already a test-plan §4 mandate sourced from arch's Test-Relevant Conventions; a new enumeration/classification pass over `scenarios/*.toml` should reuse that loader seam rather than re-parsing TOML independently. Whether such a loader is reachable from the chosen host is research's question.

## Acceptance criteria contributions
- (tests) The check's target is green under both runners — `cargo nextest run -p <crate> --test <target> --profile ci` and `cargo test -p <crate>` — with no retries configured (per test-plan §4 Framework + §10 Zero-flakiness budget).
- (tests) Every probe carries an in-suite negative arm that makes it fail over a mutated or synthetic subject; any control fixture lives in a crate-local `tests/fixtures/` tree, is consumed through the production validator, and its meaning is pinned by a production round-trip (per test-plan §6 Coverage-matrix completeness gate + §7 Self-bootstrapping requirement).
- (tests) No assertion in the check is keyed on a literal count or a fixed id range; every predicate is set-equality or per-subject enumeration against the catalog as loaded (per test-plan §6 verification signal + §1 Critical Path 6).
- (tests) The registration surface adds no sixth `agent-run.{sh,ps1}` command and leaves the envelope, `status` read and JSONL shapes untouched; if a CI step, the gate step carries no `continue-on-error` and a zero-subject or skipped run is a FAIL, not a pass (per test-plan §3 Test Harness Contract + §9 CI Integration).
