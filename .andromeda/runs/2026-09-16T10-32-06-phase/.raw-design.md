# design extract

## Relevance
Partial — the chunk changes CI launch context, not design surfaces, but the gate it is trying to make honest is precisely the arm that asserts this plan's token contract (contrast pairs, the reduce-motion block, the closed six-lamp set); outcome (B) additionally lands in the plan's Blocked/KnownResidual treatment.

## Constraints
- The token contract is the **subject** the routine arm asserts: design-system §Surface: desktop-webview / Tokens declares all 34 tokens on plain `:root` (names + values binding, NOT `@theme`) with a light block under `@media (prefers-color-scheme: light)`. Whatever launch context the chunk adopts, the running app must still present that contract to a driven session — whether a limited-token / non-elevated / scheduled-task launch changes what the webview resolves (user profile, OS theme, vendored font resolution) is research's question, not something this plan can attest.
- design-system §Motion (Hard limits) requires every transition and animation to be dropped under `@media (prefers-reduced-motion: reduce)`, declared CSS-natively in the same token bundle — that block is one of the routine arm's assertion subjects, so it is in this chunk's blast radius even though the chunk edits no CSS.
- design-system §Color Palette (Verdict vs ReportState note) requires that outcomes the machine did not pass/fail never collapse into `Fail`: `Blocked` = *never measured*, carrying the named precondition string; `KnownResidual` = *measured but pre-accepted*, carrying "expected until {named fix}". If outcome (B) ships, the a11y capability's exclusion must take one of those shapes — a measured-cause exclusion is `KnownResidual`-shaped, an unrunnable-precondition exclusion is `Blocked`-shaped — never a red row and never a red job left standing as the signal.
- The lamp set is **closed at six** (design-system §Iconography + §cli Tokens). A ratified exclusion must not introduce a seventh lamp state or a sixth `ReportState`; the plan's precedent for a run-level qualifier is the non-lamp caption set (`[ENVIRONMENT-SUSPECT]`, `[PRECONDITION]`) in the Residual-mute recessive tier, outside the lamp column.
- design-system §cli Tokens requires color to be paired with an ASCII label always (`[PASS]`/`[FAIL]`/`[MANUAL]`/`[RESIDUAL]`/`[BLOCKED]`, `✓ ✗ ? ~ • →`), never color alone, and forbids emoji in machine-parseable piped output — applies to any CLI/CI text the exclusion or the new launch step emits.
- design-system §Typography (Loading) requires self-hosted WOFF2 (Fontsource, vendored into the Tauri bundle, no runtime CDN). A changed launch principal must not be made to depend on network font fetch; conversely the rendered faces are the same under any principal that can read the bundle.
- design-system §Color Palette Text Hierarchy records that `--text-tertiary` / `--text-muted` values were solved against the full pair set in BOTH themes — token values are therefore not free to move as a convenience fix for a red contrast assertion; a value change re-opens that whole solve.

## Patterns to follow
- **§cli Component Pattern 4 (Verdict / report-state lines)** — the shipped shapes for a non-Fail outcome: `~ P-0xx Residual  &lt;thing&gt; → &lt;named fix&gt;` (ANSI 246, never red) and `• P-0xx Blocked  &lt;named precondition string&gt;` (ANSI 60). If (B) needs a rendered form, reuse these rather than inventing one.
- **§Component Patterns 6 (Run-report view)** — `KnownResidual` rows render the dashed muted lamp plus the "expected to fail until {named fix}" note so a documented residual never shows as a surprise red `Fail`; the same discipline governs how an a11y-arm exclusion should read.
- **§Component Patterns 3 (Coverage matrix) / §cli Component Pattern 3** — `conductor coverage` is a separate 4-column table (P-ID · Title · Category · Mode) with **no** verdict/state column and no bracket prefix; out-of-scope classification is expressed by tinting the Mode cell with the existing Residual-mute pair. If the exclusion is expressed as a coverage-mode classification rather than a verdict, this is its home.
- **§Surface: desktop-webview / Tokens** — assertions bind tokens **by name**, with raw values living only in this plan; the harness at `crates/conductor-tauri/ui/test/a11y/accessibility.e2e.ts` carries the names and reads values off the running app, which is why a launch-context change that alters what the app renders (theme block, missing custom props) would surface as a design-token failure rather than a harness failure.

## Anti-patterns to avoid
- design-system §Anti-Patterns (Rejected Defaults): **never conflate "no result yet" with "failed"** — a job that is red because nobody adjudicated it, or an exclusion rendered as a red `Fail`, is the exact pattern this plan rejects.
- **No new palette row, no new ANSI entry, no new lamp** for the exclusion (§cli Tokens, whose Residual-mute entry already records three non-lamp reuses of one existing pair) — reuse `--status-residual` / ANSI 246 and its bracket label.
- No raw hex / ms / px literal introduced anywhere the chunk touches CSS or styling (§Surface: desktop-webview Tokens, tokens-by-name).

## Contract bindings
- **design §Color Palette ↔ a11y §6 pair table**: the routine arm's contrast pairs are token NAMES from this plan; the plan owns the values, a11y owns the ratio thresholds (4.5:1 text, 3:1 non-text). Neither side may move alone.
- **design §Motion (reduce-motion override) ↔ a11y SC 2.3.3**: the `@media (prefers-reduced-motion: reduce)` block in the token bundle is the enforcement mechanism the routine arm reads as declarations.
- **design §Color Palette / §Iconography (lamp + label) ↔ a11y SC 1.4.1 not-color-alone**: the closed six-lamp, always-text-paired rule is asserted by the same arm.
- **design ↔ tests/CI harness**: whether the arm executes at all is the tests/CI domain's question; design's stake is only that (A) leaves the assertion subjects intact and (B) does not silently drop the token-pair, reduce-motion, or lamp assertions from what the a11y capability claims.

## Acceptance criteria contributions
- If the launch-context change touches any CSS/token surface, all token-pair ratios must still hold in BOTH theme blocks, re-solved as a set rather than per-node (per design-system §Color Palette / Text Hierarchy).
- Under the chosen launch context, the app must still present the full `:root` token contract including the light-theme block and the `prefers-reduced-motion: reduce` block — whether it already does under a non-elevated/limited-token launch is research's question (per design-system §Surface: desktop-webview / Tokens + §Motion Hard limits).
- If (B) ships: the exclusion is recorded as a non-`Fail` state carrying its own text — `Blocked` with the named precondition, or `KnownResidual` with "expected until {named fix}" — and is never rendered red nor added as a seventh lamp/`ReportState` (per design-system §Color Palette Verdict-vs-ReportState note + §Anti-Patterns Rejected Defaults).
- Any new CLI/CI text this chunk emits carries an ASCII label alongside any color, reuses the existing Residual-mute pair for a run-level qualifier, and adds zero new tokens or ANSI entries (per design-system §Surface: cli / Tokens).
