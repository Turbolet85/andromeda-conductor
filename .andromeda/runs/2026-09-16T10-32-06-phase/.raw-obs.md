- obs-plan §10 (Always-required SLO invariant) + §9 (Zero-unlogged-panics gate) require every failure to surface as a structured `tracing::error!` JSON event — a bare `^thread.*panicked` line in `logs/agent-latest.jsonl` or stderr is a CI FAIL. ## Patterns to follow
- The existing a11y-gate artifact shape per obs-plan §9: upload with `if-no-files-found: warn`, then assert in-job with `journal_conformance` under a `CONDUCTOR_RUNS_DIR` override rather than post-hoc download-and-parse.
- One-gate-serves-both-shapes per obs-plan §3: conformance asserts presence + closed sets + host-path freedom, never exclusivity — so extra resource tags on a harness artifact are admissible without a second gate.
- Detail-on-`message` per obs-plan §6 (Boundary-call wrappers): any new observable (e.g. session-attempt outcome, launch principal) rides the already-allowlisted `message` field, because a field name outside `conductor-core::redact::ALLOWLISTED_FIELDS` is dropped at the processor stage and a dedicated attribute would emit nothing.
- Job-log-vs-artifact separation per obs-plan §9 (Pipeline integration, Lint/typecheck row): lines carrying absolute runner paths may be agent-readable *from the job log* but must not be routed into any telemetry artifact — the pattern the chunk's diagnostic steps 10–12 already sit under.
- Agent-readable consumption per obs-plan §11 (Universal): every measurement this chunk produces needs a machine-parseable path (JSONL / uploaded artifact), which is the obs-side form of the scope's "read each CI run as a measurement in full".

## Anti-patterns to avoid
- obs-plan §11 (Universal) bans any self-observation OTLP export and any OTel JS SDK / browser exporter — the a11y arm drives Conductor's own webview, so frontend telemetry stays `console.log` JSON only; no `:4318`, no `auto-instrumentations-web`, even to diagnose the missing debugging endpoint.
- obs-plan §11 (CI · PII Scrubbing) bans leaking absolute host paths into logs / run-report / artifacts and bans losing telemetry artifacts — a (B) ratified-exclusion record must be host-path free and must still be uploaded, not merely written into a job-log comment.
- obs-plan §11 (Project-specific bans) bans spawning a child via shell with operator-supplied input and bans a spawn raising a visible console window on Windows (`CREATE_NO_WINDOW` via `console_suppressing_flags()`). A scheduled-task / `runas`-class launch is a new Windows spawn mechanism and inherits that ban; whether the chosen mechanism can honour it is research's question.

## Contract bindings
- obs §9 artifact table ↔ **a11y-plan §3** (a11y harness) — a11y emits the violation record; obs owns its format, upload and conformance assertion. Both sides move together.
- obs §3 envelope key set / key-presence semantics ↔ **test-plan §3** (the JSONL format owner) and **test-plan §9/§10** (CI integration / quality gates) — obs aligns to tests, not vice versa.
- obs §9 host-path freedom ↔ **security-plan** (Input Validation / Logging &amp; Monitoring) — the `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` env-handle discipline discharged at the wdio harness edge; a new launch handle inherits the same duty on the obs side as a redaction obligation.
