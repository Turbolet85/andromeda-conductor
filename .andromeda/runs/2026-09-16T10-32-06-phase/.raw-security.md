# security extract

## Relevance
Relevant — the chunk edits the `a11y` job of `.github/workflows/ci.yml` and the wdio launch edge, both of which carry governed harness-spawn forms, dev-harness env-handle boundaries, the CI-time-fetched-binary dependency class, and the CI host-path discipline.

## Constraints
- A limited-token launch (scheduled task with a non-elevated principal, or a `runas`-class trust level) executed from the `a11y` job is a candidate **seventh** governed harness-spawn form. security-plan §Security Anti-Patterns → Code Patterns rule (b) requires every governed form be array-form argv with no shell string and no `Invoke-Expression`, and — per the 5→6 widening ratified with *no* routine rule minted — a seventh crossing requires operator ratification at wrap rather than routine apply. The plan's own discriminator (per §Code Patterns rule (b), as restated by the 2026-09-09 fmt-gate amendment) is whether the step supplies a constructed argv/program versus a plain `run:` of a fixed toolchain binary with fixed argv; **which side `schtasks`/`runas`/`Start-Process -Credential` falls on is research's question.**
- Any NEW env handle introduced for the launch context inherits the per-READER validation duty (security-plan §Input Validation, boundary table; §Security Anti-Patterns → Input). Four handle classes exist (Rust-read path · dev-harness host-tool path · harness-owned constant · flag-valued); the plan requires a handle failing every clause of an existing class be ratified as a new class rather than stretched into one, and registered in §Secret Management → Storage → Development's non-secret handle inventory.
- `CONDUCTOR_A11Y_STRICT` (security-plan §Input Validation, fourth handle class) requires that an affirmatively-declared strict arm make an unresolved host-tool handle exit non-zero — this is what the plan names as the thing stopping a CI a11y gate from reporting success by skipping. The row requires the strictness stay an **ADDED arm, never a relaxation**: `nativeDriver()` / `nvdaExe()` and their `UNSAFE_PATH` checks byte-unchanged. Outcome (B) must therefore not be reached by disabling the strict arm or by adding `continue-on-error: true` to the asserting step; §Dependency Security (third dependency class) treats the *absence* of `continue-on-error` on an asserting/admitting step as part of the control.
- CI precondition and diagnostic output must be handle **NAME + boolean/version only, never a resolved path** (security-plan §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row, producer clause), and committed evidence records must carry no absolute host path and no internal seam-crate struct name (§Security Anti-Patterns → Logging, which names the per-chunk `evidence/` tree explicitly). The scope asserts `scripts/webview2-cause-probe.ps1` already carries this discipline; **whether the existing probe and session-isolation scripts actually emit no resolved path is research's question**, and any new probe inherits the mandate regardless.
- If the launch mechanism acquires any binary at job time, it enters the **third dependency class** (security-plan §Dependency Security): no lockfile gate can see it, and its sole admitting control is a pre-execution `Get-AuthenticodeSignature` check (status `Valid` + a named signer) exiting non-zero before execution, with no `continue-on-error` on fetch or install.
- The existing WebView2 acquisition must stay narrower-never-wider: §Dependency Security requires the fetch+install remain floor-conditional (entered only below the measured runtime major floor) while the `&gt;= 152` floor assertion stays **outside** the conditional and runs every job. An a11y-job restructuring must not move the floor assertion into a skipped branch.
- security-plan §Security Anti-Patterns → Universal bans an inbound listener in Conductor's **shipped binaries**; the `4444`/`4445` carve-out holds only because those ports belong to tauri-driver / the native WebDriver, live for the leg, and are absent from `conductor-cli` / `conductor-tauri`. A `--remote-debugging-port` / additional-browser-arguments route (scope open premise 3) must land on the harness side; **whether any candidate route would require a shipped-surface config change is research's question**, and if so it is a trust-boundary widening rather than a harness change.

## Patterns to follow
- The `UNSAFE_PATH` guard in `wdio.conf.ts` (security-plan §Input Validation, `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` rows): existence + `isFile` + shell-metacharacter rejection at the harness edge, then the value passed as a separate element of an array-form spawn, never as a shell string.
- The producer/reader split (security-plan §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row): the CI step-shell derives and gates the value behind a printed handle-named `Test-Path` precondition exiting non-zero, while the wdio edge stays the sole READER and sole guard site, byte-unchanged. This is the precedent shape for adding a CI-side arm without touching the harness guard.
- The sixth governed spawn form's shape (security-plan §Security Anti-Patterns → Code Patterns rule (b)): a `Start-Process -FilePath &lt;program&gt; -ArgumentList '&lt;flag&gt;','&lt;flag&gt;' -Wait -PassThru` array-form vector with no operator-supplied value anywhere in it, and the admitting control applied **before** the program executes.
- The "ADDED arm, never a relaxation" framing (security-plan §Input Validation, `CONDUCTOR_A11Y_STRICT` row): a new arm changes what an unresolved handle *costs* while every existing guard stays byte-identical — the template for a launch-context change that must not weaken the driver/NVDA guards.
- Host-path-free failure origins (security-plan §Input Validation, committed-manifest row): read faults carry `e.kind()` and the handle/file name only, never a resolved path — the form new diagnostics should copy.

## Anti-patterns to avoid
- NEVER assemble the limited-token launch as a shell string / `Invoke-Expression` / composed command line — rule (b) admits only array-form argv with the program fixed and any supplied value a separate word (security-plan §Security Anti-Patterns → Code Patterns).
- NEVER let a11y-job output, uploaded session diagnostics, or committed `evidence/` records leak absolute host paths or internal seam-crate struct names (security-plan §Security Anti-Patterns → Logging).
- NEVER introduce an inbound listener into a shipped binary to obtain the debugging endpoint — the harness-lifetime port carve-out does not extend to `conductor-tauri` / `conductor-cli` (security-plan §Security Anti-Patterns → Universal).

## Contract bindings
- **CI security gate ↔ tests §CI Integration / §Quality gates:** the `a11y` job shares `.github/workflows/ci.yml` with the `rust` job's supply-chain steps; the workflow is one file and the governed-spawn-form count for the *whole* file is security's, while the job/gate topology is tests'. An a11y-job restructure must not relocate or neutralize the audit/deny/fmt steps.
- **`CONDUCTOR_A11Y_STRICT` ↔ a11y-plan §11 Anti-Patterns → CI:** the security plan's own row cites that a11y mandate as the reason the strict arm exists (a CI a11y gate must not report success by skipping); security owns the handle's validation model, a11y owns the assert-or-fail mandate. Outcome (B)'s shape must satisfy both.
- **Evidence host-path scrub ↔ tests/obs:** committed evidence records are cross-host agent-parseable ground truth; the scrub rule is security's (§Security Anti-Patterns → Logging), the fixture/record schema is tests'/obs'.
- **`CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` ↔ a11y-plan §3 harness:** the handles' guard lives at the wdio edge per security-plan §Input Validation; a launch-context change that relocates the spawn relocates that guard's site and must carry it.

## Acceptance criteria contributions
- (security) No shell string, `Invoke-Expression`, or composed command line in any launch path added to the `a11y` job or the wdio config; every program is fixed and every supplied value is a separate array-form argv element — and if the change constitutes a seventh governed harness-spawn form, it is named as such and operator-ratified at wrap rather than routine-applied (per security-plan §Security Anti-Patterns → Code Patterns rule (b)).
- (security) The a11y job's console output, uploaded session diagnostics, and any committed evidence record carry 0 absolute host paths and 0 internal seam-crate struct names; every new precondition line prints a handle NAME plus a boolean/version, never a resolved path (per security-plan §Security Anti-Patterns → Logging; §Input Validation, `CONDUCTOR_MSEDGEDRIVER` row).
- (security) If outcome (B) ships, the exclusion adds no `continue-on-error` to the asserting step, does not disable the `CONDUCTOR_A11Y_STRICT` strict arm, and leaves `nativeDriver()` / `nvdaExe()` and their `UNSAFE_PATH` checks byte-unchanged (per security-plan §Input Validation, `CONDUCTOR_A11Y_STRICT` row).
- (security) Any new env handle carries its own §Input Validation boundary row plus §Secret Management → Storage → Development registration; any dependency delta lands only on `cargo audit` + `cargo deny check advisories bans licenses sources` green and `npm audit --omit=dev` clean; any job-time-fetched binary is gated by a pre-execution Authenticode check with the `&gt;= 152` floor assertion kept outside the fetch conditional (per security-plan §Input Validation; §Secret Management; §Dependency Security, third dependency class; §Security Anti-Patterns → Universal).
