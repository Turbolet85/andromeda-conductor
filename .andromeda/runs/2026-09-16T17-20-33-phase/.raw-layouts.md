## Patterns to follow
- Register a new launch path as a STAGE of the existing harness, not a new verb — §Surface: cli — Primary screens treats `--live` as "a sibling stage flag, never a sixth command", and the same bullet is the enumerating home for harness stage semantics.
- Name the guard by SHAPE rather than by command literal when documenting the leg (handle gate → refuse/skip class → printed-verdict assertion), the form §Surface: cli — Primary screens already uses for `--e2e` and `--live`.
- Keep the refuse-vs-skip-vs-strict three-class contrast intact: an incomplete live-Pulse environment REFUSES (exit 1, one `[PRECONDITION]` line per unmet subject), an absent host-tool handle SKIPS its leg at exit 0 with a fetch recipe, and `CONDUCTOR_A11Y_STRICT` adds the non-zero arm rather than replacing either (§Surface: cli — Primary screens).
- Treat the console as ONE surface in run states (`idle` · `live` · `hold` · `aborted`, idle-with-report a sub-state) for any spec that reasons about screens — §Primary screens and §IA notes: no router, no deep links, so a routine spec's "screen" is a state of the one window.
- Status is never color-alone on either surface (lamp + text on webview, ANSI + `[PASS]`/`[FAIL]`/`[HOLD]`/`[BLOCKED]` ASCII prefix on cli) — §Surface: cli signature-placement note and §Component — Primary content block 1/2.

## Anti-patterns to avoid
- Do not introduce routes, breakpoints, browser-style back/forward or a second window/surface to make the routine leg testable — §IA notes (Global model) and §Component — Primary navigation forbid it; the frameless window IS the surface.
- Do not add a sixth `agent-run` command for the new launch mechanism — §Surface: cli — Primary screens fixes the harness at the 5-command set with stage flags.
- Do not leak absolute host paths, internal struct names or stack traces from launcher/token-API failures into user-visible output — §Surface: cli — Component — Footer / terminator + error output.
