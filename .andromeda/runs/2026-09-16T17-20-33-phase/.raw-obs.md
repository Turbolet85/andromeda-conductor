# obs extract

## Relevance
Partial — the launch mechanism and CI wiring are Not-instrumentable per obs-plan §1 (CI/CD row), but the a11y violation record artifact, the Tauri sink's env dependence, spawn host-path hygiene and the two CI obs gates are obs-owned on both outcome arms.

## Constraints
- Obs tier is Minimal (0): the launcher adds no OTel SDK, no exporter, no metric instrument — self-observation is `tracing` JSON only, and a debugging endpoint being open changes nothing about that (per obs-plan §1 Obs Scope Summary + §3 OTel SDK init).
- The bounded span-name set is a closed contract (`scenario.run`, `timeline.execute*`, `emit.batch`, `emit.logs_batch`, `verify.readback*`, `report.generate`, `db.insert_run`, `fault.*`, `tauri.command.*`); a launcher/CI-wiring entry is required not to mint a new name, and a span attribute that is not in `conductor-core::redact::ALLOWLISTED_FIELDS` is dropped at the processor stage, so launcher witnesses (integrity SID, `WindowStation` / `UserInteractive` / `SessionName` from CARRY 2) must ride the allowlisted `message` value (per obs-plan §11 Spans/Traces + §4 Required-span-attributes constraint).
- obs-plan §9 requires the a11y violation record at `runs/a11y/&lt;run_id&gt;.jsonl` to be uploaded (`actions/upload-artifact@v4`, `if-no-files-found: warn`) with conformance asserted in-job by `journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y`; §3 requires its shape to be the eleven envelope keys PLUS the §9 resource tags `service.name` (`conductor-ui`) + `deployment.environment` — 13 keys locally, 15 under CI where `ci.run.id` + `git.commit.sha` join — and the gate asserts key PRESENCE, closed sets and host-path freedom, never key exclusivity (per obs-plan §9 CI Integration + §3 Log format JSON schema).
- The Tauri backend self-obs sink is `&lt;runs_dir.parent()&gt;/logs/conductor-tauri.jsonl` — file name fixed, directory riding `CONDUCTOR_RUNS_DIR` — so any replacement launch path (a restricted-token `CreateProcessAsUser` builds its own environment block for the child) is required to carry that handle to the child or the routine leg's log lands somewhere the leg does not read; whether the current/new launch path propagates it is research's question (per obs-plan §3 Log file location + §1 telemetry-surfaces desktop-webview row).
- No telemetry artifact may carry absolute host-file paths (drive-letter, `/home`, `/Users`, `%APPDATA%`, `~/.cargo`, `.rustup`, backtrace paths); §9's conformance check FAILS the build on one, and §11 states explicitly that the enumerated redaction sites bound only the sites they name, never every channel — a NEW spawn form is exactly the class that produced the last measured out-of-band channel (per obs-plan §9 Log conformance check + §11 PII Scrubbing).
- Zero unlogged panics is the always-required Minimal-tier SLO invariant: a launcher that fails (no token, no session, endpoint absent) must surface as a structured `tracing::error!` / `anyhow` edge, never a bare `^thread.*panicked` line in `agent-latest.jsonl` or stderr, which §9's gate greps for and fails on (per obs-plan §10 SLO Invariants + §9 Zero-unlogged-panics gate).
- Frontend telemetry stays console-JSON only — no OTel JS SDK, no browser OTLP, not to `:4318` — even though this chunk's whole subject is opening a remote-debugging channel into the webview (per obs-plan §1 desktop-webview row + §11 Universal).

## Patterns to follow
- The 2026-09-07 a11y CI gate's own wiring: violation record written under `CONDUCTOR_RUNS_DIR=runs/a11y`, validated in-job by `journal_conformance`, then uploaded — one gate serving two record shapes because it asserts presence rather than exclusivity (obs-plan §9 artifact table, §3 extension-point paragraph).
- The allowlisted-`message` escape hatch for diagnostics that have no allowlisted field name — the same mechanism §6's MCP key-set / `emit.batch` wire-shape witnesses and §4's coverage roll-up use; the right home for a token/integrity/window-station witness emitted from Rust (obs-plan §6 Boundary-call wrappers, §4 Coverage-matrix gate).
- Windows spawn hygiene as already specified: `build_command` applying `CREATE_NO_WINDOW` through `console_suppressing_flags()` under `#[cfg(windows)]` (`conductor-verify/src/spawn.rs`), with the flag value pinned by a `#[cfg(windows)]` unit test and its *effect* evidenced at the SR leg because the applied flag is not assertable at the unit tier (obs-plan §11 Project-specific bans).
- CI-specific resource attributes sourced from the workflow context — `ci.run.id` = `${{ github.run_id }}`, `git.commit.sha` = `${{ github.sha }}`, `deployment.environment` = `dev` on branch builds (obs-plan §9 CI-specific resource attributes).
- The fmt-gate precedent for host-path-bearing output: agent-readable from the job log, deliberately NOT routed into any telemetry artifact (obs-plan §9 Pipeline integration, Lint/typecheck row).

## Anti-patterns to avoid
- NEVER route launcher/diagnostic output carrying absolute host paths or internal struct names into `agent-latest.jsonl`, `runs/a11y/&lt;run_id&gt;.jsonl` or the run report — job-log only (obs-plan §11 Logs + §9 Log conformance check).
- NEVER spawn with a visible console window: a flagless spawn publishes the resolved exe's absolute path as a foreground pane title, and a `CreateProcessAsUser` launch is a fresh instance of that class (obs-plan §11 Project-specific bans + §11 PII Scrubbing).
- NEVER reach for an OTel SDK, `tracing-opentelemetry`, browser OTLP or a W3C `traceparent` to diagnose why the endpoint does or does not open — correlation is the `run_id` field only (obs-plan §11 Telemetry Strategy + §11 Spans/Traces).

## Contract bindings
- obs ↔ a11y: the a11y violation record is the one known exerciser of obs's per-scenario envelope extension point; a11y emits into obs's JSONL shape (eleven keys + resource tags) and obs owns the shape, not the violation semantics (obs-plan §3 Log format JSON schema, §9 artifact table).
- obs ↔ tests harness: `journal_conformance` is the tests-side consumer asserting obs's record shape in-job (key presence, closed sets, host-path freedom); the envelope schema is OWNED by test-plan §3 and obs aligns to it, so a shape change here is two-sided (obs-plan §3, §6 Required fields).
- obs ↔ security: the spawn ban and the console-window/host-path channel are a cross-master citation held jointly with security-plan §Security Anti-Patterns (a); the chunk's seventh-vs-eighth governed-spawn-form question is security's classification, but its telemetry consequence (a new host-path channel) is obs's (obs-plan §11 PII Scrubbing + §11 Project-specific bans).
- obs ↔ CI: §9 gates (log conformance, zero-unlogged-panics, artifact upload) apply to whatever job the routine leg runs under; on the ratified-exclusion arm the `if-no-files-found: warn` disposition governs the absent record (obs-plan §9).

## Acceptance criteria contributions
- If the routine arm reaches its assertions, `runs/a11y/&lt;run_id&gt;.jsonl` exists, passes in-job `journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y`, and is uploaded as a CI artifact; on the exclusion arm the absent record resolves via `if-no-files-found: warn` rather than a silent gap (per obs-plan §9 CI Integration).
- `CONDUCTOR_RUNS_DIR` reaches the medium-integrity child process so the routine leg's backend self-obs file lands at `&lt;runs_dir.parent()&gt;/logs/conductor-tauri.jsonl` for that suite — whether the current PowerShell path and the new `CreateProcessAsUser` path both carry it is research's question (per obs-plan §3 Log file location).
- No telemetry artifact produced by this chunk's leg contains an absolute host-file path (drive-letter / `%APPDATA%` / `.rustup` / backtrace path), including any token, integrity-SID, window-station or endpoint-probe witness (per obs-plan §9 Log conformance check + §11 PII Scrubbing).
- The new launch form raises no visible console window and no host-path-titled foreground pane, and the leg's evidence carries zero `security_finding` rows / zero `&lt;host-path&gt;` placeholders; zero unstructured `^thread.*panicked` lines appear in `agent-latest.jsonl` or stderr when the launch fails (per obs-plan §11 Project-specific bans + §9 Zero-unlogged-panics gate).
