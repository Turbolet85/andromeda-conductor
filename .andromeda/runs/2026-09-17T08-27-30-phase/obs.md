# obs extract

## Relevance
Partial — no self-obs instrumentation is added, but the a11y arm's CI telemetry artifact, its in-job conformance gate, the arm's log sink location, and the host-path-freedom rule all sit in obs's domain.

## Constraints
- The a11y violation record `runs/a11y/<run_id>.jsonl` is a REGISTERED CI telemetry artifact: obs-plan §9 (CI Integration — telemetry artifact table) requires the `a11y` job to upload it (`actions/upload-artifact@v4`, `if-no-files-found: warn`) and to assert its conformance IN-JOB via `journal_conformance` under `CONDUCTOR_RUNS_DIR=runs/a11y`. A "green a11y verdict" in obs's terms therefore includes that gate, not only the arm's printed pass/skip counts — whether the ROUTINE arm (as opposed to the scan arm) emits that record on the measured configuration is research's question (per obs-plan §9).
- The record's key set is governed: obs-plan §3 (Harness Contract → Log format JSON schema, extension-point paragraph) requires the eleven envelope keys PLUS the §9 resource tags `service.name` (`conductor-ui`) / `deployment.environment` (13 keys locally, 15 under CI where `ci.run.id` + `git.commit.sha` join), and states the gate asserts key PRESENCE, closed enum sets and host-path freedom, never key EXCLUSIVITY — which is what lets one gate serve both record shapes. An assertion-basis correction must not change what the arm writes into that record.
- No absolute host paths in any telemetry artifact or log line: obs-plan §9 (Log conformance check) requires rejection of drive-letter `X:\` / `/home` / `/Users` / `%APPDATA%` / `~/.cargo` / `.rustup` in any field, and obs-plan §11 (Logs) bans leaking host paths or internal struct names. This binds the corrected assertion's FAILURE/diagnostic text if any of it is routed into an uploaded artifact (per §9 Pipeline integration, which records that job-log diff lines are deliberately NOT written into telemetry artifacts for exactly this reason).
- Frontend telemetry ceiling: obs-plan §1 (Telemetry surfaces — desktop-webview frontend cell) and §11 (Universal) require browser-side self-observation to be `console.log` JSON ONLY — no OTel JS SDK, no `auto-instrumentations-web`, no OTLP export, and never `:4318`. Any in-page probe added to answer "why does the focus cycle wrap on the runner" must stay inside that ceiling.
- The routine arm's backend log sink is runs-dir-relative: obs-plan §3 (Log file location) fixes the NAME `conductor-tauri.jsonl` with the DIRECTORY riding `CONDUCTOR_RUNS_DIR` (`runs_dir.parent()/logs`), measured at `runs/logs/` for the routine `--e2e` arm and `runs/driven/logs/` · `runs/sr-leg/logs/` for the other suites — so CI-side diagnosis of the wrap reads `runs/logs/`, not the project-root `logs/`.
- Agent-readable verdicts: obs-plan §2 (Agent-readable invariants) and §11 (Universal) require every signal to have a machine-parseable consumption path and forbid human-review-gated analysis — the arm's printed verdict that `Assert-A11yVerdict` parses (and its expected-skip count) must stay mechanically parseable across the 11/1/2 → 12/0/2 transition.
- CI artifacts must not be lost: obs-plan §11 (CI) bans dropping telemetry artifacts. If an operator ruling (escalations 1/3/4) changes what the `a11y` job may contain, the artifact-upload step and the in-job conformance assertion must survive the edit.

## Patterns to follow
- One gate over a superset record — `journal_conformance` run with `CONDUCTOR_RUNS_DIR` pointed at the arm's runs dir, asserting presence/closed-sets/host-path-freedom rather than exclusivity (per obs-plan §3 Log format JSON schema, §9 artifact table).
- Diagnostic detail carried on the allowlisted `message` field rather than a new field name — obs-plan §6 (Boundary-call wrappers) establishes this for the key-set and wire-shape witnesses, because a field outside `conductor-core::redact::ALLOWLISTED_FIELDS` is dropped at the processor stage.
- Witness-the-observed-shape pattern: where a reader degrades silently on an unrecognized shape, record what was actually observed (names only, never values) so a divergence is distinguishable from emptiness (per obs-plan §6). Directly analogous to this chunk's problem — a count whose basis is ambiguous is indistinguishable from a count that asserts nothing.
- Redaction at source plus the a11y leg's own `<host-path>` scrub as SECOND line of defence, never the only one (per obs-plan §11 PII Scrubbing).
- Host-path-bearing output stays in the job log and out of telemetry artifacts (per obs-plan §9 Pipeline integration, Lint/typecheck row).

## Anti-patterns to avoid
- NEVER introduce an OTel SDK / OTLP exporter for self-observation on any surface, browser included (per obs-plan §11 Telemetry Strategy + Universal) — a probe that exports rather than console-logs is banned.
- NEVER mint a span name outside the bounded set (`scenario.run`, `timeline.execute*`, `emit.batch`, `emit.logs_batch`, `verify.readback*`, `report.generate`, `db.insert_run`, `fault.*`, `tauri.command.*`) (per obs-plan §11 Spans / Traces) — relevant only if the correction ends up touching Rust, which the scope says it should not.
- NEVER emit unstructured text as the machine-read signal (per obs-plan §11 Logs + §2) — the arm's verdict line is parsed by a script, so a prose-only change to it breaks a consumer.

## Contract bindings
- obs ↔ tests harness: obs-plan §3 states the JSONL format is OWNED by test-plan §3 and that obs aligns to it; `journal_conformance` (a `conductor-run` surface) is the consumer of the §3/§9 record shape. Any change to what the a11y arm records is a two-sided change.
- obs ↔ a11y: the a11y violation record at `runs/a11y/<run_id>.jsonl` is a11y's emission into obs's envelope/extension-point contract (per obs-plan §3 extension-point paragraph + §9 artifact table).
- obs ↔ security: host-path freedom in artifacts and logs is the shared clause (obs-plan §9 conformance + §11 PII Scrubbing / Project-specific bans cite security-plan's spawn ban); the four carried operator escalations are security-plan questions, and obs only asserts that whatever the job becomes must still upload + conform its telemetry artifact.
- obs ↔ CI config: `.github/workflows/ci.yml`'s `a11y` job carries the artifact upload and the in-job conformance step obs-plan §9 mandates.

## Acceptance criteria contributions
- The `a11y` job's green verdict includes the in-job `journal_conformance` pass over `runs/a11y/<run_id>.jsonl` under `CONDUCTOR_RUNS_DIR=runs/a11y`, and the record is uploaded as a CI artifact (per obs-plan §9 CI Integration — telemetry artifact handling). Whether the routine arm on the measured configuration already produces that record is research's question.
- The a11y violation record's top-level key set is unchanged by the counting-basis correction — the eleven envelope keys plus the §9 resource tags (13 local / 15 CI) (per obs-plan §3 Harness Contract — Log format JSON schema).
- No absolute host path appears in any line of the arm's uploaded artifacts or its `conductor-tauri.jsonl` under `runs/logs/`, including any new or reworded assertion/diagnostic text (per obs-plan §9 Log conformance check + §11 Logs).
- Any frontend/webview diagnostic introduced to establish the reachability basis or the wrap mechanism is console JSON only — no OTel JS SDK, no OTLP, no `:4318` (per obs-plan §1 Telemetry surfaces desktop-webview + §11 Universal).
