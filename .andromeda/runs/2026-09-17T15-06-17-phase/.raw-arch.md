## Constraints
- The webview automation surface is CLOSED at three suite families (four `wdio` suites) over ONE WebdriverIO + tauri-driver stack — the dev-only `--e2e` routine arm, the operator-local `a11y:driven` driven arm, the operator-local `sr` / `sr-empty` / `sr-error` leg; "never a second automation stack" (per architecture.md §Cross-cutting Patterns — Scope law). Every owning suite this chunk names must resolve to one of those, under those names.
- The CI enumeration is a locked arrangement: the `a11y` job runs the **Pulse-free routine arm only**, and dynamic proof requiring a live Pulse is an explicit operator/local gate — the exclusion is the live-Pulse dependency, not the end-to-end tier (per architecture.md §Established Decisions [CI/CD] and §Infrastructure Patterns — CI/CD approach). That mandate is the architectural basis for the carve-out; widening the job's spec set would move an arrangement row and require an arch amendment.
- Every a11y CI claim must be stated **with its configuration**, never as a bare verdict — arch requires the measured SET (hosted `windows-2022`, coherent 131.0.2903.86 driver/runtime pair, High integrity, run 35208593666) rather than a universal (per architecture.md §Established Decisions [CI/CD]). An ownership/carve-out sentence that says "CI gates X" without its configuration violates this.
- A CI gate that can pass by skipping is banned — that ban is what `CONDUCTOR_A11Y_STRICT` exists to enforce (unresolved `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` must exit non-zero under an affirmative flag) (per architecture.md §Occupied Resources — Environment variables). A carve-out may not be worded so that the routine gate appears to cover claims it structurally cannot run.
- `.gitattributes` pins LF repo-wide (`* text=auto eol=lf`) against a Windows dev host where `core.autocrlf=true` is the norm (per architecture.md §Infrastructure Patterns — Build system). The CARRY 1 python read-modify-write of `a11y-plan.md` must therefore write LF bytes; whether the file is LF on disk today and whether the repair preserves it is research's question.
- The suites live under `crates/conductor-tauri/ui/`, which is NOT a Cargo workspace member and is invisible to cargo (per architecture.md §Occupied Resources — Frontend asset subtree) — consistent with the scope's "no Rust surface" boundary; no workspace-crate placement decision arises.
- arch §Occupied Resources enumerates ports, workspace crate names, env vars and on-disk artifacts and registers no `.andromeda/` spec master; a requirement-text-only chunk is expected to land no new entry there (per architecture.md §Occupied Resources).

## Patterns to follow
- **Name each precondition/claim individually with its candidate causes** rather than composing one opaque string — the readiness gate's five named preconditions are the house shape for exactly this kind of "who owns what, and what is unmet" statement (per architecture.md §Standard Contracts — Readiness gate).
- **Statement + a gate that holds it to exact-set equality** is arch's standing shape for coverage claims (`check_sut_drift`, `check_scenario_backing` / the `UNBACKED_AUTO` pin, `coverage-matrix.md` as definition of done) (per architecture.md §Established Decisions [Accepted Capability Set]). The chunk's scope bans new assertions, so this is the shape a per-claim ownership table should resemble, not a mandate to build a gate here.
- **Invocation names as registered**: `npm run a11y:driven` = `wdio run wdio.conf.ts --suite driven`; the routine arm is `agent-run.ps1 run --e2e` invoked through `scripts/a11y-token-witness.ps1` (per architecture.md §Occupied Resources — Ports and §Infrastructure Patterns — CI/CD approach). Use those exact handles when attributing an owner.
- **Kebab-case Markdown on-disk artifacts / snake_case Rust** naming (per architecture.md §Conventions — Naming patterns).
- **CI-only artifacts carry a qualifier when registered** (e.g. the `scripts/*.ps1` tree comments: "solely ci.yml's a11y job, neither harness shell, no 6th command") (per architecture.md §Infrastructure Patterns — Directory structure) — the same qualifier discipline applies to describing a suite CI never runs.

## Anti-patterns to avoid
- Introducing a second automation stack, a fourth suite family, or relocating assertions across arms — banned by the Scope law (per architecture.md §Cross-cutting Patterns — Scope law).
- Restating a configuration-bound measurement as a universal verdict (the retired forms "never been green", "runnability is measured-unproven", "the app must not run elevated" are explicitly retired) (per architecture.md §Established Decisions [CI/CD]).
- Changing what the `a11y` job runs, or its runner label / driver-pin gate / gate chain, as a side effect of writing an ownership statement (per architecture.md §Infrastructure Patterns — Build system · CI/CD approach).
