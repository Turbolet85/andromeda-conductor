## Relevance
Partial — the chunk's subject (keyboard reachability + focus-order claim OWNERSHIP in a spec master) is an a11y/tests-plan concern, but the claim population is quantified per desktop-webview run-state layout (`run-console-idle` / `run-console-live` / `run-console-HOLD` / `idle-with-report`), which is layout-templates' surface/state vocabulary and the focus-order/restoration bindings it owns.

## Constraints
- The layout names the claim population must partition against is the shipped `RunState` set — `idle` · `live` · `hold` · `aborted`, with idle-with-report a SUB-STATE of `idle`, not a fifth state (per layout-templates §Surface: desktop-webview → Primary screens). The scope's four "focus order per layout" rows map onto that set minus `aborted`; whether the requirement's per-layout claim list should therefore also name `aborted` (which has no wireframe entry) is research's question, not something this extract can settle.
- There are no routes, no router, no deep links and no breakpoints on this surface — the frameless window IS the surface and the operator moves through run state (per layout-templates §Component — Primary navigation, §IA notes). This is the layout basis for the scope's "Focus restoration — no route-change surface → N/A by construction" row, and for "Skip links → N/A by construction" (no repeated nav blocks: the surface is titlebar + control row + matrix + report card, per §Wireframe — Run console (idle)).
- Focus restoration for the HOLD dialog is CONTRACT-BORNE, not primitive-supplied: layout-templates §Component — Hero / signature section requires the dialog take a `restoreFocusTo` accessor and restore explicitly in `onCloseAutoFocus`, because the hold arrives over a Tauri `Channel` and the dialog has no Radix `Trigger`. Any ownership statement for the restoration claim must attribute THAT contract, not "Radix handles it".
- The invoking control must remain focusable for restoration to have a target — §Component — Hero requires `Start` convey unavailability via `aria-disabled`, never the native `disabled` attribute. A restoration-claim owner that does not exercise this is not covering the claim.
- Keybindings are first-class on this surface: start / stop / proceed / abort are each bound to a shortcut, and every hover affordance has a keyboard equivalent with a visible `color-focus` ring plus a non-color-only `border-emphasis` edge on the active picker item (per layout-templates §Component — Primary navigation). This is the layout-side scope of the scope's "Per-surface keyboard shortcuts" claim row; whether the code already binds all four is research's question.
- Space toggles a focused operator-checklist row, and the checklist rows render as a SIBLING of the dialog `Description`, between Body and Actions (per layout-templates §Component — Hero, §Component — Operator-checklist). These are focusable elements inside the HOLD focus trap, so the HOLD focus-order claim's population includes them when the hold declares `[[checklist]]` items.
- The cli surface has its own keyboard/interaction register that the requirement's per-surface shortcut claim may span: `inquire` prompts are `isatty`-gated and the headless agent path is NEVER blocked on a prompt (per layout-templates §IA notes — Headless invariant, §Component — Primary navigation). A "per-surface keyboard shortcuts" owner named only for the webview leaves the cli leg unattributed.

## Patterns to follow
- Per-run-state layout naming: cite the four shipped `RunState` labels and the idle-with-report sub-state as the partition keys, exactly as layout-templates §Primary screens names them, rather than minting new layout names in the ownership table.
- The dialog focus region as a single composed unit: Header (frozen count) → Body (backend hold prompt) → checklist rows (conditional) → Actions (Abort, Proceed) per layout-templates §Component — Hero. Focus-order claims for `run-console-HOLD` should be stated against that part order, which is the same order the wireframe draws.
- Two-context primitive, one component: the Operator-checklist renders in the dialog AND (as target state) in the run report, and the distinction is context, not component (per layout-templates §Component — Operator-checklist). An ownership statement should not split one claim across two "components".
- Cross-surface "adapted, never forked": layout-templates §IA notes — Multi-surface coordination requires desktop and cli mirror the same behaviour by name. Ownership statements for a per-surface claim should follow that same pairing shape.
- Documenting DESIGNED-vs-SHIPPED explicitly: layout-templates §Component — Footer and §Component — Operator-checklist both mark route-owned gaps in place rather than deleting the target. The chunk's CI carve-out statement follows the same shape — state the target owner and name what gates in its place.

## Anti-patterns to avoid
- Do not introduce routes, breakpoints, nav blocks or a router to give focus-restoration or skip-link claims a home — layout-templates §IA notes forbids them on this surface; those two rows are N/A BY CONSTRUCTION and must be stated as such, not engineered around.
- Do not state a focus/keyboard claim as satisfiable by color or hover alone — §Component — Primary navigation requires a visible focus ring plus a non-color-only `border-emphasis` edge, and every status be paired with text.
- Do not treat the HOLD dialog's focus restoration as primitive-supplied; §Component — Hero explicitly records that shadcn/Radix supplies trap + Escape but NOT restoration here.
