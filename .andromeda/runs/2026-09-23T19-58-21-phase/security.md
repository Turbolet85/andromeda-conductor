## Patterns to follow
- `conductor_core::config_path::resolve_under` is the plan's traversal guard for this handle class. It REJECTS an absolute candidate or a `..` escape, never clamps (per security-plan §Input Validation, `#[tauri::command]` IPC row; the note on `logs/agent-latest.jsonl` under the table). Whether it is reachable from `conductor-run` test binaries, and whether it resolves a runs dir that does not exist yet, is research's question.
- Read faults carry `e.kind()` only, never the path. The plan uses this idiom for the committed-manifest readers (per security-plan §Input Validation, committed-manifests row).
- Failure origins name the handle and the file's own name, never a resolved path. `journal_conformance.rs` already uses this bound (per security-plan §Input Validation, env-var path-handles row).
- The absolutely-pathed `ANDROMEDA_PULSE_DATA_DIR` needs the canonicalize + explicit type/existence-check shape, not `resolve_under`. It is legitimately outside the workspace, so the shipped-edge form `std::fs::canonicalize` + existence check fits (per security-plan §Input Validation, env-var path-handles row, "How" column).

## Anti-patterns to avoid
- Never let a test-only reader of an operator-supplied path handle honour an absolute or `..` value by plain `join` under the workspace root (per security-plan §Security Anti-Patterns → Input).
- Never expose absolute host paths in failure output or in anything that could reach the per-chunk `evidence/` tree. `path.display()` in a panic/assert message is the known leak shape (per security-plan §Security Anti-Patterns → Logging; §Error Handling).
- Never "fix" a residual by recording a wider residual or widening a ban. Harden the code (per security-plan-amendments 2026-09-06-operator-gated-live-suite precedent; §Security Anti-Patterns → Input).
