## Relevance
Relevant to Part A: the three path guards are a security-vector negative-test obligation, and they sit in feature-gated test binaries. Part B is partial: the texts only need to match the test-plan's own recorded mechanisms.

## Constraints
- **Coverage trigger (security Vector 1).** Test-plan §1 (Coverage triggers → security-vector-coverage, Vector 1) requires that Rust-read `CONDUCTOR_*` path handles carry a negative test. The test must show that canonicalize plus a type/existence check rejects path traversal before any `runs.db`/journal write or manifest read. The plan sorts readers into classes by who reads the handle. A test-binary-only reader has a precedent: `CONDUCTOR_E2E_SEED_DIR` is "joined under the workspace root by the test". That precedent also shows that ONLY a hermetic test can prove such a guard, which fits the chunk's no-live-leg proof. Research must answer whether a test-binary `CONDUCTOR_RUNS_DIR` reader already has a negative test.
- **Repo-relative handle.** Per test-plan §3 (Test data bootstrap → Per-test isolation), `CONDUCTOR_RUNS_DIR` is repo-relative by design, and `resolve_under` rejects an absolute value. Guards on `runs_dir()` must keep that meaning: reject absolute values and `..`, accept relative ones. `ANDROMEDA_PULSE_DATA_DIR` is legitimately absolute (§1 Surfaces → ipc-internal Notes; §3 `boot`: its presence is graded after trim). So it cannot share the `resolve_under` rule.
- **Feature-gated files and their lint.** Test-plan §9 (Live-Pulse scenarios) puts `live_suite.rs` and `real_model_live.rs` behind the empty `[features] live-pulse = []` gate. That keeps them out of default `nextest`, out of `clippy` and out of both runner-portability runs. Each such file owes its own lint command: `cargo clippy -p conductor-run --features live-pulse --all-targets -- -D warnings`. Guard unit tests placed only inside those files would never run in the default suite or CI. Whether a shared default-suite module is needed is research's question.
- **Both runners.** Test-plan §4 (Framework) makes `cargo test -p <crate>` a standing runner-portability gate next to `cargo nextest run -p <crate>`. §10 (Zero-flakiness budget) treats a result that depends on the runner as a determinism defect.
- **Env read at the caller.** Test-plan §10 (Mutation-survivor disposition) cites the rule that env is read at the caller and passed in as a typed value, so both branches can be tested without `unsafe` env mutation. Guard tests should take the value as a parameter rather than set process env.
- **No host paths.** Test-plan §3 (Log format; Status endpoint shape) and §5 (Run report envelope) forbid absolute host paths in artifacts. The chunk's "path-free failure text" outcome is the test-binary counterpart of that rule.
- **Live legs stay operator-only.** Test-plan §9 and §11 → CI: the live captures stay operator-local. The chunk must not re-run either capture or add a CI live step.

## Patterns to follow
- **Negative-test shape.** Per test-plan §1 (Vector 1 trigger), write one small test per arm: absolute rejected, `..` rejected, relative accepted, failure text carries no path. rstest `#[case]` rows (§4 Fixture pattern; §7) group these table-driven variants.
- **Reuse the shipped guard.** `conductor_core::config_path::resolve_under` is the shipped repo-relative guard (§3 Per-test isolation; §3 `--e2e`, "rejects absolute paths and `..`"). Reuse it rather than writing a parallel guard. Whether it is reachable from `conductor-run`'s test binaries, and whether it accepts a runs dir that does not exist yet, is research's question.
- **Committed-fixture precedent.** Per test-plan §7 (Self-bootstrapping requirement), a crate-local `tests/` helper shared by several targets has precedents (`tests/common`, `tests/fixtures/`). A shared guard module under `crates/conductor-run/tests/` follows them. §10 notes that the `[\\/]tests[\\/]` coverage regex excludes it from the line gate.
- **Mechanism for text B1 (canary freshness).** Test-plan §4 (conductor-verify) and §5 (query_incident_list) define the canary as incident freshness: an incident opened after the emission stamp means proceed; an empty, stale or stamp-absent corpus means `blocked`. The `preflight.rs` comment should state that mechanism.
- **Mechanism for text B2 (`fingerprint_refs`).** Test-plan §6 (Scenario: Fingerprint-storm, verification signal) and §1 (Critical Path 2) record what `fingerprint_refs` carries: the constant `det-*` refs, plus, at `83d4060`, each incident's triggering-cue fingerprint. No shipped check keys on the array, and it is never pinned to `[]`. The `storm_harvest.rs` header should align with that.

## Anti-patterns to avoid
- Never run the live-Pulse capture as a CI gate, and never add a manual smoke step to prove the guards. Per test-plan §11 → CI and §11 → Universal, the proof is hermetic tests only.
- Never mutate process env or serialize tests with a runner knob to test the guards. Per test-plan §11 → Integration (the process-global state ban; `--test-threads=1` is banned), pass values in instead (§10's cited rule).
- Never sleep for synchronisation inside a test (per test-plan §11 → E2E).
