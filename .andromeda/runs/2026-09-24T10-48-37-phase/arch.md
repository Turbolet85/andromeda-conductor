## Relevance
Partial. Architecture covers the CI gate shape, the trust boundary and egress count, the operator-instrument and harness-surface rules, and how the plan treats env handles and `${{ env.* }}`. The `.claude/settings.json` hook fix (scope item C) is host tooling that architecture does not address, so this domain says nothing about it.

## Constraints
- Architecture §Cross-cutting Patterns — Trust boundary and §Occupied Resources — Ports require the project to have exactly ONE non-loopback egress: the CI-job-scoped `https://msedgedriver.microsoft.com` fetch, which the operator ratified. A scanner fetched at job time, whether a marketplace action or a downloaded binary, would be a second crossing. That needs operator ratification and a §Ports registration at wrap; it is not a routine add.
- Architecture §Stack and Technologies, row "Operator instruments (host runtime)", treats host Python 3 as a runtime with no lockfile and no toolchain pin. That row requires that none of its members be invoked by any CI step, and that none add a sixth `agent-run.{sh,ps1}` command. A stdlib Python scanner that CI calls would be a new kind of member (CI-invoked), and the row would need an amendment at wrap. Whether Python is available on the `windows-latest` runner is research's question.
- Architecture §Established Decisions [CI/CD] requires each gate to be its own named step with no `continue-on-error` and no `if:`. The step's `run` must open with a presence guard on its subject that emits `::error::` and exits 1, so a missing subject fails loudly instead of passing vacuously. The gate itself must be the tested artifact, invoked by the step, and never an assertion re-listed in shell.
- Architecture §Infrastructure Patterns — Build system states that every CI job runs on a Windows runner (two jobs on `windows-latest`, the `a11y` job on `windows-2022`), with `core.autocrlf=true` as the host norm and `.gitattributes` pinning LF repo-wide. The scanner's file and line reporting must give the same answer on the dev host and in CI.
- Architecture §Occupied Resources — Environment variables (`EDGEWEBDRIVER`, `RUNNER_TEMP`, `TEMP`/`LOCALAPPDATA` bullets) states that `${{ env.* }}` holds only what a workflow, job or step declares, never a runner-process variable. Runner variables must be read in the step shell (`$env:X`). The plan also records that `EDGEWEBDRIVER` is written through `GITHUB_ENV` and then read in the step shell. It does not say whether a key written to `GITHUB_ENV` can be read through `${{ env.* }}` in later steps. That is scope item 8, and it has to be settled by measurement.
- Architecture §Occupied Resources — Environment variables (closing bullet) and §Cross-cutting Patterns — Config management describe the target state as having no secrets, no secrets manager, no cloud credentials and no `DATABASE_URL`. A baseline of 0 true hits is what the plan predicts; whether the tracked tree actually has 0 is research's question. Any new env handle the scanner introduces must be registered under one of the existing registration bases, and the `CONDUCTOR_*` namespace is reserved for handles over artifacts this document defines.
- Architecture §Infrastructure Patterns — Directory structure lists the `scripts/` members, each with a qualifier (for example "invoked solely by ci.yml … wired into neither harness shell, adds no 6th command"). A new scanner under `scripts/` gets a tree entry with its own qualifier at wrap. The CI gate set is named at five sites (§Stack CI/CD row, §Established Decisions [CI/CD], the `.github/workflows/` tree comment, §Infrastructure CI/CD approach, §Inherited Defaults — CI/CD). A new gate must either fit the set as already named ("static gates over committed data") or trigger an update at all five sites.

## Patterns to follow
- The presence-guarded named-gate step: `Coverage-completeness gate` and `Scenario-assertion audit gate` in the `rust` job (per architecture §Established Decisions [CI/CD]). The scope's "shape of the flakiness-budget step" is the same family.
- An exact-set exemption ledger in which every entry carries a stated reason and the ledger can only shrink under compulsion: the `[[exempt]]` ledger in `contracts/pulse-load-envelope.toml`, the `contracts/scenario-audit-ledger.toml` two-way grading, and the `UNBACKED_AUTO` pin (per architecture §Occupied Resources — On-disk artifacts and §Established Decisions [Accepted Capability Set]). This is the model for the scanner allowlist, together with the "each entry names its crate and path inline" practice in `deny.toml` (§Infrastructure Patterns — Build system).
- A committed host-Python instrument that uses only the standard library: `scripts/arch-registry-check.py` (per architecture §Stack and Technologies, operator-instruments row).
- Adding a harness path as a selector instead of a new verb: `run --live real-model` is "a selector of `--live`, never a sixth command" (per architecture §Occupied Resources — `contracts/pulse-real-model-leg-posture.md`). This is the model for the scanner's local form.
- Output that names only the handle: `CONDUCTOR_MSEDGEDRIVER` and `CONDUCTOR_NVDA` print the handle name and a boolean, and never log or echo the value (per architecture §Occupied Resources — Environment variables). This matches the scope's rule that a hit is reported as file and line, with the matched secret never echoed in full.

## Anti-patterns to avoid
- A CI gate that can pass by skipping or passes vacuously on a missing subject is banned (per architecture §Occupied Resources — `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_A11Y_STRICT` and §Established Decisions [CI/CD]). An asserting gate step must not carry `continue-on-error` or `if:`.
- A second shell copy of a gate's assertion that can drift from its source (per architecture §Established Decisions [CI/CD]).
- Adding a CI network fetch without escalation, which would silently raise the non-loopback egress count above ONE (per architecture §Occupied Resources — Ports).

## Contract bindings
- arch ↔ security: the trust-boundary egress count (arch §Occupied Resources — Ports) is the same fact as security-plan §Dependency Security's third dependency class, which currently has one member (msedgedriver). The tool-selection record belongs in security-plan's Security Decisions Log. Architecture only registers the resulting resources: the `scripts/` entry, any env handle, and any egress.
- arch ↔ tests: the new gate step and the scanner's own tests fall under the CI gate-set enumeration (arch §Established Decisions [CI/CD] and the five enumeration sites). Test-plan keeps its own per-gate verification signal. Both the seeded known-bad inputs (a secret-shaped string, and an undeclared `${{ env.X }}`) are test-domain fixtures.
- arch ↔ obs: the `::error::` annotation must name the file and line and never the matched value. This is the same never-echo rule as the handle-only output pattern above, and it binds to obs-plan's redaction discipline.

## Acceptance criteria contributions
- The secret-scan step and the env-reference check step in `.github/workflows/ci.yml` are each their own named step with no `continue-on-error` and no `if:`. Each is presence-guarded, emitting `::error::` and exiting 1 when its subject is absent, and each exits non-zero on a seeded known-bad input (per architecture §Established Decisions [CI/CD]).
- `.github/workflows/ci.yml` gains no new non-loopback fetch. The msedgedriver pin gate remains the only CI-time network crossing, and the egress count stays ONE (per architecture §Occupied Resources — Ports / §Cross-cutting Patterns — Trust boundary).
- The scanner can be run locally without a sixth `agent-run.{sh,ps1}` command, so the 5-command harness surface is unchanged (per architecture §Stack and Technologies, operator-instruments row).
- Every wrap amendment this chunk triggers (the `scripts/` tree entry, the operator-instrument row, the CI gate-set sites) leaves `scripts/arch-registry-check.py measure --file .andromeda/architecture.md` reporting `registries: within target` (per architecture §Stack and Technologies, operator-instruments row, and amendment 2026-09-24).
