# arch extract

## Relevance
partial — the chunk changes no code and adds no seam, surface or resource. Architecture applies only to the files it touches: the workspace manifest, the nine member manifests, the npm frontend manifest and its lockfile, the repo-root file set, and the supply-chain and CI gates that read them.

## Constraints
- The workspace is the locked crate-per-seam set: nine `conductor-*` members whose `Cargo.toml` dependency edges *are* the architecture (per architecture §Established Decisions [Module Boundaries]; §Inherited Defaults → Module boundaries). A `license` key is package metadata only. Editing all ten Cargo manifests must add no member, remove none, rename none and add no dependency edge. The `conductor-*` prefix is the reserved crate namespace (per architecture §Occupied Resources → Interface routes / surfaces).
- The root `Cargo.toml` is "workspace manifest (members + shared deps)" (per architecture §Infrastructure Patterns → Directory structure). The plan does not state whether members inherit package keys through `[workspace.package]`, or which keys they inherit, and it does not state the `publish = false` posture at all. Whether every member already uses `*.workspace = true` inheritance, so that `license.workspace = true` fits the existing form, is a question for research.
- Standalone per-seam build is a MEASURED property, not a gate-enforced one: each member builds on its own targets (`--lib` for the seven libraries, `--bins` for `conductor-cli` and `conductor-tauri`). `--all-targets` is deliberately not the sweep form (per architecture §Established Decisions [Module Boundaries]). A manifest-inheritance edit touches every member's manifest, so this property must still hold after it.
- `crates/conductor-tauri/ui/` is an npm tree and NOT a Cargo member. Its gate is a committed `package-lock.json` plus `npm audit --omit=dev` clean (per architecture §Stack and Technologies → Desktop frontend; §Inherited Defaults → Frontend). So the `package.json` `license` edit and the lockfile's mirrored root entry stay inside the npm tree's own gate, apart from the cargo tooling.
- The supply-chain posture is that BOTH runners are green over the un-drifted lock: `cargo deny check advisories bans licenses sources` exit 0 and `cargo audit` exit 0 (per architecture §Infrastructure Patterns → Build system). The license allow-list describes DEPENDENCY licenses: the Tauri-tree `MPL-2.0` / `Apache-2.0 WITH LLVM-exception` and `BSD-2-Clause` for `arrayref`, each entry naming its crate and dependency path inline (same §). The plan does not address how `deny.toml` treats the workspace's OWN crates. That fork (P4) belongs to security and research, not to arch.
- `.gitattributes` pins LF repo-wide with `* text=auto eol=lf`. The measured index state is all `i/lf` / `i/none` / `i/-text`, with no `i/crlf` and no `i/mixed` (per architecture §Infrastructure Patterns → Build system). The two new root text files fall under that policy.
- The optional GUI bundle comes from the host `tauri-cli` bundler, which no lockfile resolves, and it is convenience, not a release gate (per architecture §Established Decisions [Deployment]; §Infrastructure Patterns → Deployment model). This agrees with the scope's exclusion of a Tauri bundle `license` field and an installer license page. Nothing in arch requires one.

## Patterns to follow
- Shared package metadata is inherited from the workspace root instead of repeated per member. That is the shape research is to confirm for `version` / `edition` / `rust-version` / `publish`, and `license` would join it. Arch describes the root manifest as holding "members + shared deps" (per architecture §Infrastructure Patterns → Directory structure).
- The `package-lock.json` changes only through the npm tool, never by hand, and stays committed (per architecture §Inherited Defaults → Frontend).
- A lockfile delta is stated by package COUNT, not byte-identity. `Cargo.lock` may move, or not, on a metadata-only edit, but the package set must not grow (per architecture §Infrastructure Patterns → Build system: "BOTH supply-chain runners are green over the un-drifted lock").

## Anti-patterns to avoid
- Adding a workspace member, a crate, or any `[dependencies]` / `[dev-dependencies]` edge while editing the manifests. A metadata chunk must leave the seam graph byte-equivalent (per architecture §Established Decisions [Module Boundaries]).
- Hand-editing `package-lock.json`'s `packages[""]` entry instead of regenerating it through npm (per architecture §Inherited Defaults → Frontend: committed lockfile as the gate subject).
- Adding a `deny.toml` license entry to cover Conductor's OWN crates as if they were a dependency exception. Arch's accepted-license entries each name a DEPENDENCY crate and its path (per architecture §Infrastructure Patterns → Build system). `MIT` and `Apache-2.0` are, per the scope, already allowed.

## Contract bindings
- arch ↔ security: the supply-chain runners (`cargo deny` licenses/bans/advisories/sources + `cargo audit`) read the member manifests and `Cargo.lock` this chunk touches (per architecture §Infrastructure Patterns → Build system). The own-crate license-check fork (`deny.toml` `private = { ignore = true }` vs. checked) is security's to settle.
- arch ↔ tests (CI): the `rust` job's gates run over every tracked file (per architecture §Established Decisions [CI/CD]). These are `cargo fmt --all --check`, build, nextest and clippy, plus the repository-hygiene `Secret-scan gate`, which scans file NAMES and content in `git ls-files --cached --others --exclude-standard`. Two new root files enter that listing. Whether `LICENSE-MIT` / `LICENSE-APACHE` (names or text) trip the secret-scan patterns is research's question.
- arch ↔ wrap amendment: §Infrastructure Patterns → Directory structure lists repo-root files (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `rustfmt.toml`, `.gitattributes`). The two LICENSE files are a candidate root-tree amendment at wrap, not something this chunk authors into the master.
