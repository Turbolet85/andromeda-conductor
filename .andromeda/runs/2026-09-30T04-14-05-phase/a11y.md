## Constraints
- The routine arm is a CI gate, and a11y-plan requires it to fail fast. A fix for the axe inject race must keep the step failing on `violations.length > 0` and must not turn a race into a skip or a warning. Per a11y-plan §11 A11y Anti-Patterns → CI ("NEVER skip a11y on CI/operator-gate failure"), plus §9 CI Integration and §10 SLO Invariants (build/deploy failure conditions).
- No retry-once policy is allowed for a11y results. A mocha/wdio `retries`, a re-run-until-green step, or a catch-and-retry around `analyze()` that can hide a real violation all fall under the ban. The plan makes this the counterpart of tests' zero-flakiness rule. Per a11y-plan §10 SLO Invariants (always-required invariant + cross-input parallel) and §11 → SLO. Whether a bounded frame-readiness WAIT before injection counts as a "retry" in the banned sense (a wait before the first analysis, not a second analysis after a result) is P3/P4's call, and the plan text does not settle it.
- The fix must stay inside the ONE webview-automation stack: axe injected through `@axe-core/webdriverio` into the tests' `@crabnebula/tauri-driver` + WebdriverIO session. A fallback injection route through puppeteer/CDP is not allowed. Per a11y-plan §3 A11y testing tool pick and §11 → CI ("NEVER stand up a second browser-automation stack").
- The axe configuration must stay the Minimal baseline `withTags(['wcag2a','wcag2aa','wcag21aa'])`. Using a partial `runOnly`, or dropping default rules such as `color-contrast`, to dodge the failing call requires a Decisions Log entry. Per a11y-plan §3 A11y testing tool pick (Configuration) and §11 → Strategy.
- The expected-skip SET under `CONDUCTOR_A11Y_STRICT` stays exactly two, and both harness shells must go on asserting the runner's PRINTED verdict (the `Spec Files:` failed count and the per-spec skip tally). A remedy that skips the axe spec on "frame not ready" would add a third skip, and that must stay red. Per a11y-plan §11 → Strategy (CI gates three things in place of the hold-dependent half) and §11 → CI (the strict mechanism).
- A CI a11y verdict is stated with its configuration (hosted `windows-2022`, a coherent 131.0.2903.86 driver/runtime pair, High integrity) and is never a bare verdict. The race's reproduction and its cannot-recur witness should each name the configuration they ran under. Per a11y-plan §11 → Strategy ("Each term of that configuration is load-bearing…") and §9 CI Integration.

## Patterns to follow
- The session runs with `wdio:enforceWebDriverClassic`, because on wry/WebView2 script evaluation over BiDi answers `Page/Frame is not ready` indefinitely while classic WebDriver returns normally. This is the plan's recorded prior instance of the same error string, per a11y-plan §6 Visual Design Verification → Motion tokens (the superseded-framing provenance clause). Whether `@axe-core/webdriverio`'s `assertFrameReady` / `axeSourceInject` path still reaches a BiDi or frame-readiness probe under the enforced-classic session is P3's question, and the plan cannot answer it.
- Earlier red readings in this job were diagnosed as ASSERTION or configuration defects, not a11y defects. Examples are the `:384` counting-basis defect, and the SC 2.1.1 / SC 2.4.3 walk that waited on a `BODY` sentinel, fixed 2026-09-17 to be environment-independent. They were recorded with their mechanism and their measuring run. Per a11y-plan §9 CI Integration (premise-corrected clause) and §11 → Strategy (the NARROWED carve-out).
- Results go out through the 5-command harness's `logs` verb as the structured violation JSON aligned to the obs §6 envelope. `verdict`/`state` is `Fail` when any violation tuple was recorded OR any spec failed, so a thrown inject error already counts as `Fail` in the artifact. Per a11y-plan §3 Structured violation JSON schema and §3 CI integration.

## Anti-patterns to avoid
- Marking the race "flaky" and quarantining it, lowering the gate to a warning, or adding a retry. The plan treats any retry-once policy as masking real failures. Per a11y-plan §11 → SLO and §10 SLO Invariants.
- Moving axe off `@axe-core/webdriverio`, or bypassing it with a hand-rolled or second-stack injection, without keeping the JSON `AxeResults` engine as the source of truth. Per a11y-plan §11 → CI and §11 → Strategy (axe-core library, not an extension or UI-only engine).
- Accepting "one lucky green" as proof. A skipped-green run and a real pass are indistinguishable unless the printed verdict and the skip SET are asserted. Per a11y-plan §11 → CI (the strict mechanism) and §11 → Universal ("NEVER claim WCAG conformance without machine-verifiable evidence").

## Contract bindings
- a11y ↔ tests: the routine arm rides the tests' `wdio run` webview-E2E stack and the 5-command harness (`agent-run run --e2e`, results through `logs`). The zero-flakiness / no-retries discipline in tests §9/§10 is the parallel of a11y's no-retry invariant. Per a11y-plan §3 CI integration, §9 CI Integration and §10 SLO Invariants (cross-input parallel).
- a11y ↔ obs: the violation record (including the `Fail` produced by a failed spec) folds into the obs §6 envelope with the `service.name` / `deployment.environment` (+ `ci.run.id` / `git.commit.sha` in CI) resource tags. `journal_conformance` is the reused gate. Per a11y-plan §3 Structured violation JSON schema and §9 CI Integration (CI-specific resource attributes).
- a11y ↔ security: the CI `a11y` job's pinned msedgedriver (Authenticode-gated) is the one registered network exception. A fix must not change the driver-version derivation. That rule is security-plan's, and it is noted here only because the job under repair carries it.
