## Relevance
partial — the chunk is a harness/NVDA/webview diagnosis inside the dev-only `sr*` leg; arch governs where that leg sits (scope law, trust boundary, the registered ports, env handles, landing sites, the scripts tree, and the driver-to-runtime pin posture), not the cause-finding itself.

## Constraints
- Screen-reader work stays inside the ONE WebdriverIO + tauri-driver stack: the `sr` / `sr-empty` / `sr-error` suites are one of the three suite families over it, and NVDA's own speech log is the driver on the Windows dev host. The scope law allows driving Conductor's own webview and forbids a second automation stack and any automation of Pulse's UI. Any discriminating control or remedy therefore has to run through that stack (per architecture §Cross-cutting Patterns → Scope law).
- Trust boundary for the leg: tauri-driver and the native WebDriver bind loopback `4444`/`4445` only while the harness runs. The `sr*` suites also spawn the host NVDA named by `CONDUCTOR_NVDA` and a fixed-argv PowerShell window-activation script. Neither of those opens a listener. A remedy in the launch or foreground path has to keep all of this true. Whether the current activation script is the cause is a question for research (per architecture §Cross-cutting Patterns → Trust boundary; §Occupied Resources → Ports).
- `CONDUCTOR_NVDA` is read by `crates/conductor-tauri/ui/wdio.conf.ts` (`startNvda` / `stopNvda`) and by nothing else. It is validated at the harness edge like `CONDUCTOR_MSEDGEDRIVER`, and it is used only as the program of an array-form, detached spawn with a fixed argv (`-m --no-sr-flag -c <leg config dir> -l 12 -f <leg speech log>`, then `-q`). An unset handle skips through `exitUnresolvedHandle()`. An NVDA-configuration remedy that changes that argv or the leg config dir changes a registered resource, so it becomes a §Occupied Resources amendment at wrap (per architecture §Occupied Resources → Environment variables).
- The `CONDUCTOR_*` namespace is reserved for handles over artifacts and concepts this document defines. Only `CONDUCTOR_MSEDGEDRIVER` and `CONDUCTOR_NVDA` name host dev-tools. A new handle, for example one that points at a pinned WebView2 runtime, has to be registered with its handle class and reader set. It must never be added silently (per architecture §Occupied Resources → Environment variables; §Cross-cutting Patterns → Config management).
- The driver-to-runtime pin that arch records is scoped to CI. The `a11y` job on `windows-2022` reads the runtime from the `EdgeUpdate` keys, fetches msedgedriver for that version, runs it through an Authenticode gate, and asserts driver major == runtime major. The document describes no pin for the dev-host runtime. Its one non-loopback egress (`msedgedriver.microsoft.com`) is CI-only, and no dev-host leg reaches it. A runtime or driver pin remedy on this host is therefore a new posture to register. If it fetches anything at leg time, it is a new egress crossing (per architecture §Occupied Resources → Ports; §Infrastructure Patterns → CI/CD).
- Per-suite self-obs landing sites: `sr-empty` lands at `runs/logs/conductor-tauri.jsonl`, and `sr` / `sr-error` land at `runs/sr-leg/logs/conductor-tauri.jsonl`. Both come from the one tauri-driver spawn site at `cwd` = the workspace root, which sets `CONDUCTOR_RUNS_DIR` per suite. A changed spawn or launch path keeps those sites or amends them (per architecture §Occupied Resources → On-disk artifacts, `logs/conductor-tauri.jsonl`).
- Placement: harness and webview changes live in `crates/conductor-tauri/ui/`, the frontend asset subtree. That subtree is not a Cargo workspace member. Any Rust-side change stays within `conductor-tauri`'s existing crate edges. Any new file under `scripts/` is registered in the directory tree with its qualifier (for example "wired into neither harness shell, adds no 6th command") (per architecture §Occupied Resources → Frontend asset subtree; §Inherited Defaults → Module boundaries; §Infrastructure Patterns → Directory structure).

## Patterns to follow
- Harness-edge handle guard and array-form spawn: existence check, then `isFile`, then shell-metacharacter rejection, then an array-form spawn with the path as its own argv element. The value is never logged, echoed or committed (per architecture §Occupied Resources → Environment variables, `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA`).
- A verdict is recorded against its measured configuration, never as a bare verdict. The arm is "measured and proven for that configuration and unproven elsewhere". A mechanism no probe measured is "recorded, not established". Apply this to the WebView2 154 hypothesis and to the regrade: each graded row carries the runtime, driver and NVDA versions it ran on (per architecture §Established Decisions → [CI/CD]).
- Version coherence comes from a reading, not a floor. The CI gate takes the driver version from the runtime's own registry reading and asserts that the majors match. If this chunk pins anything, it copies that shape: derive the version from what is present, never from a floating latest (per architecture §Infrastructure Patterns → CI/CD).
- Measured claims in the masters cite a committed evidence path. The 2026-09-04 `nvda-pass.json` is already cited this way for the console-suppression claim. The fresh `nvda-pass.json` this chunk commits under `evidence/` is the artifact any amended claim points at (per architecture §Occupied Resources → Service / process names).

## Anti-patterns to avoid
- No second automation stack, no automation of Pulse's UI, and no new listener beyond the harness-lifetime `4444`/`4445` pair (per architecture §Cross-cutting Patterns → Scope law / Trust boundary).
- No runtime FLOOR or runtime raise as the remedy. The `≥ 152` floor was retired because it was not necessary (a coherent 131/131 pair runs green), not sufficient (152/152 failed), and destructive (it raised a working 131 image to 153). A "require ≥ / ≠ 154" posture repeats that shape unless a two-sided control isolates the runtime (per architecture §Infrastructure Patterns → CI/CD).
- No leg-time network fetch on the dev host. The registered non-loopback egress count is ONE, CI-only, and it is reached by no dev-host harness leg (per architecture §Occupied Resources → Ports; §Cross-cutting Patterns → Trust boundary).
