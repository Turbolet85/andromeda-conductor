## Patterns to follow
- The wdio-edge `UNSAFE_PATH` guard + array-form spawn (`nvdaExe()` / `nativeDriver()` shape) is the registered pattern for any host-tool program a leg launches (security-plan §Input Validation, host-dev-tool handle rows).
- Committed SR records pass through `writeNvdaPass`'s scrub + closed sets and are asserted by the chunk's gate-1 hygiene grep (no host path / seam-crate struct name) + gate 2 (closed sets), per security-plan §Input Validation (speech-log ingest row, "Enforced by" column).
- A new spawn, egress or dependency-class member is registered as a deliberate, operator-ratified boundary widening with its admitting control stated — never added silently (security-plan §Security Anti-Patterns → Code Patterns, rule (b)'s sixth/seventh registrations; §Dependency Security, third dependency class).
- A dated reading is superseded by a later measurement, never edited in place — the pattern the plan uses for the 2026-09-02 → 2026-09-04 S1-01 reading (security-plan §Security Anti-Patterns → Code Patterns, rule (a)); applies to the prior chunk's silent `nvda-pass.json`, which stays as the dated record beside the regrade.

## Anti-patterns to avoid
- NEVER pass an operator-supplied value to a harness spawn inside a shell string or as the program outside the guarded host-tool form, and never add an eighth governed form without escalation (security-plan §Security Anti-Patterns → Code Patterns, rule (b)).
- NEVER commit raw NVDA speech text, foreign window titles, process-census command lines or registry/runtime paths un-scrubbed into `evidence/` (security-plan §Security Anti-Patterns → Logging; §Input Validation speech-log ingest row).
- NEVER introduce a dev-host network fetch of a runtime or driver as a "pin" remedy outside the registered single CI egress (security-plan §Threat Model Summary → Infrastructure; §Dependency Security, third dependency class).
