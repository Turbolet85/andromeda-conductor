# a11y extract

## Relevance
relevant — the chunk isolates the cause of a configuration-bound screen-reader focus finding, and a11y-plan §3 *Screen reader test pattern* is the master that states that finding, its candidates and its grading.

## Constraints
- a11y-plan §3 *Screen reader test pattern* requires the NVDA focus verdict to be stated as CONFIGURATION-BOUND: runtime/driver pair, Windows build, NVDA version and object model (`allowInChromium`). It records the cause as "recorded, not established" and names three standing candidates (the runtime/driver pair, the cumulative updates, the desktop), with NVDA's object model ruled out. So each control arm must record the same configuration axes, plus the desktop state, or its reading cannot be compared with the 152 / 154 rows. The §3 sentence may only be narrowed to what a control actually MEASURED (per a11y-plan §3 *Screen reader test pattern*).
- a11y-plan §3 *Screen reader test pattern* and §2 *Agent-runnable invariants* require the NVDA pass to be AGENT-DRIVEN from NVDA's own speech log (`-l 12`) over the ONE `@crabnebula/tauri-driver` + WebdriverIO stack, with zero new dependencies. The operator's role is REVIEW of the graded record. A row the agent arm cannot reach is a recorded finding with its reason, never a pass and never a manual arm. Whether a no-boundary arm (Edge 154, or another WebView2 app) can be driven this way without a new spawn form is research's question (per a11y-plan §3 *Screen reader test pattern*; §2).
- a11y-plan §3 *Screen reader test pattern* (*Pass spec format*) requires every graded row to carry its producing action, carrying node, expected output and required tokens, WCAG SC, result, ARM (agent or operator) and heard text. Rows are graded by `parse-nvda-log.ts` against `nvda-pass-spec.md`, and the operator review is transcribed into `evidence/nvda-pass.json`. A control run over a non-Conductor page has no spec rows. How its record maps onto (or deliberately stays outside) this format is a P4 question (per a11y-plan §3 *Screen reader test pattern*).
- a11y-plan §10 *Always-required SLO invariant* and §11 *SLO* forbid retry-once policies for a11y failures because they mask real failures. For the three owned reds (the focus-row count, S0-09 / E0-05, one-configuration `false`), that means no regrade by rerunning until something is announced. They regrade only after the cause is removed, or route forward with a named owner (per a11y-plan §10; §11 *SLO*).
- a11y-plan §9 *CI Integration* and §3 *Bootstrap phases* (`screen-reader-test-spec-setup`) keep the screen-reader leg operator/local and not CI-gated. `CONDUCTOR_NVDA` is its host-tool handle, and an unset handle means skip at exit 0. No control arm may be wired into the `a11y` CI job (per a11y-plan §9; §3 *Bootstrap phases*).
- a11y-plan §11 *SLO* (inherited from the tests' Status JSON constraint) and §3 *Structured violation JSON schema* forbid a11y artifacts from carrying absolute host paths or internal seam-crate struct names. NVDA speech logs are untrusted third-party text that can speak a host path, so any committed control evidence must be scrubbed before it lands (per a11y-plan §11 *SLO*; §3 *Structured violation JSON schema*).
- a11y-plan §2 *Agent-runnable invariants* and §11 *Universal* make the SR pass SUPPLEMENTAL, never sole. The routine `--e2e` arm (axe + colorjs.io + WebdriverIO-keyboard) is the machine baseline. If the chunk touches wdio config or specs for control (1), that baseline and its strict expected-skip SET (exactly two, per §11 *Strategy*) must stay unchanged (per a11y-plan §2; §11 *Universal*; §11 *Strategy*).

## Patterns to follow
- The `sr` / `sr-empty` / `sr-error` wdio suites over the one stack, with `CONDUCTOR_NVDA` set per command and NVDA's speech log as the recording driver. This is the existing agent-driven SR shape a control arm should reuse rather than replace (per a11y-plan §3 *Bootstrap phases* `screen-reader-test-spec-setup`; §3 *Screen reader test pattern*).
- A per-row ARM attribution (agent vs operator), so a mixed pass is never read as wholly automated or wholly manual. This applies equally to a control arm driven by a manual Tab (per a11y-plan §3 *Screen reader test pattern*, *Pass spec format*).
- Dated, configuration-bound readings in the master: the §3 platform set is stated as "last heard on … (date)" and "on runtime X / build Y / NVDA Z … measured at {evidence path}". A new measurement EXTENDS that set with its configuration and evidence pointer rather than overwriting it (per a11y-plan §3 *Screen reader test pattern*).
- The distinction between live regions (which still speak on 154) and focus changes (heard only in the first burst). Each control reading should grade both separately (per a11y-plan §3 *Screen reader test pattern*).

## Anti-patterns to avoid
- A rerun-until-announced regrade of any focus row, or a soft or relaxed bar for the three owned reds (per a11y-plan §11 *SLO*; §10).
- A second browser-automation stack (puppeteer/CDP) stood up to drive the no-boundary page. axe, keyboard and SR driving ride the one WebdriverIO + tauri-driver/msedgedriver stack. Whether pointing that stack at Edge rather than `conductor-tauri` counts as the same stack is for P3/P4 to settle against security rule (b) (per a11y-plan §11 *CI*).
- Human-only NVDA review with no machine record. A manual-keyboard control arm still needs NVDA's speech log as its evidence, never operator recollection alone (per a11y-plan §11 *CI*; §11 *Universal*).

## Contract bindings
- a11y ↔ tests: the SR leg is one of the three suite families over the tests §6 webview stack (`npm run a11y:sr*`). Any control-arm spec or wdio config change lands in that shared harness (per a11y-plan §9 *Per-pipeline-stage a11y artifacts*; §3 *Focus management test harness*).
- a11y ↔ security: SR speech-log ingest is bounded and scrubbed to `<host-path>`. A new driving form for the no-boundary page (a different program under the driver) is a harness-spawn question owned by security rule (b), not by this plan (per a11y-plan §11 *SLO*; §3 *Screen reader test pattern*).
- a11y ↔ wrap drift: if control (1) narrows the candidate list (for example, silent in Edge 154 or another WebView2 app puts the cause below Conductor), the §3 "cause is recorded, not established … candidates" sentence becomes stale against the chunk's evidence. That is an amendment candidate on a11y-plan §3 *Screen reader test pattern* for the wrap, never a silent edit (per a11y-plan §3 *Screen reader test pattern*).

## Acceptance criteria contributions
- Every control arm's evidence record states its full configuration and the arm (agent/operator) that produced each reading, and grades focus changes separately from live-region speech. A reading missing any axis is not usable as a control. The axes are: WebView2 runtime and driver versions (or the Edge version for an Edge arm), Windows build, NVDA version, `allowInChromium` value and desktop state (per a11y-plan §3 *Screen reader test pattern*).
- The evidence states what each arm's outcome LICENSES. An Edge-154 reading and another-WebView2-app reading are recorded as distinct subjects, and no focus verdict is extended beyond the configuration it was measured on (per a11y-plan §3 *Screen reader test pattern*).
- None of the three owned reds is graded `announced-as-expected` or otherwise passed by rerun. Each is either regraded after the cause is removed, with the removing change named, or routed forward with a named owner and the measured cause (per a11y-plan §10 *Always-required SLO invariant*; §11 *SLO*).
- Committed control evidence carries zero absolute host paths (per a11y-plan §11 *SLO*). If wdio config or specs changed, the strict routine `--e2e` arm still reads 0 failed with the expected-skip SET at exactly two (per a11y-plan §11 *Strategy*).
