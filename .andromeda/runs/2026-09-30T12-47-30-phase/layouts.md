## Relevance
partial — the chunk creates or changes no surface. Its three owned reds, though, grade whether keyboard focus on the desktop-webview console reaches NVDA, and the layout plan defines those focus positions. Control (1)'s plain focus page, the PREREQ gates and the evidence record sit outside this plan.

## Constraints
- The focus claim at stake is layout-owned: selecting a control by keyboard moves the visible focus, and that focus position must be communicated to assistive tech (a11y derives the semantics) (per layout-templates §Surface: desktop-webview → Component — Primary navigation). Silence after the first burst means this requirement is not met on the measured configuration. Whether the cause is Conductor's webview posture or the host/runtime is the control's question; the layout plan does not answer it.
- The console is ONE surface in different run states (`idle` · `live` · `hold` · `aborted`), with no router, no breakpoints and no back/forward (per layout-templates §Surface: desktop-webview → Primary screens; §IA notes). Any focus-row re-grade or routing record names the run state each row was driven in, and does not invent a screen or route.
- The focusable topology the SR focus rows walk is fixed by the plan: the control row (picker → Start → Stop, with Start kept focusable through `aria-disabled`, never native `disabled`); the coverage matrix as a region with exactly ONE tab stop (roving focus, with the scroll container itself not a tab stop); and the go/no-go dialog, which traps focus and restores it explicitly through `restoreFocusTo` (per §Component — Primary navigation; §Component — Primary content block 1; §Component — Hero / signature section). A control arm that departs from this topology is not measuring Conductor's surface.
- The catalog load-error region inserts its visually-hidden re-assertion once, on the FIRST `focusin`. The three sibling error regions keep the empty-mount shape because they fire at arbitrary times rather than before the screen reader binds (per §Component — Primary content block 1 → States, SR row R0-01). This is a timing-sensitive, first-focus mechanism on the same surface. Whether it bears on the "first burst only" reading is research's question; the plan states the design and does not attest to its behaviour on WebView2 154.
- Status is never colour-alone, and the focus ring (`color-focus`) is visible on every interactive control, with a `border-emphasis` edge so focus is never colour-only (per §Component — Primary navigation; §Component — Primary content block 1 → States). A "heard in the first burst" reading therefore concerns AT delivery, not visible focus. The evidence record should keep those two apart.
- Single letters stay free for the picker's type-ahead and the screen reader's browse mode, and console keys are modifier-only (per §Component — Primary navigation). Any keyboard driving in control (1), or in a Conductor re-run, uses Tab/arrow/modifier keys and does not rely on single-letter bindings the surface deliberately leaves unbound. This keeps the E0-09 browse-mode finding separate.

## Patterns to follow
- Record each measured focus fact with its SR row id and date, in the plan's own convention ("measured 2026-09-02, SR row E0-01"; "SR row S0-16, measured 2026-09-04") (per §Component — Primary content block 1 → States). A routed or re-graded focus row keeps that row-id + date + configuration shape.
- Separate designed state from shipped state explicitly ("Designed, NOT shipped", "as shipped … the checklist render being UNBUILT there") (per §Component — Footer; §Component — Primary content block 2). A routing record for the three reds says which focus claims are designed and which are measured on this configuration, and never merges the two.
- A route-owned gap is named, not built, inside the plan's section (per §Component — Footer; §Component — Operator-checklist). The unbuilt product lever (Tauri `additionalBrowserArgs`) follows the same named-not-built shape. It is not a layout element, so the layout plan owns no text for it.

## Anti-patterns to avoid
- Do not restructure the focus topology (tab stops, roving focus, dialog trap/restore, the load-error re-assertion siting) as a way to "make NVDA hear it". Any layout edit is out of this chunk's boundaries and would confound the isolation (per §Component — Primary navigation; §Component — Primary content block 1; §Component — Hero / signature section; scope §Boundaries).
- Do not add a new screen, route or modal to host a control page inside Conductor. `AlertDialog` is the only modal, and the console has no routes (per §IA notes). Control (1)'s plain page lives outside Conductor's surface; where its fixture lives is P4's call.
