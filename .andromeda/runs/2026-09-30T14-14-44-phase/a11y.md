# a11y extract

## Relevance
relevant — the chunk is the screen-reader leg's confound control plus a regrade of NVDA focus and browse rows, which a11y-plan §3 *Screen reader test pattern* governs directly.

## Constraints
- a11y-plan §3 *Screen reader test pattern* (Per-surface test spec) requires the NVDA pass to be AGENT-DRIVEN from NVDA's own speech log (`-l 12`) over the SAME `@crabnebula/tauri-driver` + WebdriverIO session, with zero new dependencies and the operator's role limited to REVIEW of the graded record. Any OS-level key path that step 1 validates has to fit that shape. Whether the current `sr*` harness can deliver OS-level keys at all is a question for research.
- a11y-plan §3 *Screen reader test pattern* requires the focus verdict to be CONFIGURATION- and INPUT-PATH-BOUND. A verdict names the configuration it was measured on. Silence heard on the injected, driver-launched path is scoped to that path, never to a keyboard user's experience, and the physical keyboard stays "unmeasured" until arm K runs. The plan records the cause as not established, and states the injected-keys vs driver-launch confound as open. Step 1's result has to be stated in that same bound form, with its epistemic status.
- a11y-plan §3 *Screen reader test pattern* requires browse-mode rows to stay "pending OS-level key injection" until they are actually driven. They are recorded as findings, never as passes, and never as a manual arm. An E0-09-class row stays a finding unless it is driven on the OS path and heard.
- a11y-plan §3 *Screen reader test pattern* (Pass spec format) requires one row per must-announce item over the shipped `RunState` set. Each row carries its producing action, carrying node, expected NVDA output with required tokens, WCAG SC, result, arm and heard text. Rows are graded by `parse-nvda-log.ts` from the speech log against `nvda-pass-spec.md`, with `operator_review` transcribed into `evidence/nvda-pass.json`.
- a11y-plan §3 *Supplemental to automated* and §11 *Universal (agent-driven specific)* require that the SR pass is never the sole verification. It judges announcement quality only, and axe-core carries SC 4.1.2 / 4.1.3 programmatically. So arm K (the physical keyboard) is supplemental evidence, never a gate substitute.
- a11y-plan §3 *CI integration* and §9 *Pipeline integration* keep the screen-reader leg as an operator/local gate, not a CI gate. Per §3 *Bootstrap phases* (screen-reader-test-spec-setup), `CONDUCTOR_NVDA` is the host-tool handle, and an unset handle means the leg skips at exit 0. A harness change must not pull the `sr*` leg into the routine `--e2e` arm or into CI.
- a11y-plan §5 *Keyboard Navigation* keeps single letters, Ctrl+W and Alt+F4 unbound, because the picker's type-ahead and NVDA browse mode keep them. OS-level keys sent for browse-class rows reach NVDA's own key handling, so the key choice has to respect that reservation.

## Patterns to follow
- The measured-platform statement form in a11y-plan §3 *Screen reader test pattern*: each verdict carries the runtime/driver pair, Windows build and NVDA version, and cites its record as "as measured at `<chunk>/evidence/<file>`, <date>". §11 *Strategy* uses the same form ("stated with its configuration rather than as a bare verdict").
- The per-row `arm` field (agent / operator) from a11y-plan §3 *Pass spec format*, so a mixed pass is never read as wholly automated or wholly manual. OS-level input is a new input path, not a new arm, and should be named per verdict.
- The one-stack harness from a11y-plan §3 *A11y testing tool pick* and §11 *CI*: the `sr` / `sr-empty` / `sr-error` wdio suites over the one tauri-driver + WebdriverIO stack. Per §3 *Bootstrap phases*, these suites are the regrade's carrier.
- The not-runnable declaration pattern in a11y-plan §3 *Screen reader test pattern*: when a subject cannot be driven on this host, it is recorded as declared-not-runnable with no pass claimed. Arm K's `not-run` record takes the same shape, with its clearing event named.

## Anti-patterns to avoid
- a11y-plan §11 *SLO* and §10 *Always-required SLO invariant* ban retry-once policies because they mask real failures. A rerun-until-announced is that ban in screen-reader form. Each row is graded from the run on the validated path.
- a11y-plan §11 *CI* bans a second browser-automation stack. The OS-level key path has to supplement the one WebdriverIO + tauri-driver session, never replace it with a parallel puppeteer/CDP driver.
- a11y-plan §11 *SLO* bans a11y artifacts that leak absolute host paths or internal seam-crate struct names. This covers the regrade record, the speech-log excerpts and the heard text.

## Contract bindings
- a11y ↔ tests §6: the `sr*` suites are tests-owned wdio suites over the shared webview driver. A change to their key path or launch posture is a change to that shared session, per a11y-plan §3 *Focus management test harness* and *Bootstrap phases*.
- a11y ↔ security rule (b), harness-spawn forms: committing OS-level `SendInput` into the driver-stack leg is a boundary question that security owns. a11y-plan does not decide it. a11y only requires that the input path be named in every verdict.
- a11y ↔ obs §6: the SR record inherits the envelope's no-host-path / no-struct-name constraint, per a11y-plan §3 *Structured violation JSON schema* and §11 *SLO*.
- a11y ↔ wrap drift: a11y-plan §3 *Screen reader test pattern* currently states the injected-keys vs driver-launch confound as open, and E0-09-class browse rows as "pending OS-level key injection". Step 1's result, and any browse row driven on the OS path, would make those clauses stale. That calls for a §3 amendment at wrap, stated with its configuration.

## Acceptance criteria contributions
- Every regraded verdict (S0-09, E0-05, E0-09 and each previously silent focus row R0-02..R0-04, E0-02..E0-06) names runtime × driver × NVDA × OS build × input path. No verdict is stated as a keyboard user's experience unless it was measured on that path (per a11y-plan §3 Screen reader test pattern).
- An E0-09-class browse row grades `announced-as-expected` only when it was driven on the OS-level path and its required tokens appear in the heard text. Otherwise it stays a recorded finding with its reason, never a pass and never a manual arm (per a11y-plan §3 Screen reader test pattern).
- The regrade rows are graded by `parse-nvda-log.ts` from the NVDA speech log against `nvda-pass-spec.md`. Each row carries its `arm` and heard text, and none is hand-asserted (per a11y-plan §3 Pass spec format).
- No row is closed by repeating a run until it announces. Each regraded verdict traces to the run on the path step 1 validated (per a11y-plan §11 SLO and §10 Always-required SLO invariant).
