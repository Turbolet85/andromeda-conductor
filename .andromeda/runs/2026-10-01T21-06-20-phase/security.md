## Relevance
partial: the chunk changes emit behaviour inside the loopback-egress model. Security binds only through the dependency gate (if shape (a) brings in an entropy source), the crypto-algorithm ban (if identity is derived by hashing), the spawn and env-handle rules (if shape (b) lands in the harness shells), and the ban on reaching Pulse's stores outside the MCP tool surface.

## Constraints
- Egress must stay loopback OTLP/gRPC to `127.0.0.1:4317` only. Neither shape may add a new egress target, a new port bind or an inbound listener in a shipped binary (per security-plan §Threat Model Summary → Attack surface, OTLP/gRPC egress vector; §Security Anti-Patterns → Universal, the scope-law/listener ban).
- If shape (a) needs a per-run uniqueness source that the tree does not already resolve (an OS-entropy or UUID crate, say), that is a dependency delta. `cargo audit` and `cargo deny check advisories bans licenses sources` must be verified green over the NEW `Cargo.lock`, the lock must be committed with no drift, and any new license or advisory goes through the justified-comment `deny.toml` mechanism, never a silent skip (per security-plan §Dependency Security, Pinning / Accepted exceptions; §Security Anti-Patterns → Universal). Whether the tree already holds a usable source (the existing `ChaCha8Rng` / `rand` lineage in `conductor-emit`) is research's question.
- If shape (a) derives `trace_id` / `span_id` by hashing (seed, per-run discriminator), it must not use MD5, SHA-1 or any other deprecated algorithm. The ban is active for `conductor-emit`, which already ships a blake3 derivation for the exception fingerprint (per security-plan §Security Anti-Patterns → Data Protection, the deprecated-crypto ban).
- The test that proves "both drives land" must establish landing only through the MCP tool surface (read-back), or through Pulse's own log read via the guarded `capture_paths` resolution. It must never open, copy or stage rows in Pulse's stores directly to induce or observe a SUT state (per security-plan §Security Anti-Patterns → Data Protection, the `corpus.db` file-access ban and its staging clause; §Input Validation, the real-model capture ingest row).
- If shape (b) adds a new tunable (for example a minimum-gap env handle in the `CONDUCTOR_*` namespace), it must be classified and validated per READER. A path-valued handle must be canonicalized and bounds-checked at the `conductor-cli` edge. A flag- or integer-valued handle must never become a path, an argv element or a log value. The handle must stay non-secret (per security-plan §Input Validation, env-handle rows and the closing paragraph on non-path handles; §Secret Management → Storage).
- If shape (b) is enforced in `scripts/agent-run.{sh,ps1}` and adds any subprocess spawn there, that spawn falls under harness-spawn rule (b): an array-form argv, no shell string, no `eval`-equivalent. A NINTH governed form escalates under playbook `:124` for the founder's live word and never becomes routine (per security-plan §Security Anti-Patterns → Code Patterns, rule (b)). A plain in-shell wait adds no form.
- Every artifact must stay sanitized. A per-run discriminator, or the span identities themselves, written into the JSONL journal, `<run_id>.md`, `runs.db` or committed evidence must carry no absolute host path and no internal seam-crate struct name (per security-plan §Error Handling, run-report artifact sanitization; §Security Anti-Patterns → Logging).

## Patterns to follow
- Use the existing `blake3` derivation in `conductor-emit` as the sanctioned hash primitive, if identity is derived rather than drawn (per security-plan §Security Anti-Patterns → Data Protection).
- Admit a dependency on a measured basis: state it as the package COUNT or a new-package diff over the new lock, never as lockfile byte-identity, with `cargo deny` verified green over that lock (per security-plan §Dependency Security, admitting a new dependency).
- Route a refused export as a typed value: a `tonic::Status` from the `:4317` export is a typed verification input through the verdict/error wall, never a panic (per security-plan §Error Handling, Error format; §Security Anti-Patterns → Universal).
- If the test reads `CONDUCTOR_RUNS_DIR` or `ANDROMEDA_PULSE_DATA_DIR` in a test binary, resolve them through the shared guard module `conductor-run/tests/capture_paths` (`runs_dir_from` / `pulse_logs_dir_from`), with path-free rejection reasons (per security-plan §Input Validation, the path-handle row and the capture ingest row).

## Anti-patterns to avoid
- NEVER introduce a dependency delta without `cargo-audit` and `cargo-deny` green and a committed `Cargo.lock` with no drift (per security-plan §Security Anti-Patterns → Universal).
- NEVER reach Pulse's stores (`corpus.db` or its buffer files) directly to prove or induce "landed", and never stage a row to create the SUT state under test (per security-plan §Security Anti-Patterns → Data Protection).
- NEVER interpolate an operator-supplied value (a gap value, a seed or a run discriminator) into a shell string or a spawn program in the harness shells (per security-plan §Security Anti-Patterns → Code Patterns, rule (b)).

## Contract bindings
- security ↔ arch (determinism): the security plan does not rule on whether span identity is part of the "same scenario+seed ⇒ same stream shape" invariant. That is architecture's call. Its only binding is that any uniqueness source added for shape (a) is subject to the dependency gate above. If a wall-clock source is used, the journal-stamp clock rule (std::time, never tokio's virtual clock) binds only the journal and report stamps (per security-plan §Security Anti-Patterns → Logging).
- security ↔ tests: the proving test runs against loopback gRPC stubs only (no `:4317` live bind without the operator's grant). Any Pulse-side read in a live variant goes through the MCP and capture-guard surfaces above (per security-plan §Threat Model Summary → Attack surface; §Input Validation, capture ingest row).
- security ↔ playbook: the plan registers boundary widenings for new subprocess crossings, non-loopback egress, third-class dependencies and data-protection scope. A change confined to `conductor-emit`'s span-id derivation, with no new dependency, spawn or egress, touches none of those classes in this plan. Whether the playbook names emit behaviour a widening on other grounds sits outside security-plan (per security-plan §Security Anti-Patterns → Code Patterns; §Dependency Security, third dependency class).
