## Relevance
relevant — the chunk closes the two stated fingerprint residuals inside security-plan's ratified Data Protection exception for real-model captures, and touches the capture scrub chain, its digest-pinned harvest reader and the committed `evidence/` tree.

## Constraints
- The ratified exception admits corpus-rendered model text into a chunk's committed `evidence/` tree ONLY through `mask_workspace_key` + `redact_value` + `mask_host_paths` + `elide_fingerprints`, with every fingerprint-shaped token elided. Today the plan states two residuals against that clause: the frozen 2026-09-22 prefix, and the graded 2026-10-01 d3 all-digit prefix marked "RULED BY THE OVERSEER, FOUNDER RATIFICATION PENDING". The fix must make the clause hold with no stated exception, and retiring that residual prose is a wrap amendment to this master (per security-plan §Security Anti-Patterns → Data Protection).
- The real-model capture ingest row requires the four scrubs in a fixed ORDER (workspace-key mask, then `redact_value`, then `mask_host_paths`, then `elide_fingerprints`). It also defines `elide_fingerprints`' shape: eight or more lowercase hex digits holding at least one letter, so an all-digit run passes. Two things are research's question: whether the code implements exactly that definition, and whether either P4 option for d3 (a context-keyed `fingerprint_hex=` elision, or a widened shape) keeps the order and the unkeyed all-digit pass. Whichever option is chosen, the row's shape definition and its "the 2026-10-01 d3 residual" pointer are master text that must change to match (per security-plan §Input Validation, the Real-model capture ingest row).
- The harvest reader `real_model_harvest` must load each committed capture from `CARGO_MANIFEST_DIR` plus a hard-coded path with no `CONDUCTOR_*` handle. It must check the capture against its sha256 digest pin over the LF-normalized content, and grade the file only after the digest matches. So a re-elided graded capture (d3) needs its pin moved in the same change, and the gate must stay grade-after-digest (per security-plan §Input Validation, the Real-model capture ingest row).
- No committed capture text may sit in test source. The `no_committed_capture_text_sits_in_test_source` arm holds this, and the 2026-09-29 breach remedy depends on it. A re-expressed "zero un-elided values" arm must count over the evidence FILES, never quote a capture line or a fingerprint value as a literal (per security-plan §Security Anti-Patterns → Data Protection).
- Committed evidence records must not leak absolute host paths or internal seam-crate struct names. Any rewritten capture and any touched harvest source remain subject to the chunk's host-path hygiene gates (per security-plan §Security Anti-Patterns → Logging; §Input Validation, the "chunk's host-path hygiene gates over the capture and the harvest" clause).
- The exception's scope is corpus-rendered model text in real-model captures. The plan classifies fingerprints elsewhere as synthetic test telemetry Conductor itself emits, not PII and not user data. So security-plan states no mandate to elide the outside-class population the scope's census lists (conductor-0.2.0 live-leg JSONL, the harvest test-source literals). Whether to widen is the scope's P4 fork, not a security-plan requirement (per security-plan §Threat Model Summary → Data classification; §Data Protection).
- A boundary widening is ratified only by the founder's live word. The d3 residual's "FOUNDER RATIFICATION PENDING" wording retires because of the fix, never by a delegate's ratification. If the P4 outcome leaves any residual standing, it must be recorded as such, not as ratified (per security-plan §Security Anti-Patterns → Data Protection; .claude/rules/security.md Session Additions 2026-09-29).

## Patterns to follow
- The 2026-09-30 remedy is the precedent for an evidence fix: an elided copy lands under the fixing chunk's `evidence/`, gets its own sha256 pin, and is graded from the file. That is the plan's existing route for the frozen 2026-09-22 file, whose graded copy already sits under `2026-09-30-interpretation-re-proven-on-a-clean-named-data-dir/evidence/` (per security-plan §Security Anti-Patterns → Data Protection).
- The workspace-key mask is a context-keyed scrub: it masks the value of every `workspace=` line "whatever it holds". That is the same shape as a `fingerprint_hex=`-keyed elision, so the plan already admits keyed-value masking (per security-plan §Input Validation, the Real-model capture ingest row).
- Masks render as stable placeholder tokens (`<fingerprint>`, `<workspace-key>`, `<host-path>`). Envelope `fingerprints` stay elided to counts (per security-plan §Input Validation, the Real-model capture ingest row).
- A synthetic leak control that a gate needs as its known positive (for example a planted un-elided value proving the new arm goes red) lives in the gitignored `.andromeda/cache/`, never in a committed evidence tree (per .claude/rules/security.md Session Additions 2026-09-30; inverse-control precedent per security-plan §Security Anti-Patterns → Data Protection, "a planted report line red, removed green").

## Anti-patterns to avoid
- Never resolve a residual by ratifying or re-wording it as accepted. The founder ruling mandates a fix, and an overseer or delegate ruling is not ratification (per security-plan §Security Anti-Patterns → Data Protection).
- Never put capture text or a fingerprint value into test source as a byte-equal literal. That re-opens the 2026-09-29 breach class (per security-plan §Security Anti-Patterns → Data Protection).
- Never let the harvest grade a capture before its digest matches, and never weaken the digest pin to accommodate a rewrite (per security-plan §Input Validation, the Real-model capture ingest row).
