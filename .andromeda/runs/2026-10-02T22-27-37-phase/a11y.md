## Constraints
- a11y-plan §1 (Entity: conductor-cli) and §11 Universal (the last bullet) require the cli/`agent-run` surface to be treated as NOT-assertable: the round's graded verdicts on the headless path need no axe/WebdriverIO assertion, and their ASCII `[PASS]`/`[FAIL]`/`[BLOCKED]` prefixes are output-stream discipline, not an a11y verification path. Claim no a11y coverage for them.
- a11y-plan §1 (Critical paths) scopes the must-be-accessible paths to the Conductor desktop-webview only. The round's hands-off posture (scope §Boundaries: Pulse's UI is not automated, nobody touches the desktop during the round, for P-037) sits outside this harness. Per a11y-plan §1 (A11y surfaces, Notes), the WebdriverIO/tauri-driver stack drives Conductor's OWN webview, so no a11y leg may be pointed at Pulse's windows during the round.
- a11y-plan §9 (E2E row, the DRIVEN arm) and §11 Strategy (OWNER of the hold-dependent half) require the operator-only `npm run a11y:driven` arm to run behind a preflight-ready live Pulse. Pinning `retrieve_incident_events` as a fifth `required_tools` name changes what "preflight-ready" means for that arm: against any Pulse build before S, the arm's preflight would surface the missing-tool `Blocked` precondition. Whether the driven arm and the `sr*` leg reach preflight through the same `required_tools` gate is research's question. So is whether any operator-local a11y session still runs against a pre-S Pulse.
- a11y-plan §9 (Pipeline integration) and §11 Strategy (CARVE-OUT) require the CI-wired ROUTINE arm to stay Pulse-free, seeding its own committed fixture through the production writer. The contract pin must not add a live-Pulse or MCP dependency to that arm. Whether the routine arm's seeding path reads `contracts/mcp-contract.toml` at all is research's question.
- a11y-plan §1 (Entity: Verdict / report-state lamp) and §11 Visual (not color-alone) require every Verdict/ReportState, `Blocked` included, to carry its text label + glyph wherever the webview renders it. A new missing-tool `Blocked` reason that reaches the GUI must arrive through the existing six-state lamp, never as a new color-only treatment. Whether the GUI renders preflight `Blocked` precondition strings at all is research's question.
- a11y-plan §11 SLO (the last bullet) and §9 (CI-specific resource attributes) bar a11y artifacts from leaking absolute host paths or internal seam-crate struct names. This binds only if the chunk emits or re-records any a11y artifact, which the scope does not plan.

## Patterns to follow
- The §11 Strategy claim→owner enumeration (`claim-ownership.ts` checked by `npm run a11y:ownership`, per a11y-plan §11 Strategy, Extended 2026-09-30) holds a11y claims to named owners. This chunk adds no a11y claim, so the enumeration should stay byte-unchanged. Leave it alone rather than registering a P-075 row: P-075 is Pulse's ledger, and the scope says the chunk links no capability.
- a11y-plan §1 (Entity: conductor-cli) treats the cli status prefixes as text-paired output discipline. Any new seventh-assertion line printed to the operator follows the same `[PASS]`/`[FAIL]`/`[BLOCKED]`-prefixed form, with an absent sample rendered as UNGRADED text, never as a bare color.

## Anti-patterns to avoid
- a11y-plan §11 Universal (the last bullet) bans treating the cli surface as accessibility-assertable. Do not record the round's headless verdicts as a11y evidence, and claim no WCAG SC for them.
- a11y-plan §11 CI (the ONE webview-automation stack bullet) bans a second automation stack. The scope's "Pulse's UI is not automated" boundary already forbids driving Pulse's windows, and this ban additionally forbids standing up any other driver for the round.
