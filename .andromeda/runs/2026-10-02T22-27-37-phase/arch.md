# arch extract

## Relevance
relevant: the chunk adds a fifth consumed MCP tool to the pinned contract manifest and the readiness gate's required-tool set. It also adds a new read-back call through the hand-rolled client and a std::time-stamped window around an existing write. And it collides with two stated arch clauses that the SUT's HEAD move to S makes stale.

## Constraints
- The readiness gate checks required-tool presence against the pinned manifest. Tool absence is one of the gate's FIVE named preconditions, with its own distinct `Blocked` string (per architecture §Standard Contracts → Readiness gate; §Established Decisions [Read-Back Dependency Posture]). Pinning `retrieve_incident_events` in `contracts/mcp-contract.toml` therefore moves what the gate blocks on, so every preflight against a pre-S Pulse becomes `Blocked`. Whether the code derives the gate's tool set from the manifest, or from a literal four-name set held in readers/tests, is research's question. The gate itself must stay at five preconditions, so a missing fifth tool must not become a sixth precondition.
- The tool must be consumed through the hand-rolled line-delimited JSON-RPC client (`tools/call`, raw `serde_json::Value` result, no MCP `content` envelope, no SDK) (per architecture §Established Decisions [MCP Read-Back Client]; §Conventions → Interface surfaces). The client lives in `conductor-verify` (per architecture §Occupied Resources → Crate names; §Infrastructure Patterns → Directory structure). The architecture requires the direction to be Pulse-supplies-the-value, with Conductor passing `incident_id` only. Research must confirm the arity and the field names against S's source; the arch plan does not settle them.
- The verdict/error wall applies. Read-back JSON-RPC errors (the tool's `-32603` / `incident not found` arm included) fan out into `VerifyError` variants (`Transport`/`Protocol`/`Decode`/`JsonRpc`) and become typed `Blocked`/`Fail` values or, at harvest tier, an UNGRADED sample. They must never be a panic, and `Result::Err` is reserved for harness faults (per architecture §Conventions → Error handling; §Cross-cutting Patterns → Verdict/error wall; §Established Decisions [Error Handling]).
- The resolve call's wall-clock window (request sent → response received) must be stamped from `std::time::SystemTime`/`Instant`, never tokio's virtual clock (per architecture §Conventions → Data model conventions; §Cross-cutting Patterns → Determinism discipline). Comparing a Pulse-supplied `occurred_unix_nano` against that window follows the same shape as the canary's freshness rule (Conductor's `std::time` stamp vs Pulse's `opened_at_unix_nano`) (per architecture §Established Decisions [Read-Back Dependency Posture]). Whether `probe_resolve_lifecycle` already exposes such a window is research's question.
- The sidecar is spawned by a fixed NAME resolved through the inherited `PATH`, and `PATH` is a spawn-resolution input. An operator-driven live leg must carry a `PATH` prefix resolving S's `andromeda-pulse-mcp` as part of its firing form. A miss surfaces as `Blocked` in ~ms with all tools `absent`, indistinguishable at row level from a SUT-side gate failure (per architecture §Occupied Resources → Service / process names). `ANDROMEDA_PULSE_DATA_DIR` must still propagate to the sidecar (per architecture §Occupied Resources → Environment variables).
- A dynamic proof that requires a live Pulse is an operator/local gate, never a CI gate (per architecture §Infrastructure Patterns → CI/CD approach; §Established Decisions [CI/CD]). Ports `:4317`/`:4318` are Pulse-owned loopback, and the chunk adds no bind of its own (per architecture §Occupied Resources → Ports; §Cross-cutting Patterns → Trust boundary).
- Several arch clauses state a SUT reading that is false at S. §Occupied Resources → Interface routes says "the four consumed MCP tool names … are the complete route-equivalent set". §Standard Contracts → Readiness gate gives the live surface as "8 tools" and has a four-key `required_tools` sample. §Established Decisions [Read-Back Dependency Posture] says `incident_events` "reaches no MCP tool at any width (… HEAD `83d4060`)" and calls reaching it "a Pulse 0.4.0 residual candidate". All of these are point-in-time readings at `83d4060`. They are wrap-amendment subjects, attributed to the SUT's HEAD move, and the chunk must not hand-edit them mid-implement.

## Patterns to follow
- Runtime-state fidelity is proven by writing through `mark_incident_resolved` and observing the consequence (`query_incident_list` active-set membership), with attribution riding LIVENESS rather than a spared control (per architecture §Established Decisions [Read-Back Dependency Posture], `conductor-run/tests/lifecycle_harvest.rs`). Assertion 7 is the same axis on a non-L4-authored table, so it survives deterministic L4 for the same reason.
- An assertion graded at harvest/test tier under a rule committed before the drive ships in a `conductor-run` test, leaving `conductor-verify`'s `classify()` unchanged and adding no `Verdict`/`ReportState` variant or envelope key (per architecture §Established Decisions [Probabilistic-Assertion Policy]).
- Committed evidence is graded from its file under sha256 digest pins, with `sha2` as the existing `conductor-run` dev-dependency and no new package (per architecture §Stack and Technologies → Hashing / digest; §Infrastructure Patterns → Build system).
- The pinned contract manifest is resolved through `CONDUCTOR_CONTRACT_MANIFEST` → `contracts/mcp-contract.toml` (per architecture §Occupied Resources → Environment variables; §Occupied Resources → On-disk artifacts). No new `CONDUCTOR_*` handle is minted for the round.

## Anti-patterns to avoid
- Widening the trust boundary: no inbound listener, no egress beyond loopback gRPC/MCP-client, and no operator-chosen or config-derived sidecar program (per architecture §Cross-cutting Patterns → Trust boundary; §Occupied Resources → Service / process names).
- Changing the shared shapes: the eleven-field run envelope and the nine-key `CheckRecord` stay byte-unchanged, and the `state` set stays the closed five variants (per architecture §Standard Contracts → Run report envelope / Per-check record).
- Turning a missing new tool into a sixth gate precondition, or letting an absent `retrieve_incident_events` sample count as met (per architecture §Standard Contracts → Readiness gate).
