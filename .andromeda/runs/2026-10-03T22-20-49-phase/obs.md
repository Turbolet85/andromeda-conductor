## Relevance

## Constraints
- A call to the new tool falls under the MCP boundary-call wrapper mandate. The plan requires the tool name, latency, any error and the **observed key set** of the raw result, with key NAMES only (never values) carried on the allowlisted `message` field. Without that witness, a reader that degrades to empty on an unrecognized shape cannot be told apart from an empty response (per obs-plan §6 Log Coverage → Boundary-call wrappers). Research must answer whether the shipped `verify.readback.call_tool` path already emits this witness for any tool name, or only for the four it was written against.
- Every span attribute must be a name in `conductor-core::redact::ALLOWLISTED_FIELDS`. The processor stage drops any other field silently, so a dedicated attribute for `incident_id`, `event_kind`, `occurred_unix_nano` or the resolve window would emit nothing. That is why the plan puts the incident id on `message` for the lifecycle WRITE (per obs-plan §4 Known-residual classification path → Required span attributes; §6 Boundary-call wrappers → MCP lifecycle WRITE).
- Span names stay inside the bounded set (`verify.readback*` covers read-back calls). The chunk must not mint a new span family for the incident-events read or the timed resolve sibling (per obs-plan §11 Obs Anti-Patterns → Spans / Traces).
- The `mark_incident_resolved` lifecycle WRITE is deliberately not wired into `execute_scenario` or any run path, and its first production caller is `probe_resolve_lifecycle`. The additive timed sibling from scope Q3 inherits that posture: the same bounded `verify.readback.call_tool` span with `mcp_tool`, plus the applied/declined outcome (per obs-plan §6 Boundary-call wrappers → MCP lifecycle WRITE; §1 Instrumentation scope, `conductor-verify` row).
- The resolve call's request→response window, which assertion 7 grades `occurred_unix_nano` against, must be stamped from `std::time` (`SystemTime` for epoch nanos) and never from tokio's virtual clock (per obs-plan §11 Obs Anti-Patterns → Project-specific bans; §5 Metric Coverage → Per-surface / per-path metrics).
- The round's delegated-timing assertions (3–6) grade on each Pulse leaf's own field, and the field names differ by leaf: `duration_ms` on the hue, discovery and counter-refresh leaves, `value` on `metric.report.render_ms`. The bounds are never tied to `latency_ms`, `budget_ms` or `effective_deadline_ms`. The rule is worst in-window sample, inclusive, with an absent sample UNGRADED (per obs-plan §4 Known-residual classification path → Delegated-timing family; P-025 per `contracts/pulse-p025-measurement-contract.md` as cited there).
- Assertion 1's fingerprint match is computed at the test tier only, in-process by the `live-pulse`-gated `p075_round_live` leg. It never goes through a span or the envelope, and `fingerprints_read_back_count` stays a count (per obs-plan §4 Fingerprint-storm scenario → Required span attributes).

## Patterns to follow
- The MCP key-set witness and the emit wire-shape witness are both carried on the `message` field and need no new allowlist entry. The incident-events read follows the read-back twin (per obs-plan §6 Log Coverage → Boundary-call wrappers).
- The prior round's per-assertion test ids are `lifecycle_harvest::p075_round_assertion_1_*` and `delegated_timing_harvest::tests::p075_round_assertion_{3..6}_*`. Each grades from a digest-pinned capture or ledger. This round's new ids follow that shape, and the prior six stay bound to their own evidence (per obs-plan §4 Fingerprint-storm scenario; §4 Known-residual classification path → Delegated-timing family, "Re-graded 2026-10-02").
- Pulse's own tracing lines are a harvest-tier evidence surface. A grade reads the unredacted leaf it needs and treats a `"<redacted>"` counter as proof only that the observer ran (per obs-plan §4 Severity-lifecycle full pass → Required log fields).
- `conductor-verify` logs at base level `info`. A per-target `RUST_LOG` directive must be paired with the global level, and neither form may be set for a run that also executes the test suite (per obs-plan §6 Log Coverage → Per-module log levels).

## Anti-patterns to avoid
- Never leak absolute host paths into logs, run-report, `runs.db` or committed evidence. The scrub set includes `/home`. This applies specifically to the Linux leg's `PATH`, which points into the Pulse checkout's `target/release`, and to any sidecar error text naming a path (per obs-plan §11 Obs Anti-Patterns → Logs; §9 CI Integration → Log conformance check). The standing warning also applies: the three named redaction sites do not bound every host-path channel, and a new boundary needs its own check (per obs-plan §11 → PII Scrubbing, last bullet).
- Never panic on malformed or errored MCP input. The documented `incident not found` JSON-RPC error (-32603), an unrecognized response shape or a `truncated` response must each become a typed value, `Blocked`, `Fail` or UNGRADED, never a panic or a false pass (per obs-plan §11 Obs Anti-Patterns → Error Reporting; → Project-specific bans).
- Never add a new envelope key or W3C trace context to carry incident-event data. The scenario record keeps the eleven envelope fields, and correlation stays `run_id` (per obs-plan §3 Observability Harness Contract → Log format JSON schema; §11 → Spans / Traces).
