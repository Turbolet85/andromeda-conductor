relevant — the chunk repairs the `tauri::test` mock-runtime command-dispatch tier (test code only) so the `--unit` gate's nextest leg is green on both hosts.

## Constraints
- The mock-runtime command-dispatch tier is a STANDING tier, not optional: each read-only Tauri command carries a mock-runtime IPC test asserting its payload against the seam source it single-sources (per test-plan §5 Integration Test Strategy, the "Deferred to the GUI test-harness leg" bullet — "The mock-runtime command-dispatch half is NO LONGER deferred"). The repair must keep every such test executing and asserting; it may change only how the request's origin is formed.
- The driver is fixed: `tauri` 2.10.3 `test` feature via `mock_builder()` + `mock_context(noop_assets())` + `get_ipc_response()` (per test-plan §8 Mocking & Stubbing Discipline, Mocking-libraries table "Tauri command runtime" row; per test-plan §5 driver list). The fix stays inside this driver — no new mocking library, no replacement runtime. Whether the mock context exposes the host-correct webview origin from which the request URL can be derived (rather than a literal) is research's question.
- Zero-flakiness: no nextest `retries` > 0, no retry-once policy, and a result that differs by execution environment is a defect removed at its CAUSE, never pinned around (per test-plan §10 Quality Gates & Coverage Targets, "Zero-flakiness budget"). Note: §10 names a RUNNER-dependent result (nextest vs `cargo test`), not a HOST-dependent one; the cause-removal posture is the applicable principle, and the scope's "no skip / `#[ignore]` / `cfg`-exclusion on either host" boundary is the chunk's own expression of it.
- The unit gate is `cargo nextest run --workspace --profile ci` (JUnit at `[profile.ci.junit]`), reached through `agent-run.{sh,ps1} run --unit`; doctests and clippy are separate stages (per test-plan §3 5-command implementation, the CI stage-selector bullet; per test-plan §9 CI Integration, Pipeline structure Unit / Doctest / Lint rows). Any unit/integration test failure is a build failure — nextest exit 100/101 (per test-plan §10 "Build failure conditions"; per test-plan §9 "Build failure conditions").
- Lint covers test code: `cargo clippy --workspace --all-targets -- -D warnings` + `cargo fmt --check` (per test-plan §9 Pipeline structure, Lint row) — the `#[cfg(test)]` edits in `commands.rs` / `pause.rs` fall under `--all-targets`.
- CI arrangement is unchanged by this chunk: the `rust` job runs on `windows-latest` and no OS matrix exists today; a three-OS matrix is TARGET state owned by another route entry (per test-plan §9 CI Integration, Matrix builds "OS" bullet). The Linux leg here is the dev host, not a CI job — consistent with the scope's "No new CI job" boundary.
- Coverage floor stays `--fail-under-lines 60` and is never lowered (per test-plan §10 Coverage thresholds + enforcement paragraph; per test-plan §11 Quality).

## Patterns to follow
- A single shared request-construction helper for mock-runtime dispatch (the `request()` helper the scope names at `commands.rs:417`) as the one source of the origin; the inline construction at `pause.rs:243` routes through that same source rather than repeating a literal — the single-source discipline the §5 command-dispatch tier already applies to payload expectations (per test-plan §5 Integration Test Strategy, "Deferred to the GUI test-harness leg" bullet: "asserting its payload against whichever seam source it single-sources").
- Prefer dependency-injection / reading the value the test runtime itself provides over patching production code (per test-plan §8 "Anti-monkey-patching"; per test-plan §11 Mocking, "NEVER monkey-patch production code at runtime").
- Per-seam unit isolation: run `cargo nextest run -p conductor-tauri` as the focused leg before the workspace leg (per test-plan §4 Unit Test Strategy, Test grouping bullet).

## Anti-patterns to avoid
- Making a failing test pass by skipping, ignoring or retrying it — "NEVER ignore flaky tests — quarantine and fix immediately; do NOT set nextest `retries`" and "NEVER skip quality gates 'just this once'" (per test-plan §11 CI; per test-plan §11 Quality). The scope additionally forbids `#[ignore]` and `cfg`-exclusion on either host.
- Weakening what the test asserts to reach green — e.g. an origin-agnostic dispatch or a widened capability — which would turn the command-dispatch tier into an over-stub that no longer tests real dispatch (per test-plan §11 Mocking, "NEVER over-stub (you stop testing real behavior)"; per test-plan §11 Test Strategy, "NEVER over-mock at integration level").
- Changing production code to accommodate a test fixture (per test-plan §11 Mocking, "NEVER monkey-patch production code at runtime — use DI").
