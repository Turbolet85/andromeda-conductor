`2026-06-14` — Initial security plan generated by `/andromeda-security`
- **Tier:** Minimal (0) — justified by: single-developer, local-only, no-cloud, no-multi-tenancy tool with no user accounts (auth "none"), no PII/payment/health/credentials owned by Conductor (only self-generated synthetic test telemetry + run-metadata in `runs.db`/JSONL), zero network exposure (loopback gRPC/MCP client, no inbound listener), and no compliance triggers. Residual risk classes are exactly Minimal-tier: dependency/supply-chain audit (`bundled` SQLite from C + OTLP/gRPC/MCP tree), input validation on operator-supplied scenario config and `CONDUCTOR_*` path handles, and error sanitization at the `anyhow` edges + run-report artifacts.
- **Key decision:** Subprocess-spawn hardening for the MCP stdio sidecar child is the single most architecture-relevant control (security-research.md MCP-sidecar STDIO command/argument-injection finding, CVE-2026-30623): spawn `andromeda-pulse-mcp` as a fixed hard-coded program path, pass `ANDROMEDA_PULSE_DATA_DIR` strictly via `.env(...)`, never interpolate operator input into argv/shell, and reject argument-injection metacharacters before spawn. Paired with `cargo-audit` 0.22.2 (+ recommended `cargo-deny` 0.19.8) in CI as the supply-chain control, and two required dependency bumps: toolchain ≥ 1.94.1 (tar-rs symlink-chmod CVE-2026-33056) and `tauri` ≥ 2.10.3 (origin-confusion CVE-2026-42184).
- **Open questions:** (1) Whether the optional `conductor-tauri` GUI will use any Tauri plugin beyond the IPC commands + `Channel` — if the `shell-open` plugin is ever added it MUST be explicitly scoped (CVE-2025-31477); flagged so a downstream Tauri scope can decide. (2) `cargo-deny` adoption (over `cargo-audit` alone) is recommended-not-required for a single-developer tool — left to setup-project / operator preference; `cargo-audit` is the firm minimum bar. (3) No secret-scanning tool was researched in Phase 2 — secret scanning was not a researched category because Conductor owns no secrets (Threat Model Summary § Data classification: credential "none"). The optional defense-in-depth secret-scanning CI gate (Secret Management + Bootstrap phases) therefore names no specific tool; no maintained option was researched for this category, so selection is deferred to setup-project / operator. Revisit only if Conductor ever acquires secret material (it has none today).

`2026-09-24` — Secret-scanning tool selected: an in-repo Rust static gate (closes Initial entry open question 3)
- **Decision:** the secret-scanning CI gate is `crates/conductor-core/tests/secret_scan_gate.rs` — a `conductor-core` test target using `regex` (a dev-dependency edge, already locked; no new package) — run by the `rust` job's presence-guarded `Secret-scan gate` step and locally by `agent-run run`'s workspace nextest. Its subject is git's cached + untracked-not-ignored listing; its allowlist is an exact set, EMPTY at selection (0 hits over the tracked tree, with every rule firing on a runtime-built sample).
- **Rationale:** a job-time-fetched scanner (a marketplace action or a downloaded binary, gitleaks being the one considered) would have been a second member of the third dependency class (§Dependency Security) and a second CI non-loopback egress — a boundary widening. The in-repo gate adds neither, and it carries in-suite negative arms proving it can fail. Its trade-off is recorded: a small rule set Conductor maintains itself, with no entropy scoring.
- **Impact:** §Bootstrap phases `secret-scanning-ci-gate` and §Secret Management "Secret scanning in CI" now describe a realized gate; §Threat Model Summary CI/CD lists it; §Security Anti-Patterns → Secrets names the gate as enforcing. No egress, spawn-form or dependency-class count moves.
- **By:** manual edit by the operator's P4 selection (`2026-09-24-secret-scanning-ci-gate`), recorded at that chunk's wrap.
