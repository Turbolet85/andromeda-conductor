# security extract

## Relevance
partial — the chunk touches two standing security controls (the secret-scan gate and the real-model capture-protection arms that live in `real_model_harvest`) and adds a CI step; it adds no shipped surface, no input boundary and no dependency.

## Constraints
- The secret-scan gate must never pass over an empty subject: security-plan §Secret Management → *Secret-scan gate shape* requires the CI `Secret-scan gate` step to be a presence-guarded invocation that fails when git lists no tracked files, and requires in-suite negative arms proving every rule can fail. The new no-`.git` skip must therefore fire only on a tree with no git repository, never on a `git ls-files` failure inside one, and the existing "listed nothing" vacuity guard stays. Whether the CI step's presence guard sits in `ci.yml` or only inside the test is for research to establish. It decides whether a skip inside the test can ever turn the CI step green.
- The gate's git spawn keeps its recorded shape, per security-plan §Security Anti-Patterns → Code Patterns (the rule-(b) clause recording `secret_scan_gate.rs`'s spawn, 2026-09-24): a fixed PATH-resolved program, fixed argv, no operator-supplied value, never a shell string. Any probe added for the skip (a `.git` presence check or a second git call) must keep that shape, or the test binary's "outside rule (b), adds no governed form" status no longer holds.
- The capture-protection arms that the split moves are a security control, not ordinary test code. security-plan §Security Anti-Patterns → Data Protection (the remedy for the 2026-09-29 BREACH) and §Input Validation (the real-model capture ingest row) require the following: every committed capture is graded from its file only after its sha256 digest pin over LF-normalized content matches; capture paths are anchored from `CARGO_MANIFEST_DIR` + a hard-coded path with no `CONDUCTOR_*` handle; and `no_committed_capture_text_sits_in_test_source`, `every_committed_capture_carries_no_un_elided_fingerprint_value` and `the_2026_10_01_captures_carry_no_fingerprint_and_no_workspace_key` keep holding. The split must preserve every one of them with the same assertion. The digest pins must stay byte-equal, since no capture changes.
- `no_committed_capture_text_sits_in_test_source` must still cover ALL test source after the split, including every new per-series target and `tests/real_model_common/` (per security-plan §Security Anti-Patterns → Data Protection). Whether the arm finds its haystack by a fixed file list, by the harvest's own file name, or by a directory walk is research's question. A fixed list naming only `real_model_harvest.rs` would leave the new files unscanned, and the arm would pass vacuously. Note that the plan names the breach site as `tests/real_model_series/mod.rs` while the scope names `tests/real_model_common/`. Research should confirm which module or modules exist at HEAD.
- The `stub-server` CARRY gate must admit no new package. Per security-plan §Dependency Security (Pinning; CI integration) and §Security Anti-Patterns → Universal, `Cargo.lock` stays committed and un-drifted, and `cargo audit` + `cargo deny check advisories bans licenses sources` stay green over the lock the chunk ends with. Whether enabling `stub-server` moves the lock at all is research's question. State the basis as a package count, never as lockfile byte-identity.
- Any CI edit stays within the loopback/no-egress posture: per security-plan §Threat Model Summary and §Security Anti-Patterns → Universal, the `stub-server` step introduces no fetched tool and no network egress. The `stub_pulse_mcp` bin it compiles is a test stub, and if P4 chooses to RUN `preflight_spawn.rs`, that stub must bind no listener beyond the tests-only loopback/stdio stub model.
- Before the supply-chain gate, the local advisory-db copy's currency is checked per security-plan §Dependency Security (the 2026-09-05 re-adjudication of the TOOL-vs-DATABASE fork): porcelain clean, or a fresh `--db` clone. Only then is a red result trusted.

## Patterns to follow
- The capture reader pattern from the §Input Validation real-model capture ingest row: workspace-root anchoring from `CARGO_MANIFEST_DIR`, hard-coded relative paths, the digest check before grading, and file-graded assertions. The lift into `real_model_common` should centralize this as-is rather than re-derive it per series file.
- The secret-scan gate's existing failure discipline from §Secret Management → *Secret-scan gate shape*: a hit names `path:line` and never echoes its match, and negative arms are runtime-built samples. The skip reason string should be just as host-path-free (per §Error Handling: never leak absolute host paths).
- The test-binary spawn classification from §Security Anti-Patterns → Code Patterns: a cargo test binary's fixed-argv spawn sits outside rule (b)'s three loci and adds no governed form.
- A justified `deny.toml` entry, never a silent skip, if enabling `stub-server` surfaces a non-actionable advisory or license (§Dependency Security → Accepted exceptions).

## Anti-patterns to avoid
- A secret-scan skip that is broad enough to fire on a `git ls-files` error inside a real checkout, which turns the gate green over no subject. This is banned by the presence-guard and vacuity requirements of §Secret Management → *Secret-scan gate shape*.
- Moving capture-protection logic so that capture text, or a quoted elided or un-elided value, lands in test source (the new per-series files or `real_model_common`). That is the 2026-09-29 BREACH shape, banned under §Security Anti-Patterns → Data Protection.
- A new `ci.yml` spawn shape beyond a plain toolchain invocation. Per §Security Anti-Patterns → Code Patterns, `ci.yml` is a rule-(b) locus holding eight governed forms, and a ninth crossing escalates. Whether a plain `cargo check --tests --features stub-server` step counts as a governed form should be confirmed against that enumeration. It names no plain cargo step.

## Contract bindings
- security ↔ tests. Here the CI security gate is the `rust` job's `Secret-scan gate` step plus the workspace nextest run (§Secret Management → *Secret-scan gate shape*). The no-`.git` skip changes how that test target behaves under cargo-mutants copies, so the mutation-measurability claim that motivates it belongs to tests and the gate's non-vacuity belongs to security.
- security ↔ tests/CI. The new `stub-server` `cargo check` step lands in the same `ci.yml` that hosts the `cargo audit`/`cargo deny` steps (§Dependency Security → CI integration).
- security ↔ obs. The capture scrub chain (`mask_workspace_key` → `redact_value` → `mask_host_paths` → `elide_fingerprints`) is the shared redaction contract. The split must not reorder or bypass any grading that holds it (§Input Validation, the capture ingest row).

## Acceptance criteria contributions
- `cargo nextest run -p conductor-core --test secret_scan_gate` still passes in the real checkout, and its negative arms all still fire. The test skips cleanly only in a tree with no `.git`, which is shown by running the gate in a `.git`-less copy. An induced `git ls-files` failure inside a repository still fails rather than skips (per security-plan §Secret Management → *Secret-scan gate shape*).
- After the split, every capture-protection arm still exists by name with an unchanged assertion: `no_committed_capture_text_sits_in_test_source`, `every_committed_capture_carries_no_un_elided_fingerprint_value`, `the_2026_10_01_captures_carry_no_fingerprint_and_no_workspace_key` and the per-file sha256 digest pins. Every committed `rm-capture*.txt` is byte-unchanged (per security-plan §Security Anti-Patterns → Data Protection).
- The no-capture-text arm's haystack demonstrably includes every new split file and `tests/real_model_common/`. An inverse control proves it: a report line planted in a NEW split file goes red, and removing it returns green (per security-plan §Security Anti-Patterns → Data Protection — the inverse-control form the remedy was measured with).
- `cargo audit` and `cargo deny check advisories bans licenses sources` both exit 0 over the chunk's final `Cargo.lock`, with the package count unchanged, after the advisory-db porcelain check (per security-plan §Dependency Security; §Security Anti-Patterns → Universal).
