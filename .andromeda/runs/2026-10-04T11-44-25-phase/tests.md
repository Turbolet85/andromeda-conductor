## Constraints
- Runner portability is a standing gate: test-plan §4 (Framework) requires the suite green under BOTH `cargo nextest run` and `cargo test -p <crate>`, and §10 (Zero-flakiness budget) classes a runner-dependent result as a determinism break. Every new split target and the edited `secret_scan_gate` must hold under both runners. Whether the split's targets share any process-global state across tests that today sit in one binary is research's question (§11 Integration's singleton ban).
- The real-model harvest's evidence discipline must survive the split. Per test-plan §7 (Self-bootstrapping requirement) and §6 (Fingerprint-storm, "Real-model interpretation leg"), committed captures are read-only and `CARGO_MANIFEST_DIR`-anchored, and each one is checked against its sha256 digest pin before any grade reads it. A capture is evidence and is never a fixture copied elsewhere. §6 also names the arms that must survive: a one-byte tamper arm, a source arm holding that no committed capture text sits in test source, a byte-exact-prefix assertion over the recorded 2026-09-23 rule, and the population arm `every_committed_capture_carries_no_un_elided_fingerprint_value` with its inverse control. Each split target that grades a capture must verify the pin first.
- The source arm's subject widens with the split. §6 requires that no committed capture text sits in test source. If that arm reads the harvest file by name or path, renaming or splitting the file narrows or breaks it. Whether the arm keys on `real_model_harvest.rs` by name is research's question. After the split, its subject must cover every split target plus `real_model_common`.
- The repository-hygiene skip must not pass vacuously. test-plan §6 (Coverage-matrix scenario, "Repository-hygiene legs") defines the secret-scan leg's subject as `git ls-files --cached --others --exclude-standard`, graded both ways against an exact-set allowlist, CI-guarded on a non-empty `git ls-files`. §6's webview rule states the general principle: "a context-skip is never a pass". So the `.git`-absent skip must be distinguishable from a green scan in its output. It must leave the "listed nothing" vacuity guard and the exact-set allowlist grading untouched.
- The skip exists to unblock the §4 mutation instrument. test-plan §4 (Mutation instrument) makes cargo-mutants an operator-local instrument that runs at the epoch-boundary audit only (§9 Scoped mutation audit). Its tally, not its exit code, is the verdict. The chunk's skip should let `conductor-core`'s tier run in cargo-mutants' `.git`-less copy, and it adds no CI stage and no sixth `agent-run` command.
- A feature-gated target owes its own lint line. test-plan §9 (Live-Pulse scenarios paragraph) says a gated file is invisible to the default lint pass, so such a leg OWES `cargo clippy -p <crate> --features <feat> --all-targets -- -D warnings`, and it names the `stub-server`-gated `preflight_spawn.rs` as the in-repo precedent. The CARRY's `cargo check --tests` is the weaker form of that owed command. §1 (Surfaces, ipc-internal MCP) and §5 (`retrieve_incident_events`) both rely on `preflight_spawn.rs` against the child stub, and §1 calls the stub-server leg "fully CI-runnable". Whether any CI job or harness verb builds or runs it today is research's question; the scope's take-up count says none names it.
- Five-command discipline holds. test-plan §3 `run` (5-command implementation, CI stage selectors) maps `--integration` to the hand-rolled MCP stub leg and fixes the command count at five. If the stub-server gate is placed in the harness, it belongs inside an existing `run` selector, never a new verb. If it is placed in CI, §9's stage table is "the complete inventory of gates CI enforces", so the placement is a P4 decision with a §9 consequence.

## Patterns to follow
- Shared integration-test module as `tests/<name>/mod.rs` (not its own target): `conductor-verify/tests/common/mod.rs` per test-plan §4 (What unit tests cover, conductor-verify), and `conductor-emit/tests/common` per §10 (Coverage thresholds). Under §10's exclusion regex, a `tests/` tree needs no coverage-exclusion entry, so the lifted grading in `real_model_common` adds no coverage-gate work.
- One test binary per assertion family, the crate-local `tests/` tier: test-plan §6 names one harvest target per family (`baseline_harvest.rs` · `storm_harvest.rs` · `restart_harvest.rs` · `severity_harvest.rs` · `pii_harvest.rs` · `connection_harvest.rs` · `lifecycle_harvest.rs`). This is the precedent shape for splitting `real_model_harvest.rs` by series. §11 Integration (a) also endorses one-file-per-test-binary as the default isolation answer.
- Gates that prove they can fail: the hygiene legs prove failure in-suite on inputs built at test time, with no committed fixture (test-plan §6 Repository-hygiene legs). The harvest's tamper arm and inverse controls do the same (§6 Real-model interpretation leg). Each relocated arm keeps its known-bad control beside it.
- Test commands the implementation must pass: `cargo nextest run -p conductor-run --profile ci` and `cargo test -p conductor-run` (both runners, §4); `cargo nextest run -p conductor-core --test secret_scan_gate --profile ci` and `cargo test -p conductor-core` (§6 · §4); `cargo clippy --workspace --all-targets -- -D warnings` (§9 Lint); `cargo clippy -p conductor-verify --features stub-server --all-targets -- -D warnings` (§9, the owed gated-lint form).

## Anti-patterns to avoid
- Never let a renamed target leave a live command that silently runs nothing. test-plan §4 (Mutation instrument) records the same failure class: a `-f`/`-p` selector that "silently matches nothing" and "`Found 0 mutants` is a NO-OP, never a pass". A stale `--test real_model_harvest` is the nextest analogue. §11 Quality also bans skipping a gate "just this once".
- Never serialize the split or the gate with a runner knob (`--test-threads=1` / a profile setting) to make a shared-state interaction pass (test-plan §11 Integration; §10 Zero-flakiness). Never set nextest `retries` > 0 (§11 CI · Quality).
- Never assert on implementation details or fixture internals when lifting the grading (test-plan §11 Unit). The lift must keep each arm asserting the graded outcome (the `(verdict, state)` pair and the named failure) that §6 specifies, not a helper's internals.

## Acceptance criteria contributions
- Behaviour preserved across the split. Compare `cargo nextest list -p conductor-run` before and after. Every test function the old harvest target held must still exist under exactly one new target, with the same pass/skip/ignore posture. The new targets and `real_model_common` must be green under both `cargo nextest run -p conductor-run --profile ci` and `cargo test -p conductor-run` (per test-plan §4 Framework; §10 Zero-flakiness).
- Evidence arms intact. After the split, every target that grades a committed capture verifies its sha256 pin before reading it, and the tamper arm still fails on a one-byte change. The source arm covers every split file plus `real_model_common`, and the committed captures hold byte-equal (per test-plan §6 Real-model interpretation leg; §7 Self-bootstrapping requirement).
- Secret-scan skip is conditional and visible. In a tree with no git repository, `cargo nextest run -p conductor-core --test secret_scan_gate` exits 0 and prints a skip that names its reason. Inside a repository, a failing `git ls-files` still fails the gate, and the "listed nothing" vacuity guard and the both-direction allowlist grading still fail on their known-bad inputs (per test-plan §6 Repository-hygiene legs; §4 Mutation instrument).
- Stub-server gate is executable and exit-coded. `cargo clippy -p conductor-verify --features stub-server --all-targets -- -D warnings` (or, at minimum, the CARRY's `cargo check --tests` form with that feature) exits 0 at HEAD, and the chosen harness or CI site invokes it by that exact form (per test-plan §9 Live-Pulse scenarios, the owed gated-lint command; §3 `run` five-command discipline).
