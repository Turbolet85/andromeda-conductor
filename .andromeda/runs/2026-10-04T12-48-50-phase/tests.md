## Constraints
- A mutation run has fixed rules, per test-plan §4 (Mutation instrument). Pass `-f` as the full workspace-root crate path (`-f crates/conductor-emit/src/identity.rs`, `-f crates/conductor-run/src/canary.rs`). `--test-tool=nextest` is required. `Found 0 mutants to test` is a no-op, not a pass. The cargo-mutants exit code is not a verdict in either direction: grade on the `mutants.out/` tallies, or through the committed form `python -X utf8 scripts/mutation-gate.py {unit}`. Create the `--output` parent before the run, never the leaf. The overseer asked for a targeted liveness run of the five survivors, and it is bound by all of these rules.
- §9 (Scoped mutation audit) says the mutation instrument runs "at the epoch-boundary code audit ONLY, never per chunk (founder ruling, 2026-09-30)". The overseer's per-chunk liveness run (scope "Operator directives") therefore has to be squared with that ruling, either as a measurement that serves the audit's own disposition or as a recorded exception. Research or P4 decides which. This extract does not.
- Each named survivor must end in one of two states, per test-plan §10 (Mutation-survivor disposition): **killed**, or **accepted-deliberate**. Accepted-deliberate needs either a cited standing rule or a proof of equivalence, meaning no input in the domain tells the mutant apart from the original, measured rather than argued (the `member-emit-1` precedent). A survivor that turns out to be equivalent gets a citation-home roster entry plus a `scripts/mutation-roster.toml` row joined on `member`. It is not a production restructure: §10's `member-emit-1` rejects "restructuring … so the boundary becomes observable (a production behaviour change made to satisfy a mutation tool, which §11 forbids)". The scope's clause allowing "production code changes only if a survivor proves … equivalent-mutant-shaped" has to be read against that rejection.
- Identify roster members by cargo-mutants' mutation DESCRIPTION, never by `file:line:col` or function plus column. The tally comparison is a multiset over `(file, mutation)`, per test-plan §4 (Roster member identity and registration). Registration is the `[[unit]]` declaration. Two questions are for research, not for this extract: whether `conductor-run` (home of `canary.rs`) has a registered `[[unit]]` today (§4 names only `conductor-cli`, `conductor-verify` and `conductor-emit` as roster-carrying units), and whether `conductor-emit`'s unrostered timeouts make `mutation-gate.py conductor-emit` fail closed regardless of the two `identity.rs` kills. §10 `member-emit-1` says it fails closed with one `TIMED OUT, not in roster` line per timeout until the audit seeds those rows.
- The kills must be deterministic and must not depend on the host. Zero-flakiness rules out nextest `retries` and any kill that holds on one host and not another, per test-plan §10 (Zero-flakiness budget) and the rejected alternative in §10 `member-4`. The suite must be green under BOTH `cargo nextest` and `cargo test -p <crate>`, per test-plan §4 (Framework: runner-portability gate). For `emit_canary_storms`, egress must use a loopback stub on `127.0.0.1:0`, never Pulse's `:4317`, per test-plan §5/§8 and §10 `member-3`. That entry records the fixed `DEFAULT_OTLP_ENDPOINT` as not injectable. Whether `emit_canary_storms` takes an injectable endpoint or dispatcher is research's question.
- The split must preserve behaviour across the harvest tier's digest-pinned evidence. Per test-plan §7 (Self-bootstrapping requirement), committed live-leg capture evidence is read-only, anchored on `CARGO_MANIFEST_DIR`, and checked against its sha256 pin before any grade reads it. It is never copied into a fixture. Per test-plan §2 (Agent-runnable invariants), the `p075_reround_assertion_*` grades sit "in `lifecycle_harvest` and `delegated_timing_harvest`" at the harvest tier over that evidence. Moving code into child modules must not change which evidence path each test resolves, its pin, or its pass/skip/ignore posture.
- The lint lines are blocking in the plan's own contract. Test-plan §3 `run` (`5-command-implementation`) puts the workspace `cargo clippy … -- -D warnings` line plus the two feature-gated `-D warnings` lines (`conductor-verify --features stub-server`, `conductor-run --features live-pulse`) in `agent-run run`'s bundled default in both shells. §9 (Pipeline structure, Lint row) says CI reaches them through the `rust` job's dogfood step. Both §9 and §10 (Build failure conditions) list "clippy `-D warnings`" as a build failure. Test-plan, then, already states the blocking reading the CARRY expects. The divergent site is obs-plan §10, which is outside this domain.

## Patterns to follow
- The previous corrective split `real_model_harvest.rs` into child modules of ONE target (session handoff, scope item 1). With one target, the target name the plan cites stays valid (test-plan §2 cites the `delegated_timing_harvest` target by name; §4 Conventions place integration tests in crate-local `tests/`). Splitting into several targets would rename what §2 cites and would need a test-plan amendment at wrap.
- Process-global state needs care when tests are regrouped. If any moved test touches a first-install-wins singleton (e.g. `init_observability`), the remedy is the §11 Integration set: its own test binary, or an in-module `static Mutex<()>` guard. A runner knob such as `--test-threads=1` is never acceptable (test-plan §11 → Integration).
- `rekey_trace_identity` already has a stated unit-tier property in test-plan §4 (What unit tests cover → conductor-emit): a per-salt bijection that preserves parent linkage, keeps an empty id empty and moves no content byte. The two `xor_in_place` survivors (`^=`→`|=`, `^=`→`&=`) are naturally killed by tightening assertions at that tier, with salts injected as fixed `Some(N)` per test-plan §8 (Random sources). Whether the existing tests already exercise a mask/byte pair that separates XOR from OR/AND is research's question.
- To grade a mutation run, use the committed gate's ordered checks: all four tallies present, per-class counts equal to `outcomes.json`, the conservation sum, then the multiset comparison of `missed`/`timeout` against the roster. `unviable` is graded by counts only, never rostered (test-plan §4 Mutation instrument).

## Anti-patterns to avoid
- Do not set nextest `retries` > 0. Do not serialize a file with a runner knob. Do not accept a kill whose result depends on the host or on `PATH` (test-plan §11 → CI / Quality / Integration; §10 `member-4` rejected alternative).
- Do not change production code so that a mutant becomes observable. Do not loosen an assertion into a tolerance band to "catch" a mutant (test-plan §10 `member-emit-1` rejected alternatives; §11).
- Do not read a gate's exit through a pipe, and do not trust cargo-mutants' exit code as a verdict (test-plan §4 Mutation instrument; §3 `run`: "reading the exit from the BARE command (never through a pipe)").
