## Constraints
- **Firing form is the `--live real-model` selector and nothing else** — test-plan §3 `run` (key `5-command implementation`) requires every drive to go through `agent-run run --live real-model` with its fixed step order: the posture-scoped preconditions probe, the capture-binary pre-build, the non-recursive removal of the three named `runs/live-suite/` files, the grading rule's record written into the capture BEFORE the leg (a non-zero exit there stops the arm so no counted drive is spent), the leg, then the capture. It requires identical semantics in `.sh` and `.ps1` and adds no port, env var, `CONDUCTOR_*` handle, sixth command or new selector. Whether the Linux host needs ANY edit to that arm (host-shaped forms) is research's question; if it does, §3 `run` requires the `.ps1` twin to stay semantically identical, and the same key records that the ps1 red path is unmeasurable on a host with no `pwsh`.
- **The series is pre-stated and never CI** — test-plan §9 Live-Pulse scenarios requires the real-model leg to be driven only as the pre-stated series of `contracts/pulse-real-model-leg-posture.md`, fixed before its first drive, every drive recorded and never replaced, with only a Conductor-side environment or pipeline fault re-fired, once; pickup is recorded as a measurement, never budgeted. §2 Agent-runnable invariants adds that each counted drive is graded against a rule recorded before it fires, and that the leg is NOT seed-deterministic — carried only as the §9/§11 operator-local-gate exception.
- **Grading sits at the harvest tier, in the default suite, over the file** — test-plan §6 (Scenario: Fingerprint-storm → Real-model interpretation leg) requires the interpretation claim to grade at the `conductor-run` harvest tier over the drive's scrubbed capture, against the rule stated before the drive (the rule's span recorded into the capture ahead of the leg and asserted to predate it), with the three-way outcome mapping it states (`Identified` / `NotIdentified` / nothing-to-grade) and the appended-rule byte-exact-prefix assertion. A `NotIdentified` maps to a reported state, not a hard fail (§11 E2E, the reported-states ban). The plan names the harvest home as `real_model_harvest.rs`; the scope names a `real_model_grading/` child-module layout — which file the series module, its pins and its verdict test land in today is research's question.
- **Every committed capture is digest-pinned evidence, never a fixture and never test-source text** — test-plan §6 (same leg) and §7 Self-bootstrapping requirement require each committed capture to be held by a sha256 pin over its LF-normalized content and graded from the file only after the digest matches, with a tamper arm that names the file and never the text, a source arm holding that no capture text sits in test source, and the capture read read-only, `CARGO_MANIFEST_DIR`-anchored, from the chunk's `evidence/` tree (evidence, never copied elsewhere as a fixture).
- **The committed-capture population arm covers the new files** — test-plan §6 (same leg) requires every committed `rm-capture*.txt` to hold zero un-elided keyed fingerprint values and be a fixed point of the elision, with the population PINNED BY COUNT beside its inverse control. New drive captures enlarge that population; whether the arm's pinned count must move with this chunk's captures (and by how many, given a canary-blocked or ungraded drive may still commit a capture) is research's question.
- **Test-binary path handles go through the shared guard** — test-plan §1 Coverage triggers (security-vector-coverage, the FIFTH class) requires `real_model_live`'s reads of `CONDUCTOR_RUNS_DIR` and of the `ANDROMEDA_PULSE_DATA_DIR` value (the Pulse log and the workspace-key basename) to resolve through `conductor-run/tests/capture_paths`, with the default-suite `capture_paths_guard` target green under both runners. The fresh letters-only data dir on the Linux host must therefore be an existing directory whose canonical form the guard accepts; whether the guard's canonicalize/basename path behaves identically on a Linux parent is research's question.
- **Runner portability, zero retries, and the owed lint line** — test-plan §4 Framework requires the suite green under BOTH `cargo nextest` and full non-doc `cargo test -p <crate>`; §10 Zero-flakiness budget forbids nextest `retries` and treats a runner-dependent result as a defect; §9 Live-Pulse scenarios requires any target under the `live-pulse` feature to be linted by `cargo clippy -p conductor-run --features live-pulse --all-targets -- -D warnings` (in `agent-run run`'s bundled default per §3 `run`), compiled and linted in CI but never RUN there.

## Patterns to follow
- **One harvest verdict test per series, synthetic arms beside it** — test-plan §6 (Real-model interpretation leg) records each prior series as a dated verdict over pinned captures, with synthetic arms covering every outcome plus the extraction, token-surface, mask and `skip_reason`-pairing arms; `skip_reason` rides the `canary:` line as a trailing field, recorded and never graded (the rule reads the first token). If the new section changes how the rule reads a digest line (the `TRIGGER: ` question in the scope), §6's byte-exact-prefix assertion over the recorded rule is the constraint a rule edit must satisfy — whether the reading can be stated without touching the recorded rule text is P4's decision.
- **Harvest-tier precedent for a live claim** — test-plan §6 (Scenario: Headless deterministic scenario run; Scenario: Restart-suppression) and §5 (`mark_incident_resolved` · `retrieve_incident_events`) show the shape: the scenario row lands declare-only, the live claim grades hard at the `conductor-run` harvest tier over verbatim/digest-pinned leg evidence, driven by a feature-gated operator leg.
- **Quiet windows are firing form, not test synchronisation** — test-plan §11 E2E (the `sleep(N)` ban's scope clause) and §6 (the driven arm's quiet-window firing form) class a harness-level wait between drives that waits out Pulse's dedupe window as part of the leg's firing form; the series section's quiet windows follow that class.
- **Test selection for fast iteration** — test-plan §3 `run` (Test selection): `cargo nextest run -p conductor-run` for the seam, `-E 'test(<name>)'` for one test; the bundled `agent-run run` default (nextest → doctest → workspace clippy → the two feature-gated clippy lines, stopping at the first red cargo line) is the full gate.
- **Supply-chain gate form** — test-plan §9 Supply-chain audit form: the gate is the BARE `cargo audit` beside `cargo deny check`; the `--deny warnings` form is never the gate.

## Anti-patterns to avoid
- NEVER run the live-Pulse / real-model leg as a CI gate, and never fake Pulse's reaction as a CI verdict (test-plan §11 CI; §11 Test Strategy).
- NEVER sleep inside a test to synchronise, and never treat `Blocked` / `ManualCheck` / `CalibrationRegion` as a non-zero process exit (test-plan §11 E2E) — a `NotIdentified` or zero-graded series is a recorded outcome, not a red harness.
- NEVER add a retry policy or serialize a file with a runner knob to get a harvest test green (test-plan §11 Quality; §11 Integration; §10 Zero-flakiness budget). Related scope tension to resolve in the plan: the scope lists "mutation" among the heavy daytime gates, while test-plan §9 Scoped mutation audit states the mutation instrument runs at the epoch-boundary code audit ONLY, never per chunk — test-plan owes this chunk no mutation run.
