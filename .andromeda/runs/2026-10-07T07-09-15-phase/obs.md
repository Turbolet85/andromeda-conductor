# obs extract

## Relevance
partial — the series is observed through the existing self-obs and envelope surfaces and graded at the harvest tier; obs-plan mandates that a real-model drive add no span, log line or field, so the domain contributes guard rails and a wrap-time dated record, not instrumentation.

## Constraints
- obs-plan §1 Obs Scope Summary fixes the tier at Minimal (0): self-observation is structured `tracing` JSON only, with no OTel SDK, no metrics and no trace context. Nothing this chunk builds (the contract section, the series module, the harvest test, the walker mark) raises instrumentation depth.
- obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture requires the `real-model-interpretation` scenario to add NO critical path, span name or span attribute: it rides the Critical Path 1 chain with the standard eleven-field envelope. A fifth series inherits that; a drive that needs a new span or allowlisted field is outside what the section permits.
- obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture requires the interpretation to be graded at the harvest tier (`conductor-run/tests/real_model_harvest.rs`, over the scrubbed capture) and never through the envelope. The series verdict (`Identified` / `NotIdentified`) therefore must not be read from `verdict` or `state`.
- obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture requires a scenario whose declared L4 posture differs from the posture its run's gate evaluated to be recorded scenario-level `Blocked` inside `scenario.run`, before the ready check, with one `info` line on the allowlisted `message` field. So each drive must reach the scenario through the headless real-model gate; a `Blocked` envelope from a posture mismatch is a launch-path fault to read, not a graded drive.
- obs-plan §6 Log Coverage → Required fields requires every envelope record to carry the eleven keys, where required means the KEY IS PRESENT (the five measurement fields serialize as `null` on a blocked row). A canary-blocked drive's envelope is conformant with nulls; it is not a malformed record.
- obs-plan §6 Log Coverage → Per-module log levels requires a per-target `RUST_LOG` directive to be paired with the global level (`info,{crate}=debug`), because the target form replaces the default, and forbids setting either form for a run that also executes the test suite. Any debug opt-in used while diagnosing a drive is bound by both halves.
- obs-plan §10 SLO Invariants & Telemetry Budgets → Build / deploy failure conditions makes a `cargo clippy … -D warnings` red blocking on `agent-run run`'s bundled default, alongside the log-conformance and zero-unlogged-panics conditions. The chunk's Rust delta (series module, harvest test, the token in `conductor-tauri/src/commands.rs`) is gated by it.

## Patterns to follow
- Evidence that is not Conductor's own quantity is read from PULSE's own log lines at the harvest tier, each from its own exact field, never bound to an envelope or journal-relative term (per obs-plan §4 Scenario: Known-residual classification path → Delegated-timing family). The series' model and prompt witnesses follow that shape: the 2026-10-06 record in obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture reads `model_identity` and `prompt_version` from Pulse's own log. Whether Pulse at `f70be92` still logs both fields unredacted, and with what value for `prompt_version`, is research's question.
- The capture's `canary:` line count is not the storm count: obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture states three storms per drive against two printed `canary:` lines, the third landing at the scenario's emission instant. A harvest assertion over the new captures counts on that basis; whether the capture code still prints that shape is research's question.
- Where a diagnostic value has to be witnessed and its field name is not allowlisted, it rides the allowlisted `message` field as key names or counts, never as a dedicated attribute (per obs-plan §6 Log Coverage → Boundary-call wrappers). The real-model canary's existing message-borne `canary fingerprint computed` line is the in-plan instance (per obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture).
- The self-obs stream of a headless drive is `logs/agent-latest.jsonl` in agent mode, located relative to `CONDUCTOR_RUNS_DIR` (per obs-plan §3 Log file location); every line carries the self-obs base set including `run_id` (per obs-plan §3 Log format JSON schema → Two record shapes). A drive's self-obs lines and its envelope are matched by `run_id`, and they are two distinct record shapes.
- The walker-mark edit sits in a file whose eight command handlers each carry a manual `tracing::info_span!("tauri.command.<name>").entered()` guard rather than the attribute form (per obs-plan §4 Span / Trace Coverage → Auto-instrumentation per surface, desktop-webview row). The token lands on the inline test only and leaves those guards as they are.

## Anti-patterns to avoid
- NEVER leak an absolute host path or an internal struct name into logs, the run report, `runs.db` or the journal (per obs-plan §11 Obs Anti-Patterns → Logs), and never assume the three named redaction sites bound every host-path channel (per obs-plan §11 Obs Anti-Patterns → PII Scrubbing). The series' home-rooted data dir, the model path handle and the llama binary path handle are all host paths that pass near a drive.
- NEVER widen the bounded span-name set or add a W3C trace context for self-observation (per obs-plan §11 Obs Anti-Patterns → Spans / Traces). A real-model drive gets no span name of its own.
- NEVER export self-observation OTLP to `:4317` or `:4318`, and never introduce an OTel SDK or exporter (per obs-plan §11 Obs Anti-Patterns → Universal; §11 Obs Anti-Patterns → Telemetry Strategy). The ports granted for this chunk serve Pulse's receiver and Conductor's PRODUCT fault stream only.

## Contract bindings
- obs ↔ tests: the eleven-field envelope and the two self-obs line variants are owned by test-plan §3, with obs aligned to it (per obs-plan §3 Log format JSON schema). Key presence on each drive's journal is the run-journal conformance gate's assertion (per obs-plan §6 Log Coverage → Required fields); the series verdict is the harvest tier's (per obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture).
- obs ↔ tests (parity): a real-model-posture scenario is outside both-surface parity by design, the Tauri path keeping the deterministic gate and recording it scenario-level `Blocked` (per obs-plan §4 Scenario: Both-surface parity). obs-plan cites test-plan §1 Critical Path 7 for it; that citation is test-plan's to confirm.
- obs ↔ security: host-path freedom in Conductor-generated artifacts is enforced by `conductor-core::redact` at the processor stage (per obs-plan §11 Obs Anti-Patterns → PII Scrubbing). obs-plan names the capture only as "the scrubbed capture" and does not describe its scrub chain; that chain is security's extract to state.
- obs ↔ wrap (dated record): obs-plan §4 Scenario: Headless deterministic scenario run with MCP read-back verification → Real-model posture carries a dated record per live drive or series (2026-09-23, 2026-09-29, 2026-10-06), the latter two anchored "as measured at that chunk's `evidence/attempt-ledger.md`". The master is read-only in phase and implement, so a fifth-series record (the Pulse sha, the model and prompt versions as Pulse's own log reads them, each drive's envelope landing state, and whether the chunk added any span, log line or field) is an Expected amendment for the wrap, and the attempt ledger has to hold those readings for it to cite.
