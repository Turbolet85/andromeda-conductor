## Constraints
- The supply-chain gate binds over the NEW lock: security-plan §Dependency Security requires `cargo audit` and `cargo deny check advisories bans licenses sources` BOTH green over the committed `Cargo.lock` the removal produces, and requires the porcelain check of the local advisory-db checkout to be read before an audit reading is trusted (red or green). Whether the post-removal lock reads green is research's and the build's question, not assumable.
- `deny.toml` exceptions stay justified per entry: security-plan §Dependency Security (the accepted-exceptions paragraph and its "Retired 2026-09-07" precedent) requires every `[advisories] ignore` / `[licenses] allow` entry to carry a comment describing a dependency path that exists in the tree; an entry whose justifying path left the lock goes, one the remaining graph still needs stays with its consumer named. Which of the current entries are Tauri-only is P3's measurement against the new lock.
- `Cargo.lock` committed and un-drifted after the crate leaves: security-plan §Security Anti-Patterns → Universal requires the lock committed so the audit stays deterministic; the removal's dependency delta is a lock change that must land in the same commit as the member-line removal.
- The secret-scan gate survives the `ci.yml` edit: security-plan §Secret Management (secret-scan gate shape) requires the `rust` job's presence-guarded `Secret-scan gate` step to keep running `crates/conductor-core/tests/secret_scan_gate.rs`; removing the `frontend`/`a11y` jobs and the frontend-bundle step must not touch it. Whether its exact-set allowlist names any path under `crates/conductor-tauri` (an entry that would then describe nothing) is research's question.
- Harness-spawn rule (b) shrinks only by retirement, never by loosening: security-plan §Security Anti-Patterns → Code Patterns requires every spawn that REMAINS on the routine `scripts/agent-run.{sh,ps1}` path and in `ci.yml` to stay array-form with no shell string and no `eval`-equivalent — the fifth form (`conductor cleanup <run_id>` behind `valid_run_id` / `Test-RunId`) is a routine-path form and stays. Which of the eight forms are driver-stack-only (and so leave with what they spawn) is P3's measurement; rule (a) (the MCP sidecar spawn in `conductor-verify`) is untouched under B3.
- No listener and no new crossing: security-plan §Security Anti-Patterns → Universal requires the shipped binaries to open no inbound listener beyond the `:4317` occupier; security-plan §Threat Model Summary (attack surface, the single-deliberate-exception vector) scopes the `4444`/`4445` driver ports to the dev-only driver legs, which leave here. The removal adds no bind, egress, env handle or command word (B5).
- Env-handle duties bind per READER: security-plan §Input Validation (the `CONDUCTOR_MSEDGEDRIVER` / `CONDUCTOR_NVDA` / `CONDUCTOR_E2E_SEED_DIR` / `CONDUCTOR_A11Y_STRICT` rows) attaches each duty to a named reader; a handle whose every reader leaves takes its row's duty with it, while a surviving reader keeps it. In particular the `CONDUCTOR_E2E_SEED_DIR` row requires that no shipped binary read that handle — if `envelope_fixture.rs` survives (B1's "two webview fixtures") with its setter gone, it must stay an unset no-op. Whether it survives is P3's question.

## Patterns to follow
- The 2026-09-07 `number_prefix` retirement (security-plan §Dependency Security, "Retired 2026-09-07"): remove a `deny.toml` entry on `deny.toml`'s own justified-comment requirement once its named dependency path has left `Cargo.lock`, and record which path left.
- The audit/deny overlap with the porcelain-first reading (security-plan §Dependency Security, "Two distinct external-decay faults"): read the advisory-db checkout's porcelain before trusting any audit result, and treat a red reading as the tree's only once the local copy is clean.
- The closed-allowlist harness selector (security-plan §Input Validation, CLI-arguments row): the shells' `run --live` selector is a closed `case` allowlist where an unknown token prints usage and exits 2 before any probe. Removing the `--e2e` / a11y / `sr*` arms keeps that shape: a removed token is refused, never silently passed through.
- Record each reader, don't assume it (security-plan §Input Validation, committed-manifests and path-handle rows): each env handle's surviving readers are measured and named, and none is inferred from the handle's former role.

## Anti-patterns to avoid
- Never add a `deny.toml` ignore or allow, and never drop the `cargo deny` step, to turn the post-removal gate green: security-plan §Dependency Security limits the justified-exception mechanism to a non-actionable item a NEW dependency pulls, and this chunk adds none.
- Never leave the msedgedriver fetch, or the leg that executes the fetched binary, standing without its pre-execution Authenticode gate (security-plan §Dependency Security, third dependency class; §Security Anti-Patterns → Code Patterns, rule (b)): the fetch, the gate and the executing driver stack leave together, or the gate stays.
- Never skip or weaken the secret-scanning CI gate while editing `ci.yml` (security-plan §Security Anti-Patterns → Secrets).
