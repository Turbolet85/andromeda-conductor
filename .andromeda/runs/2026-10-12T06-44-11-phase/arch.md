## Constraints
- Engine logic stays in the runtime-agnostic library crates, and `conductor-cli` stays a thin shell that drives them. Each new command-line entry (catalogue listing, graceful stop, past-run envelope standing, checklist items) is therefore a clap surface in `conductor-cli` over a library function, never logic written in the bin (per architecture §Design Philosophy "Headless-drivable core, thin shell"; per architecture §Established Decisions [Workspace / Core Structure]).
- The verbs are whichever `Commands` (`cli.rs`) declares. The plan holds no literal verb list, and layout-templates §Surface: cli Primary screens is the place that lists them. A new verb or flag lands as a `Commands` declaration and is never added to this plan as a list (per architecture §Stack and Technologies, the CLI argument parsing row).
- Crate dependency edges are the architecture: a forbidden cross-seam edge must not compile. A re-homed envelope reader has to reach `run_envelope` through an edge the members' `Cargo.toml` files already permit. Whether `conductor-cli` → `conductor-report` exists already, so that `read_envelope`'s stated reason (the window crate had no `conductor-report` edge) has gone, is research's question (per architecture §Established Decisions [Module Boundaries]; per architecture §Occupied Resources, crate names).
- The catalogue listing is a capability-set load site. `list_scenarios(dir, &manifest)` (identity-only summaries) and `load_catalog(dir, &manifest)` are named as the `conductor-core` loaders that carry the manifest through. So any listing verb must take a `&CapabilityManifest`, and an absent or malformed manifest stays a `CoreError` harness fault, never a widen. The summary type keeps an architectural role outside the picker (per architecture §Established Decisions [Accepted Capability Set]).
- The checklist bound is a load-time garde rule: `length(min = 1, max = MAX_CHECKLIST_TEXT)` on both halves of `ChecklistItem`, plus the sibling rule `Scenario::check_checklist()` called from `from_toml_str`. The plan's justification "a dialog row's display bound" is panel-shaped. A bound has to remain, and the stated reason (and possibly the number) is the part that changes (per architecture §Conventions, config conventions; per architecture §Established Decisions [Validation Library]).
- The live-update channel is retired ("no live-update surface remains"), so a run-event channel payload has no architectural home left. `drive_run` is still registered as `conductor-run`'s "live-counter run driver". The plan also names it as a caller of the deterministic `preflight()`, beside `conductor suite`. Re-shaping it into a command-line graceful stop keeps the deterministic-posture gate (per architecture §Established Decisions [Real-time Strategy]; per architecture §Occupied Resources, crate names; per architecture §Standard Contracts, Readiness gate).
- `logs/conductor-tauri.jsonl` is registered "no writer since 2026-10-11 … the sink goes at `Panel-shaped types retired`". `CONDUCTOR_E2E_SEED_DIR` is registered as read only by `envelope_fixture.rs`, with no setter. Removing either subject means the registry row retires through the wrap's amendments, never through a phase edit (per architecture §Occupied Resources, on-disk artifacts; per architecture §Occupied Resources, environment variables).

## Patterns to follow
- Stored state is read only through the storage seam. `runs.db` uses raw SQL over rusqlite bound parameters and is kept synchronous, off the async runtime. `run_envelope` is the run-level envelope standing keyed `run_id` (`classification` · `cause`), and a past run's standing is a cross-run SELECT in that seam (per architecture §Established Decisions [ORM]; per architecture §Occupied Resources, on-disk artifacts).
- Outcomes are values. Any new CLI output that carries a `Verdict` or `ReportState` keeps them as `Ok(...)` values. Interrupting a run is not a harness fault by default, and `Result::Err` stays reserved for Conductor's own failures (per architecture §Design Philosophy "Outcomes are values, errors are harness faults"; per architecture §Cross-cutting Patterns, Verdict/error wall).
- `current_thread` runtime, owned by the core, with `#[tokio::main(flavor = "current_thread")]` on the CLI path. A graceful mid-run stop is wired onto that runtime and has to leave the seeded stream shape and the `std::time` journal stamps untouched (per architecture §Established Decisions [Async Runtime Flavor]; per architecture §Cross-cutting Patterns, Determinism discipline).
- The standalone per-seam build is measured, not enforced by a gate: each of the eight members builds on its own targets (`--lib` for the seven libraries, `--bins` for `conductor-cli`) and never with `--all-targets`. Removing a crate's dependency or feature use can expose a gap that workspace unification had hidden (per architecture §Established Decisions [Module Boundaries]).

## Anti-patterns to avoid
- No new inbound listener, socket or non-loopback egress. The port-occupier stays the only deliberate bind, so a graceful stop must not open a control port (per architecture §Cross-cutting Patterns, Trust boundary; per architecture §Occupied Resources, ports).
- No new `CONDUCTOR_*` handle beyond the configuration handles over concepts the plan already defines, and no sixth `agent-run.{sh,ps1}` command, because the 5-command harness surface is unchanged (per architecture §Occupied Resources, environment variables; per architecture §Stack and Technologies, the operator instruments row).
- Re-homing a type must not add a cross-seam dependency edge just to save a move, for example a library crate depending on `conductor-cli`, or `conductor-core` taking a seam crate's dependency. The edges are the architecture (per architecture §Established Decisions [Module Boundaries]).
