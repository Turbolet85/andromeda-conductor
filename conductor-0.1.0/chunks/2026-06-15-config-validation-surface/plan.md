## Goal
Attach the validation seam to `conductor-core`'s scenario identity model — the structs the previous chunk
(`conductor-core-shared-types`) deliberately left serde-only, with doc-comments naming this chunk as where
garde lands (`scenario.rs:5-6,33`, `error.rs:13`). Three deliverables: (1) `#[derive(garde::Validate)]` on
`Scenario`/`PId` with the rules expressible over the current identity fields (non-empty `p_ids`, the `P-NNN`
001..060 format, a no-duplicate-P-IDs struct-level custom validator); (2) the garde→`CoreError` bridge filling
the reserved `#[non_exhaustive]` extension point so a validation failure is a typed `Result::Err` harness fault,
never a `Verdict`/`ReportState` (the verdict/error wall); (3) a reusable `CONDUCTOR_*` path-handle guard
(`std::fs::canonicalize` + bounds-check) that lives in core and is *called* at the CLI edge later.

This establishes the validation PATTERN (per arch §Validation Library + security-plan §Input Validation) — the
struct-level `#[garde(custom)]` mechanism that the Epoch-2 emission-spec rules (error-fraction ∈ [0,1],
p50≤p95≤p99, severity-mix sums) will extend once those fields exist. It is pure load-time validation + one sync
path helper: no async, no scenario-file loader, no env-reading, no UI. Per the P4 decisions: the path guard is a
pure `resolve_under(base, candidate)` helper in `conductor-core::config_path` (reusable + unit-testable now,
wired at the cli edge in a later chunk), and the worked custom-validator example is **no-duplicate-P-IDs**.

1. **Add the garde dep edge.** In `crates/conductor-core/Cargo.toml`, add `garde.workspace = true` to

   minimal per security posture).
2. **Validate `PId`.** Derive `garde::Validate` on `PId`; apply a field-level `#[garde(custom(pid_format))]`
   to its `.0`. `pid_format(value: &str, _ctx: &()) -> garde::Result` accepts exactly `P-` + three digits whose
   numeric value is 001..=060; rejects anything else (wrong prefix, wrong digit count, 000, >060). Keep the
   existing serde-`transparent` derive untouched.
3. **Validate `Scenario`.** Derive `garde::Validate` on `Scenario`:
   - `name`: `#[garde(length(min = 1))]` (non-empty scenario name).
   - `p_ids`: `#[garde(length(min = 1), dive)]` — the "no scenario without a P-ID" law as a non-empty rule,
     plus `dive` to recurse each `PId`'s own validation.
   - `seed`: `#[garde(skip)]` (any `u64` is a valid seed).
   - `slo_tier`: `#[garde(skip)]` (the closed enum is already type-validated).
   - struct-level `#[garde(custom(no_duplicate_pids))]`: `no_duplicate_pids(s: &Scenario, _ctx: &()) ->
     garde::Result` rejects a `p_ids` list containing a repeated P-ID — the worked cross-cutting custom
     validator the Epoch-2 emission rules will sit beside.
4. **Bridge garde → `CoreError`.** In `error.rs`, extend the `#[non_exhaustive]` `CoreError` with the reserved
   variant, e.g. `#[error("config validation failed: {0}")] Validation(#[from] garde::Report)`. Keep
   `Config(String)`. This makes `?` on a `.validate()` call inside a `core::Result<T>` fn produce a harness
   fault — never a verdict. Add a unit test asserting a `garde::Report` converts into `CoreError::Validation`
   (and that `Verdict`/`ReportState` remain non-error values — the wall holds).
5. **Path-handle guard.** New `crates/conductor-core/src/config_path.rs`: `pub fn resolve_under(base: &Path,
   candidate: &Path) -> crate::Result<PathBuf>`. Canonicalize the (existing) `base`; resolve `candidate`
   against it; reject (as `CoreError`) any result that escapes the canonicalized `base` (`../` traversal, an
   out-of-scope absolute path, or a symlink that climbs out). Sync `std::fs` only; reads NO env vars (the
   `CONDUCTOR_*` lookup + base selection is the later cli-edge chunk's job). Wire `mod config_path;` +
   `pub use config_path::resolve_under;` in `lib.rs`, and soften the lib doc-note to acknowledge the single
   sync-fs helper.
6. **Tests** (in-file `#[cfg(test)] mod tests`, plain `#[test]` — nextest/rstest are a later chunk). Positive +
   negative matrices per the acceptance criteria below; the path-guard test uses `env!("CARGO_MANIFEST_DIR")`
   as a guaranteed-existing base (no new dev-dep needed).
7. **Gates.** `cargo test -p conductor-core` green (old serde tests + new validation/guard tests); `cargo
   clippy --workspace --all-targets -- -D warnings` clean; `cargo build --workspace` green; `Cargo.lock`

## Implementation notes
- **garde 0.23 API to confirm at implement:** the struct-level `#[garde(custom(...))]` form, the field-level
  `custom`/`dive`/`length` combinators, and the validation entrypoint signature (`.validate(&())` vs
  `.validate()` for unit context). The plan commits to the shapes in the P4 previews; reconcile exact tokens
  against the installed garde 0.23 docs.

  joined candidate stays under it — do NOT canonicalize a not-yet-created target path (a future `runs/` dir
  won't exist yet). This is why the signature takes an explicit, existing `base`.
- **No new dev-deps:** path-guard tests use `env!("CARGO_MANIFEST_DIR")` as the existing base; `assert_fs`/
  `tempfile` arrive with the later test-framework chunk.
- **Scope boundary (do NOT pull forward):** no per-phase emission-spec fields, no scenario-file loader, no
  env-var reading, no cli/tauri wiring, no UI rendering of config errors (the design extract is forward-looking
  only — this chunk renders nothing).
