## Goal
Build the MCP `initialize` preflight readiness gate in `conductor-verify` — the once-at-suite-start check
that proves the Pulse read-back path is trustworthy before any scenario depends on it (arch §Standard
Contracts; security-plan §Threat Model, MCP read-back vector). Three assertions over the chunk-1
`ReadbackClient`, each producing a distinct `Blocked` precondition on failure and **never** a silent
downgrade (preflight integrity): (1) the negotiated protocol version equals the manifest-pinned `2024-11-05`;
(2) all four required read-back tools are present against the pinned contract manifest; (3) a data-dir canary
incident reads back from the shared corpus. The result is a serializable `ReadyState` value matching the
architecture's readiness JSON; `ready:false` is the signal the run report later maps every dependent scenario
to `ReportState::Blocked` (conductor-core's existing enum @ `report_state.rs:24` — no new state).

Per the P4 scope decision (AskUserQuestion: **read-back assertion only**), the gate owns the canary's
*read-back assertion* only — it takes the canary's identity as a parameter and asserts `query_incident_list`
returns it. The canary's *emission* is orchestrated upstream by the Epoch-8 CLI suite runner (which will
depend on both `conductor-emit` and `conductor-verify`); `conductor-verify` therefore stays
`conductor-core`-only, preserving the workspace's star topology (no seam→seam edge — research §Graph impact).
CI exercises every leg against the in-process rmcp stub; the live emit→corpus→read-back path is operator-gated
(test-plan §5).

This chunk also lands chunk 1's deferred follow-up: the real `TokioChildProcess` child-spawn integration test
plus a stub-child MCP-server binary, exercising the connect→preflight→canary path over a true child process
(not just the in-proc duplex) — intrinsic to the data-dir canary.

Provide a `report_state(&self) -> ReportState` helper returning `Blocked` when `!ready`, else `Pass`.
3. **The gate assertions** (`src/preflight.rs`). `run_preflight(client: &ReadbackClient, manifest: &ContractManifest, canary: &CanaryMarker) -> Result<ReadyState, VerifyError>`, instrumented under the bounded `verify.readback.preflight` span (obs-plan §4; research §Conventions):
   - **Protocol pin** — compare `client.negotiated_protocol_version()` (@ `client.rs:72`) to `manifest.expected_protocol_version`; mismatch ⇒ `ready:false` + precondition `"protocol version mismatch: expected 2024-11-05, got <v>"`.
   - **Tool presence** — `client.list_tools()`; mark each manifest tool `Present`/`Absent`; any `Absent` ⇒ `ready:false` + precondition naming the absent tool(s).
   - **Canary read-back** — `client.query_incident_list(None)`; parse the `CallToolResult`; assert an incident matching `canary` (a marker string the upstream emitter stamped) is present. Empty/no-match ⇒ `ready:false` + precondition `"canary round-trip failed: incident not found in corpus"`. A failed *call* (transport) maps to the same `Blocked` leg (the precondition is unmet), not a panic (security-plan §Anti-Patterns).

## Implementation notes (optional)
- **Verdict/error wall (the crux):** MCP-reachability + the 3 preconditions become `Ok(ReadyState{ready:false,…})` — `Err(VerifyError)` is reserved for true harness faults (manifest parse, `DataDirRejected`, an unclassifiable mid-call fault). The gate is the layer that translates chunk-1 `VerifyError`s into `Blocked` readiness.
- **Open question 2 (version ⇒ Blocked):** verify whether rmcp 1.7.0 exposes a wrong server version as a readable `peer_info().protocol_version` (→ step 3) or hard-errors `initialize` (→ classify in step 4's boot wrapper). The wrong-version stub test pins whichever path; either way the outcome is `Blocked`, never `Err`.
- **Open question 3 (`data_dir` redaction):** redact the serialized `data_dir`; the canary proves wiring by the *fact* of a corpus match, not by exposing the raw path.
- **Open question 4 (stub-bin mechanism):** prefer the feature-gated `[[bin]] stub-pulse-mcp` + `env!("CARGO_BIN_EXE_…")` (env-discoverable) over `examples/` (no `CARGO_BIN_EXE`); keep it out of the default build surface.
- **rmcp `#[non_exhaustive]`:** build `ClientInfo`/params/`ServerInfo` via `::new()`/`with_*()`, never struct literals (SEP-1319; verification-harness.md session note).
- **No seam→seam edge:** do NOT add `conductor-emit` to `conductor-verify` — the canary identity is a parameter; emission is the Epoch-8 CLI's job (P4 scope decision).
