## Goal

Add the **statistical-anomaly family** of the `scenarios/` catalog — the declarative TOML config for Pulse's
first four baseline-accumulation capabilities **P-009..P-012** (`pulse-capability-spec.md` §3). Unlike the hard
signals (ch2, detectable from the first span), these require a **converged baseline before a deviation can be
flagged**, so each scenario is a `baseline → detection` timeline. Per the user decision (P4) the four P-IDs are
delivered as **two per-pair files** — the shape the architecture's own canonical example uses
(`error-baseline-spike` / `p_ids=["P-009","P-010"]`, architecture.md §Standard Contracts) and the only shape
that lets a detection check rest on a real baseline phase (a P-009-alone "scenario" is baseline-only
infrastructure with nothing to assert).

This is **config + tests over primitives that already exist** (Epoch-3 latency-shaping, error-spans,
traffic-rate ramps) — **zero new emit primitive, zero new dependency, and zero `Scenario`/`ExpectedCheck`/
`PhaseSpec` model change** (per arch extract + tests extract "zero-model-change", confirmed in research). The
research proved the model already carries everything needed: `ComparisonKind::CountAtLeast` is documented and
evaluator-wired (`conductor-verify/src/slo.rs:79`) precisely as "the sample-count floor (≥50-sample latency /
≥10-span error-rate)" — i.e. the P-009 10-span and P-011 50-sample boundaries — and `gap_ms` (≤1h) expresses
the 90s/60s recipe windows with no phase-duration field. Each scenario therefore declares two `class="Hard"`
checks: a **`CountAtLeast` baseline-floor** check (the converged-baseline P-ID) + a **`Contains` candidate**
check (the detection P-ID). All four checks are **`Hard`** — baseline math + threshold detection are
deterministic (arch §Probabilistic-Assertion Policy); the model-interpretive severity that *consumes* these
attention cues is P-020 (a later severity-lifecycle chunk), not asserted here. This is the clean all-`Hard`
counterpart to ch2's single P-008 `CalibrationRegion` exception.

The **±10%/±15% baseline-match tolerance** and **persistence-window / SLO timing** are *evaluated logic* owned
by the Epoch-8 evaluator + CLI driver, not the TOML (arch extract "declare-intent only" + ch2 precedent); the
catalog declares phases + expected markers only. No live MCP run happens in this chunk (Epoch-8 / Epoch-10).

  ≥floor) it is a hard pass; the evaluator's `CountAtLeast && !matched → calibration` softening (`slo.rs:79`)
  only fires on an unmet floor — a safety net, not a reason to declare the check non-`Hard`. So the all-`Hard`
  guard is correct.
