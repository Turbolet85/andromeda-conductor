Pulse simply creates no incident from the emitted storm.
3. **arch §Standard Contracts / §[MCP Read-Back Client] canary premise is contradicted by reality (spec↔reality).** The pinned design "round-trip a canary incident (emit one known incident → assert `query_incident_list` returns it)" is WRONG: Conductor emits *telemetry* (a fingerprint-storm); Pulse's write-path is OTLP → L1 → L2 RetryStorm cue (deterministic, ≥5 same fingerprint/30s) → L3 digest (cadence 20–60s) → **L4 LLM inference (llama.cpp, Llama-3.2-3B, llama-cli subprocess) decides Dismiss/Severity → incident**. An incident forms ONLY if the 3B LLM surfaces it; L4 is behind a degraded-mode backoff; Pulse's own dev never cleanly reproduced a reliable incident (its AI-Model/RESUME-NOTE: "incident → red dot NOT confirmed"). ⇒ **incident-readback verification cannot be deterministic against the real LLM** — fundamentally at odds with Conductor's zero-flakiness/determinism bar.
4. **arch §Standard Contracts P-049 wrong:** `corpus.db` is **plaintext SQLite** (header "SQLite format 3"), NOT "encrypted at rest / OS keychain". The keychain-failure canary mode in §Standard Contracts does not apply.
5. **MCP read-back surface (amend the contract):** live tool count is **8**, not 4 (4 live-buffer: `query_traces`/`query_metrics`/`query_logs`/`generate_snapshot` + the 4 corpus tools). Only the **persistent-corpus** tools (`query_incident_list`/`retrieve_report`/`retrieve_telemetry_slice`/`mark_incident_resolved`) work cross-process; the in-memory-buffer tools return EMPTY from a Conductor-spawned sidecar (separate process, no shared memory with pulse-app).
6. **incidents filter column is `workspace`** (not `workspace_root` as arch §Standard Contracts implies). Incident item shape: `{id, status, severity, title, opened_at}`; `retrieve_telemetry_slice` → `{incident_id, span_refs, fingerprint_refs, timestamps_unix_nano}`.
