## Goal
Wire the desktop go/no-go surface for an operator pause: when the run reaches a `HoldPoint` (a non-Conductor action — the empty-`expected` operator-checklist scenarios already build one in `execute_scenario`), the GUI raises the **already-shipped** `OperatorPauseDialog` (Radix AlertDialog, component-primitives-library), the operator answers Proceed/Abort, and that `Decision` (`Go`/`NoGo`) flows back to the awaiting background run thread, which records a `HoldResolution` and resumes or stops. This is the **Tauri implementation of the `conductor_core::PauseResolver` seam** — the third shell after the agent `HeadlessResolver` and the CLI `inquire` `PromptResolver` (per architecture §Real-time Strategy + §Async Runtime Flavor; the seam is `conductor_core::pause`).

**Scope decision (P4 AskUserQuestion — "Full bridge" selected):** ch8 ALSO generalizes `conductor_run::drive_run` to accept the resolver (it currently hardcodes `HeadlessResolver::proceed()` at `lib.rs:303`), so the bridge is end-to-end: when Epoch-10 brings a live Pulse, the operator-checklist holds (P-025/026/027/P-032) drive the GUI dialog with zero further wiring. Research confirmed the blast radius is the Tauri caller (`commands.rs:201`) + `drive_run`'s 2 unit tests only — the CLI release-gate path calls `execute_scenario` directly (already generic over the resolver) and is untouched.

The dialog cannot fire in a real run without a live Pulse (every scenario short-circuits to `Blocked` before the hold), so — consistent with every Epoch-9 view — ch8 is **build/type-gated + unit-gated**; the wired dialog is demonstrated in the DEV gallery, and GUI/axe/keyboard assertions defer to the Epoch-9 Desktop a11y harness (ch9) per the carried route note. The hold-resolution adds no new critical path and does not reshape the run-report envelope (obs §3).

The CLI (`execute_scenario` caller) needs no change.
2. **Build the `TauriResolver` + hold gate (conductor-tauri, new `src/pause.rs`).** Mirror the `conductor-cli/src/pause.rs` resolver-as-concrete-type pattern (one Tauri resolver kind → a struct, not an enum):
   - A managed `HoldGate` = `Arc<Mutex<Option<oneshot::Sender<Decision>>>>` (the single in-flight hold's reply slot — the run thread awaits each hold before continuing, so one slot suffices; no per-hold id).
   - A `HoldPrompt` (serde `Serialize`) — the webview-facing projection of a `HoldPoint`: `title` (e.g. the P-ID + step), `body` (the `prompt`), `allow_no_go`. Derived in the resolver so the dialog never re-authors the hold (a11y §1 binding: surface `p_id`/`step`/`prompt`).
   - `TauriResolver { gate: HoldGate, on_hold: Channel<HoldPrompt> }` impl `PauseResolver`: `resolve(hold)` → build a fresh `oneshot::channel::<Decision>()`, store the `Sender` in `gate`, `on_hold.send(HoldPrompt::from(hold))` to open the dialog, then `await` the `Receiver`. A dropped sender (run aborted / webview gone) collapses to `Decision::NoGo` — the abort-safe default (mirrors `conductor-cli/src/pause.rs:56`). Never blocks Tauri's GUI thread (the await is on the core `current_thread` runtime, off the GUI reactor — arch §Async Runtime Flavor).
3. **Add the resolve `#[tauri::command]` (conductor-tauri).** `resolve_operator_hold(decision: Decision, gate: tauri::State<HoldGate>) -> Result<(), String>`: take the `Sender` out of the gate and `.send(decision)` (ignore a closed receiver — the hold already timed out / aborted). Open a manual `tauri.command.resolve_operator_hold` span; emit one boundary `info!` line carrying `run_id` + an allowlist-safe `decision` field; route any error through `conductor_core::sanitize_error` (obs 2026-06-26 rule). `Decision` is `#[derive(Deserialize)]` PascalCase, so the webview calls `invoke('resolve_operator_hold', { decision: 'Go' | 'NoGo' })`.

Read the gate via `tauri::State`/the managed handle (clone the `Arc` into the spawned thread, like `abort` is cloned today at `commands.rs:162`).
5. **Register state + command (conductor-tauri `main.rs`).** `.manage(HoldGate::default())` alongside `RunControl`; add `commands::resolve_operator_hold` to `generate_handler!`.

## Implementation notes (optional)
- **One in-flight hold.** The run thread `await`s each `resolve_hold` before the next scenario, so the `HoldGate` is a single `Option<Sender>` slot — no queue / correlation id. If a 2nd hold somehow arrives while one is pending, the newer `Sender` overwrites the slot; the older `Receiver` then drops → `NoGo` (acceptable; cannot happen with the sequential driver).
- **Hold unreachable without a live Pulse.** With no live Pulse every scenario is `Blocked` before the hold (`execute_scenario` `lib.rs:118`), so the dialog never fires in a CI/headless run — exactly why the resolver decision-capture is unit-tested directly (not via a streamed run) and the visual surface is the gallery. This mirrors the CLI's `select_off_tty_is_headless` proof + the 2026-06-23 "Blocked-first, never reaches the prompt" finding.
- **Frontend build-order.** `tauri::generate_context!` resolves `ui/dist` at compile time — `npm run build` MUST precede any cargo compile of conductor-tauri (frontend 2026-06-24 rule); the `agent-run.sh run` smoke handles this via `ensure_frontend`.
- **Headless invariant preserved.** The CLI/agent path keeps `HeadlessResolver` (never blocks); only the Tauri shell injects the interactive `TauriResolver`. `drive_run`'s generalization does not change the agent default — the GUI caller chooses the resolver.
