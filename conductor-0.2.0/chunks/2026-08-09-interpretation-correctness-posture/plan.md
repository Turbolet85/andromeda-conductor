## Goal

Pulse's deterministic L4 mode (`ANDROMEDA_PULSE_L4_DETERMINISTIC=true`) replaces the Llama-3.2-3B inference
with a canned `L4Output`, which is what makes every live leg conductor-0.2.0 plans reproducible. The cost,
named in intent §4 **F3**, is that those legs exercise the plumbing and never the interpretation — while
Pulse's own positioning memo calls interpretation-correctness *"the single most important test in all of
Pulse"*. This chunk makes that boundary a **recorded, enforced decision** rather than an accident.

`v2-05` admits two branches and the operator chose **Branch B — a recorded deferral**, because Branch A is
not buildable inside this chunk's boundaries: a real-model leg must *assert the top hypothesis*, but
`execute_scenario` grades every `ExpectedCheck` against the literal placeholder `"incidents-listed"`
(`conductor-run/src/lib.rs:216`), and real per-check read-back extraction is `v2-09` in Epoch 2, which this
chunk's scope excludes. A real-model leg is also non-deterministic by construction and so could never enter
the zero-retry CI set (per test-plan §10 + arch §CI/CD).

The deferral is made **load-bearing** rather than narrated by the finding P3 surfaced: **eleven
`CoverageMode::Auto` capabilities have no verifying scenario at all** — `P-031`, `P-033`, `P-034`, `P-039`,
`P-041`, `P-042`, `P-043`, `P-044`, `P-073`, `P-074`, `P-079` — and **no gate in the repo can see this**.
`check_sut_drift` compares classification↔manifest, never classification↔scenarios, so Conductor currently
claims "auto-verified" for 43 capabilities while 11 of those claims have nothing behind them. Four of the
eleven (`P-031`/`P-033`/`P-034`/`P-044`) are exactly the diagnostic-quality cluster F3 says deterministic L4
bypasses. So this chunk ships a `check_sut_drift` **sibling** that holds the unbacked-`Auto` set to an exact
pinned ledger, carries the interpretation deferral (and its named owner, a **conductor-0.3.0 entry**) in that
pin's doc comment, and surfaces the count on the three coverage roll-ups so a reader of a green artifact can
see what the green does not cover. Per the 2026-08-09 sut-drift-check pattern: the gate is green immediately
and can only shrink under compulsion.

## Implementation Steps

1. **Add the `CoreError` variant.** Extend `crates/conductor-core/src/error.rs` with a fourth thiserror
   variant for unbacked coverage — a harness fault carrying a named reason, distinct from
   `CoreError::SutDrift` (that asks "did Pulse's ledger advance past our classification?"; this asks "does
   our own `Auto` claim have anything behind it?"). Message is identity-only: capability ids and counts, never
   a filesystem path and never an internal type name (security-plan §Error Handling).

2. **Add the pinned ledger `UNBACKED_AUTO` to `crates/conductor-core/src/drift.rs`,** beside
   `KNOWN_UNCLASSIFIED`, holding the eleven ids above. Its doc comment is the **deferral record** and must
   state, in prose that ships with the code:
   - what the ledger is (a record of work owed, never a source of truth, and never a range expression);
   - that it can only shrink — the gate fails on a pinned id that has since gained a scenario;
   - the **interpretation-correctness deferral** explicitly: under deterministic L4 the model is replaced by a
     canned `L4Output`, so `P-031`/`P-033`/`P-034`/`P-044` exercise the plumbing and not the interpretation;
     **"Conductor green" does not mean interpretation is trustworthy**; the owner is a **conductor-0.3.0
     entry**, because closing it needs both `v2-09` and a live Pulse run with deterministic mode OFF.
   - Name the retiring condition, mirroring `KNOWN_UNCLASSIFIED`'s doc-comment convention (`drift.rs:25-30`).

3. **Add `check_scenario_backing` to `drift.rs`,** shaped exactly like `check_sut_drift` (`drift.rs:47`) — a
   pure set comparison over `BTreeSet<&str>`, no runtime IO inside the function, the caller supplying the
   scenario-claimed ids. It takes the classification rows, the P-IDs claimed by the committed catalog, and the
   pinned ledger; returns `Ok(())` iff the unbacked-`Auto` set equals the pin **exactly**. Three drift
   conditions, each named separately in the message (mirror `drift_message`, `drift.rs:70`):
   - an `Auto` row with no scenario and not pinned → a new unbacked claim;
   - a pinned id that *does* have a scenario → pin rot, shrink the ledger;
   - a pinned id no longer classified `Auto` → the pin lost its backing (reclassified or retired).
   Only `Auto` rows participate: `DriveObserve` is operator-confirmed by definition, `StaticOnly` and
   `NotConductors` are deliberately not Conductor's to drive (`coverage.rs:16-36`).

4. **Export both** from `crates/conductor-core/src/lib.rs:37`, beside the existing
   `pub use drift::{KNOWN_UNCLASSIFIED, check_sut_drift};`.

5. **Assert the gate over the committed artifacts.** `check_sut_drift` has **no production call site** — it is
   live via the in-crate test `committed_artifacts_match_the_known_gap` (`drift.rs:138`), which is the release
   gate because `cargo nextest` is. Mirror that exactly: a test that loads the real
   `contracts/pulse-capabilities.toml`, walks the real `scenarios/` catalog via
   `conductor_core::list_scenarios` (its `ScenarioSummary` already carries `p_ids`,
   `scenario_catalog.rs:23`), and asserts `check_scenario_backing` is green against `UNBACKED_AUTO`. Add unit
   tests for each of the three drift conditions plus an empty-pin pass, mirroring `drift.rs:145-177`, and an
   identity-only message test mirroring `drift.rs:178`.

6. **Surface the count on the three coverage roll-ups — reading the pin, not the filesystem.** This is the
   architectural move that keeps the change small: the gate proves `UNBACKED_AUTO` equals reality, so the
   roll-ups may cite `UNBACKED_AUTO.len()` with **no IO and no signature change**, preserving
   `CapabilityRow`'s documented "no allocation and no runtime IO" property (`coverage.rs:59`).
   - `crates/conductor-report/src/coverage.rs:76` (`summary_line`) — qualify the auto term, e.g.

   - Every number stays derived; no literal counts anywhere (the 2026-08-08/08-09 de-hardcoding rule).
