## Goal

`2026-08-08-sut-capability-manifest` made the *accepted* capability set data — `contracts/pulse-capabilities.toml`,
82 ids at `sut_version = "v0.3.0"` — so a scenario may name anything Pulse actually ships. Nothing, however,
asserts that Conductor has *reckoned with* those ids: `coverage_matrix()` is still a `static [CapabilityRow; 60]`
over `P-001..P-060` (`crates/conductor-core/src/coverage.rs:60,73`). Manifest and classification disagree by 22
ids and no gate says so. That is the exact failure the version exists to end — 22 Pulse capabilities went
unnoticed across a 41-day pause because nothing in the repo could notice.

This chunk builds the detector: an offline, deterministic comparison of the shipped `CapabilityManifest` against
the shipped coverage classification that returns a **harness fault** naming the offending ids. The accepted set
enters only through `CapabilityManifest::load` / `accepts` (the chunk's CARRY) — no second parse, no re-derived
id universe, no hardcoded range as the reference (per architecture.md §Established Decisions [Accepted Capability
Set] + security-plan.md §Input Validation). Drift is `Result::Err`, never a `Verdict`/`ReportState`, upholding
the verdict/error wall (per architecture.md §Conventions "Error handling" + test-plan.md §3).

**The gate is live and green from day one, via a pinned known-gap ledger** (operator decision, P4). A plain
zero-drift assertion would fail on the committed tree and block this chunk's own wrap, so `check` compares the
*observed* gap against an explicit pinned list of the 22 ids Conductor knowingly has not classified yet. Today
that matches exactly → `Ok`. The moment Pulse's ledger advances (a manifest id outside the pin), or the pin rots
(a pinned id that has since been classified), or a classified row loses its manifest backing, the check fails
naming the ids. The next chunk (`v2-03`, *Current-SUT coverage classification*) empties the pin and the check
degenerates to the plain zero-drift assertion it was always meant to be. The surface is the **core unit tier
only** (operator decision, P4) — matching `verification-matrix.json#v2-02`'s declared `method: unit`, enforced in
CI through the existing `agent-run run` dogfood step, and leaving operator-facing surfacing to the Epoch-6
*Coverage completeness gate* entry that already owns it. No cli output constraint binds this chunk.

## Implementation Steps

1. **Add the `SutDrift` harness-fault variant** to `CoreError` in `crates/conductor-core/src/error.rs`. The enum
   is `#[non_exhaustive]` and its doc explicitly anticipates later chunks extending the surface (`error.rs:12`),
   so this is the sanctioned extension point — do **not** overload `Config` ("scenario config error: …" is the
   wrong label for a SUT-drift condition). Message prefix should name the condition, not a struct.

2. **Create `crates/conductor-core/src/drift.rs`** holding the comparison. Confirmed name-free: the P3 graph
   existence query for `%drift%` returned 0 rows across the workspace.

3. **Model the two directions.** Compute, from the manifest's `capabilities` and the classification's `p_id`s:
   - `unclassified` — manifest ids with no classification row (the acceptance's named direction);
   - `retired` — classification rows with no manifest entry (a capability Pulse dropped). Not required by
     `v2-02`'s acceptance, but it is one extra set difference and it reports nothing today (the classification is
     a subset of the manifest), so it is a free latent guard rather than added risk.
   Both lists must be **deterministically ordered** (sort, or preserve manifest/classification order — either is
   stable) so the failure message is byte-identical across runs, per test-plan.md §10 (zero-flakiness budget).

4. **Pin the known gap** as an explicit `const` id **list** in `drift.rs` — the 22 ids currently in the manifest
   but unclassified. Three requirements, all load-bearing:
   - it is an explicit list of ids, **never** a range expression (`061..=082`) — a range is the banned shape and
     re-encodes exactly the compile-time bound this version removed;
   - it carries a doc comment stating (a) this is Conductor's *not-yet-classified residual ledger*, **not** a
     second source of the accepted set (the manifest remains the sole reference universe, per architecture.md
     §Established Decisions [Accepted Capability Set]), and (b) its retirement owner: the `v2-03` classification
     chunk empties it;
   - the check must reject a **rotted** pin — a pinned id that is no longer drifted (someone classified it) is
     itself a failure, so the pin cannot silently outlive its truth.

5. **Write the entry point** as a public fn over `(&CapabilityManifest, &[CapabilityRow], &[&str] /* pin */)`
   returning `crate::Result<()>`: `Ok(())` iff `unclassified` equals the pin as a **set, exactly** (neither
   direction slack) and `retired` is empty; otherwise `Err(CoreError::SutDrift(..))`. Keep the pin a parameter,
   not an implicit read, so the tests can drive the post-`v2-03` empty-pin shape without editing the const.

6. **Compose the failure message** naming the offending ids plus the manifest's `sut_version` and `captured_at`
   (which exist to make a red gate actionable), and stating what is owed. It must carry no absolute host path and
   no internal struct name — build it from `String`/`Display`, never `Debug`, mirroring the sanitized-fault
   construction at `capability_manifest.rs:37-43`.

7. **Export from `crates/conductor-core/src/lib.rs`** — one `mod drift;` line in the `mod` block (`:16-31`) and
   one `pub use` in the re-export block (`:33-50`), matching the flat convention. Additive only: the P3
   `crate_edges` query shows six inbound consumers of `conductor-core`, none of which this touches.

8. **Unit tests in `drift.rs`'s `#[cfg(test)] mod tests`** (crate-local, per test-plan.md §2/§4), reusing the
   in-repo `manifest(&[…])`-style fixture-builder shape from `capability_manifest.rs:93` so no test re-sources
   the accepted set:
   - **live gate** — the committed manifest (loaded via `CapabilityManifest::load` from the `CARGO_MANIFEST_DIR`-
     relative path, as `capability_manifest.rs:89` does) + `coverage_matrix()` + the shipped pin ⇒ `Ok`;
   - **Pulse advanced** — a fixture manifest carrying an id outside the pin ⇒ `Err` whose message names that id;
   - **pin rot** — a pinned id present in the classification ⇒ `Err`;
   - **retired capability** — a classification row absent from the manifest ⇒ `Err` naming it;
   - **post-`v2-03` shape** — in-sync manifest + classification with an empty pin ⇒ `Ok`;
   - **artifact hygiene** — the failure message contains no absolute host path and no internal struct name, and
     does carry `sut_version` + `captured_at`; model it on `load_failure_message_never_contains_the_path`
     (`capability_manifest.rs:120`);
   - **determinism** — identical inputs produce a byte-identical message.

9. **Do not touch** `coverage.rs`'s `matrix_has_exactly_sixty_capabilities` / contiguity tests, nor
   `conductor-report/src/coverage.rs`'s `"**Capabilities** 60 · 40 auto · 13 drive+observe · 7 static-only"` and
   `.count(), 60` assertions (`:89`, `:104`). Those freeze the current classification and are `v2-03`'s to move
   (its CARRY says so). This chunk is additive and must leave the 428-test baseline otherwise intact.

## Implementation notes

- **The pin is the one genuinely delicate artifact.** It is a residual ledger, not a capability source. Write its
  doc comment for the reader who finds it in six months and must not mistake it for "the ids Conductor supports".
  Name `v2-03` as its retirement owner in the comment itself.
- **Exact-set equality both ways** is deliberate: pin-shrinks-when-classified is what stops the ledger rotting
  into a permanent excuse. Expect `v2-03` to edit the pin down to `[]` and this chunk's tests to keep passing
  unchanged — that is the design working.
- **Order sensitivity:** `CapabilityManifest.capabilities` is a `Vec<String>` in file order and `coverage_matrix()`
  is a `static` array in table order; both are already deterministic, but the *set difference* is not unless you
  sort or iterate a stable source. Sort explicitly rather than relying on either input's incidental order.
- **`is_pid_shaped` already exists** (`crate::scenario::is_pid_shaped`, used at `capability_manifest.rs:70`) and
  the manifest's own `validate` has already enforced shape + no-duplicates before `load` returns — the check may
  assume well-formed ids and must not re-validate them.
- **Do not instrument for its own sake:** obs-plan §11 bans over-instrumenting non-critical paths, and a unit-tier
  check needs no span. If a `tracing` line is added at all, keep it to allowlisted fields.
