## Goal

Nothing in this repo states how a verifiable Pulse must be launched (intent §Theme 3 F11). This chunk records
that contract as a committed artifact and makes preflight assert it, naming each unmet term individually — the
third instance of the committed-SUT-manifest pattern already shipped twice in `conductor-core`
(per architecture.md §Occupied Resources · security-plan §Input Validation).

The working entry named two terms — deterministic L4 and a shared data dir. The preceding chunk proved both are
**necessary but not sufficient**: it had both, with deterministic L4 confirmed active in all three arms, and
still recorded `cues_emitted: 0` with the service in baseline bootstrap, so no incident formed under any
workspace key. P3 research found why, and it is not what the scope assumed. The storm shape was never the gap:
`emit_canary` already emits **6** identical-fingerprint exceptions explicitly over Pulse's `>=5 in 30s` floor
(`conductor-run/src/lib.rs:105-107,146-150`). What is missing is that **the canary storm is the canary
service's first-ever traffic**, so Pulse has no baseline for it and the L2 cue evaluator never considers it. A
contract that prescribed storm shape would restate what already holds and leave the real blocker unnamed.

So the contract's operative content is **incident-formation viability**: a warm-up pre-roll that carries the
canary service out of baseline bootstrap before the counted storm begins, and a poll budget that covers L3's
20-60s digest cadence with L4 behind it (today's default is 30s — below the cadence's own upper bound). This is
the entry the arm-3 CARRY names as owning "an incident actually forms", and these two terms are how it does so.
The L4 term itself is asserted through a **shell-declaration proxy** with a named fallback (operator decision at
P4): Conductor reads its own inherited environment — the same shell that launches `pulse-app` — and when the
declaration is absent surfaces a precondition naming the condition and both candidate causes, never claiming a
measurement of a process Conductor does not launch (the binding v2-17 precedent, per security-plan
§Security Anti-Patterns → Universal).

Claims `verification-matrix.json#v2-18`. It does **not** claim v2-04 (owned by the Epoch-6 operator-gated live
suite) and does **not** claim `ready:true` (owned by the later Epoch-2 *First live green preflight*).

## Implementation notes
- **Cascade order matters.** The contract-term arm goes after the tool checks and before the canary arms. An
  unmet L4 or bootstrap term *explains* a failed canary, so surfacing the canary symptom first would send the
  operator to the wrong cause — the failure mode the preceding chunk documented.
- **Do not add a `ReadyState` field.** Four full struct literals across two crates would need editing, and a
  composed string already satisfies "names each unmet term individually". If a later entry genuinely needs
  structured terms, that is its cost to pay, with the four sites enumerated in `research.md`.
- **The warm-up lengthens the preflight.** Warm-up + poll must stay inside the load envelope's
  `max_scenario_duration_ms` (600000) and should stay well short of it — the gate runs on every `agent-run boot`.
  Keep the stub-path budget at `CanaryPoll::immediate()` so unit/integration tests stay real-clock-free
  (`preflight.rs:66-68`).
- **The live leg may still block.** If bootstrap warm-up does not produce an incident, record that as the
  finding rather than reshaping the contract to match a green run. Evidence honesty is the deliverable; the
  green run belongs to *First live green preflight*.
