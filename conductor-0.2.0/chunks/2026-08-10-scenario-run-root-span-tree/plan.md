## Goal

Make Conductor's self-observation span tree **real**. obs-plan §4 Critical Path 1 mandates the chain
`scenario.run` (root) → `timeline.execute` → `emit.batch` → `verify.readback` → `report.generate` →
`db.insert_run`. Research proved two independent gaps: three of the six spans do not exist
(`scenario.run`, `report.generate`, `db.insert_run`), **and the subscriber layer emits no span records
at all** — `JsonObsLayer` implements only `on_event` and never reads span context
(`crates/conductor-core/src/obs.rs:239-276`), so even the three shipped spans are invisible. The
committed `logs/agent-latest.jsonl` carries **0** occurrences of `timeline.execute` / `emit.batch` /
`verify.readback`, which is the empirical proof rather than an inference.

The chunk therefore does three things, in dependency order: it teaches the layer to emit span lifecycle
records (the enabling change, without which nothing else is observable — operator-approved at P4), it
adds the three missing spans, and it widens the redaction allowlist to the field names those spans
actually carry. It closes the CARRY the operator assigned at the 2026-08-10 wrap: `conductor-report`
emits zero `tracing::` calls across all five of its files while obs-plan §4 CP1 mandates
`report.generate` → `db.insert_run`, a deferral route-sequenced to "the Epoch-8 cli/timeline caller"
that outlived its owner when Epoch 8 completed without it.

Scope is instrumentation only, per obs-plan §11 and arch §Stack: plain `tracing` nesting, **no OTel
SDK, no `tracing-opentelemetry`, no `traceparent`** — `run_id` stays the sole correlation key, and the
only OTLP in the system remains the PRODUCT fault stream to `127.0.0.1:4317`. No `Verdict`/`ReportState`
value, run-report envelope field, `runs.db` column, or cli stdout line changes.

**Root placement (operator decision, P4).** The root is per-scenario at the composition root —
`conductor-run::execute_scenario` — so one instrumentation site serves CLI `run`, CLI `suite` and the
GUI identically (arch §Occupied Resources — Crate names). `report.generate` and `db.insert_run` are
emitted where they occur inside `persist`, a **sibling** of `execute_scenario`, correlated by the
`run_id` the layer already stamps on every line. This is forced by the call structure, not preference:
the graph shows `persist` is called by `execute_scenario`'s callers at all three production sites, and
under `suite`/`drive_run` **one** `persist` serves N scenarios whose spans have already closed.

1. **Teach `JsonObsLayer` to emit span records** (`crates/conductor-core/src/obs.rs`). Add `on_new_span`
   and `on_close` beside the existing `on_event`. Each emits one JSON line carrying the same flat
   identity block `on_event` already builds (`timestamp_ms`, `level`, `target`, the three service fields,
   `run_id`), plus the span's name, a lifecycle discriminator, and — on the `new` record — the span's own
   attributes recorded through `JsonVisitor` so the allowlist still gates them. Include the enclosing
   parent's name so a reader can reconstruct the tree; `Registry::default()` is already the base
   (`obs.rs:146-157`), so span storage and parent lookup are available with no subscriber-stack change.
   Follow the existing direct-insert precedent for layer-supplied keys (the pattern `timestamp_ms` /
   `level` / `target` use) and route only user-supplied span attributes through the visitor.

3. **Add the `scenario.run` root span** (`crates/conductor-run/src/lib.rs:253`, `execute_scenario`).
