## Goal

Today a live `conductor preflight` against a real Pulse ends in `Blocked: canary round-trip failed: incident
not found in corpus` — a string that names nothing an operator can act on. Research confirmed why, first-hand
against the Pulse source: incidents are filtered `WHERE workspace = ?1`; `pulse-app` derives that key from its
detected workspace root while the MCP sidecar Conductor spawns always keys on `ANDROMEDA_PULSE_DATA_DIR`
(`andromeda-pulse-mcp.rs:74`, under a comment still claiming parity that has been stale since Pulse's P-079).
When they disagree the sidecar queries a key nobody writes, so the corpus returns zero rows *forever* — and
Conductor reports it as if the canary were merely slow.

This chunk makes that condition **nameable**. The canary path already distinguishes two causes of "not found"
— the corpus returned zero incidents (`preflight.rs:276`) versus incidents exist but none carries the emitted
fingerprint (`:290`) — and it collapses both into one string. Zero-rows-forever is the divergence's signature,
so this chunk promotes that branch to its own named precondition stating the app/sidecar key-agreement
requirement, and keeps the fingerprint-miss branch distinct. It is a **precondition in exactly the sense the
gate already uses** (per architecture.md §Standard Contracts): `UNREACHABLE_PRECONDITION` names a condition it
never measures either. The precondition therefore names both candidate causes honestly — a key divergence, or
Pulse raising no incident — rather than claiming a measurement Conductor cannot make. Research established
that it cannot: `dispatch_query_incident_list` accepts no arguments, so read-back cannot probe a second key;
Pulse never logs its resolved key; and the corpus is out of bounds by rule (per security-plan §Security
Anti-Patterns → Data Protection).

The second deliverable is the version intent's *first action*: run the live two-launch check and record its
verdict. Research falsified the premise the check was specified on — `workspace_detector::detect` records the
`.andromeda` marker and VCS as **fields on the returned context, not success conditions**, so detection
succeeds for virtually any real cwd and a "marker-less temp dir" launch keys to that temp dir rather than
falling back to `data_dir`. Both specified arms should therefore block, which is itself the verdict (no
cwd-based interim unblock exists). A third arm — launching with `cwd == the data dir`, the only position where
the two keys could agree — is added because it is the only arm that can come back positive, and because
Windows `canonicalize` returns the `\\?\` verbatim prefix while the sidecar uses the raw `data_dir` string, so
even that agreement is in question. The real fix stays Pulse-side and out of scope.

## Implementation notes

- **The stub's empty arm IS the simulated mismatch.** A diverged workspace key and an empty corpus are
  byte-identical on the wire — `query_incident_list` returns `{items: [], total: 0}` either way. That is why
  the precondition names both candidate causes; do not write a test or a string that claims to have
  distinguished them.
- **Order sensitivity in the cascade.** The call-error branch (`:167`) must stay ahead of the
  `canary_round_trip != Ok` branch: a JSON-RPC error already has its own precondition and must not be
  reclassified as a key divergence.
- **Do not re-implement Pulse's detector.** The operator-selected design detects nothing on Conductor's side;
  replicating `workspace_detector::detect` was considered and rejected (Conductor's cwd is unrelated to
  `pulse-app`'s).
- **Windows `\\?\` caveat for arm 3.** `canonicalize` returns the verbatim prefix while the sidecar uses the
  raw `data_dir` string, so arm 3 may block for a *second* reason. Record which reason it was — that
  distinction is what the next entry (the Pulse run contract) needs.
