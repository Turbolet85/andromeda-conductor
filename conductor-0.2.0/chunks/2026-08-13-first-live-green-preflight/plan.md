## Goal

Point Conductor's shipped preflight gate at a real, running Pulse for the first time and record what it
returns. Everything the leg exercises already exists — `conductor preflight --json` → `readiness` →
`canary_gate` → `emit_canary` (with the `[incident_formation]` warm-up) → the five-arm cascade in
`run_preflight` — and none of it has met a live response. Three mechanisms get their first empirical test at
once: the warm-up pre-roll (which today rests on a single falsification and zero confirmations), the
workspace-key precondition's ability to discriminate its two named causes, and `extract.rs`'s readers, which
were written against Pulse's source and degrade silently to empty on a shape they do not recognize.

**The chunk is planned for the outcome research predicts, not for the one the route entry names.** Pulse keys
incidents on `pulse-app`'s *detected* workspace root while the sidecar keys on the raw
`ANDROMEDA_PULSE_DATA_DIR` string, and `workspace_detector::detect` succeeds for virtually any real cwd — so
no launch position is known to make the two agree, and arm 3 (the only candidate) runs into the open Windows
`\\?\` canonicalization question. The probable result is three measured, blocked arms that *confirm* the
divergence rather than a `ready:true`, with the repair falling to a Pulse-side chunk. That is a real result:
the 2026-08-10 probe could not distinguish "diverged key" from "no incident formed", and this run can, because
the warm-up now exists to make an incident form. The chunk's value must not depend on which way the
measurement goes, so two CI-provable repairs land alongside the live evidence (per architecture.md
§Infrastructure Patterns — CI/CD approach: dynamic proof is an operator gate, never a CI one).

Those two repairs are the ones research found blocking or blinding the leg. First, the documented live
entrypoint currently kills the run it wraps: `agent-run.sh boot` applies `timeout ${CONDUCTOR_PREFLIGHT_TIMEOUT:-30}`
while the in-process budget is now ≈135s (a 45s warm-up plus a ≥90s poll floor), and `agent-run.ps1 boot`
applies no timeout at all — so the identical-semantics rule (test-plan.md §3) is broken in the direction where
bash fails and PowerShell succeeds. Second, there is no way to see a raw read-back payload, which makes the
carried key-diff impossible to perform; the observed key SET gets logged through the existing
`verify.readback.observe` boundary line, inside the redaction boundary, since key names are not corpus content
(per obs-plan.md §6 Boundary-call wrappers + §11 PII Scrubbing).

## Implementation Steps

1. **Re-verify the `[inferred]` scope portions against research first** (plan-template discipline). Two matter:
   the scope's assumption that the chunk might deliver "evidence only" is now false — steps 2–4 are real code —
   and the scope's open question on the warm-up's success criterion resolves to *Pulse-side telemetry Conductor
   cannot read*, so the harness-side observable is "did an incident appear in `query_incident_list`", nothing more.

2. **Derive the `boot` budget from the run contract, in both shells.** `scripts/agent-run.sh` reads
   `warmup_ms` and `min_canary_poll_seconds` out of `contracts/pulse-run-contract.toml` as plain `key = value`
   lines and sets the `timeout` wrapper to `warmup_seconds + poll + margin`, where `poll` is
   `CONDUCTOR_PREFLIGHT_TIMEOUT` when set and `min_canary_poll_seconds` otherwise. `CONDUCTOR_PREFLIGHT_TIMEOUT`
   keeps its existing meaning for the in-process poll (it raises, never lowers — `conductor-run/src/lib.rs:222-229`);
   the wrapper simply stops being shorter than the run it guards. `scripts/agent-run.ps1` gains the equivalent
   wrapper, which it currently lacks entirely. Keep both readers tolerant of surrounding whitespace and fail
   loudly (not silently to a default) if either key is absent — a silently-defaulted budget is how this
   re-breaks. Do not add a sixth harness command and do not change `boot`'s exit-code contract
   (per test-plan.md §3 5-command implementation → `boot`).

3. **Add a pure key-set reader to `crates/conductor-verify/src/extract.rs`.** A small function taking a
   `&serde_json::Value` and returning its top-level object key names, sorted, empty for a non-object. Pure, no
   IO, no tracing — so it is unit-testable in the file's existing `#[cfg(test)] mod tests` style, exactly like
   `incident_ids` / `fingerprint_refs` / `list_text` (the 2026-08-10 rule: keep the logic a pure function of its
   inputs and let the caller do the effect).

4. **Log the observed key set at every raw-response arrival point.** Two call sites, because they are reached
   under different conditions and this distinction is what makes the chunk useful on a blocked run:
   - `extract.rs::observe` — one line per tool result (`query_incident_list`, `retrieve_report`,
     `retrieve_telemetry_slice`). Reached only when preflight is `ready` (`conductor-run/src/lib.rs:288` returns
     Blocked before read-back otherwise).
   - `preflight.rs::assert_canary` — the `query_incident_list` result on the first poll attempt, and the
     `retrieve_telemetry_slice` result when incidents exist. Reached on **every** preflight, blocked or not.

   Carry the key names in the log **message**, not as a field: a non-allowlisted field name is dropped at the
   processor stage and would vanish silently (obs-plan.md §4 Required span attributes; the trick `extract.rs`
   already uses for the degraded flag at `:111-116`). Emit once per tool per pass, not once per poll attempt —
   a 90-attempt poll must not produce 90 identical lines. Keep the existing bounded span names; add none.

5. **Run the live leg, three arms, `pulse-app`'s cwd as the variable.** Per the full operator recipe
   (scope §Absorbed annotations) and the correction below: sidecar built and on PATH; both env terms exported in
   the shell that launches both; `pulse-app` launched from a cwd outside this repo, once per arm — the Conductor
   repo root · a marker-less temp dir · the data dir itself. **Conductor itself always runs from the repo root**
   for every arm. Capture each arm's `ready`, `blocked_precondition`, and the key-set lines from stderr.

6. **Perform the key-diff before reading any verdict.** Compare the logged key sets against `extract.rs`'s
   expectations — `items[].{id|incident_id,status,severity,title}` · `markdown` · `degraded_mode` · `span_refs` ·
   `fingerprint_refs`. Record the comparison as a finding either way. If a live key diverges, land the repair
   **with a stub test pinning the live shape**, never a silent adjustment of the readers (per security-plan.md
   §Security Anti-Patterns → Input; test-plan.md §7). If they agree, record the agreement — that is what retires
   the CARRY.

7. **Append the three arms to `two-launch-verdict.md`.** Extend the existing 2026-08-10 file with a dated
   section carrying the same table shape, arms named **by role**, plus a short verdict paragraph stating which
   of the precondition's two causes each arm blocked for (or that an arm went green). State plainly whether the
   warm-up produced an incident — that is the `[incident_formation]` confirmation-or-falsification this leg
   exists to obtain.

8. **Record the run-contract term status observed live.** The `l4-deterministic` term is the only one that can
   block (`shell-declaration`); `shared-data-dir` is `declared-not-observable` and never blocks. Note in the
   evidence which terms were satisfied, so a reader can tell a contract block from a canary block.

9. **Re-run the supply-chain gate and record it.** `cargo audit` — fourteenth consecutive, silently re-pinning
   under the operator's L5 ratification. Verify `cargo deny check` green against **this chunk's own** lockfile
   delta (this chunk should move `Cargo.lock` zero lines — no new dependency is planned). No floor raise, no
   `deny.toml` ignore, no CI edit (per security-plan.md §Dependency Security).

## Implementation notes

- **The route entry's arm phrasing is wrong twice, and following it literally produces two harness faults.**
  It says "Re-run `conductor preflight --json` from the three cwd roles". (a) The key under test is
  `pulse-app`'s detected workspace root — Conductor's cwd never reaches it, since the sidecar keys on
  `ANDROMEDA_PULSE_DATA_DIR`. `two-launch-verdict.md:10` records what the 2026-08-10 probe actually varied:
  "`pulse-app` launched … once per arm, with a different working directory". (b) Conductor resolves all four
  `contracts/*.toml` handles relative to `std::env::current_dir()` (`paths.rs:27-33`,
  `conductor-run/src/lib.rs:144-146`, `config_path.rs:33`), so running it from a temp dir or the data dir fails
  at contract load with a harness `Err` — not a measured Blocked arm. Vary `pulse-app`'s cwd; keep Conductor's
  at the repo root.
- **The key-diff's reach is gated by the very blocker being measured, and the plan is built around that.**
  `observe` (the only caller of `retrieve_report`) runs solely on a `ready` preflight — `execute_scenario`
  returns Blocked before read-back otherwise (`conductor-run/src/lib.rs:288`). `assert_canary` runs on every
  preflight, but it only reaches `retrieve_telemetry_slice` when the corpus returns incidents. So on the
  probable outcome (empty corpus), the single live shape witnessed is `query_incident_list`'s top-level keys —
  which is still the highest-value one, because `incident_ids` returning empty is precisely what makes every
  downstream reader silently empty. Record what was and was not witnessed; do not imply a full key-diff was
  performed when only one tool answered.
- **The warm-up is skipped when the run contract is unmet** (`emit_canary(&contract, status.is_satisfied())`,
  `conductor-run/src/lib.rs:126`). An arm that blocks on the `l4-deterministic` declaration therefore never
  exercises `[incident_formation]` at all — check the contract status before concluding anything about the
  warm-up.
- **`boot` does not pass `--agent-mode`** (`agent-run.sh:53`), so the live leg's self-obs goes to stderr, not
  `logs/agent-latest.jsonl`. Capture stderr for the arm records. Do **not** add `--agent-mode` to `boot` to fix
  this: the sink truncates per invocation, so a `boot` would clobber the previous `run`'s artifact.
- **A live observation must never be folded back into the stub as an assertion about Pulse's behavior**
  (test-plan.md §8). A live *shape* may be pinned as a stub fixture; a live *reaction* may not become a CI verdict.
- **`v2-10` is not claimed by this chunk** — a deterministic decline, not a weakened claim. Its acceptance
  requires `ready:true`, and research establishes no launch position known to produce it. The cap stays pooled
  (`chunk: null`) with one `notes` line recording the failed concretization, so the next phase does not
  re-derive the dead end. If the live leg unexpectedly reaches `ready:true`, the evidence is recorded and a
  follow-up chunk claims the cap on it.
- **Expected amendments (wrap):** `test-plan.md` §3 (5-command implementation → `boot`, Timeout) — the wrapper
  budget is now derived from `warmup_ms` + `min_canary_poll_seconds` rather than being
  `CONDUCTOR_PREFLIGHT_TIMEOUT` alone, and `.ps1` acquires the wrapper it lacked. Possible second:
  `obs-plan.md` §6 (Boundary-call wrappers) — the must-log boundary-call set gains the observed-key-set line.
