## Goal

Pulse delegated four timing budgets to Conductor and, at HEAD `f0c38f5`, has built every measurement
surface they need. This chunk is the **assertion round Pulse cannot perform for itself** (its own P-075
`notes` say so explicitly): drive a live Pulse, obtain each capability's real measured duration, and grade
it against its own budget — P-025 hue update ≤2s · P-027 constellation discovery ≤5s · P-037 report render
≤2s · P-045 findings counter refresh ≤1s.

Research settled the two questions that decide the shape. First, **the four values reach no MCP read-back
surface** — all four are `tracing::info!` events on Pulse's own self-observation stream, and none of the 8
MCP tools reads it (for P-037 doubly so: `dispatch_retrieve_report` builds the report inside the sidecar and
`mcp-server/Cargo.toml:32-33` records that importing `pulse-app` would be a dependency cycle). But Pulse
**persists that stream to disk** — `tracing_appender::rolling::daily(&logs_dir, "agent-latest.jsonl")`
(`pulse-app/src/observability.rs:2462`) — which is the same agent-parseable artifact class prior legs already
harvest. So the grading tier is the **harvest tier**, the shape seven families already ship (per arch
§Standard Contracts + test-plan §6 + obs-plan §4), and **no new Conductor ingestion surface is needed** —
the trust-boundary question arch flagged is dropped, not escalated.

Second, **`budget_ms` is the wrong instrument and must not be used here.** `evaluate_slo` computes
`latency_ms = read_back_observed_at_ms − journal_emitted_at_ms` (`conductor-verify/src/slo.rs:39`), and the
call site states that a scenario's checks "share one latency by construction — the corpus is observed once"
(`conductor-run/src/lib.rs:414-416`). `budget_ms` therefore bounds **Conductor's MCP round-trip**, never a
Pulse-internal duration; binding P-025's ≤2s hue bound to it would measure Conductor's read-back speed and
label it Pulse's hue latency — a hollow `verified` (per architecture.md §Timing-Tolerance Model, and
corroborated independently by the obs and tests extracts).

## Constraints & rejected approaches

- **REJECTED — grading these budgets through `budget_ms` / `effective_deadline_ms`.** It bounds Conductor's
  read-back round-trip, not a Pulse-internal duration; using it would be a category error producing a hollow
  `verified`. This is the single most important do-not in this plan.
- **REJECTED — a Conductor-side runtime reader for Pulse's tracing stream.** It would be a fourth inbound
  surface and a trust-boundary change requiring an arch decision. Unnecessary: the harvest tier reads the
  same values as test fixtures.
- **REJECTED — re-classifying P-025/P-027 from `DriveObserve` to `Auto`** even though research measured that
  both fire autonomously. It is not required to grade the budgets, it would pull both coverage gates into
  the chunk, and `DriveObserve` remains defensible (it covers the VISUAL confirmation; the timing number is a
  separate harvestable quantity). Operator-decided at P4.
- **REJECTED — adding `[[expected]]` timing checks to the four TOMLs.** No read-back surface can carry them;
  a retained check with no surface lands `Blocked`, and an `Absent`-style twin would pass vacuously — the
  exact failure mode `2026-08-16-fingerprint-storm-live-proof` recorded.
- **DO NOT drive Pulse's GUI programmatically**, and do not start/stop `pulse-app` from Conductor — both are
  stated non-goals. P-037's report-open is an **operator** step.
- **DO NOT assume a uniform field name** across the four targets — `metric.report.render_ms` carries `value`,
  the other three carry `duration_ms`.

## Implementation notes

- **Fresh data dir + restart per leg.** Three mechanisms bite otherwise: Pulse's 60s storm-retention
  carry-over, dedupe against any OPEN incident (measured: even a unique fingerprint came back
  `created:false, deduped:true`), and auto-resolve of an idle incident. Four legs ⇒ four fresh dirs.
- **`findings-counter-refresh` is NOT declare-only** — it carries one `[[expected]]`, so if its read-back
  finds an empty active list it lands **`Blocked`**, not the `AutoResolved` `KnownResidual` the other three
  get. Expect this and do not read it as a defect of this chunk.
- **Pre-leg line count is never 0** on a fresh dir (~2.2k lines of `pulse-app` boot output before the OTLP
  receiver opens). Capture it after readiness, before the first dispatch, or the harvest window mixes in
  boot output.
- **Windows capture**: `pulse-app` is a GUI-subsystem binary that never attaches to a console, so a console
  tee yields 0 bytes. The real sink is `{data_dir}/logs/agent-latest.jsonl.<date>`.
- **`PATH` check before every leg** (`which andromeda-pulse-mcp`, POSIX form `/d/dev/…` — bash splits a
  Windows-form path on the drive-letter colon). A `[BLOCKED]` row in ~0s is a resolution failure, not a SUT
  verdict; elapsed time is the discriminator.
- **Seed**: `--seed` rides only an explicitly set `SEED`; the TOML-declared seed governs otherwise. None of
  these four legs needs a seed override.
- **PREREQ auto-satisfy signature**: `cargo audit` true exit 1 whose FIRST diagnostic line is
  `duplicate advisory ID: RUSTSEC-2026-0244` AND `cargo deny check advisories bans licenses sources` true
  exit 0 → record `probe unchanged, 37th consecutive`, no basis re-authoring. ANY deviation (changed
  diagnostic, moved exit code, overlap shift, or a dependency delta that ADMITS a package) restores the FULL
  form. This chunk should admit zero packages.
- **PREMISE (P-025, research not task)**: the Halo State Pulse canvas is orphaned at Pulse HEAD; the
  severity→hue semantic lives on the constellation dot (`severityToHueFraction`,
  `constellation-types.ts`), and `hue_update_ms` measures that. Refine `halo-hue-encoding.toml`'s halo
  wording accordingly. **The capability semantic is UNCHANGED, and the canvas's fate is Pulse's own entry —
  never scope it here.**
