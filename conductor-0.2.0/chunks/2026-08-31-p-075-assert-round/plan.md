## Goal

Prove the one kind of read-back fidelity Conductor can honestly assert against a deterministic-L4 Pulse, and
record — with its mechanism — the kind it cannot.

The round's positive content is **runtime-STATE fidelity**: `mark_incident_resolved` writes across the MCP
boundary and `query_incident_list` observes the consequence. This survives deterministic L4 precisely because
it depends on no L4-authored field, unlike payload fidelity, where every field is a fixture constant (arch
§Established Decisions [Read-Back Dependency Posture]). Pulse asserts exactly this pairing in-process
(`mcp-server/src/tools.rs:934`, "no longer in the active list"); this chunk asserts it across the wire for the
first time. That first is real: `ReadbackClient::mark_incident_resolved` has **zero references workspace-wide**
on the code-graph `refs` view — four independent bases agree (research.md §Graph impact), and test-plan §5
currently mandates the tool as stub-only with no production call site.

The round's recorded content is the **second-axis premise disproof**. `incident_events` — new in Pulse's
five-table corpus at `user_version 2`, and the one table that persists non-L4-authored lifecycle content —
is written by `crates/triage/src/incident/persistence.rs::save_incident_event` and read only corpus-side, with
**zero references in `crates/mcp-server`** (measured at Pulse HEAD `83d4060`). No MCP tool surfaces it at any
width, so the 2026-08-16 posture holds unchanged rather than being reopened.

The round asserts **nothing about the three delegated budgets**. `v2-20` already carries them `verified` with
three shipped tests; P-075's Pulse-side claim closes by **quoting those fixtures** as its external evidence
reference, exactly as v2-20's acceptance text anticipated. Re-certifying verified work from a weaker basis is
this chunk's explicit anti-goal (scope §Boundaries).

## Implementation Steps

1. **Add a declined-arm response mode to the shared read-back stub.** In
   `crates/conductor-verify/tests/common/mod.rs`, extend the existing config switch (the `:54`
   error-returning mode is the precedent) so `mark_incident_resolved` can return a JSON-RPC **error**
   carrying Pulse's real reason text, `"incident changed concurrently; resolution not applied"`. The stub
   already lists the tool at `:95`; only the response mode is new.

2. **Assert the declined arm lands as a typed value, in `crates/conductor-verify/tests/readback.rs`.** Drive
   the stub's declined mode through `ReadbackClient::mark_incident_resolved` and assert the call yields
   `VerifyError::JsonRpc { code, .. }` — not a panic, not `Transport`, not a harness `Err` escaping to the
   caller (arch §Cross-cutting Patterns Verdict/error wall; security-plan §Error Handling). Assert also that
   the error's `Display` renders the code only, so the server's text cannot reach an artifact unsanitized
   (`error.rs:29-32`).

3. **Assert the applied arm's result shape against the stub, same file.** `{"resolved": true, "incident_id":
   <id>}` read as a RAW `serde_json::Value` — no `{content:[…]}` envelope assumption, because Pulse's
   `tools/call` is non-MCP-compliant (arch §Established Decisions [MCP Read-Back Client]).

4. **Add the live-leg driver.** Wire a caller for `mark_incident_resolved` on the run side. It must: read the
   active set; select an incident **by id**; resolve that id; re-read the active set. The id must **not**
   become a span attribute — `incident_id` is absent from `ALLOWLISTED_FIELDS` (research.md), so it rides the
   allowlisted `message` field. No new instrumentation is needed: all four tool methods delegate to
   `call_tool`, which already carries the bounded `verify.readback.call_tool` span and the allowlisted
   `mcp_tool` field (`client.rs:124`).

5. **Run the live leg in its two-incident control form** (operator-selected at P4). Preflight forms canary
   incident **A**; drive a storm so incident **B** forms; `query_incident_list` ⇒ `{A, B}`; resolve **B**;
   re-read ⇒ `{A}`. The **surviving control A is the load-bearing part** — it is what separates Conductor's
   write from Pulse's own auto-resolver (120s idle / 30s resolver ticks), whose single-incident observation
   would be identical. test-plan §6 already requires this mis-pairing be pinned as a negative test.

6. **Capture and pin the leg.** Following `delegated_timing_harvest.rs`, create
   `crates/conductor-run/tests/lifecycle_harvest.rs` with pure grading helpers plus plain `#[test]`s over the
   **verbatim** captured lines. The live run happens once by hand; the committed test grades the logic against
   the frozen capture, so it stays CI-safe with no `#[ignore]` and no live-process gating (eleven sibling
   harvest files ship this shape).

7. **Pin the negative test.** A test asserting that observing the active set drop from `{A}` to `{}` — one
   incident, no control — does **not** establish that a resolve caused it. This is the mis-pairing guard as an
   executable assertion, not prose.

8. **Record the disproof and the citation.** Under `## Implementation notes` → Expected amendments, name the
   arch sites (both of them) and the residuals pin. Do not edit spec masters here.
