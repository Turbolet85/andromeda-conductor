## Goal

The per-run journal `runs/<run_id>.jsonl` is the agent-parseable ground truth every SLO measurement reads, and
it is the one governed artifact with no conformance gate: obs-plan §9 states in writing that the run-report
envelope "gets its own (not-yet-built) conformance gate", while the shipped gate at `ci.yml:112-160` covers
only the self-obs stream. This chunk builds that gate — every journal row asserted schema-complete against its
declared shape and free of absolute host paths, red on violation.

Two facts measured at P3 shape it. First, **the gate is a regression guard, not a bug hunt**: across the 71
journals on this host the rows are 74 envelopes + 1 check record, with zero non-conformant rows, zero
unparseable lines and zero host-path hits — so a first run is expected GREEN on real artifacts, exactly the
`2026-06-27-obs-ci-conformance-gate` precedent (PASS-on-real + FAIL-on-a-removed-field). Its value is that
host-path freedom currently holds by upstream convention across ~6 producers with nothing asserting it —
`conductor-report` contains no `redact_value` call at all, so obs-plan §11's application site (b) is
unimplemented and the property is one careless field away from breaking silently.

Second, **the gate's central requirement is already violated by a shipped reader**. `read_run_journal`
(`run_journal.rs:39`) parses every line as `RunRecord`, so a run that emitted per-check records fails the read
outright — measured, not reasoned: `conductor report 2026-08-21T18-53-35-135` exits 1 with `missing field
\`seed\``, while an envelope-only control renders at exit 0. Two production callers are affected (`conductor
report`, the Tauri `run_report`). test-plan §3's amendment (d) predicted this hazard in writing at the very
chunk that introduced the second shape; the spec was corrected and the code was not. Fixing it is the gate's
own rule applied once, at the one place that provably breaks it — and it lets the reader and the gate share a
single discrimination rule rather than two.

The CARRY from `2026-08-21-per-check-latency-measurement` rides with it: the harness `cleanup` verb deletes
from `runs` alone, leaving orphans in `run_check` and `run_envelope`. P3 measured why that has never been
caught — **`sqlite3` is absent from this host entirely and CI never installs it**, and both shells guard their
DB arm on `command -v sqlite3` / `Get-Command sqlite3`, so the delete has never executed anywhere we can
observe. Operator-decided at P4: the teardown moves **into the binary**, where test-plan §3:162's prescribed
form (`DELETE … WHERE run_id = ?1`, "rusqlite bound parameters") is expressible at all — which the `sqlite3`
CLI cannot do. Cleanup becomes portable, testable, host-dependency-free, and the string-interpolation tension
the CARRY records disappears rather than doubling.

## Implementation Steps

1. **Add a journal-line classifier to `conductor-core/src/run_journal.rs`.** One function classifies a single
   journal line into exactly one registered shape — an envelope (`RunRecord`), a per-check record
   (`CheckRecord`), or an error naming the line as conforming to neither. Discrimination is by typed parse,
   sound because the two shapes have disjoint REQUIRED (non-`Option`) keys — an envelope needs `seed` /
   `p_ids` / `slo_tier` / `scenario` / `state` / `run_id`, a check record needs `check_index` / `kind` /
   `deadline_ms`, and neither line can supply the other's (arch §Standard Contracts; obs-plan §3). Attempt the
   envelope shape first, then the check shape; report the ORIGINAL envelope parse error when neither matches,
   since the envelope is the dominant shape and its error names the missing field.
   **The typed parse settles SHAPE and the closed enum sets — it does NOT settle key presence.** Measured on
   serde 1.0.229 with four controls: a derived `Deserialize` accepts an ABSENT `Option` field as `None`
   without any `#[serde(default)]`, so the envelope's five `Option` keys (`journal_emitted_at`,
   `read_back_observed_at`, `verdict`, `latency_ms`, `fingerprints`) and the check record's `budget_ms` all
   deserialize cleanly when simply missing. Presence is therefore a SEPARATE assertion, owned by step 5.
2. **Make `read_run_journal` tolerate the second shape.** It keeps returning `Vec<RunRecord>` — its two
   production callers want the scenario grain — but now classifies each line and skips check records instead
   of failing on them. A line matching NEITHER shape stays a hard error, so genuinely malformed rows still
   surface. Re-export the classifier from `conductor-core/src/lib.rs` beside `read_run_journal` (`:63`) so the
   gate asserts through the same rule the reader uses (obs-plan §11 single-location ownership, applied to
   shape discrimination as well as redaction).
3. **Pin the reader regression in `run_journal.rs`'s own unit tests.** A journal carrying an envelope line
   followed by a check line reads back the envelope rows and does not error; a line conforming to neither
   shape still errors with a message naming the missing field. This is the assertion whose absence let the
   defect stand.
4. **Seed a per-check record into the fixture subject** — `crates/conductor-run/tests/envelope_fixture.rs`,
   `seed_into` at `:134`, currently passes `&[]` as `persist`'s `checks` argument. Pass one `CheckRecord`
   consistent with the fixture's lamps subject. This is the ONLY way to obtain a `run_check` row and a
   `CheckRecord` journal line without a live Pulse, and it goes through the production writer, which is what
   test-plan §7 requires (a hand-populated `runs.db` is banned). **Ordering:** unreachable before step 2,
   because `envelope_fixture.rs:115` re-reads the persisted journal through `read_run_journal`.
5. **Build the conformance gate** as `crates/conductor-run/tests/journal_conformance.rs`. Over two subjects —
   the committed `tests/fixtures/lamps-journal.jsonl`, and a journal produced in-test through
   `conductor_run::persist` carrying BOTH shapes — assert four properties per line:
   (a) **shape** — it classifies as exactly one registered shape via step 1's classifier;
   (b) **key presence** — a `serde_json::Value` key-set check, independent of the typed parse because the
   typed parse cannot see an absent `Option` key: the object's key set must be a SUPERSET of the shape's full
   name list (all eleven envelope names, or all nine check names). Extra keys are ALLOWED — obs-plan §3 keeps
   the per-scenario extension point open, which is the same reason `deny_unknown_fields` is rejected below.
   This is what makes "a Blocked row's five measurement fields are PRESENT and null, never absent" (arch
   §Standard Contracts; security-plan §Error Handling) an assertion rather than a hope; the writer already
   emits explicit nulls (`RunRecord::blocked` sets `None`, and no field carries `skip_serializing_if`), so the
   property is real today and the check guards agent parsers against a future `skip_serializing_if`;
   (c) **closed sets** — `verdict` and `state` fall in their closed sets, with the crosswalk's governed
   co-occurrences accepted (a11y-plan §6);
   (d) **host-path freedom** — every string-valued field survives `conductor_core::redact_value` unchanged.
6. **Add the gate's negative arms** in the same file, because a gate never exercised against a violation is
   not known to fail. THREE arms, and the middle one is the reason step 5(b) exists at all:
   (i) a row with a REQUIRED key removed (e.g. `seed`) — caught by the typed parse;
   (ii) a row with an **`Option` key removed** (e.g. `latency_ms`) — caught ONLY by the key-set check, since
   the typed parse accepts it as `None` (measured, step 1). An arm that removes a required key would never
   exercise the presence check, so this arm is not optional;
   (iii) a row carrying an injected absolute host path — caught by the redaction predicate.
   Construct all three by mutating a serialized record in-test — never by committing a malformed fixture.
7. **Add `RunsDb::delete_run` to `crates/conductor-report/src/db.rs`** — the storage seam owns the SQL. Three
   `DELETE … WHERE run_id = ?1` statements over `runs`, `run_check` and `run_envelope` with rusqlite BOUND
   parameters, applied in one transaction so teardown is all-or-nothing, and idempotent (deleting nothing is
   success). Follow the file's existing raw-SQL, no-migration idiom (arch §Established Decisions [ORM]).
8. **Unit-test `delete_run` in `db.rs`** against a DB carrying rows in all three tables: every table returns
   `count(*) = 0` afterwards, and a second call is a no-op. This is the count-zero verification test-plan
   §3:164 has always specified and nothing ever implemented.
9. **Add the `cleanup` verb to `conductor-cli`** — a `Cleanup { run_id }` variant on `Commands`
   (`cli.rs:20-60`), a `commands/cleanup.rs` handler, and its registration + dispatch in `commands/mod.rs`
   (which today declares `coverage`/`preconditions`/`preflight`/`report`/`run`/`suite`). It resolves the runs
   dir through the existing CLI path edge so `CONDUCTOR_RUNS_DIR` + `resolve_under` apply unchanged, calls
   `RunsDb::delete_run`, and prints one confirmation line in the shipped `render` style — no new colour, no
   new bracket label (design-system §Surface: cli / Tokens).
10. **Point both shells at the verb.** In `scripts/agent-run.sh` (`:232-234`) and `scripts/agent-run.ps1`
    (`:253-255`), replace the `sqlite3`-guarded block with the binary invocation each file already uses for
    every other verb (`"$CARGO" run -q -p conductor-cli --bin conductor -- cleanup "$id"` / the pwsh array
    form). Keep each shell's existing run-id guard (`valid_run_id` `:60`/`:230`; `Test-RunId` `:58`/`:249`),
    keep the `rm -f` on the two named artifacts, and keep idempotency. The agent-run verb count stays five and
    both shells stay at identical semantics (layout-templates §Surface: cli — Primary screens).
11. **Add a CI journal-conformance step** to `.github/workflows/ci.yml`, beside the obs gate. Its producer
    already exists — the obs gate's `ANDROMEDA_PULSE_DATA_DIR: 'pulse;injection'` step (`:118-124`) yields a
    Blocked envelope at exit 0 and writes `runs/<run_id>.jsonl` as a side effect nothing currently asserts.
    **Mechanism: the step RUNS THE RUST GATE over that journal — it does not re-implement it in `jq`.** A `jq`
    re-listing of the key names would be a THIRD copy of the schema (the Rust structs · obs-plan §3/§6 · the
    YAML), and the chunk's whole posture is single-sourcing. So `journal_conformance.rs` reads
    `CONDUCTOR_RUNS_DIR` when set and asserts over the journals it finds there (falling back to its fixture +
    in-test subjects when unset, so an ordinary suite run is unchanged), and the CI step invokes that test
    target with the handle pointed at the producer's output. `CONDUCTOR_RUNS_DIR` is an EXISTING handle — no
    new handle and no fourth handle class. The host-path half MAY mirror the obs gate's anchor set in YAML as
    the pre-existing exception noted below, but the key lists live in exactly one place.

## Constraints & rejected approaches
- **Rejected: the `sqlite3`-CLI deletes the CARRY literally describes** — unverifiable on this host and in CI
  (no `sqlite3` anywhere), and it would double the string-interpolation form while leaving test-plan §3:162's
  "rusqlite bound parameters" contradicted by the code.
- **Rejected: a Rust test re-declaring the shells' SQL** — it would verify a copy, not the code changed. With
  the teardown in the binary the same test now covers the real path.
- **Do NOT mint a second host-path predicate.** `is_host_path_token` is private (`redact.rs:120`); the gate
  binds through `redact_value(s) == s`. Copying its anchor list into Rust would create the second definition
  obs-plan §11 forbids — the `ci.yml` YAML mirror is a pre-existing exception, not a licence.
- **Rejected: a `jq` key-name list in the CI step.** It would be the THIRD copy of the schema (Rust structs ·
  obs-plan §3/§6 · YAML) and would drift silently from the first two. The CI step runs the Rust gate instead;
  only the host-path anchor set may be mirrored in YAML, as the pre-existing `ci.yml:143` exception.
- **Rejected: relying on the typed parse for key presence.** Measured false on serde 1.0.229 — an absent
  `Option` field deserializes to `None` with no `#[serde(default)]`. Presence needs its own `Value`-level
  check, and the negative arm proving it must remove an `Option` key.
- **Rejected: `#[serde(deny_unknown_fields)]` on the record types.** obs-plan §3 keeps the per-scenario
  extension point OPEN (only its one known instance, `degraded_mode_response`, was retired on 2026-09-06);
  denying unknown fields would close a point the spec deliberately leaves open, and is a schema change this
  chunk has no authority to make.
- **Rejected: a hand-populated `runs.db` or a committed malformed fixture** — test-plan §7 / §11 ban the
  former; the latter would put a non-conformant artifact in the tree the gate must then except. Both are
  constructed in-test or seeded through `persist` instead.
- **No sixth `agent-run` verb.** The 5-command discipline is closed without a test-plan amendment; a new
  `conductor` CLI verb is a different surface (layout-templates: the verb set is "whichever `Commands`
  declares").
- **Rejected: a new `CONDUCTOR_*` handle.** The probe reuses `CONDUCTOR_E2E_SEED_DIR` (the settled third
  class) and `CONDUCTOR_RUNS_DIR`; the namespace's three classes stay closed.
- **No `rm -rf` in the probe or the shells.** `2026-09-06-operator-gated-live-suite` ruled that a
  `CONDUCTOR_*`-derived path must not reach a recursive delete; the shells keep `rm -f` on named artifacts.
- **Do not widen the bounded span-name set** — no new `db.*` span for `delete_run` (obs-plan §6; the operator
  ruled against a `db.*` wildcard at `2026-09-01-live-per-p-id-verdict-lamps`). A boundary `info!` inside the
  caller's span is the sanctioned form.

## Implementation notes
- **Step order is load-bearing.** Step 4 cannot pass before step 2, because `envelope_fixture.rs:115` re-reads
  the persisted journal through `read_run_journal`. Implement 1→2→3 before 4.
- **Watch the `--e2e` a11y arm's subject.** Step 4 adds a `run_check` row and a per-check Markdown line to the
  seeded fixture. The webview run-report renders records from `read_run_journal`, which after step 2 returns
  envelopes only, so the a11y assertions should be unaffected — verify rather than assume if the routine arm
  is run.
- **The serde Option-absence fact, with its basis.** Measured 2026-09-06 in a scratch crate on serde 1.0.229
  against a faithful mirror of `RunRecord` (plain derive, no field attributes — the same shape
  `run_record.rs:16-42` carries), with four controls: all 11 keys present → `Ok`; the 5 `Option` keys absent →
  `Ok` with those fields `None`; the required key `seed` absent → `Err(missing field \`seed\`)`; an extra
  unknown key → `Ok`. The last control is also the evidence that the extension point is open by default,
  which is why `deny_unknown_fields` is rejected rather than merely unused.
- **The gate's first run is predicted GREEN** on real artifacts (71 journals measured at P3: 74 envelope + 1
  check row, 0 non-conformant, 0 host-path hits). Record what the measurement SHOWS; a red first run is a
  finding about the shipped rows, not a gate defect, and must not be softened away.
- **`RunsDb::open` creates the DB and schema if absent**, so `cleanup` on a runs dir with no `runs.db` will
  create an empty one rather than erroring. That is idempotent and harmless, but note it — the prior shell
  behaviour skipped silently.
- Exactly one local journal reproduces the reader defect (`runs/2026-08-21T18-53-35-135.jsonl`). It is
  gitignored residue, so it is deliberately NOT a Test Command subject; the regression is pinned by the
  seeded fixture and by constructed unit fixtures.
- Secondary and optional: the reader's parse failure is classified `CoreError::Config` and renders as
