## Goal

The `a11y` CI job is correctly wired and correctly RED. On the hosted `windows-2025` runner a WebView2-mode
session never exposes `DevToolsActivePort`, through `@crabnebula/tauri-driver` and direct at `msedgedriver`
alike; every suspect the prior chunk named is measured out and the cause beyond that statement is UNMEASURED.

This chunk is **diagnose-only**. It fires **one probe push** carrying three measurements that together
localize the cause, then **disposes of `v2-24`** on what the runner shows. It ships no remedy, because the
one remedy that looked cheap is now measured not to be one.

**Hypothesis 2 is RETIRED as a remedy — measured on the dev host at the P5 review, not argued.** The
WebView2 loader *does* honour `WEBVIEW2_USER_DATA_FOLDER`: a bare launch of the release binary with that
handle plus `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=0` writes
`<dir>\EBWebView\DevToolsActivePort` in **1 s**. But on the driver path the handle is irrelevant:
`msedgedriver` in webview2 mode creates the session in **0.7 s** and the app's profile lands in the
**driver's own** `%TEMP%\scoped_dir<pid>_<rand>\EBWebView\`, and it does so *even when
`WEBVIEW2_USER_DATA_FOLDER` is exported to the driver* — the inherited directory stays empty. **The driver
sets the folder itself and overrides any inherited value**, and its verbose log never names it (0 lines),
which is exactly why the CARRY read "no path". An `appEnv` key would therefore be a no-op on the only path
that matters. This supersedes the P3 finding that the env chain makes the handle "one added key": the chain
propagates, and the driver overwrites at the end of it.

So the deliverable is a **measured cause**, and the three probes are shaped to partition it rather than to
fix it. Each is transcribed from a form the overseer validated on the dev host first — where the real path
passes 12/12 — so a probe that fails on the runner is evidence about the runner, never about the probe.
