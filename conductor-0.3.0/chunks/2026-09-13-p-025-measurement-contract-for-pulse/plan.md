## Goal

Pulse delegated a ≤2 s hue-shift latency budget to Conductor, and Conductor has spent two chunks establishing
that it cannot grade it: `metric.constellation.hue_update_ms` measured 35 581 ms and 36 705 ms against the
2 000 ms bound, and the 2026-09-07 re-drive — 360 dispatches at 2/s, the service never quiet — still read
14 525.9 ms, matching its offset to the preceding 15 s lifecycle tick to 1.1 ms. The observable reports
`t_sample − t_last_refreshing_tick`, not an update latency. The bound is not failing; it is unmeasured.

This chunk writes the **ask**: a committed contract stating what Pulse must emit for the bound to become
measurable. Per the working entry it must name four things — which observable, at what resolution, over what
window, and what comparison constitutes a hard grade — and per `v3-07` it must be complete enough that Pulse
can implement it without a follow-up question, addressed to a value Pulse produces rather than one Conductor
already records for its own emission window (arch §Established Decisions [Timing-Tolerance Model]; obs-plan
§4 Delegated-timing family).

Research settled what the ask actually is, and it is narrower than "measure it differently".
`ServiceListItem` carries no timestamp for `priority_tier` — the registry holds no incident data, and the
`services.list_with_states` resolver enriches the tier by joining the incident registry — so the canvas, at
the moment it sees a tier change, cannot know **when** that tier became effective. `last_seen_unix_nano` is
the only per-service instant it is handed, which is why the effect reached for it. The missing value is a
**start instant**, and the contract asks Pulse to supply it on the item the canvas already receives. This
chunk writes no code that grades anything: the live re-drive is `v3-08`, blocked until Pulse implements this.

4. **Write `## The window`** — the two instants, both named as Pulse-internal events:

   **end** = the canvas paint of the new hue, which the existing effect already observes.

   **Name the source, and state the rule — the ask is to EXPOSE an instant, not to mint one.** The tier is
   computed at `pulse-app/src/services_router.rs:97-103`, where `list_with_states` filters
   `incident_registry.list_active()` to the service's scope and takes `.max_by_key(tier_rank)`. That site
   already holds the full `Incident` records, so both timestamps the rule needs are in hand there:
   `opened_at_unix_nano` (`crates/triage/src/contract.rs:418`) and, for the incident leaving the active set,

   - the max **RISES** — an incident opens at a tier above the current max ⇒ that incident's
     `opened_at_unix_nano`;
   - the max **FALLS** — every incident holding the current max leaves the active set (resolve/ack) ⇒ the
     `transitioned_at_unix_nano` of the last one to leave.

   State the fact that makes this exhaustive: **an incident's `priority_tier` is immutable after opening**,
   so there is no in-place escalation arm. Basis (measured at HEAD `83d4060`):

   `resolved_unix_nano` / `payload` / `read_unix_nano` only). So the service's max tier changes only when
   the active SET changes, and the two cases above are the whole space.

   State explicitly that neither instant is a value Conductor records for its own emission window — this is
   the `v3-07` qualifier, and `latency_ms` / `budget_ms` / `effective_deadline_ms` are named as excluded
