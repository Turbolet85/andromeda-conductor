3. **Secret-scan gate** — new `crates/conductor-core/tests/secret_scan_gate.rs`, shaped like
   `scenario_audit_gate.rs` (`repo_root()` from `CARGO_MANIFEST_DIR` + `../..`; positive · negative · control arms):
   - **Subject:** the workspace as git sees it — `git -C <repo_root> ls-files -z --cached --others
     --exclude-standard` (tracked + untracked-not-ignored, so a new file is scanned before it is committed; an
     ignored `.env` is excluded by design, the ignore rule being the guard for it). `git` is spawned as a fixed
     program name with fixed argv and no operator value. A spawn failure or non-zero exit panics with a message
     naming the cause — the gate never passes on an empty listing.
   - **Scan:** skip a path absent on disk (a tracked file deleted in the worktree) and a binary file (a NUL byte in
     the first 8 KiB); split text on `\n`, trim a trailing `\r`; apply the 14 content rules research measured
     (§Measurements 3: private-key block · AWS access key id · GitHub classic token · GitHub fine-grained PAT · Slack
     token · Slack webhook · Stripe live key · Google API key · JWT · Anthropic key · OpenAI key · npm token ·
     URL-embedded credentials · generic quoted `password|passwd|pwd|secret|api_key|access_token|auth_token|
     client_secret` assignment of ≥ 8 non-space chars) plus the file-name class of step 1.
   - **Hit report:** one line per hit, `{repo-relative path}:{line}: secret-shaped string ({rule}, {N} chars)` (a
     file-name hit reads `{path}: secret-shaped file name ({class})`); never the matched text and never an absolute
     path. The failing assertion lists every hit.
   - **Allowlist:** a test-local const of `(path, rule, reason)` entries, EMPTY at this chunk (the measured baseline
     has 0 hits). Graded exact-set in both directions: an unallowlisted hit fails; an entry matching no hit fails as
     rot, naming the entry. Every future entry carries a stated reason (the deny.toml idiom).
   - **Arms:** (a) POSITIVE — the real subject yields no unallowlisted hit, with vacuity guards: the listing is
     non-empty and at least one text file was scanned; (b) CONTROL, one per content rule — a sample built at RUNTIME
     by concatenation (so no file anywhere contains a literal match) fires its own rule; (c) NEGATIVE — a planted
     sample in an in-memory `(path, contents)` set makes the scan fail with a message containing that `path:line`
     and rule name and NOT containing the sample; the same for a planted file-name hit; (d) ALLOWLIST — an entry
     suppresses exactly its hit, and a stale entry fails as rot naming it. No committed fixture file (test-plan §7):
     every bad input exists only at test time.
4. **Workflow env-context gate** — new `crates/conductor-core/tests/workflow_env_gate.rs`:
   - **Subject:** every `.github/workflows/*.yml` / `*.yaml` under `repo_root()`; presence guard — at least one file,
     else panic naming the absence.
   - **Line model** (the YAML subset these workflows use): a line whose first non-space char is `#` OUTSIDE a block
     scalar is a YAML comment and is skipped; a key line ending in a block indicator (`|`, `|-`, `>`, `>-`) opens a
     block scalar whose content is every following line indented deeper than that key (blank lines included) — block
     content is SCANNED, comment-looking lines too, because the runner substitutes `${{ }}` inside `run:` text before
     the shell sees it.
   - **Reads:** every `env.NAME` token inside a `${{ … }}` on a scanned line, and inside the whole value of a bare
     `if:` line (implicit expression); the token must not be preceded by a word char or `.` (so `github.env…`-style
     paths and `$env:NAME` shell reads are not reads of the `env` context).
   - **Declarations:** every key of an `env:` mapping at any level (the key lines indented deeper than the `env:`
     line, until the first line at or above its indent), plus every `NAME` a scanned line writes to `GITHUB_ENV` — a
     line containing `GITHUB_ENV` that also carries a quoted `NAME=` (both the pwsh `Add-Content -Path
     $env:GITHUB_ENV -Value "NAME=…"` form at `ci.yml:342` and the bash `echo "NAME=…" >> "$GITHUB_ENV"` form).
   - **Verdict:** a read whose NAME is in no declaration set fails, the message naming the workflow file, line and
     key. File-wide admission (not per-job/per-step visibility) is the CARRY's own reading: "a key no workflow, job
     or step declares".
   - **Arms:** POSITIVE over the committed workflows, with vacuity guards (≥ 1 `${{` expression parsed · ≥ 1
     declaration found · ≥ 1 `env.` read found — step 5's probe provides it); NEGATIVE on in-memory YAML: an
     undeclared `${{ env.X }}` in a `run:` block fails naming `X` and its line; a bare `if: env.X == 'y'` fails naming
     `X`; CONTROL: the same `${{ env.X }}` in a YAML comment line passes; the same inside a block-scalar line starting
     with `#` (a shell comment) FAILS; a step-level `env:` key, a `GITHUB_ENV`-written key (each writer form) and
     `${{ github.sha }}` / `${{ runner.temp }}` all pass.

## Constraints & rejected approaches
- A job-time-fetched scanner (gitleaks or any marketplace action / downloaded binary) — rejected by the operator: a
  second non-loopback CI egress and a second third-class dependency member (arch §Occupied Resources — Ports;
  security-plan §Dependency Security).
- A `scripts/` Python scanner invoked by CI — rejected by the operator: it would be the first CI-invoked operator
  instrument (arch §Stack operator-instruments row) with no registered Python runner for its negative arms (test-plan §4).
- The env-key check as an inline shell `grep` in the flakiness-budget step's literal shape — rejected: an inline
  step cannot carry the in-suite negative arms test-plan §6 requires; the new step keeps that step's position and its
  `::error::` presence-guard shape, and the CARRY's "names the key" is carried by the test's failure message.
- Per-job / per-step `env` visibility in the env-context gate — rejected: the two paid traps were keys declared
  NOWHERE (ci.yml `:351-356`; host-win32.md 2026-09-17), and visibility scoping would grow the YAML-subset model for
