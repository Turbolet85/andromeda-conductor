## Goal
Two drives of the same scenario and seed, fired inside one Pulse buffer window, must both land. Today the second
drive's spans are refused. Every span the dispatcher emits draws its `(trace_id, span_id)` from
`emission_seed(scenario.seed, phase, occurrence)` (`dispatch.rs:78` → `exception.rs:185-187`). Pulse keys its span
store on exactly that pair: `spans` `PRIMARY KEY (trace_id, span_id)` at Pulse `a2addb3` `buffer/src/schema.rs:36`.
A replayed identity rejects the whole batch at flush (Pulse's own test `appender.rs:996`), logged as `duckdb.append`
`reject_reason=append_failed`. Pulse holds rows for 600 s plus a 100 s sweep (`retention.rs:41-51`,
`contract.rs:109`). That is the d2 gap of the 2026-10-01 series (scope.md, research.md).

The fix gives each production execution its own span identity and leaves everything else seed-pure. A new
`conductor-emit` primitive re-keys a built trace request. It is a deterministic bijection derived from a `u64` salt
on `ChaCha8Rng`. It XORs every non-empty `trace_id`, `span_id` and `parent_span_id` with salt-derived masks, so
linkage inside a drive is preserved and no content byte moves. Content means fingerprints, events, attributes,
durations, the PII corpus a live harvest re-derives, counts and timing. The dispatcher takes the salt as a required
`connect` parameter. `execute_scenario` passes the `std::time` emission instant it already reads (`emitted_ms`,
`execute.rs:85`), the same per-run base the canary has used since 2026-06-27 (`canary.rs:294`). The dispatcher tier
driven without a salt keeps its identity bytes, so the `dispatch_wire__*` goldens and
`the_same_seed_reproduces_the_same_stream` stay unchanged.

Proof comes in two tiers. In CI, two same-seed drives through the real `Dispatcher` into a loopback stub must share
no `(trace_id, span_id)` pair. That models Pulse's key as verified in Pulse's source, and the test fails when the
re-key is removed. In the operator pass, a live witness runs on the operator's word ("measured over inferred"). It
uses one deterministic-posture `pulse-app` on the `a2addb3` binaries, sha256-verified first. Two
`conductor run exception-event-capture` drives run inside Pulse's retention window, and the witness grades Pulse's
own log: 0 `append_failed`, `append_rejections` 0, spans appended after the second drive. The production wiring
(`execute_scenario` → salt) is only reachable live, because the ready path emits to the fixed `:4317`. So the
witness is the proof of that half.

## Implementation Steps
1. **The identity primitive** — create `crates/conductor-emit/src/identity.rs` with
   `pub fn rekey_trace_identity(request: &mut ExportTraceServiceRequest, salt: u64)`.
   - Derive one 16-byte trace mask and one 8-byte span mask from `ChaCha8Rng::seed_from_u64(salt)`, drawn in that
     order, reusing `span_tree::gen_id`.
   - For every span in every resource/scope, XOR the mask into `trace_id` (16 B), `span_id` and `parent_span_id`
     (8 B), and into each link's `trace_id` / `span_id`. Skip any id field that is EMPTY: a root's empty
     `parent_span_id` stays empty.
   - Touch no other field.
   - The doc comment states the contract: a bijection per salt, linkage preserved, content untouched, a pure
     function of `(request, salt)`, no clock, no I/O and no self-observation.
   - Unit tests in the same file (`#[cfg(test)]`):
     - (a) on an `error_trace_request(…, ErrorPlacement::DeepChild { depth: 3 }, …)`, every child's
       `parent_span_id` still equals its parent's re-keyed `span_id`, and all spans share one re-keyed `trace_id`;
     - (b) the same request and salt, re-keyed twice, gives byte-equal results;
     - (c) two distinct salts on the same request give `(trace_id, span_id)` sets with an empty intersection;
     - (d) blanking the three id fields (and links) of the original and of the re-keyed request yields byte-equal
       encoded messages, so no content byte moved; use an `exception_trace_request` so the exception event and
       fingerprint attribute are covered;
     - (e) an empty `parent_span_id` stays empty.
2. **Export it** — in `crates/conductor-emit/src/lib.rs`, add `mod identity;` and
   `pub use identity::rekey_trace_identity;` beside the existing re-exports. Add no dependency: `rand_chacha` and
   `opentelemetry-proto` are already this crate's.
3. **The dispatcher carries the salt** — in `crates/conductor-run/src/dispatch.rs`:
   - Change `Dispatcher::connect(scenario, endpoint)` to `connect(scenario, endpoint, identity_salt: Option<u64>)`.
     The field is held on the struct.
   - Route every TRACE export in `dispatch` through one private helper. When the salt is `Some`, it calls
     `rekey_trace_identity` on the request just before `self.traces.export`. The trace-emitting shapes are
     Plain/Traces, Error, Exception, Latency, Pii/Traces, Ramp and Topology.
   - Leave the logs path untouched: Pulse keys logs on a timestamp + `seq` (Pulse `schema.rs:82`), so logs cannot
     replay.
   - The doc comments state the two tiers. `None` means seed-pure identity, the tier the `dispatch_wire__*`
     goldens pin. `Some` means per-execution identity, the production path.
   - Leave `emission_seed` and the per-slot seed fed to builders unchanged, so content stays seed-pure
     (`pii_harvest.rs:104-119` re-derives the PII corpus from it).
4. **Production passes a per-execution salt** — in `crates/conductor-run/src/execute.rs`, `execute_scenario` passes
   `Some(emitted_ms as u64)` to `Dispatcher::connect` (`execute.rs:88`). `emitted_ms` is the existing `now_ms()` read
   at `execute.rs:85`, from `std::time`. Add a one-line comment citing the canary's `now_ms()` base
   (`canary.rs:294`) and the Pulse key. Do not change the signature of `execute_scenario`; its callers are
   `commands/run.rs:23`, `commands/suite.rs:32` and `drive.rs:80`, settled by grep because the async fn has no graph
   symbol.
5. **The CI proof** — in `crates/conductor-run/tests/dispatch_wire.rs`:
   - The `drive_scenario!` macro passes `None`, so every existing test and the three goldens are unchanged.
   - Add a salted twin, `drive_scenario_salted!(scenario, salt)` or an extra macro arm, that passes `Some(salt)`.
   - Add the test `two_same_seed_drives_inside_one_window_share_no_span_identity`. Use one scenario whose phases
     cover an Exception phase (the d2 shape, `occurrences = 5`) and an Error phase with depth ≥ 1, so linkage is
     exercised. Drive it twice with the same seed and two distinct salts. Assert:
     - (i) the union of `(trace_id, span_id)` pairs across both drives has exactly `|A| + |B|` members (Pulse's
       key, `schema.rs:36`), with `|A| = |B| > 0`;
     - (ii) both drives carry the same span count and the same exception fingerprint attribute values in the same
       order (content unchanged);
     - (iii) every child `parent_span_id` in drive B names a `span_id` present in drive B;
     - (iv) the same salt twice reproduces identical identity.
   - Before the final green, /implement shows the test RED with step 3's re-key call removed and records that
     reading in `evidence/revert-red.md`. This is the "fails when the fix is reverted" witness.
6. **The live witness binary** — create `crates/conductor-run/tests/span_landing_live.rs`.
   - Gate it on `#![cfg(feature = "live-pulse")]` and add `mod capture_paths;`. It is auto-discovered like
     `real_model_live.rs`, so it needs no Cargo.toml edit.
   - It drives nothing. It reads:
     - (a) `runs/live-suite/span-a.jsonl` and `span-b.jsonl`, resolved through
       `capture_paths::runs_dir_from(&workspace_root(), CONDUCTOR_RUNS_DIR)`;
     - (b) every file named `agent-latest.jsonl*` under `capture_paths::pulse_logs_dir_from(ANDROMEDA_PULSE_DATA_DIR)`.
   - From each journal it takes the single `run_id` it carries and the `timestamp_ms` of its ONE `timeline.execute`
     span-`new` line. That is the scenario's emission instant; the canary's `emit.batch` lines precede it.
   - From Pulse's lines (JSON, `target` + `fields` + ISO `timestamp`) it takes:
     - the count of `target == "duckdb.append"` lines carrying `fields.reject_reason`;
     - the LAST `buffer.tick` `fields.append_rejections`;
     - the LAST `buffer.tick` `fields.retention_window_seconds`, which must be present;
     - the count of `duckdb.append` lines with `fields.table_name == "spans"` stamped at or after drive B's
       instant.
   - Parse the ISO stamp to epoch ms by hand (full date + time, so a UTC date change cannot fold), as
     `live_suite.rs:111` does for its own parse.
   - Pass iff: 2 distinct run_ids; `0 < Δ = tB − tA < retention_window_seconds × 1000`; `reject_lines == 0`;
     `append_rejections == 0`; `spans_after_b ≥ 1`.
   - Print exactly one summary line: `span-landing: PASS run_ids=2 delta_ms=N retention_ms=N reject_lines=0
     append_rejections=0 spans_after_b=N` (each N an integer). On failure, panic with the same field set and the word `FAIL`.
   - It prints counts and integers only, never a Pulse line, a path or a fingerprint, so nothing it emits needs the
     capture scrub chain. Every guard rejection keeps `capture_paths`' path-free text.

   - Use a Write-tool `.ps1` in the scratchpad, ASCII only (host-win32.md 2026-09-30), run by path.
   - It calls `Start-Process` without `-Wait`. The fresh letters-only data dir `%TEMP%/pulse-legs/spanlanding` is

   - Set `ANDROMEDA_PULSE_L4_DETERMINISTIC=true` and `ANDROMEDA_PULSE_MCP_ENABLED=true`. Remove
     `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` and `RUST_LOG`.
   - Confirm the posture from Pulse's own log before any drive: `interpretation.model.load` `inference_mode:
     deterministic`, `app.boot.workspace_key` basename `spanlanding`, `app.boot.otlp.grpc.bind` `127.0.0.1:4317`,
     and no bootstrap-override line.
   - Record the PID and UTC CreationDate.
9. **Drive A** — run the non-priming `preconditions` probe, then drive A, then the freeze to
   `runs/live-suite/span-a.jsonl`. Never run `boot` first (verification-harness.md:53).
10. **Quiet window** — at least 180 s after drive A ends: Pulse's 120 s idle plus a 30 s resolver tick plus margin
    (verification-harness.md:50; the posture contract's 150 s). This keeps drive B's preflight canary from deduping
    against A's open incident. It stays well inside the 600 s retention, and the witness asserts that rather than
    assumes it.
11. **Drive B** — the probe, drive B, then the freeze to `span-b.jsonl`.
12. **Witness** — run step 6's binary against the live data dir and record its summary line in
    `evidence/witness-ledger.md`. A witness that FAILs only on `Δ ≥ retention` is a harness-timing fault: the leg ran
    too slowly to be inside the window. It is re-fired once from step 9 on a new slot, never graded as a landing
    result (verification-harness.md 2026-09-30 re-fire rule). Any other FAIL is the result.
13. **Teardown** — stop `pulse-app` by PID AND CreationDate (`CloseMainWindow`, then `Stop-Process -Force`). Take the
    after-census by parentage. Confirm `:4317` has no listener.
14. **Mint-then-read** — `status` on drive B's run_id.
15. **Evidence** — `evidence/witness-ledger.md` records:
    - the census before and after;
    - the slot and its grant;
    - both sha256 values;
    - the launch posture as Pulse logged it;
    - each entry's exit and atoms;
    - both run_ids and the witness summary;
    - the teardown.
    No Pulse log text, path or workspace key is copied in. Then run the evidence host-path probe, `gate.py hygiene`,
    the operator's pre-CI commit, the push and the CI read.

## Constraints & rejected approaches
- **Shape (b), a measured minimum gap between same-seed drives, is rejected.**
  - A refused row clears only at eviction, 600 s retention plus a 100 s sweep (Pulse `retention.rs:41-51`,
    `contract.rs:109`; d1 evicted 19:48-19:51Z). Every same-seed drive would wait ≥ 700 s, and the gap would ride a
    Pulse launch setting Conductor cannot read.
  - It leaves the deterministic `--live` legs with the same replay.
  - It would mint a new harness wait or contract term. The entry's CONTEXT offered both shapes; the evidence decides
    for (a).
- **A salt on the SEED (mixing it into `emission_seed`) is rejected.** The per-slot seed also draws the CONTENT, and
  `pii_harvest.rs:104-119` re-derives the live PII corpus from it. Salting the seed would break that harvest and move
  latency, rate and PII bytes per run. Only identity moves.
- **A builder method (`Dispatcher::with_identity_salt`) is rejected for a required `connect` parameter.** Leaned
  decisively per `execute.rs:84-88`. `execute_scenario`'s ready path emits to the fixed `:4317`, so no CI test can see
  a production path that forgot an opt-in builder. A required parameter makes the omission a compile error at both
  call sites (graph + grep: `execute.rs:88`, `dispatch_wire.rs:130`).
- **Do not salt the canary** (`canary.rs`): it is already unique per run, and the deterministic canary stays
  byte-identical (arch-history 2026-09-29).
- **Do not add a conductor-emit → conductor-core edge**, an OS-entropy source, `StdRng`, the OTel SDK id generator,
  or a new hash dependency for identity (arch [Determinism RNG] / [Module Boundaries]; obs-plan §3).
- **Do not prove landing by reading or staging Pulse's stores.** The CI proof is stub-received requests; the live
  proof is Pulse's own log lines through `capture_paths` (security-plan §Security Anti-Patterns → Data Protection).
  The witness commits counts only, never Pulse text.
- **Do not grade the drives' verdicts** in this chunk. `exception-event-capture`'s read-back outcome is not the
  subject; landing is.
- **No new real-model series, no `v3-09` re-grade, no posture-contract edit.** The contract is add-only, and a
  fourth series awaits the founder (scope.md).
- **Not a Boundary widening** — playbook `.andromeda/playbook.md:124`, named and answered. The overseer accepted
  the clause-by-clause reading at P4 on 2026-10-01. No read-only channel gains a write, no validated surface admits
  a new input class, and no subprocess/IPC boundary gains a crossing. The same OTLP message types go to the same
