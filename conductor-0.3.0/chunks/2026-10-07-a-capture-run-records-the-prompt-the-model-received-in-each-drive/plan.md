## Goal
Drive the fifth series' three-drive design once more, on a fresh data dir, with `pulse-app` launched from a shell
whose model-binary handle names the operator's recording pass-through, so that Pulse's builder can read the prompt
each generation received. The founder picked that vehicle himself (inputs#I1 §1; inputs#I2): the pass-through, its
env file and its capture folder are the operator's, and Conductor's two boundary clauses stand unamended (per
security-plan §Security Anti-Patterns → Data Protection; architecture §Occupied Resources → Environment variables).

Conductor's part is three things. It pre-registers the run and discloses the launch posture. It drives d1..d3
through the existing `run --live real-model` arm and commits its own scrubbed captures, digest-pinned and graded
from their files, as every series did (per security-plan §Input Validation, real-model capture ingest row;
test-plan §6 Scenario: Fingerprint-storm → Real-model interpretation leg). And it gives the tie: each drive's start
and end instants, beside the per-generation stamps its captures already print, so the reader can bracket the
operator's per-invocation directories by time. It reads nothing the pass-through recorded.

The run is a capture, never a `v3-09` verdict. Each drive's grade is the harvest's, recorded as an observation.
Three `Identified` do not make `v3-09` met, and a miss does not count against it; no verdict test and no ref test
is written, and the matrix is not touched. If no drive misses, that is reported as a finding and the run is still
delivered (inputs#I1 §2).

Part A is everything d1 reads. Part B is the sitting. Part C pins and grades what the sitting left.
